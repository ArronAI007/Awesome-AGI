# 安全模型与容器化沙箱

> pi 的安全模型建立在一个明确的取舍之上：核心不做权限沙箱,把隔离责任完全交给操作系统层面的容器/虚拟化方案。理解这个取舍,才能理解"项目信任(trust)"这个机制到底在保护什么、不保护什么。

## 学习目标

- 理解 pi "默认没有内置权限系统、以启动它的用户权限运行"这一设计,以及背后的取舍理由。
- 弄清楚"项目信任(project trust)"机制具体保护的是哪些资源、它明确不做什么。
- 能对比 Gondolin extension、纯 Docker、OpenShell 三种沙箱方案各自的隔离边界与适用场景。
- 知道 bind mount 场景下"宿主机文件仍可被容器内写入"这一注意事项。
- 知道如何按规范上报安全漏洞,以及哪些问题被明确排除在漏洞范畴之外。

## 没有内置权限系统的设计取舍

根目录 `README.md` "Permissions & Containerization" 一节把这件事说得很直接:

> Pi does not include a built-in permission system for restricting filesystem, process, network, or credential access. By default, it runs with the permissions of the user and process that launched it.

`packages/coding-agent/docs/security.md` 补充了完整的理由,而不只是陈述结论:

> This is intentional. Pi is designed to operate on local source trees, invoke project toolchains, and integrate with the user's existing development environment. A partial in-process sandbox would be easy to misunderstand as a security boundary while still depending on the host shell, filesystem, package managers, credentials, and extension code. Real isolation needs to come from the operating system or a virtualization/container boundary.

翻译成中文的核心论点是:

- **pi 的定位决定了它必须能自由操作本地工具链**——读写文件、跑构建命令、调用语言服务器、执行测试命令,这些都是"侵入式"的本地开发操作,如果处处加权限拦截,pi 就无法胜任日常编码工作。
- **一个"半吊子"的进程内沙箱比没有沙箱更危险**,因为它会给人一种"这里有安全边界"的错觉,但只要底层的 shell、文件系统、包管理器、凭证、扩展代码仍然共享同一个进程权限,这层"沙箱"本质上挡不住真正想绕过它的攻击路径,反而可能让用户放松警惕。
- **真正的隔离只能来自操作系统或虚拟化层面的边界**——也就是本文后半部分要讲的容器化方案,而不是在应用代码里模拟一套权限系统。

`SECURITY.md` 用"信任边界(trust boundary)"这个概念重新表述了同一件事:

> Pi treats the local user account and files writable by that account as inside the same trust boundary as the Pi process itself.

也就是说,pi 进程和启动它的本地用户账户、这个账户能写入的所有文件,被视为同一个信任域。如果攻击者已经能修改用户主目录、工作区、shell 启动文件、环境变量或 pi 配置下的文件,那么 pi 本身"允许其被这些内容影响"并不构成一个新的安全漏洞——因为攻击者本来就已经拥有了本地写权限,这不是 pi 授予的。

## 项目信任(Project Trust)机制:它保护什么、不保护什么

项目信任不是沙箱,`security.md` 明确定义了它的作用范围:控制 pi 是否加载**项目本地的设置、资源、包、扩展**。它不限制模型在你开始工作之后能让工具做什么。

### 什么会触发"需要信任"

pi 在当前工作目录下发现以下任意一项,就认为这个项目存在"需要信任的资源":

- `.pi/settings.json`
- `.pi/extensions`、`.pi/skills`、`.pi/prompts`、`.pi/themes` 目录
- `.pi/SYSTEM.md` 或 `.pi/APPEND_SYSTEM.md`
- 当前目录或祖先目录中的项目级 `.agents/skills`

一个**只是存在但是空的** `.pi` 目录本身不算需要信任的项目资源。

### 信任决策的解析顺序

当交互式会话在一个存在待信任资源、且当前目录或其父目录都没有已保存决策的项目里启动时,pi 遵循全局设置里的 `defaultProjectTrust`,默认值是 `"ask"`——在有 UI 的情况下询问是否信任。已保存的信任决策按"规范化目录"存储在 `~/.pi/agent/trust.json` 里,当前目录或父目录路径上**最近的**一条已保存决策优先于全局默认值生效。

信任一个项目之后,pi 才会加载:

- `.pi/settings.json`
- `.pi` 下的扩展、skills、prompt 模板、主题等资源
- 项目设置里配置的、缺失的项目包
- 项目本地扩展和项目包管理的扩展

拒绝信任则会跳过这些受保护的资源。但有一类文件是**无论是否信任都会加载**的例外:`AGENTS.override.md`、`AGENTS.md`、`CLAUDE.md` 这类上下文文件,除非显式关闭了上下文加载功能。在信任决策做出之前,pi 只会加载上下文文件、用户/全局级扩展,以及命令行 `-e` 参数指定的扩展;用户/全局扩展和 CLI 扩展可以处理 `project_trust` 事件,第一个返回是/否决定的扩展拥有最终决定权。

### 非交互模式下的行为

`-p`(打印模式)、`--mode json`、`--mode rpc` 这几种非交互模式**不会弹出信任提示**。在没有匹配到已保存信任决策的情况下:`defaultProjectTrust` 为 `"ask"` 或 `"never"` 时会**忽略**这些受保护资源(即当作不信任处理),为 `"always"` 时才会信任。也可以用 `--approve`/`-a` 或 `--no-approve`/`-na` 命令行参数,对单次运行覆盖项目信任的判定结果。

### 关键限制:信任只是"输入加载"的守卫

`security.md` 用一句话划清了边界:

> Project trust is only an input-loading guard. It prevents a repository from silently changing pi's settings or extensions before you approve it. It does not make untrusted code, untrusted prompts, or untrusted model output safe.

也就是说,信任机制解决的是"一个仓库不能在你还没同意之前,就悄悄改掉 pi 的设置或悄悄加载扩展代码"这一具体问题。它不解决、也无法解决 prompt injection(提示注入)——文档原话是仓库文件、注释、文档、构建产物里的提示注入"是预期中的本地 Agent 风险,pi 无法可靠地防范它"。

## 没有沙箱时该怎么办:三种容器化方案对比

`packages/coding-agent/docs/containerization.md` 给出两条总体路径:要么把整个 `pi` 进程装进隔离环境,要么让 `pi` 跑在宿主机上、只把工具执行路由进隔离环境。文档给出的三种具体方案:

| 方案 | 被隔离的范围 | 适用场景 | 关键限制/说明 |
|---|---|---|---|
| **Gondolin extension** | 内置工具(read/write/edit/bash/grep/find/ls)和 `!` 命令 | 想要本地 micro-VM 级隔离,同时把 Provider 认证信息留在宿主机上 | 其他自定义扩展工具默认仍在宿主机执行,除非它们自己也做了委托 |
| **纯 Docker** | 整个 `pi` 进程 | 追求最简单的本地容器隔离 | Provider API Key 会进入容器内部 |
| **OpenShell** | 整个 `pi` 进程 | 需要文件系统/进程/网络/凭证/推理调用都受策略控制的本地或远程托管沙箱 | 需要一个正在运行的 OpenShell 网关(gateway) |

### Gondolin extension

[Gondolin](https://github.com/earendil-works/gondolin) 是一个本地 Linux micro-VM(微虚拟机)。它的定位是"`pi` 本身留在宿主机上,但所有内置工具都路由进 VM 执行":

```bash
cp -R packages/coding-agent/examples/extensions/gondolin ~/.pi/agent/extensions/gondolin
cd ~/.pi/agent/extensions/gondolin
npm install --ignore-scripts

cd /path/to/project
pi -e ~/.pi/agent/extensions/gondolin
```

这个扩展会把宿主机当前工作目录挂载到 VM 里的 `/workspace`,并重写 `read`、`write`、`edit`、`bash`、`grep`、`find`、`ls` 这几个内置工具的实现,让它们实际在 VM 内执行;用户输入的 `!` 命令也会被路由进 VM。`/workspace` 下的文件改动会直接写回宿主机。这种方案的好处是 Provider 认证(API Key、OAuth token)始终留在宿主机进程里,不会被带进隔离环境;代价是需要 Node.js >= 23.6.0(供 `@earendil-works/gondolin` 使用)以及通过系统包管理器安装 QEMU。需要注意:如果你自己写的自定义扩展工具没有主动把操作委托给 VM,它们依然会在宿主机上直接执行——Gondolin 只接管内置工具和 `!` 命令。

### 纯 Docker

把整条流水线全部塞进容器,是三种方案里最简单直接的一种:

```dockerfile
FROM node:24-bookworm-slim
RUN apt-get update \
  && apt-get install -y --no-install-recommends bash ca-certificates git ripgrep \
  && rm -rf /var/lib/apt/lists/*
RUN npm install -g --ignore-scripts @earendil-works/pi-coding-agent
WORKDIR /workspace
ENTRYPOINT ["pi"]
```

```bash
docker build -t pi-sandbox -f Dockerfile.pi .
docker run --rm -it \
  -e ANTHROPIC_API_KEY \
  -v "$PWD:/workspace" \
  -v pi-agent-home:/root/.pi/agent \
  pi-sandbox
```

这里 Provider API Key 是通过 `-e ANTHROPIC_API_KEY` 直接注入到容器环境变量里的,也就是说密钥本身进入了容器——这是文档明确指出的这种方案的一个特点(而不是 Gondolin 那样把凭证留在宿主机)。用命名卷(`pi-agent-home`)挂载 `/root/.pi/agent` 可以让容器拥有自己独立的设置和会话数据;如果反过来把宿主机的 `~/.pi/agent` 挂进去,容器就能访问到宿主机的认证信息和历史会话,等于放弃了这层隔离的意义。

### OpenShell

[NVIDIA OpenShell](https://docs.nvidia.com/openshell/about/overview) 提供的是策略控制的沙箱,能力覆盖文件系统、进程、网络、凭证、推理调用多个维度,可以通过本地网关(基于 Docker、Podman 或某种 VM runtime)或远程 Kubernetes 网关运行:

```bash
openshell gateway add <gateway-url> --name <name>
openshell gateway select <name>
openshell sandbox create --name pi-sandbox --from pi -- pi
```

在这种模式下,整个 `pi` 进程、内置工具、`!` 命令、扩展工具全部在 OpenShell 边界内执行。如果使用的是远程网关,项目文件不会自动 bind mount 到沙箱里,沙箱内的写入也不会反映到宿主机,需要显式上传/下载:

```bash
openshell sandbox upload pi-sandbox ./repo /workspace
openshell sandbox download pi-sandbox /workspace/repo ./repo-out
```

OpenShell 的一个独特能力是可以让**原始的模型 API Key 完全不进入沙箱**:配置好推理路由后,沙箱内部代码可以调用一个统一的 `https://inference.local` 地址,由网关在沙箱外部注入真正的 Provider 凭证并转发请求——这是三种方案里对"凭证永不进入被隔离环境"支持得最完整的一种,前提是你需要按对应的 OpenAI 兼容或 Anthropic 兼容端点配置 pi 的模型路由。

### 共同的注意事项:bind mount 的读写风险

无论用哪种方案,只要用了 `-v "$PWD:/workspace"` 这类读写挂载(bind mount),隔离环境内部对这个目录的写入就会**直接反映到宿主机文件系统**——这一点 Gondolin 和纯 Docker 方案的文档都各自提到过。如果你想要更强的"防止意外写入宿主机"的保护,应该使用只读挂载,或者干脆把文件复制进沙箱、处理完再把结果复制出来,而不是依赖读写挂载 + 事后审查这种模式。

## 安全漏洞上报流程

`packages/coding-agent/docs/security.md` 把上报入口指向仓库的 `SECURITY.md`;`SECURITY.md` 给出的具体渠道:

- 发邮件到 `security@earendil.com`,或
- 通过 GitHub Security Advisories 对该仓库提交私有报告

**不要为安全敏感的问题开公开 issue。** 报告应包含:问题描述及影响、复现步骤/概念验证(PoC)/相关日志、受影响的包/版本/commit/配置、已知的缓解措施。范围(scope)覆盖仓库中分发的包、命令行工具、API、仓库代码,以及 earendil 运营的 `pi.dev` 基础设施。

### 明确排除在漏洞范畴之外的情形

`SECURITY.md` 的 "Out Of Scope" 列表相当长,核心逻辑是:**凡是 pi 本身设计上就承认、且文档已明确声明的"预期中的本地 Agent 行为",不算漏洞**,包括但不限于:

- 本地代码执行或缺少沙箱本身(pi 有意不内置沙箱)
- 用户安装的扩展或 skill 的行为
- 在不受信任仓库里工作产生的风险
- 安装不受信任的扩展、skill、包或工具产生的风险
- 不可信的中间人(MITM)代理导致的问题
- pi 安装实例暴露在公网上
- 提示注入(prompt injection)攻击
- 属于第三方/用户自己的凭证泄露
- 需要先获得"在目标机器上创建、修改、删除或替换文件/目录/符号链接/环境变量/shell 配置或其他用户可控本地状态"能力才能成立的报告(明确点名 `~/.pi`、`~/.pi/agent/models.json`、工作区文件、`AGENTS.md`、skills、扩展及其配置、dotfiles 等),除非报告能证明是 pi 自身授予了这种访问能力
- 由用户主动弱化配置导致的问题
- 需要"受信任的本地输入/配置"才能对 pi CLI 造成资源耗尽/拒绝服务的说法
- 关于恶意模型输出本身的报告
- 用户自己批准或主动发起的本地操作,被包装成"漏洞"来报告

`SECURITY.md` 总结得很直白:**最有价值的报告是展示一个当前存在、可复现的安全边界绕过(security boundary bypass),并有实际影响的证明**;只是展示"预期中的本地 Agent 行为"、"提示注入"或"一个恶意的、用户自己信任并安装的扩展/skill 做了坏事",在这套安全模型下都不构成漏洞。

## 思考题

1. 假设你要给团队写一份"什么时候必须用容器化方案跑 pi"的内部规范,结合本文的三种方案对比,你会给"处理来源不可信的开源仓库"和"跑无人值守的自动化任务"这两种场景分别推荐哪种方案?为什么?
2. `.pi/settings.json` 需要项目信任才能加载,但 `AGENTS.md`/`CLAUDE.md` 无论是否信任都会加载。结合 prompt injection 被列为 "Out Of Scope" 这一事实,思考一下这种差异化处理背后,项目信任机制到底想防住哪一类攻击、又刻意放弃了防住哪一类攻击。
3. 如果你在 OpenShell 沙箱里跑 pi,并把推理路由配置为 `https://inference.local`,相比直接把 `ANTHROPIC_API_KEY` 作为环境变量传进 Docker 容器,这两种方式在"凭证一旦沙箱被攻破会造成多大损失"这个维度上有什么本质区别?

## 小结

pi 的安全模型可以浓缩成一句话:核心保持"无沙箱、与启动它的用户同权限"的简单状态,把两类完全不同的问题分开处理——项目信任机制只负责"仓库不能在你不知情的情况下悄悄改配置、装扩展",容器化方案才负责"真正意义上的执行隔离"。这个设计避免了一个常见的错误:在应用层做一套看似安全、实则漏洞百出的伪沙箱。理解了这一点,你才能准确判断什么时候必须上容器/VM 隔离(处理不可信仓库、无人值守自动化),什么时候项目信任的确认弹窗已经足够(日常在自己信任的项目里开发),以及为什么"提示注入"和"恶意扩展"这类问题在 pi 的安全边界定义里被明确排除在外——因为它们本来就不属于 pi 声称要防御的那类问题。
