# 内置工具全解析

> `packages/coding-agent/src/core/tools/` 目录下的七个内置工具（read/bash/edit/write/grep/find/ls）是 pi coding agent 真正"动手"的地方；理解它们的参数、并发安全机制和输出截断策略，是读懂整个 Agent 执行链路的前提。

## 学习目标

- 说出七个内置工具各自的职责、输入参数与返回结构。
- 理解 `file-mutation-queue.ts` 为什么要把同一文件的写操作排队，以及它是如何识别"同一文件"的（含符号链接场景）。
- 理解 `truncate.ts` 与 `output-accumulator.ts` 如何在"不撑爆上下文"和"不丢失关键信息"之间做取舍。
- 通过阅读 `edit.ts` 和 `edit-diff.ts` 的真实代码，讲清楚 `edit` 工具"精确文本替换"的匹配、去重、防重叠逻辑。
- 通过阅读 `bash.ts` 的真实代码，讲清楚 `bash` 工具的超时、流式输出、abort 处理机制。

## 工具总览

`index.ts` 用一个 `ToolName` 联合类型统一枚举了七个内置工具：

```ts
export type ToolName = "read" | "bash" | "edit" | "write" | "grep" | "find" | "ls";
export const allToolNames: Set<ToolName> = new Set(["read", "bash", "edit", "write", "grep", "find", "ls"]);
```

`index.ts` 还提供了几组便捷工厂函数：`createCodingTools`（read/bash/edit/write，面向"能改代码"的场景）和 `createReadOnlyTools`（read/grep/find/ls，面向只读探索场景，例如子 Agent 或安全受限模式）。每个工具都有两层包装：

1. `create<Name>ToolDefinition(cwd, options)`：返回一个 `ToolDefinition`，除了 `execute` 之外还带有 `renderCall`/`renderResult`（终端渲染逻辑）、`promptSnippet`/`promptGuidelines`（写入系统提示词的说明）。
2. `create<Name>Tool(cwd, options)`：调用 `wrapToolDefinition()` 把 `ToolDefinition` 降级成 Agent 运行时真正认识的 `AgentTool`（只保留 `execute` 等运行时必需字段，渲染部分被裁掉）。

`tool-definition-wrapper.ts` 里的 `wrapToolDefinition` 就是这层适配：

```ts
export function wrapToolDefinition<TDetails = unknown>(
	definition: ToolDefinition<any, TDetails>,
	ctxFactory?: () => ExtensionContext,
): AgentTool<any, TDetails> {
	return {
		name: definition.name,
		label: definition.label,
		description: definition.description,
		parameters: definition.parameters,
		constrainedSampling: definition.constrainedSampling,
		prepareArguments: definition.prepareArguments,
		executionMode: definition.executionMode,
		execute: (toolCallId, params, signal, onUpdate, ctx?: ExtensionContext) =>
			definition.execute(toolCallId, params, signal, onUpdate, ctx ?? (ctxFactory?.() as ExtensionContext)),
	};
}
```

这也是为什么扩展（extension）在 `pi.registerTool()` 时只需要提供 `ToolDefinition` 的子集：底层运行时并不关心"怎么在终端里画出来"，只关心"怎么执行"。

所有工具都支持"可插拔操作"（Pluggable Operations）模式：每个工具都定义了一个 `XxxOperations` 接口（比如 `EditOperations`、`BashOperations`），默认实现指向本地文件系统 / 本地 shell，但可以被替换成远程实现（例如 `examples/extensions/ssh.ts` 就是把所有工具的 `operations` 换成走 SSH 执行）。这是 pi 支持"远程编码"的关键设计。

## read：读文件（含图片）

**参数**（`readSchema`）：
- `path`：文件路径（相对或绝对）
- `offset`：起始行号（1-indexed，可选）
- `limit`：最大读取行数（可选）

**行为要点**：
- 支持文本文件与图片（jpg/png/gif/webp/bmp），图片会被 `processImage` 自动压缩到 2000x2000 以内（`autoResizeImages` 选项，默认开启），并作为 `image` 类型的 content block 附加。如果当前模型不支持图片输入（`ctx.model.input` 不含 `"image"`），会额外追加一段文字提示。
- 文本内容默认按 2000 行 / 50KB（谁先触发谁生效）截断，这两个阈值定义在 `truncate.ts` 的 `DEFAULT_MAX_LINES` 和 `DEFAULT_MAX_BYTES` 里。截断时会在正文后追加一行可操作的提示，例如：

```
[Showing lines 1-2000 of 5000. Use offset=2001 to continue.]
```

这行提示直接把"如何继续读"的方法写进了工具返回值里，让模型不需要额外推理就知道下一步该传什么参数。
- 如果某一行本身就超过字节上限（例如一个巨大的 minified JS 文件），`read` 不会强行截断出半个乱码字符串，而是返回一条提示，建议改用 `bash` 的 `sed -n '<行号>p' <path> | head -c <字节数>` 来兜底。
- 路径解析走 `resolveReadPathAsync`（`path-utils.ts`），会自动尝试几种 macOS 特有的文件名变体：NFD（分解式 Unicode）归一化、macOS 系统截图文件名里的窄不换行空格（AM/PM 前）、弯引号变体，用来兼容"模型抄错了 macOS 截图文件名里的特殊字符"这种真实会发生的情况。

## write：整文件写入

**参数**（`writeSchema`）：`path`、`content`（完整文件内容）。

**行为要点**：
- 若父目录不存在会自动 `mkdir(dir, { recursive: true })` 后再写文件，调用方不需要自己处理目录创建。
- 整个"建目录 + 写文件"过程包裹在 `withFileMutationQueue(absolutePath, ...)` 里（见下文"并发安全"一节），避免与同一时间对同一文件生效的 `edit` 调用互相踩踏。
- `write` 工具的系统提示词明确写着"仅用于新文件或整体重写"（`Use write only for new files or complete rewrites.`），把"小范围精确修改"的场景让给 `edit`。

## edit：精确文本替换（详解）

`edit` 是七个工具里逻辑最复杂的一个，因为它要在"模型描述的旧文本"和"文件的真实字节"之间做匹配，还要处理多组编辑互不重叠的约束。下面按代码逐段拆解。

### 参数结构

```ts
const replaceEditSchema = Type.Object({
	oldText: Type.String({
		description:
			"Exact text for one targeted replacement. It must be unique in the original file and must not overlap with any other edits[].oldText in the same call.",
	}),
	newText: Type.String({ description: "Replacement text for this targeted edit." }),
});

const editSchema = Type.Object({
	path: Type.String({ description: "Path to the file to edit (relative or absolute)" }),
	edits: Type.Array(replaceEditSchema, {
		description:
			"One or more targeted replacements. Each edit is matched against the original file, not incrementally. ...",
	}),
});
```

关键约束写在 schema 的 `description` 里而不只是文档里：**每个 `edits[].oldText` 都是针对"原始文件"匹配的，而不是链式地在上一步编辑结果上继续匹配**。这意味着如果两处改动挨得很近或有重叠，模型必须合并成一个 `edit` 条目，而不能拆成两个相邻的 `oldText`。

### 兼容旧参数形状

`prepareEditArguments` 处理了两类历史遗留输入：

```ts
function prepareEditArguments(input: unknown): EditToolInput {
	...
	// 有些模型（Opus 4.6、GLM-5.1）把 edits 发送成 JSON 字符串而不是数组
	if (typeof args.edits === "string") {
		try {
			const parsed = JSON.parse(args.edits);
			if (Array.isArray(parsed)) args.edits = parsed;
		} catch {}
	}

	// 旧版单组 oldText/newText 顶层参数，兼容恢复旧会话时的工具调用
	const legacy = args as LegacyEditToolInput;
	if (typeof legacy.oldText !== "string" || typeof legacy.newText !== "string") {
		return args as EditToolInput;
	}
	const edits = Array.isArray(legacy.edits) ? [...legacy.edits] : [];
	edits.push({ oldText: legacy.oldText, newText: legacy.newText });
	...
}
```

这是"`prepareArguments` 钩子"的典型用法：在 schema 校验之前把各种历史格式统一成当前 schema 认可的形状，而不是放宽 schema 本身。

### 执行逻辑：读文件 → 应用编辑 → 写回

```ts
async execute(_toolCallId, input: EditToolInput, signal?: AbortSignal, _onUpdate?, _ctx?) {
	const { path, edits } = validateEditInput(input);
	const absolutePath = resolveToCwd(path, cwd);

	return withFileMutationQueue(absolutePath, async () => {
		const throwIfAborted = (): void => {
			if (signal?.aborted) throw new Error("Operation aborted");
		};
		throwIfAborted();
		await ops.access(absolutePath);       // 1. 文件必须存在且可读写
		throwIfAborted();
		const buffer = await ops.readFile(absolutePath);
		const rawContent = buffer.toString("utf-8");
		throwIfAborted();

		const { bom, text: content } = stripBom(rawContent);          // 2. 剥离 BOM
		const originalEnding = detectLineEnding(content);              // 3. 记住原始换行符（\r\n 还是 \n）
		const normalizedContent = normalizeToLF(content);              // 4. 统一按 \n 处理，避免 \r\n 干扰匹配
		const { baseContent, newContent } = applyEditsToNormalizedContent(normalizedContent, edits, path);
		throwIfAborted();

		const finalContent = bom + restoreLineEndings(newContent, originalEnding); // 5. 换回原始换行符再写回
		await ops.writeFile(absolutePath, finalContent);
		throwIfAborted();

		const diffResult = generateDiffString(baseContent, newContent);
		const patch = generateUnifiedPatch(path, baseContent, newContent);
		return {
			content: [{ type: "text", text: `Successfully replaced ${edits.length} block(s) in ${path}.` }],
			details: { diff: diffResult.diff, patch, firstChangedLine: diffResult.firstChangedLine },
		};
	});
}
```

值得注意的实现细节：
1. **BOM 与换行符归一化**：模型描述的 `oldText` 里不会包含不可见的 UTF-8 BOM，也不会准确带上 Windows 风格的 `\r\n`，所以 `edit` 先剥离 BOM、把内容统一转成 `\n`，匹配完成后再用 `restoreLineEndings` 换回原始换行风格写回磁盘，这样既不破坏 Windows 项目的行尾约定，也不会因为行尾差异导致匹配失败。
2. **每次 `await` 之后都调用 `throwIfAborted()`**：代码注释解释了为什么不在 `signal` 的 `abort` 事件监听器里直接 `reject`——那样会在文件系统操作仍在进行时提前释放互斥队列，造成竞态。改为在每次 `await` 之后主动检查 `signal.aborted`，既能响应取消，又能保证队列在真正操作完成前不被释放。

### 匹配算法：`applyEditsToNormalizedContent`（`edit-diff.ts`）

真正决定"能不能替换、要不要报错"的逻辑在 `edit-diff.ts`：

```ts
export function applyEditsToNormalizedContent(
	normalizedContent: string,
	edits: Edit[],
	path: string,
): AppliedEditsResult {
	...
	const initialMatches = normalizedEdits.map((edit) => fuzzyFindText(normalizedContent, edit.oldText));
	const usedFuzzyMatch = initialMatches.some((match) => match.usedFuzzyMatch);
	const replacementBaseContent = usedFuzzyMatch ? normalizeForFuzzyMatch(normalizedContent) : normalizedContent;

	const matchedEdits: MatchedEdit[] = [];
	for (let i = 0; i < normalizedEdits.length; i++) {
		const edit = normalizedEdits[i];
		const matchResult = fuzzyFindText(replacementBaseContent, edit.oldText);
		if (!matchResult.found) throw getNotFoundError(path, i, normalizedEdits.length);
		const occurrences = countOccurrences(replacementBaseContent, edit.oldText);
		if (occurrences > 1) throw getDuplicateError(path, i, normalizedEdits.length, occurrences);
		matchedEdits.push({ editIndex: i, matchIndex: matchResult.index, matchLength: matchResult.matchLength, newText: edit.newText });
	}

	matchedEdits.sort((a, b) => a.matchIndex - b.matchIndex);
	for (let i = 1; i < matchedEdits.length; i++) {
		const previous = matchedEdits[i - 1];
		const current = matchedEdits[i];
		if (previous.matchIndex + previous.matchLength > current.matchIndex) {
			throw new Error(`edits[${previous.editIndex}] and edits[${current.editIndex}] overlap in ${path}. Merge them into one edit or target disjoint regions.`);
		}
	}
	...
}
```

三层安全校验，全部通过明确抛错反馈给模型，而不是静默地做"最可能正确"的猜测：

1. **必须找到（`getNotFoundError`）**：`oldText` 在文件里一个都找不到时报错，提示"必须逐字符匹配，包括所有空白和换行"。
2. **必须唯一（`getDuplicateError`）**：`oldText` 匹配到多处时报错并附带出现次数，要求模型补充更多上下文让文本变得唯一，而不是替换第一个或全部替换——因为 pi 无法确定模型的真实意图，贸然替换全部或替换第一个都可能造成"修改了错误位置"的静默错误。
3. **禁止重叠（"overlap" 错误）**：多个 `edits[]` 按匹配到的位置排序后，如果前一个编辑的结束位置越过了下一个编辑的起始位置，直接报错并要求模型合并成一个 `edit`。这是为了避免"两处编辑的区间互相包含或交叉"时替换顺序不确定导致的结果歧义。

此外还有一层**模糊匹配兜底**（`fuzzyFindText` + `normalizeForFuzzyMatch`）：如果精确匹配失败，会在"去除行尾空白、把智能引号/破折号/特殊空格归一化为 ASCII 等价字符"之后的文本上再试一次。这是为了兼容模型把直引号打成弯引号、把普通连字符打成 en-dash 等常见的"复制粘贴走样"问题，但一旦命中模糊匹配，替换结果仍然会通过 `applyReplacementsPreservingUnchangedLines` 尽量保留未改动行的原始字节，只重写真正被触碰到的行。

## bash：执行 Shell 命令（详解）

**参数**（`bashSchema`）：`command`（必填）、`timeout`（秒，可选，默认不超时）。

### 超时换算与上限保护

```ts
const MAX_TIMEOUT_MS = 2_147_483_647; // Node setTimeout 的最大安全值（2^31 - 1）
const MAX_TIMEOUT_SECONDS = MAX_TIMEOUT_MS / 1000;

function resolveTimeoutMs(timeout: number | undefined): number | undefined {
	if (timeout === undefined) return undefined;
	if (!Number.isFinite(timeout) || timeout <= 0) throw new Error("Invalid timeout: must be a finite number of seconds");
	const timeoutMs = timeout * 1000;
	if (timeoutMs > MAX_TIMEOUT_MS) throw new Error(`Invalid timeout: maximum is ${MAX_TIMEOUT_SECONDS} seconds`);
	return timeoutMs;
}
```

`MAX_TIMEOUT_MS` 直接取 32 位有符号整数的最大值，这是 Node.js `setTimeout` 底层的硬限制——超过这个值会被静默截断成 1ms 立即触发，所以这里显式校验并报错，而不是让 bug 在运行时才暴露。

### 进程执行与信号处理

`createLocalBashOperations` 内部用 `child_process.spawn` 启动 shell（`detached: process.platform !== "win32"`，方便后续用 `killProcessTree` 杀掉整个进程组），并同时挂了三类"终止来源"：

- **超时**：`setTimeout` 到时调用 `killProcessTree(child.pid)`，随后在 `waitForChildProcess` 返回后检测 `timedOut` 标志，抛出 `timeout:<seconds>` 格式的错误。
- **abort 信号**：`signal.addEventListener("abort", onAbort, { once: true })`，同样杀掉整棵进程树。
- **正常退出**：`waitForChildProcess(child)` 拿到 `exitCode`，非 0 且非 `null` 时在上层被转成"Command exited with code N"的错误。

### 流式输出与节流更新

`bash` 支持在命令执行过程中通过 `onUpdate` 回调向 UI 增量推送输出，但没有对每一个 data 事件都触发渲染，而是做了节流：

```ts
const BASH_UPDATE_THROTTLE_MS = 100;
const scheduleOutputUpdate = () => {
	if (!onUpdate) return;
	updateDirty = true;
	const delay = BASH_UPDATE_THROTTLE_MS - (Date.now() - lastUpdateAt);
	if (delay <= 0) { clearUpdateTimer(); emitOutputUpdate(); return; }
	updateTimer ??= setTimeout(() => { updateTimer = undefined; emitOutputUpdate(); }, delay);
};
```

即最多每 100ms 推送一次快照，避免命令产生海量输出（例如 `yes` 或密集日志）时把 UI 渲染循环打爆。

### 会话环境变量注入

`resolveSpawnContext` 会在 `exposeSessionEnvironment`（默认 `true`）开启时，把当前会话信息注入到子进程环境变量：`PI_SESSION_ID`、`PI_SESSION_FILE`、`PI_PROVIDER`、`PI_MODEL`、`PI_REASONING_LEVEL`。这也是为什么 `bash` 工具的 `promptGuidelines` 里写着"可以检查 `PI_*` 环境变量获取当前模型和会话信息"——这是留给命令行脚本（比如自定义的 pre-commit 钩子）读取上下文的正式接口。

## grep / find / ls：只读探索三件套

这三个工具都遵循同一套设计模式：底层依赖外部二进制（`ripgrep` 给 `grep`，`fd` 给 `find`；`ls` 则是纯 Node `fs` 实现），通过 `ensureTool()`（`utils/tools-manager.ts`）按需下载/定位可执行文件，再用 `spawn` + `readline` 逐行解析输出。

- **`grep`**（`grepSchema`）：`pattern`（正则或字面量）、`path`、`glob`（文件名过滤）、`ignoreCase`、`literal`（把 `pattern` 当纯字符串而非正则）、`context`（前后文行数）、`limit`（默认 100 条匹配）。匹配结果自动尊重 `.gitignore`。单行匹配超过 `GREP_MAX_LINE_LENGTH`（500 字符）会被截断并加上 `... [truncated]` 后缀，避免一行超长的 minified 代码把输出撑爆。
- **`find`**（`findSchema`）：`pattern`（glob，如 `**/*.spec.ts`）、`path`、`limit`（默认 1000）。同样尊重 `.gitignore`。`relativizeFindResultPath` 会把结果统一转成相对搜索根目录的 POSIX 风格路径（哪怕在 Windows 上运行）。
- **`ls`**（`lsSchema`）：`path`（默认当前目录）、`limit`（默认 500 条）。返回条目按字母排序，目录名带 `/` 后缀，包含点文件。

三者的输出都要经过 `truncate.ts` 的字节/行数双重限制，并在超限时附加一句可读的截断提示（例如 `[Truncated: 100 matches limit]`），这与 `read`/`bash` 的截断哲学一致：**永远返回完整的行，而不是从行中间硬切**（`truncateHead`/`truncateTail` 的实现里专门处理了这个边界情况）。

## 并发安全：`file-mutation-queue.ts`

`edit` 和 `write` 都会修改文件，而 pi 默认是**并行执行同一批工具调用**的（同一条模型消息里的多个 tool_call 会并发执行）。如果两个工具调用同时改写同一个文件，天真的"读-改-写"会发生经典的丢失更新问题：两者都读到旧内容，各自算出新内容，后写的一个会覆盖先写的一个的改动。

`withFileMutationQueue` 用一个 `Map<string, Promise<void>>` 为每个文件维护一条串行队列：

```ts
export async function withFileMutationQueue<T>(filePath: string, fn: () => Promise<T>): Promise<T> {
	const registration = registrationQueue.then(async () => {
		const key = await getMutationQueueKey(filePath);
		const currentQueue = fileMutationQueues.get(key) ?? Promise.resolve();
		let releaseNext!: () => void;
		const nextQueue = new Promise<void>((resolveQueue) => { releaseNext = resolveQueue; });
		const chainedQueue = currentQueue.then(() => nextQueue);
		fileMutationQueues.set(key, chainedQueue);
		return { key, currentQueue, chainedQueue, releaseNext };
	});
	registrationQueue = registration.then(() => undefined, () => undefined);

	const { key, currentQueue, chainedQueue, releaseNext } = await registration;
	await currentQueue;
	try {
		return await fn();
	} finally {
		releaseNext();
		if (fileMutationQueues.get(key) === chainedQueue) fileMutationQueues.delete(key);
	}
}
```

几个关键设计点：

1. **按文件而非全局加锁**：不同文件的写操作仍然完全并行，只有同一文件的操作才会排队，最大化并发度。
2. **`getMutationQueueKey` 用 `realpath()` 归一化路径**：对已存在的文件，先解析成真实路径（跟踪符号链接），保证"两个不同的符号链接指向同一个真实文件"时也能共享同一条队列；对不存在的文件（`ENOENT`/`ENOTDIR`，比如 `write` 要新建文件），退回使用 `resolve()` 后的路径,因为这时候还没有真实文件可以 `realpath`。
3. **`registrationQueue` 二级队列**：为了让"取号排队"这个动作本身也是原子的（避免多个并发调用同时读取到同一个 `currentQueue` 从而错误地排在同一个位置），注册环节又被串行化了一次。

`edit.ts` 和 `write.ts` 都把整个"检查存在 → 读文件 → 计算新内容 → 写回"过程包在 `withFileMutationQueue` 内部，而不是只包住最后的 `writeFile` 调用——这是必须的，因为竞态发生在"读"和"写"之间的窗口，只锁写入本身没有意义。扩展开发者自定义的会修改文件的工具，也应当遵循同样的模式（第二篇《扩展 Extension 开发指南》会展开）。

## 输出截断：`truncate.ts` 与 `output-accumulator.ts`

pi 的每个工具输出都要送进模型的上下文窗口，所以必须有硬性上限。`truncate.ts` 定义了两个默认值：

```ts
export const DEFAULT_MAX_LINES = 2000;
export const DEFAULT_MAX_BYTES = 50 * 1024; // 50KB
export const GREP_MAX_LINE_LENGTH = 500;
```

并提供两种截断方向：

- **`truncateHead`**（从头保留）：给 `read` 用——读文件通常想看开头，超限后明确告诉模型"用 offset=N 继续读"。
- **`truncateTail`**（从尾保留）：给 `bash` 用——命令输出通常最有价值的是最后的报错和结果，所以反而从后往前保留。`truncateTail` 有一个特殊边界情况：如果连最后一行都超过字节上限（比如一行几十 MB 的日志），允许返回这一行的"部分内容"（`lastLinePartial: true`），这是唯一允许出现"半行"的地方。

`output-accumulator.ts` 则是给 `bash` 专门设计的**流式**累加器，因为命令输出是边执行边产生的，不能等命令结束才处理：

- 用 `TextDecoder({ stream: true })` 增量解码字节流，正确处理跨 chunk 被截断的多字节 UTF-8 字符。
- 维护一个"滚动尾部"文本（`tailText`），只保留最近 `maxBytes * 2` 字节左右，超过后从缓冲区里裁掉前面的部分——这保证了内存占用不会随着长时间运行的命令无限增长。
- 一旦检测到总字节数或总行数超过阈值（`shouldUseTempFile()`），自动切换成把原始数据流写入一个临时文件（`tempdir()` 下的 `pi-bash-<random>.log`），这样即使展示给模型的内容被截断了，完整输出依然可以通过 `bash` 结果里返回的 `fullOutputPath` 由用户或后续 `read`/`grep` 调用取回，不会真的丢失数据。

这套"展示截断 + 临时文件兜底完整数据"的组合，是 pi 在"控制上下文成本"和"不让用户真的丢失信息"之间的核心权衡策略，`read`、`grep`、`find`、`ls` 的截断策略都遵循类似的哲学（只是没有临时文件兜底，因为文件本身或搜索结果本来就可以用更精确的参数重新获取）。

## 动手练习

1. 在本地克隆的 pi 仓库中，用 `bash` 工具或普通终端运行一个会产生大量输出的命令（例如 `find / -name "*.ts" 2>/dev/null` 或 `yes | head -100000`），观察 pi 交互模式下工具结果末尾出现的 `[Truncated: ...]` 提示和 `Full output: /tmp/pi-bash-xxx.log` 路径，并用 `read` 工具读取该临时文件确认完整内容确实被保留。
2. 写一个小实验：让 pi 对同一个文件在一次回复里发出两个 `edit` 调用，其中一个的 `oldText` 有意与另一个存在重叠（比如两个 `oldText` 共享几行代码）。观察 pi 是否按本文描述的"overlap" 错误提示要求你合并成一个 `edit`，并思考如果没有这层校验，两个重叠编辑的应用顺序会如何影响最终文件内容。

## 小结

七个内置工具可以分成两组：`read`/`bash`/`edit`/`write` 面向"读写与执行"（`createCodingTools`），`grep`/`find`/`ls` 面向"只读探索"（`createReadOnlyTools`）。所有工具都通过统一的 `ToolDefinition` → `wrapToolDefinition()` → `AgentTool` 管线接入 Agent 运行时，并共享同一套可插拔 `Operations` 接口以支持远程执行。写文件相关的工具（`edit`、`write`）依赖 `file-mutation-queue.ts` 按真实文件路径（而非原始参数字符串）串行化读改写窗口，避免并行工具调用互相踩踏；所有产生大量输出的工具（尤其是 `read` 和 `bash`）都依赖 `truncate.ts` 的行数/字节双限制策略，并通过在截断提示里嵌入"如何继续"的可执行建议，让模型在有限上下文里也能高效完成长任务。`edit` 工具的多层匹配校验（唯一性、无重叠、模糊匹配兜底）体现了 pi 在"精确控制"与"容错性"之间的具体权衡，也是后续开发自定义文件修改工具时最值得参考的实现范式。
