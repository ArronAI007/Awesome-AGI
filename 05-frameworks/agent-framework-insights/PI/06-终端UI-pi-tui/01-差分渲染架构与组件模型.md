# 差分渲染架构与组件模型

> `packages/tui` 是 pi 的终端 UI（Terminal UI）库，用"差分渲染"（differential rendering）而不是每帧全量重绘来驱动一个几乎不闪烁的命令行界面——本文从真实源码出发，讲清楚它是怎么做到的。

## 学习目标

- 理解什么是差分渲染，以及它相较于全量重绘（full redraw）在终端场景下的必要性。
- 读懂 `tui-main-screen.ts` 中逐行对比新旧帧、只重绘变化区间的核心算法。
- 掌握 `layout.ts` / `layout-node.ts` 的布局节点模型：组件树如何被摆放、测量、裁剪。
- 弄清主屏幕（main screen）与备用屏幕（alt screen）两种渲染模式的差异与各自的适用场景。
- 梳理"按键输入 → 编辑器组件 → 撤销栈/kill-ring/自动补全"这条完整的编辑体验链路。

## 背景与设计动机

终端（terminal）本质上是一个字符网格加一个只能顺序执行的转义序列（escape sequence）解释器。如果每次界面有变化——哪怕只是一个字符的输入光标闪烁——都把整个屏幕清空再重新打印一遍，会带来两个明显问题：

1. **视觉闪烁**：`\x1b[2J`（清屏）之后到内容重新绘制完成之间，用户会看到一次黑屏或跳动，在慢速终端（比如通过 SSH、Windows Terminal、tmux 多路复用）上尤其明显。
2. **I/O 放大**：终端渲染 CLI Agent 这样的场景里，一屏内容可能有几十上百行（对话历史、代码块、进度条），每次输入一个字符都全量重绘，意味着几 KB 的转义序列通过管道来回传输，在网络终端上会造成明显的输入延迟。

`packages/tui` 的 README 把自己定义为："Minimal terminal UI framework with **differential rendering** and synchronized output for flicker-free interactive CLI applications"（下文简称"差分渲染 + 同步输出"）。它的核心思路和前端框架的虚拟 DOM diff 异曲同工：每次渲染都先在内存里生成一份完整的"新一帧"字符串数组，再和"上一帧"逐行比较，只把变化的行通过转义序列发送给终端，配合 CSI 2026 同步输出（synchronized output）把这批更新包裹成一次原子提交，从而避免闪烁。

## 核心机制详解

### 1. Component 接口：渲染是纯函数

所有组件都实现同一个最小接口，定义在 `packages/tui/src/tui.ts`：

```typescript
// packages/tui/src/tui.ts
export interface Component {
	/** Render the component to lines for the given viewport width */
	render(width: number): string[];
	/** Optional handler for keyboard input when component has focus */
	handleInput?(data: string): void;
	/** If true, component receives key release events (Kitty protocol). Default false. */
	wantsKeyRelease?: boolean;
	/** Invalidate any cached rendering state (e.g. on theme change). */
	invalidate(): void;
}
```

`render(width)` 是一个（近似）纯函数：给定当前视口宽度，返回一组字符串行。它不直接操作终端，只是把"这一帧应该长什么样"描述出来。这个设计是差分渲染能够成立的前提——只有当渲染结果是可重复、可比较的字符串数组，上一帧与这一帧才能逐行 diff。

`Container` 类（同文件）把多个子组件的渲染结果按顺序拼接成一份行数组，是构建组件树最基础的容器（`render()` 内部就是遍历 `children`、逐个调用 `child.render(width)` 再 `push` 进结果数组，不做任何裁剪或换行处理）。

### 2. 差分渲染的核心算法：`TuiMainScreen.doRender()`

真正的"新旧帧对比、只重绘变化行"的逻辑在 `packages/tui/src/tui-main-screen.ts` 的 `doRender()` 里。这个类用于渲染进主屏幕（会写入终端的可滚动历史/scrollback），是 pi CLI 交互模式默认使用的渲染器。

它维护了一份状态，其中 `previousLines: string[]` 就是"上一帧"，`previousWidth`/`previousHeight` 记录上次渲染时的终端尺寸，`previousViewportTop` 记录滚动缓冲区里当前可见视口的起始行号。每次 `doRender()` 被调用时，先渲染出 `newLines`（"这一帧"），随后进行逐行比较：

```typescript
// packages/tui/src/tui-main-screen.ts
// Find first and last changed lines
let firstChanged = -1;
let lastChanged = -1;
const maxLines = Math.max(newLines.length, this.previousLines.length);
for (let i = 0; i < maxLines; i++) {
	const oldLine = i < this.previousLines.length ? this.previousLines[i] : "";
	const newLine = i < newLines.length ? newLines[i] : "";

	if (oldLine !== newLine) {
		if (firstChanged === -1) {
			firstChanged = i;
		}
		lastChanged = i;
	}
}
```

这段代码就是差分渲染的"diff"步骤：把新旧两个字符串数组按索引比较，找出第一处和最后一处发生变化的行号。如果两帧完全一致（`firstChanged === -1`），代码会直接 `return`，什么都不重绘，只顺带处理一下硬件光标位置是否需要挪动（`positionHardwareCursor()`）——对应源码里 `// No changes - but still need to update hardware cursor position if it moved` 这条注释。

如果只有中间某几行变化（典型场景：一个 spinner 动画在刷新，或用户在编辑器里敲了一个字符），只需要把光标移动到 `firstChanged`，然后只重绘 `firstChanged` 到 `lastChanged` 这个区间，代码里专门注释说明了这一点：

```typescript
// packages/tui/src/tui-main-screen.ts
// Only render changed lines (firstChanged to lastChanged), not all lines to end
// This reduces flicker when only a single line changes (e.g., spinner animation)
const renderEnd = Math.min(lastChanged, newLines.length - 1);
for (let i = firstChanged; i <= renderEnd; i++) {
	if (i > firstChanged) buffer += "\r\n";
	const line = newLines[i];
	// ...
	buffer += "\x1b[2K"; // Clear current line
	// ...
	buffer += line;
}
```

`\x1b[2K` 是"清除当前行"的 CSI 序列，只对发生变化的那一行做清除再重绘，而不是清空整个屏幕。这是差分渲染相比全量重绘节省 I/O、减少闪烁的关键：终端收到的数据量从"整屏字符"降为"变化区间的字符 + 少量光标移动指令"。

整个更新过程还被包裹在一对 `"\x1b[?2026h"`（Begin synchronized output）和 `"\x1b[?2026l"`（End synchronized output）之间——这是终端的"同步输出"扩展协议（CSI 2026）。支持该协议的终端会把中间的所有写入缓冲起来，直到收到结束标记才一次性刷新到屏幕，避免了"终端画到一半"被用户看到的中间态闪烁。这与前端框架的批量更新（batching）思路相通：把多次小的写操作合并成一次原子提交。

### 3. 什么时候必须"全量重绘"

差分渲染不是万能的，`doRender()` 里明确列出了几种必须放弃增量更新、走 `fullRender(true)` 全量重绘路径的场景，源码里的判断条件本身就是很好的教材：

```typescript
// packages/tui/src/tui-main-screen.ts
// Width changes always need a full re-render because wrapping changes.
if (widthChanged) {
	logRedraw(`terminal width changed (${this.previousWidth} -> ${width})`);
	fullRender(true);
	return;
}

// Height changes normally need a full re-render to keep the visible viewport aligned,
// but Termux changes height when the software keyboard shows or hides.
if (heightChanged && !isTermuxSession()) {
	logRedraw(`terminal height changed (${this.previousHeight} -> ${height})`);
	fullRender(true);
	return;
}
```

原因很直接：终端宽度变化会导致文本重新换行（word wrap），旧帧里第 N 行对应的文字，在新宽度下可能已经不在第 N 行了，逐行比较失去意义，必须整体重画。高度变化也类似，会影响可视视口（viewport）与内容的对齐关系。

还有一种边界情况——差分渲染只能触及"当前实际可见"的区域，源码里有一句直白的注释：`// Differential rendering can only touch what was actually visible.` 如果 `firstChanged < prevViewportTop`（变化发生在已经滚出可视视口之上的历史内容里），同样必须调用 `fullRender(true)` 整体重绘。

这体现了一个务实的工程取舍：差分渲染的收益建立在"变化通常发生在可见区域内"这个假设上，一旦假设被打破（比如极端情况下历史内容被回溯修改），代码选择用一次完整重绘换取正确性，而不是维护更复杂的增量算法。`fullRedraws` 计数器（`TuiBase.fullRedrawCount`）被暴露出来供调用方观测重绘频率，说明这是一个刻意做了可观测性设计的性能敏感路径。

### 4. 布局系统：`layout.ts` 与 `layout-node.ts`

组件树里除了简单的"垂直拼接"（`Container`），还有需要真正计算尺寸的场景：水平/垂直排列（stack）、滚动视图（scroll）、弹性伸缩（grow/shrink）。这部分由 `layout-node.ts` 定义节点类型，`layout.ts` 实现具体的布局算法。

节点类型定义得很克制，只有两种：

```typescript
// packages/tui/src/layout-node.ts
export interface StackLayoutEntry {
	component: Component;
	basis?: number | "auto";
	grow?: number;
	shrink?: number;
	minSize?: number;
	maxSize?: number;
	visible?: (viewport: LayoutViewport) => boolean;
}

export interface StackLayoutNode {
	type: "vstack" | "hstack";
	entries: readonly StackLayoutEntry[];
	gap: number;
	align: "stretch" | "start" | "center" | "end";
}

export interface ScrollLayoutNode {
	type: "scroll";
	component: Component;
	state: ScrollLayoutState;
}

export type LayoutNode = StackLayoutNode | ScrollLayoutNode;
```

熟悉 CSS Flexbox 的读者会立刻认出 `basis`/`grow`/`shrink`/`minSize`/`maxSize` 这套字段——`StackLayoutEntry` 本质上是把 Flexbox 的伸缩盒模型搬到了终端字符网格上。`getLayoutNode()` 用一个 `Symbol`（`LAYOUT_NODE`）做类型探测：

```typescript
// packages/tui/src/layout-node.ts
export const LAYOUT_NODE = Symbol.for("@earendil-works/pi-tui/layout-node");

export interface LayoutComponent extends Component {
	[LAYOUT_NODE](): LayoutNode;
}

export function getLayoutNode(component: Component): LayoutNode | undefined {
	const candidate = component as Partial<LayoutComponent>;
	return typeof candidate[LAYOUT_NODE] === "function" ? candidate[LAYOUT_NODE]() : undefined;
}
```

这是一个鸭子类型（duck typing）风格的可选协议：一个组件如果实现了 `[LAYOUT_NODE]()` 方法，布局引擎就把它当作"有结构的容器"（stack 或 scroll）来递归布局；否则就退化为最普通的组件，直接调用 `render(width)` 拿到固定的行数组。这样设计的好处是布局能力是可选叠加的，不会强迫每个简单组件（比如一段静态文本）都要实现复杂的布局协议。

具体的布局计算在 `layout.ts` 的 `layoutComponent()` 里递归进行。以最简单的"无布局节点"分支为例，其核心逻辑是：先用 `renderCached()` 拿到该组件在给定宽度下的渲染行数组，再算出分配到的高度 `allocatedHeight`；如果内容行数超过了分配高度，还会用 `lines.findIndex((line) => line.includes(CURSOR_MARKER))` 找到光标所在行，计算出一个 `lineOffset` 把视图裁剪窗口滚动到能看见光标的位置。

这里有两个值得注意的细节：第一，`renderCached()` 会把同一个组件在同一宽度下的渲染结果缓存起来（`Map<Component, Map<number, string[]>>`），因为在一次布局过程里，一个组件的"自然高度"往往需要被测量多次（比如 vstack 需要知道每个子项的内在高度才能分配空间），缓存避免了重复调用 `render()`；第二，`lineOffset` 的计算是编辑器组件被塞进一个高度受限的容器（比如弹出框）时依然能正确显示光标的关键。

`vstack`/`hstack` 分支则使用 `allocateStackSizes()`（定义在 `components/stack.ts` 引用的布局条目基础上）做类似 Flexbox 的尺寸分配，按 `grow`/`shrink` 比例把剩余或超出的空间分摊给各子项，这里不再展开源码，但其输入输出的字段命名（`basis`、`grow`、`shrink`、`minSize`、`maxSize`）已经清楚地表明它是在实现一个简化版的弹性盒子算法。

最终，`renderLayoutFrame()` 把整棵布局树"画"到一个 `string[]` 数组上（`paintBox()` 递归调用），产出的仍然是普通的行数组——这份数据接着会被传给前面讲的差分渲染管线去和上一帧比较。也就是说，**布局系统负责"这一帧长什么样"，差分渲染负责"怎么把这一帧高效地画到终端上"**，两者是清晰分层的。

### 5. 主屏幕 vs. 备用屏幕（alt screen）

pi-tui 提供两种渲染器实现同一个 `TUI` 接口：`TuiMainScreen`（主屏幕）和 `TuiAltScreen`（备用屏幕），源码分别在 `tui-main-screen.ts` 和 `tui-alt-screen.ts`。

主屏幕渲染进终端的正常输出流和 scrollback（回滚历史）。它的差分渲染逻辑正是上面第 2 节讲的内容——因为内容会不断向下追加（比如对话历史越来越长），它需要处理"新增行"（appended lines）、"内容变短需要清除多余行"等一系列相对于滚动缓冲区的边界情况。适合命令行 Agent 这种"历史记录持续累积、用户可以用终端自身滚动条回看"的场景。

备用屏幕则完全不同，它在启动时切换进终端的 alternate screen buffer（一块独立的、退出后会恢复原屏幕内容的画布），代码里体现为：

```typescript
// packages/tui/src/tui-alt-screen.ts
const ENTER_ALT_SCREEN = "\x1b[?1049h";
const EXIT_ALT_SCREEN = "\x1b[?1049l";
// ...
protected override beforeTerminalStart(): void {
	// ...
	this.terminal.write(
		`${ENTER_ALT_SCREEN}${DISABLE_AUTOWRAP}${this.mouseEnabled ? mouseSequence : ""}\x1b[2J\x1b[H\x1b[?25l`,
	);
}
```

`\x1b[?1049h` 就是大多数全屏终端应用（vim、htop、less 等）用来"借用"整块屏幕的标准序列；退出时用 `\x1b[?1049l` 把屏幕内容恢复成进入前的样子。因为拥有了一整块独占的画布，`TuiAltScreen` 实现了应用自己管理的滚动视口（`ScrollView`）、鼠标拖拽选择文本、滚动条拖拽等能力（构造函数里可以看到 `selectionAnchor`、`scrollbarDrag`、`mouseEnabled` 等状态），这些是主屏幕模式不具备的，因为主屏幕依赖终端本身的 scrollback 来"滚动"。

两者的切换时机由使用方决定：pi 的交互式命令行界面用主屏幕（保留了终端原生的滚动、复制历史等习惯），而需要更丰富交互（鼠标选区、内部视口滚动）的全屏工具型界面会选择备用屏幕。二者共享同一个 `TuiBase` 抽象基类（`tui.ts`），也共享 `Component`/`Container`/overlay（浮层）等上层概念，只是"如何把一帧行数组变成终端字节流"这一层的实现完全不同——`TuiMainScreen` 靠逐行 diff，`TuiAltScreen` 则是靠 `renderLayoutFrame()` 生成的布局帧结合自己的一套全屏绘制/裁剪逻辑（`paintBox()`、`compositeTuiLine()` 等）。

退出备用屏幕时还有一个细节：如果不要求 `preserveScreen`，代码会把最后一帧内容重新画一遍并"贴"回主屏幕，让退出后用户仍能在普通终端历史里看到最后的界面状态（见 `afterTerminalStop()` 中 `this.lastDocument = ...` 的处理），而不是像很多全屏 TUI 那样退出后什么都不留。

### 6. 输入处理链路：从按键到编辑体验

pi-tui 里一次按键从"终端字节流"到"编辑器状态改变"要经过几层：

**第一层：`TuiBase.handleTerminalInput()`**（`tui.ts`）是所有输入的入口，先处理终端应答（OSC 11 背景色查询、颜色方案上报、单元格尺寸响应）等"协议层"数据，再依次交给全局输入监听器（`inputListeners`），最后转发给当前拥有焦点的组件：

```typescript
// packages/tui/src/tui.ts
if (this.focusedComponent?.handleInput) {
	// Filter out key release events unless component opts in
	if (isKeyRelease(data) && !this.focusedComponent.wantsKeyRelease) {
		return;
	}
	this.focusedComponent.handleInput(data);
	// Keyboard input is latency-sensitive. Avoid the throttled timer path,
	// where even setTimeout(0) can take a full 16 ms tick on Windows.
	this.requestImmediateRender();
}
```

值得一提的是最后这行注释：普通的渲染请求会走一个节流的 `scheduleRender()`（限制最小渲染间隔 `MIN_RENDER_INTERVAL_MS = 16` 毫秒，约等于 60fps），但键盘输入被认为是延迟敏感的，会强制走 `requestImmediateRender()` 抢占节流队列，保证"敲键盘"到"看见字符出现"之间没有额外等待。

**第二层：按键语义化（`keys.ts` / `native-modifiers.ts`）**。原始输入是一串转义序列字节，`keys.ts` 里的 `matchesKey(data, keyId)` 负责把这串字节和一个类型安全的按键标识符（如 `"ctrl+w"`、`"alt+backspace"`）做匹配，同时兼容传统终端序列和 Kitty 键盘协议（Kitty keyboard protocol，一种能区分按下/释放、携带更精确修饰键信息的现代协议）。`native-modifiers.ts` 则通过原生插件（`darwin-modifiers.node` / `win32-console-mode.node`）在必要时查询操作系统级别的修饰键状态（Shift/Command/Control/Option），弥补部分终端协议本身无法可靠上报组合键的问题。

**第三层：按键语义 → 逻辑动作（`keybindings.ts`）**。pi-tui 没有把 `"ctrl+w"` 这种具体按键硬编码进编辑器逻辑，而是引入了一层间接的"逻辑动作"（keybinding id），比如 `"tui.editor.deleteWordBackward"`。默认映射表定义在 `TUI_KEYBINDINGS` 里：

```typescript
// packages/tui/src/keybindings.ts
"tui.editor.deleteWordBackward": {
	defaultKeys: ["ctrl+w", "alt+backspace"],
	description: "Delete word backward",
},
"tui.editor.yank": { defaultKeys: "ctrl+y", description: "Yank" },
"tui.editor.yankPop": { defaultKeys: "alt+y", description: "Yank pop" },
"tui.editor.undo": { defaultKeys: "ctrl+-", description: "Undo" },
```

`KeybindingsManager.matches(data, keybinding)` 会先查用户是否自定义了这个动作对应的按键，否则退回默认按键表，再调用 `matchesKey()` 判断。这一层间接映射的价值在于：编辑器内部逻辑只需要问"是否触发了删除前一个单词这个动作"，完全不关心具体是哪个按键组合触发的，用户自定义快捷键因此可以做到不侵入业务代码。

**第四层：编辑器组件消费动作（`components/editor.ts`）**。真正的多行编辑器实现（约 2300 多行）在 `handleInput()` 里按优先级依次判断各种 keybinding：

```typescript
// packages/tui/src/components/editor.ts
handleInput(data: string): void {
	const kb = getKeybindings();
	// ...（字符跳转模式、粘贴模式的特判）...

	// Undo
	if (kb.matches(data, "tui.editor.undo")) {
		this.undo();
		return;
	}
	// ...（自动补全模式下的方向键/Tab/Enter 特判）...

	if (kb.matches(data, "tui.editor.deleteWordBackward")) {
		this.deleteWordBackwards();
		return;
	}
	// ...
	if (kb.matches(data, "tui.editor.yank")) {
		this.yank();
		return;
	}
	if (kb.matches(data, "tui.editor.yankPop")) {
		this.yankPop();
		return;
	}
	// ...
}
```

这是一条清晰的责任链（chain of responsibility）：按顺序尝试匹配"跳转模式中的取消"、"粘贴中的累积"、"撤销"、"自动补全导航"、"删除类动作"、"kill-ring 相关动作"、"历史导航"、"光标移动"……命中即处理并 `return`，没有一处需要理解按键的原始字节含义。

### 7. 撤销栈、kill-ring 与自动补全

编辑器的"手感"很大程度上来自几个体量很小但语义精确的辅助数据结构。

**撤销栈**（`undo-stack.ts`）是一个只有几十行的通用类，用 `structuredClone` 做深拷贝，保证弹出的历史快照与当前状态完全隔离：

```typescript
// packages/tui/src/undo-stack.ts
export class UndoStack<S> {
	private stack: S[] = [];

	/** Push a deep clone of the given state onto the stack. */
	push(state: S): void {
		this.stack.push(structuredClone(state));
	}

	/** Pop and return the most recent snapshot, or undefined if empty. */
	pop(): S | undefined {
		return this.stack.pop();
	}
	// ...
}
```

编辑器在每一次会改变内容的操作前调用 `pushUndoSnapshot()` 把 `{ state, pastes, pasteCounter }` 存进栈里；`undo()` 则弹出快照并用 `Object.assign` 覆盖回当前状态。这正是本课程系列反复强调的"不可变数据"思路的一个具体应用：不直接在原地记录"如何撤销这次修改"（那样容易遗漏边界情况），而是简单粗暴地保存"修改前的完整快照"，用空间换取正确性和实现的简单性。

**Kill-ring**（`kill-ring.ts`）是 Emacs 风格的剪切环：多次连续的删除操作（比如连续按 `Ctrl+K` 删除到行尾）会被合并累积成一条记录，而不是分别独立存储：

```typescript
// packages/tui/src/kill-ring.ts
push(text: string, opts: { prepend: boolean; accumulate?: boolean }): void {
	if (!text) return;

	if (opts.accumulate && this.ring.length > 0) {
		const last = this.ring.pop()!;
		this.ring.push(opts.prepend ? text + last : last + text);
	} else {
		this.ring.push(text);
	}
}
```

编辑器里通过一个 `lastAction` 状态标记"上一次操作是否也是删除（kill）"，只有连续的删除动作才会传入 `accumulate: true`：例如 `deleteToStartOfLine()`（对应 `Ctrl+U`）会这样调用：

```typescript
// packages/tui/src/components/editor.ts
this.killRing.push(deletedText, { prepend: true, accumulate: this.lastAction === "kill" });
this.lastAction = "kill";
```

`prepend: true` 表示这是一次"向前删除"（删除光标前的内容），累积时新文本要拼在已有内容前面，这样连续几次 `Ctrl+U` 删除多行行首内容后，一次 `Ctrl+Y`（yank，粘贴）就能把这些内容按原始顺序整体贴回来，这也是经典 Emacs 编辑手感的核心行为。`yankPop`（`Alt+Y`）则通过 `KillRing.rotate()` 把最近一条记录移到队首，实现"连续粘贴时循环切换到更早的删除记录"。

**词边界导航**（`word-navigation.ts`）用 `Intl.Segmenter`（JS 内置的语义分词器）而非简单的空白符切分来判断"一个词"的边界，这对中日文等没有空格分词的语言更友好：

```typescript
// packages/tui/src/word-navigation.ts
export function findWordBackward(text: string, cursor: number, options?: WordNavigationOptions): number {
	// ...
	const segments = segmentFn ? [...segmentFn(textBeforeCursor)] : [...wordSegmenter.segment(textBeforeCursor)];
	// ...
}
```

`Ctrl+W`（删除前一个词）、`Alt+F`/`Alt+B`（按词移动光标）等动作都基于这两个纯函数（`findWordBackward`/`findWordForward`）计算目标位置，函数本身不修改任何状态，是典型的"纯函数 + 调用方负责应用副作用"模式。

**自动补全**（`autocomplete.ts` + `fuzzy.ts`）走另一条路径：`autocomplete.ts` 负责识别输入中的文件路径片段、构造 `fd`/文件系统查询；`fuzzy.ts` 提供不要求连续子串、只要求字符按序出现的模糊匹配算法，并对得分做了若干启发式加权（连续匹配加分、词边界匹配加分、命中位置越靠后小幅减分）：

```typescript
// packages/tui/src/fuzzy.ts
// Reward consecutive matches
if (lastMatchIndex === i - 1) {
	consecutiveMatches++;
	score -= consecutiveMatches * 5;
} else {
	consecutiveMatches = 0;
	// Penalize gaps
	if (lastMatchIndex >= 0) {
		score += (i - lastMatchIndex - 1) * 2;
	}
}
// Reward word boundary matches
if (isWordBoundary) {
	score -= 10;
}
```

编辑器在 `handleInput()` 里检测到自动补全处于激活状态（`this.autocompleteState`）时，会把方向键、Tab、Enter 等按键都临时转发给 `autocompleteList`（一个 `SelectList` 组件）处理，直到用户确认选择或按 Escape 取消——这也是前面讲的责任链模式的又一处体现：`autocompleteState` 存在与否，决定了同一个按键在不同上下文里触发完全不同的逻辑分支。

### 8. 面向扩展开发者：如何用这套组件搭自定义界面

`packages/coding-agent/docs/tui.md` 是专门写给 pi 扩展（extension）开发者的文档，说明了如何在不理解上述内部实现细节的前提下使用这套组件系统。几个要点：

- **组件必须遵守宽度约束**：文档反复强调 `render(width)` 返回的每一行都"必须不超过 `width`"，否则 `TuiMainScreen.doRender()` 里会直接抛出运行时错误并写崩溃日志（对应源码里 `visibleWidth(line) > width` 的检查分支）。这是差分渲染能正确工作的隐含契约——如果某一行实际显示宽度超出终端列数，后续所有基于列偏移的合成计算（`compositeTuiLine`）都会错位。
- **`Focusable` 接口用于 IME 光标定位**：文档给出的例子和 `tui.ts` 里 `CURSOR_MARKER`（一个终端会忽略的零宽 APC 转义序列）的实现完全对应——组件在获得焦点时于渲染输出里嵌入这个标记，`TuiBase.extractCursorPosition()` 会扫描并提取它的位置，再把标记从最终输出里剥离、把硬件光标移动过去，这样中文/日文/韩文输入法的候选词窗口才能出现在正确位置。
- **通过 `ctx.ui.custom()` 挂载自定义组件**、用 `overlay: true` 声明浮层（overlay），浮层的定位选项（`OverlayOptions`：`anchor`、`row`/`col`、百分比宽高、`margin` 等）在 `tui.ts` 的 `resolveOverlayLayout()` 里实现，文档里的示例代码和源码字段是一一对应的。
- **组合已有的构建块**（`Text`、`Box`、`Container`、`Spacer`、`Markdown`、`Image`）比从零实现 `Component` 接口更省力；只有需要自定义交互（比如一个带过滤功能的选择器）时才需要自己写 `handleInput` 和 `render`，文档里的 `MySelector` 示例演示了最小实现范式：内部维护状态、用 `matchesKey()` 判断按键、用 `invalidate()` 清理渲染缓存。

需要坦诚说明的是：`docs/tui.md` 面向的是"使用者"视角，本文引用的差分渲染、布局引擎等实现细节，扩展开发者在日常使用中并不需要关心——这也印证了这套架构分层的合理性：内部渲染优化（第 2、3 节）对上层完全透明，暴露给扩展开发者的只是一个简单的 `Component` 接口。

## 小结与思考题

- 差分渲染的本质是"先算出完整的下一帧，再和上一帧逐行 diff，只把变化的部分写给终端"，配合同步输出（CSI 2026）避免中间态闪烁；但它建立在"变化通常发生在可见视口内、终端宽高不变"的假设上，一旦假设被打破（宽度变化、变化发生在已滚出视口的历史行），代码会主动退化为全量重绘以保证正确性而非追求极致的增量更新。
- 布局系统用一个可选的 `[LAYOUT_NODE]()` 协议把"简单组件"与"结构化容器（stack/scroll）"区分开，递归产出的仍然是普通字符串数组，因此布局层和差分渲染层可以完全解耦。
- 主屏幕与备用屏幕是同一个 `Component`/`TUI` 抽象下的两种"如何把一帧画到终端"的实现，选择依据是应用是否需要独占屏幕、内部管理滚动与鼠标选区。
- 输入处理链路的关键设计是"按键标识符"和"逻辑动作 id"之间的两层间接：`matchesKey()` 解决"这串字节是什么按键"，`KeybindingsManager` 解决"用户希望这个按键触发什么动作"，业务代码（编辑器）只依赖第二层，从而天然支持按键自定义。

思考题：

1. 如果要给 `TuiMainScreen` 增加一个"局部区域高亮闪烁"的动画效果（比如某一行文字短暂反色提示错误），在现有差分渲染算法下，怎样设计渲染节奏才能既触发多次微小的 diff，又不会因为动画帧率过高而被 `MIN_RENDER_INTERVAL_MS` 的节流机制吞掉关键帧？
2. `KillRing.push()` 依赖调用方传入的 `accumulate` 布尔值来判断"是否与上一次操作合并"，这个判断目前完全由编辑器里的 `lastAction === "kill"` 字符串比较驱动。如果未来要支持"删除单词"和"删除到行尾"两种不同动作之间也能像 Emacs 那样合并进同一个 kill 条目，你会如何改造 `lastAction` 的类型设计，使其既表达"上一次是不是删除"，又不需要 kill-ring 本身感知具体是哪一种删除？
3. 文档要求所有组件 `render(width)` 输出的行不能超过 `width`，但这依赖组件作者自觉调用 `visibleWidth`/`truncateToWidth`。如果要把这个契约从"约定"提升为"编译期或运行期强约束"，你会在 `Component` 接口或 `TuiBase` 的渲染管线里加入什么样的校验，使违规更早被发现（例如在 `layout.ts` 的 `renderCached()` 阶段而不是最终写终端时）？
