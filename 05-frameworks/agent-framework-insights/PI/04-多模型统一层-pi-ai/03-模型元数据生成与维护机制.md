# 模型元数据生成与维护机制

> pi-ai 内置了三十多个 Provider、几百个模型的目录（定价、上下文窗口、是否支持工具调用/推理等能力标记），这份目录不是手写的，而是由 `scripts/generate-models.ts` 从 models.dev、OpenRouter、Vercel AI Gateway 等外部数据源抓取并叠加大量人工修正规则后生成的——理解这套生成与校验机制，才知道为什么仓库规则强调"绝不能手动修改 `models.generated.ts`"。

## 学习目标

- 说清楚为什么模型元数据（定价、上下文窗口、能力标记）要走"代码生成"而不是手写维护。
- 理解 `models.generated.ts`、`providers/<id>.models.ts`、`providers/data/<id>.json` 三层产物各自的角色，以及它们之间的生成关系。
- 读懂 `scripts/generate-models.ts` 的整体流程：抓取数据源 → 应用修正规则 → 校验 → 原子性写回文件。
- 理解 `model-catalog.ts` 的 `flattenModelCatalog()` 如何用 TypeScript 映射类型把 JSON 数据转成带类型的模型目录。
- 结合根目录 README 里 `npm run build` 与 `npm run build:offline` 的区别，说清楚"刷新模型数据"和"离线构建"是两个可以独立控制的关注点。

## 背景与设计动机

LLM 行业的模型目录变化极快：厂商几乎每周都在调价、上线新模型、调整上下文窗口上限、给某个模型加上/摘掉工具调用支持。如果 pi-ai 把这几百个模型的元数据手写在 TypeScript 源码里，会有两个必然出现的问题：

1. **信息很快过期**。定价、上下文窗口这类数字性质的数据,人工维护很容易忘记同步,而且没有一个"这份数据是什么时候生成的"的可信时间戳。
2. **同一个 Provider 内部差异巨大，容易出错**。同样是"OpenAI 兼容"的 Chat Completions 协议，DeepSeek、Together、Moonshot、Cerebras、z.ai 等厂商在细节上（是否支持 `store` 字段、`developer` 角色、`reasoning_effort` 参数、`max_tokens` 还是 `max_completion_tokens`……）各不相同，这些差异原本要在每个 Provider 的适配器代码里写一堆 `if (provider === "together") {...}` 式判断，容易遗漏。

pi-ai 的解法是：把"抓取上游数据 + 应用已知的人工修正规则 + 推断兼容性开关"这套逻辑写成一个**生成器脚本**（`scripts/generate-models.ts`），生成器本身归 git 版本管理、可以被审查和修改；而生成器的产物（`models.generated.ts` 等文件）被视为**编译产物**，永远不手改，改了也会在下次生成时被覆盖。这是"生成代码 vs 手写代码"这个通用工程模式在模型元数据这个具体场景下的应用。

## 核心机制详解

### 1. 三层产物：数据、类型外壳、聚合入口

模型目录数据从底层到顶层分三层文件：

**第一层——原始 JSON 数据**（`packages/ai/src/providers/data/<provider>.json`）：按 API 分组、按模型 ID 索引的纯 JSON，是"可移植的数据快照"，不含任何 TypeScript 语法。

**第二层——按 Provider 的类型外壳**（`packages/ai/src/providers/<provider>.models.ts`，例如 `amazon-bedrock.models.ts`）：

```ts
// packages/ai/src/providers/amazon-bedrock.models.ts（生成格式示例，见 generate-models.ts:2856-2863）
// This file is auto-generated by scripts/generate-models.ts
// Do not edit manually - run 'npm run generate-models' to update

import values from "./data/amazon-bedrock.json" with { type: "json" };
import { flattenModelCatalog, type ModelCatalog } from "../model-catalog.ts";

export const AMAZON_BEDROCK_MODELS: ModelCatalog<typeof values, "amazon-bedrock"> =
	flattenModelCatalog("amazon-bedrock", values);
```

这一层的作用是把纯 JSON 数据"包装"成一个带精确 TypeScript 类型的常量——`flattenModelCatalog()`（`packages/ai/src/model-catalog.ts:22-27`）用映射类型把"按 API 分组的模型 JSON"压平成一个"模型 ID → `Model<Api>`"的对象，同时利用 TypeScript 的类型推断让每个模型 ID 成为字面量类型,从而在使用 `getBuiltinModel("amazon-bedrock", "...")` 时可以获得输入法自动补全和拼写校验（下一节展开）。

**第三层——聚合入口**（`packages/ai/src/models.generated.ts`）：

```ts
// packages/ai/src/models.generated.ts:1-3, 44-47（节选）
// This file is auto-generated by scripts/generate-models.ts
// Do not edit manually - run 'npm run generate-models' to update

import { AMAZON_BEDROCK_MODELS } from "./providers/amazon-bedrock.models.ts";
// ...（39 个 provider 各一行 import）

export const MODELS: {
	readonly "amazon-bedrock": typeof AMAZON_BEDROCK_MODELS;
	// ...
} = {
	"amazon-bedrock": AMAZON_BEDROCK_MODELS,
	// ...
};
```

这是全仓库唯一一个"知道所有 Provider 都叫什么名字"的聚合点，`providers/all.ts` 之后的所有运行时查询都建立在这个 `MODELS` 常量之上。

三层文件顶部**全部**带有同一句注释——"This file is auto-generated by scripts/generate-models.ts / Do not edit manually"——这正是 `AGENTS.md` 里那条规则的代码依据：

> Never modify `packages/ai/src/models.generated.ts` directly; update `packages/ai/scripts/generate-models.ts` instead, then regenerate. Including the resulting `models.generated.ts` diff is always OK, even if regeneration includes unrelated upstream model metadata changes.

也就是说，正确的修改路径永远是"改生成器脚本里的规则 → 重新跑生成命令 → 把生成结果连同脚本改动一起提交"，而不是直接在生成文件里手改一行价格。仓库的 git 提交规范甚至专门为这一点开了绿灯——`models.generated.ts` 的 diff 可以和你自己改动的文件一起提交，即使它顺带把其它无关模型的最新数据也更新了。

### 2. 生成器的数据来源

`generateModels()`（`packages/ai/scripts/generate-models.ts:2273` 起）是整个脚本的入口函数，它从多个外部数据源拉取原始模型信息：

```ts
// packages/ai/scripts/generate-models.ts:2274-2280（节选）
// models.dev: Anthropic, Google, OpenAI, Groq, Cerebras
// OpenRouter: xAI and other providers (excluding Anthropic, Google, OpenAI)
// AI Gateway: OpenAI-compatible catalog with tool-capable models
const modelsDevModels = await loadModelsDevData();
const openRouterModels = await fetchOpenRouterModels();
const aiGatewayModels = await fetchAiGatewayModels();
```

- **models.dev**（`https://models.dev/api.json`）：一个社区维护的、跨厂商的模型元数据聚合站点，是大多数一线 Provider（Anthropic、Google、OpenAI、Groq、Cerebras 等）数据的主来源。
- **OpenRouter API**（`https://openrouter.ai/api/v1/models`）：`fetchOpenRouterModels()` 只保留 `supported_parameters` 包含 `"tools"`（工具调用能力）的模型,把 `pricing`（按 token 计价，单位是"每 token 美元"）换算成 pi 统一用的"每百万 token 美元"（`roundCost(parseFloat(...) * 1_000_000)`）。
- **Vercel AI Gateway API**：同样只保留带 `"tool-use"` 标签的模型。
- **NVIDIA NIM API**：`fetchNvidiaNimModelIds()` 只用于校验/规范化模型 ID 大小写和分隔符（`normalizeNvidiaModelId()` 把下划线换成点号），因为 NVIDIA 的模型 ID 格式和 models.dev 报告的不完全一致。

三个来源合并时"models.dev 优先"（`generateModels()` 里注释写明），冲突的模型 ID 以 models.dev 数据为准。

### 3. 修正规则层：为什么生成器里有大量硬编码的例外表

单纯抓取上游数据并不够——上游数据本身经常滞后或有已知错误。生成器脚本里有大段大段的常量表专门"打补丁"，例如：

```ts
// packages/ai/scripts/generate-models.ts:324-331
// Kimi Coding is subscription-backed, so models.dev reports zero cost. Use the
// equivalent Moonshot API rates to estimate the value of subscription usage.
const KIMI_CODING_IMPLIED_COSTS: Record<string, Model<Api>["cost"]> = {
	k3: KIMI_K3_COST,
	"kimi-for-coding": { input: 0.95, output: 4, cacheRead: 0.19, cacheWrite: 0 },
	"kimi-for-coding-highspeed": { input: 1.9, output: 8, cacheRead: 0.38, cacheWrite: 0 },
	"kimi-k2-thinking": { input: 0.6, output: 2.5, cacheRead: 0.15, cacheWrite: 0 },
};
```

这个例子很典型：Kimi Coding 是订阅制产品，按官方数据源报告成本是 0（因为用户不是按 token 付费的），但 pi 想让用户在成本统计里看到"这次调用如果按 API 计费大概值多少钱"这种参考值，于是用同厂商按 token 计费的 Moonshot API 价格作为替代估算值，并在注释里说明了理由。

类似的修正贯穿整个脚本，形式包括：

- `XAI_BUILTIN_EXCLUDED_MODEL_IDS`：models.dev/OpenRouter 报告了但 pi 不想内置暴露的模型 ID 黑名单。
- `OPENAI_SHORT_CONTEXT_CAPPED_MODEL_IDS` / `OPENAI_LONG_CONTEXT_PRICING_MODEL_IDS`：OpenAI 部分 GPT-5.x 模型的上下文窗口和阶梯定价在官方文档和 models.dev 之间有出入，用显式集合覆盖。
- `GITHUB_COPILOT_THINKING_LEVEL_OVERRIDES`：注释写明"Checked manually against the authenticated GitHub Copilot /models endpoint on 2026-06-15"——这是**人工验证过的**修正,不是自动抓取来的,体现了生成器并不是纯自动化黑盒,而是"自动抓取 + 人工审校补丁"的混合模式。
- `applyThinkingLevelMetadata()`（`generate-models.ts:806-936`）：把各家推理强度（reasoning effort）参数体系映射到 pi 统一的 `ThinkingLevel`（`minimal`/`low`/`medium`/`high`/`xhigh`/`max`）取值上,逐个模型标注哪些等级不支持（映射为 `null`）。

还有一类函数专门推断上一篇提到的 `Model.compat` 兼容性开关，例如 `detectOpenAICompletionsCompat()`（`generate-models.ts:610-703`）通过检查 `provider`/`baseUrl` 里的关键字（`isZai`/`isTogether`/`isMoonshot`/`isNvidia`/`isAntLing` 等布尔判断）批量推断出 `supportsStore`、`supportsDeveloperRole`、`supportsReasoningEffort`、`maxTokensField`、`thinkingFormat` 等十几个字段的默认值,再用 `openAICompletionsCompatDelta()` 只保留和默认值（`OPENAI_COMPLETIONS_DEFAULT_COMPAT`）不同的部分写进最终数据,避免生成的 JSON 里充斥大量重复的默认字段。这正是上一篇讲的"厂商协议差异被编码成模型元数据而不是写死在协议实现代码里"的具体落地位置。

### 4. 输出与校验：暂存、原子替换、失败回滚

`generateModels()` 的尾段（`generate-models.ts:2760` 起）先把所有模型按 `provider → api → modelId` 分组，然后分阶段写文件：

```ts
// packages/ai/scripts/generate-models.ts:2811-2828（节选，简化）
const stagingRoot = mkdtempSync(join(providersDir, ".model-generation-"));
const stagedDataDir = join(stagingRoot, "data");
try {
	mkdirSync(stagedDataDir, { recursive: true });
	for (const providerId of generatedDataProviderIds) {
		writeFileSync(join(stagedDataDir, `${providerId}.json`), serializeJson(generatedDataProviders[providerId]));
	}
	writeJson(join(stagedDataDir, MODEL_DATA_MANIFEST_FILE), createModelDataManifest(...));
	validateModelDataDirectory(modelDataStructure, stagedDataDir);
	// ... 校验通过后才继续生成 .models.ts 分片和 models.generated.ts 聚合文件
```

关键设计是**先写到临时目录、校验通过后再用 `renameSync()` 原子替换正式目录**，如果中途校验失败，会把之前的 `src/providers/data` 目录整体恢复（`restoreGeneratedCatalog()`/`previousDataDir` 回滚逻辑），不会让仓库停留在"写了一半"的不一致状态。这在一个会同时改写几十个文件（39 个 Provider 各一份 JSON + 一份 `.models.ts` + 一份聚合文件）的生成器里是必要的安全网。

`.manifest.json` 是这套校验机制的核心（`packages/ai/scripts/model-data.ts`）：

```ts
// packages/ai/scripts/model-data.ts:10-15
export interface ModelDataManifest {
	schemaVersion: number;
	generatedAt: string;
	structureHash: string;
	files: Record<string, string>; // 文件名 -> sha256
}
```

`structureHash` 是"provider→modelId→api"这份结构的哈希，`files` 是每个 JSON 数据文件内容的 SHA-256。`validateModelDataDirectory()` 会核对：文件列表是否和聚合文件里 import 的 Provider 列表一致、每个模型是否具备 `id`/`provider`/`api`/`name`/`baseUrl`/`reasoning`/`input`/`contextWindow`/`maxTokens`/`cost` 等必填字段且类型合法、manifest 里记录的哈希是否和实际文件内容匹配。`packages/ai/scripts/check-model-data.ts` 就是单独把这套校验拎出来做成一个独立命令（`npm run check:model-data`），可以在不重新抓取网络数据的情况下,纯粹检查当前仓库里的生成产物是否内部一致——这一步被接入了 `build:offline` 脚本（见下文）。

### 5. 生成器的命令行模式：`--strict` / `--data-only` / `--json-only`

```ts
// packages/ai/package.json（scripts 节选）
"generate-models": "node scripts/generate-models.ts --strict",
"hydrate-model-data": "node scripts/generate-models.ts --strict --data-only",
"generate-model-catalog": "node scripts/generate-models.ts --strict --json-only --json-output ../../.artifacts/model-catalog",
"check:model-data": "node scripts/check-model-data.ts",
"build": "npm run generate-models && npm run build:offline",
"build:offline": "npm run check:model-data && tsgo -p tsconfig.build.json && shx rm -rf dist/providers/data && shx cp -r src/providers/data dist/providers/data"
```

三个标志位对应三种不同的使用场景：

- **`--strict`**：任何一个数据源抓取失败就直接抛错终止（而不是打印警告后用空列表继续），用在需要"数据不完整就不能生成"的正式生成流程里。
- **`--data-only`**（对应 `hydrate-model-data`）：只重新写 `providers/data/<id>.json` 这些原始数据文件，不touch `.models.ts` 分片和聚合文件的结构——用于"只是想刷新一下价格/上下文窗口这类数值，不想让 Provider 列表结构发生变化"的场景，`generatedDataProviderIds` 这时会从现有的 `models.generated.ts` 里反查 Provider 列表（`readModelDataProviderIds()`），而不是重新按抓取结果决定。
- **`--json-only` + `--json-output`**（对应 `generate-model-catalog`）：完全不碰仓库里的 TypeScript 源文件，只是把最终模型目录导出成一份独立的 JSON（`models.json`/`providers.json`/`providers/<id>.json`），供仓库外部消费（比如 `.artifacts/model-catalog` 目录，根目录还有对应的 `diff:model-catalog`/`check:model-catalog` 脚本用于比对发布前后的目录差异）。

### 6. 运行时怎么用这份数据：`providers/all.ts` 与 `model-catalog.ts`

生成的数据最终要变成一个可查询、可发请求的运行时对象。这一步分两层：

**类型层面的压平**——`flattenModelCatalog()`：

```ts
// packages/ai/src/model-catalog.ts:22-27
export function flattenModelCatalog<const TProvider extends ProviderId, const TGroups extends ModelGroups>(
	_provider: TProvider,
	groups: TGroups,
): ModelCatalog<TGroups, TProvider> {
	return Object.assign({}, ...Object.values(groups)) as ModelCatalog<TGroups, TProvider>;
}
```

`ModelCatalog<TGroups, TProvider>` 是一个映射类型，把"按 API 分组的模型字典"（`{ "bedrock-converse-stream": { "anthropic.claude-...": {...} } }`）压平成"模型 ID 直接映射到 `Model<Api>`"的扁平对象，同时保留每个模型该属于哪个具体 API 子类型的类型信息。

**运行时的静态读取**——`providers/all.ts` 里的三个函数直接读 `models.generated.ts` 导出的 `MODELS` 常量：

```ts
// packages/ai/src/providers/all.ts:61-86（节选）
export function getBuiltinModel<TProvider extends BuiltinProvider, TModelId extends keyof (typeof MODELS)[TProvider]>(
	provider: TProvider, modelId: TModelId,
): Model<BuiltinModelApi<TProvider, TModelId>> {
	const models = MODELS[provider] as Record<string, Model<Api>> | undefined;
	return models?.[modelId as string] as Model<BuiltinModelApi<TProvider, TModelId>>;
}

export function getBuiltinProviders(): BuiltinProvider[] {
	return Object.keys(MODELS) as BuiltinProvider[];
}

export function getBuiltinModels<TProvider extends BuiltinProvider>(provider: TProvider) { /* ... */ }
```

这三个函数就是"列出可用模型、查询单个模型能力标记"这类需求最直接的入口——比如要判断"这个模型是否支持工具调用"，看的就是 `Model.reasoning`/`Model.input`/`Model.compat` 这些由生成器写好的字段（上一篇、上上篇已经详细讲过这些字段如何在协议实现里被消费，例如 Bedrock 适配器读 `model.reasoning`/`model.thinkingLevelMap`/`model.compat?.supportsStrictMode` 来决定要不要发推理参数、要不要用严格工具模式）。

**运行时的完整 Provider 集合**——`builtinProviders()`/`builtinModels()`：

```ts
// packages/ai/src/providers/all.ts:89-141（节选）
export function builtinProviders(): Provider[] {
	return [
		amazonBedrockProvider(),
		anthropicProvider(),
		// ...（39 个内置 Provider 工厂逐一调用）
	];
}

export function builtinModels(options?: CreateModelsOptions): MutableModels {
	const models = createModels(options);
	for (const provider of builtinProviders()) {
		models.setProvider(provider);
	}
	return models;
}
```

这里把上一篇讲过的 `createModels()`（`models.ts`）运行时容器和本篇讲的生成目录粘合到了一起：每个 `xxxProvider()` 工厂内部都会 `import { XXX_MODELS } from "./xxx.models.ts"`，也就是本篇第 1 节说的"第二层类型外壳"。

**动态刷新与生成时快照的区别**——除了本篇讲的"构建期生成"之外，`models.ts` 里的 `Provider.refreshModels?()` 和 `models-store.ts` 的 `ModelsStore` 接口（`read`/`write`/`delete`，附带 `InMemoryModelsStore` 实现）还支撑了另一条独立的机制：某些 Provider（比如 OpenRouter、Vercel AI Gateway）的模型列表在两次 pi 发版之间也可能变化，`createProvider()` 支持传入 `fetchModels` 回调，在运行时按需刷新并持久化到 `ModelsStore`（带 `Last-Modified`/`ETag` 增量校验，见 `ModelsStoreEntry` 定义）。要分清楚这是**运行时缓存刷新**，而生成器脚本处理的是**随每次发版打进代码仓库/安装包里的构建期快照**——两者互补但不是一回事：前者解决"两次发版之间目录轻微变化"的问题，后者解决"每次发版时目录基准线要不要重新对齐"的问题。

### 7. `npm run build` 与 `npm run build:offline`：刷新数据与离线构建的关系

回到根目录 `README.md` 的说明：

```
npm run build         # Refresh model data, then build all packages
npm run build:offline # Rebuild using existing model data without network access
```

对应到 `packages/ai/package.json` 的脚本定义：

```
"build": "npm run generate-models && npm run build:offline",
"build:offline": "npm run check:model-data && tsgo -p tsconfig.build.json && shx rm -rf dist/providers/data && shx cp -r src/providers/data dist/providers/data",
```

`build`（默认构建）会先跑一次完整的 `generate-models`（联网抓取 models.dev/OpenRouter/Vercel AI Gateway/NVIDIA NIM 四个数据源，重新生成三层产物），再执行 `build:offline`；而 `build:offline` 本身**完全不联网**——它先用 `check:model-data`（第 4 节讲的校验脚本）确认当前仓库里已有的生成产物内部一致，再用 `tsgo` 编译 TypeScript，最后把 `src/providers/data`（原始 JSON 快照）整体拷贝进 `dist` 产物目录。

这个拆分解决了两个不同的问题：

- **日常开发/CI 的确定性构建**：`build:offline` 不依赖外部网络请求成功与否，也不会因为上游数据源当天恰好抖动/限流就导致构建失败或悄悄拿到不一致的数据，只要仓库里已经 commit 了一份生成产物,任何人在任何时间、任何网络环境下都能得到完全一样的构建结果。
- **模型数据的定期刷新**：只有显式运行 `npm run generate-models`（或者 CI 里专门的定时任务）才会真正联网抓取最新数据、修正规则，并把结果作为一次正常的代码改动提交，纳入 code review。

README 里另一段关于"从发布源码构建二进制"的说明进一步印证了这一点：

> `./scripts/build-binaries.sh --offline-model-data --platform linux-x64 --out "$PWD/out"` ... `--offline-model-data` builds with that snapshot instead of refreshing it from live provider catalogs.

也就是说，正式发布的二进制产物默认使用**发布时打进源码归档里的那份快照**，保证同一个版本号的发布产物在任何时间重新构建都得到完全一致的模型目录——这对可复现构建（reproducible build）和供应链安全（同一版本号不会因为重新构建的时间点不同而拿到不同的第三方数据）都很重要。而 `hydrate-model-data`（`--data-only`）提供了一个中间态：只刷新数值型数据快照，不改变 Provider/模型 ID 的结构集合，适合作为一个独立的、影响面更小的定期刷新任务。

## 小结与思考题

pi-ai 的模型元数据本质上是一条小型的数据流水线：`scripts/generate-models.ts` 从 models.dev、OpenRouter、Vercel AI Gateway、NVIDIA NIM 四个外部数据源抓取原始信息，叠加大量出于真实踩坑经验写成的人工修正规则（价格订正、上下文窗口订正、能力开关推断），校验后原子性地写出三层产物——`providers/data/*.json`（可移植数据快照）、`providers/*.models.ts`（带类型的薄外壳）、`models.generated.ts`（唯一聚合入口）——这三层文件全部标记为"自动生成，禁止手改"。运行时通过 `providers/all.ts` 的 `getBuiltinModel`/`builtinModels()` 等函数消费这份数据，`model-catalog.ts` 的 `flattenModelCatalog()` 负责把 JSON 结构转换成精确类型化的 TypeScript 对象。`npm run build` 与 `npm run build:offline` 的区别，本质上是把"要不要联网刷新数据"这个决策，从"要不要构建"这个决策里显式拆分了出来，服务于可复现构建这个更大的工程目标。

思考题：

1. 如果你要新增一个 Provider（比如接入一个新的国产大模型 API），应该往 `scripts/generate-models.ts` 里的哪个环节加代码：是加进已有的 models.dev/OpenRouter 抓取分支，还是像 `deepseekV4Models`/`antLingModels` 那样直接在脚本里手写一段静态模型列表？两种方式各适合什么场景？
2. `validateModelDataDirectory()` 会检查每个模型的 `id`/`provider`/`api` 字段是否和它在目录结构里的位置一致。如果这项校验被去掉，`providers/data/<id>.json` 里混入一条 `provider` 字段写错了的模型数据，实际运行时会在哪个环节暴露出问题（提示：结合 `model-catalog.ts` 的 `ModelCatalog` 类型定义和 `createProvider()` 的模型分发逻辑思考）？
3. `hydrate-model-data`（`--data-only`）和完整的 `generate-models` 相比，少做了"重新生成 `.models.ts` 分片和 `models.generated.ts` 聚合文件"这一步。如果某次上游数据变化导致一个 Provider 新增了一个此前完全没见过的模型 ID，用 `hydrate-model-data` 能不能把这个新模型加进目录？为什么（提示：读 `generate-models.ts` 中 `generatedDataProviderIds = generatorOptions.dataOnly ? readModelDataProviderIds(packageRoot) : sortedProviderIds` 这一行，以及 `missingProviderIds` 的检查逻辑）？
