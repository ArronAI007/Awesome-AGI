# 课程总结与延伸阅读

> 回顾这套课程讲了什么、OpenHarness 作为一个"贴身复刻 Claude Code"的项目在架构上体现出哪些独特判断，把它和 PI、DeepSeek Harness、Hermes Agent 放在一起做一次四方对比，最后给出一手资料和练习方向。写作过程中，本课程多次在"假设某个机制存在"之后回去读代码验证，发现假设不成立就如实改写——这份诚实本身也是这门课程想传达的方法论。

## 学习目标

- 用一条主线串联起全部 10 章内容，建立整体认知而不是碎片记忆。
- 提炼 OpenHarness 项目在"复刻 Claude Code"这条主线之外体现出的、可以迁移到其他 Agent 系统的工程判断。
- 完成 PI / DeepSeek Harness / Hermes Agent / OpenHarness 四个真实开源 Agent Harness 在同一组维度上的对比，理解"同一类问题、四种不同定位的答案"。
- 知道除了本课程之外还有哪些一手资料可以继续深入，以及几个可以动手验证的进阶方向。

## 课程回顾

### 第一条主线：快速上手与仓库全景（第 00～02 章）

OpenHarness 的入口是 `oh`（交互 TUI / `-p` 单次查询 / `--dry-run` 安全预览三种运行形态）和独立的个人 Agent App `ohmo`。`oh setup` 把"认证 + 选后端 + 定模型"收敛成一个五步 Provider Workflow，五种内置 workflow（Anthropic-Compatible API / Claude Subscription / OpenAI-Compatible API / Codex Subscription / GitHub Copilot）背后是"workflow + profile"这个抽象——同一个 profile 结构既能表示一把裸 API key，也能表示"复用本地已登录的 Claude Code/Codex CLI 凭据"。`--dry-run` 是本课程遇到的第一个"少见但很实用"的设计：不调模型、不执行工具、不连 MCP，只解析配置和 system prompt，给出 `ready/warning/blocked` 三级结论——把原本要等运行时才暴露的配置问题，提前到运行前就诊断出来。

仓库全景一章拆开了 `src/openharness/` 下 30 个子包 + 独立顶层包 `ohmo/` + 两个独立前端项目（`frontend/terminal/` 的 Ink/React TUI、`autopilot-dashboard/` 的 React/Vite 仪表盘）。`pyproject.toml` 里 `packages = ["src/openharness", "ohmo"]` 这一行本身就说明了 `ohmo` 和 `openharness` 是并列打包、依赖而非从属的关系。一个值得记住的发现：`channels/` 目录下有一份 `UPSTREAM` 文件，说明 `bus/`/`impl/` 这两块其实是从另一个开源项目 `nanobot-ai/nanobot` vendor 进来的——OpenHarness 不只复刻 Claude Code，也直接复用了其他项目已经打磨好的子系统，而不是每个能力都从零写。双前端架构那一篇追出了完整的三进程链路：`oh` 启动 → `react_launcher.py` 拉起 Ink/tsx 子进程 → 这个子进程再拉起第二个 `--backend-only` 的 Python 子进程，三者靠一套 `OHJSON:` 前缀的 JSON 行协议通信；纯 Python 的 `textual_app.py` 走的是完全不同的进程内路径，共享同一套 `RuntimeBundle` 契约，但代码里确认它目前并没有被接入 `cli.py`/`run_repl`——一份写得很完整、测试也齐全，却处于"孤儿"状态的正交实现。

### 第二条主线：Agent 核心循环（第 03 章）

`QueryEngine`（`engine/query_engine.py`）看起来像引擎，其实只是一层壳：持有对话历史、组装 `QueryContext`，真正的"模型 → 工具 → 模型"循环装在 `engine/query.py` 的 `run_query()` 一个 `while` 循环里——四种终止路径、retry/backoff（实际在 `api/client.py` 一层，靠 `ApiRetryEvent` 透传给 UI）、多工具并发执行时用 `asyncio.gather(..., return_exceptions=True)` 规避"部分工具异常导致协议破损"的真实约束。多模型适配靠一个 `SupportsStreamingMessages` Protocol 加四个具体客户端（Anthropic / OpenAI-Compatible / Codex / Copilot），其中 Copilot 客户端是通过组合/monkeypatch OpenAI 客户端实现的，而不是另起一份实现。认证体系里最值得记住的是"复用外部凭据"这条路——Claude Subscription 复用 `~/.claude/.credentials.json`、Codex Subscription 复用 `~/.codex/auth.json`，甚至在请求头上做了 Claude Code 客户端身份的伪装；两者一个有自动刷新、一个没有，这种真实存在的不对称也被课程如实记录，而不是假装两条路径完全对称。

### 第三条主线：工具生态与治理安全（第 04～05 章）

40 多个内置工具共享 `tools/base.py` 一个极简协议，名字和语义与 Claude Code 官方工具集高度重合，这是"Python port of Claude Code"这句定位在代码层面最密集的证据。Skills 的"按需加载"被课程动手验证：system prompt 里只注入 skill 的名字和一句话描述，完整内容只有模型主动调用 `skill_tool` 才会读进来。Plugins 兼容 Claude-style manifest（`${CLAUDE_PLUGIN_ROOT}` 替换、`.mcp.json` 声明），但课程也诚实指出一个真实缺口：`oh plugin install` 目前只支持本地路径，尽管帮助文本写的是"path or URL"。MCP 作为 client 支持 stdio/http，声明了 ws 但实际未实现。Hooks 有 10 种事件类型、4 种 hook 形态（其中 `prompt`/`agent` 两种会真的发起一次模型调用做语义判断），"热重载"实际上是每轮对话都会重建一次注册表，而不是需要专门的监听进程。

治理与安全一章拆开了权限审批的九步决策链（`permissions/checker.py`），三种真实权限模式是 `default`/`plan`/`full_auto`，和 Hermes 课程里 manual/smart/off 的命名体系并不一样。课程还捕捉到一处真实的"代码孤儿"：`ui/permission_dialog.py` 的 `ask_permission()` 在整个源码树里没有被任何地方 import，真正的交互式批准逻辑走的是 `textual_app.py` 的 `PermissionScreen` 和 `backend_host.py` 的 `modal_request`/`Future` 桥接。沙箱那一篇纠正了任务简介里的一个预设——`sandbox/adapter.py` 的默认后端其实是包装 Anthropic 官方 `srt` CLI（Linux 上是 bubblewrap，macOS 上是 sandbox-exec），Docker 是第二个、需要显式开启的后端，两者靠字符串比较分发而非共享接口；`path_validator.py` 是沙箱之外的第二道、宿主机侧的路径校验，但配置里 `extra_allowed` 参数在三处调用点都没有被真正传入——一个配置面存在、行为却没有真正接线的真实差距。

### 第四条主线：记忆与会话（第 06 章）

`CLAUDE.md` 沿目录树向上查找并叠加注入（不是覆盖），`MEMORY.md` 只是索引，真正的记忆条目是一堆带 frontmatter 的独立文件，靠一套启发式相关性打分（元数据权重、正文权重、重要性、使用次数、时间衰减）挑选，用的是字符级 CJK 分词而非 FTS5。课程还纠正了自己出发前的一个假设："agent 记忆"和"team 记忆"并不是"单代理 vs 多代理"的区分，而是与"项目记忆"并列的三条正交路径，各自的自动注入、同步、触发方式都不一样。会话存储是纯 JSON 快照，每一轮对话后都会落盘（不是只在退出时），`/resume` 靠 `sanitize_conversation_messages()` 修复中断会话里孤立的 `tool_use` 块。个性化系统是本章另一处"假设被推翻"的地方：`personalization/extractor.py` 并不是模型驱动的语义抽取，而是纯正则模式匹配（SSH 主机、IP、conda 环境这类结构化信号），触发点是 `close_runtime()` 里一处写死的调用，和真正的 `HookEvent` 体系是两套独立机制；真正由模型驱动的记忆抽取另有其所，在 `services/memory_extract/`。

### 第五条主线：多智能体协作（第 07 章）

Swarm 层提供机制原语：`TeamFile`/`TeamMember` 持久化团队、`worktree.py` 用真实的 `git worktree add -B` 做并行编辑隔离、`mailbox.py` 用原子改名 + 跨平台锁实现队员间通信；子代理执行后端分子进程（复用 `BackgroundTaskManager`）和进程内（`ContextVar` 隔离）两种，课程发现一个明确写在代码里的真实取舍：`agent_tool.py` 硬编码只用子进程后端，因为进程内产生的任务 ID 没法被 `task_*` 工具查询到。Coordinator 层不提供任何新机制，它是一个由环境变量 `CLAUDE_CODE_COORDINATOR_MODE` 驱动的行为分支——换一套系统提示、换一套可见工具（`agent`/`send_message`/`task_stop`），把"怎么编排团队"这件事直接写成模型可以照着执行的操作手册，配合 `agent_definitions.py` 里预置的角色模板（worker/Explore/Plan/verification）。一个容易踩坑的发现：coordinator 模式下的 `TeamRegistry`（纯内存）和 swarm 层的持久化 `TeamFile` 是两套完全不同语义、只是共享"团队"这个名字的概念，课程用 grep 验证了两者互不相通。Bridge 子系统专门负责"驱动一个 OpenHarness 会话"，但课程如实指出——在这份代码快照里，它与 swarm/coordinator/tasks 之间并没有直接的调用耦合，甚至自己独立实现了一套进程跟踪逻辑，而不是复用已有的 `BackgroundTaskManager`。

### 第六条主线：`ohmo` 与可观测性（第 08～09 章）

`ohmo` 只从 `openharness` 顶层导入了 `AuthManager`/`load_settings`，其余全部是自己的实现，但 `ohmo/memory.py` 逐字复用了 `openharness.memory` 的 scan/schema 逻辑，只是换了存储根目录——"复用一个模块的行为，但独立管理自己的存储空间"是一种值得记住的轻量集成方式。人格由 `soul.md`/`identity.md`/`user.md`/`BOOTSTRAP.md` 几份可编辑 Markdown 文件拼进 system prompt，普通用户不需要碰代码就能调整"性格"。Gateway 网关这一篇纠正了任务简介里的另一个预设：`gateway/bridge.py` 并没有复用第 07 章讲的 `openharness.bridge`（两者是同名不同物），真正的复用点是 `ohmo/gateway/runtime.py` 直接调用了 `openharness.ui.runtime.build_runtime()`——和普通 `ohmo` CLI 用的是同一个构造函数。十种 IM Channel（Telegram/Slack/Discord/飞书/钉钉/Matrix/WhatsApp/QQ/Email/mochat）共享 `BaseChannel` 三个抽象方法，实现形态却各不相同（长轮询、Socket Mode、IMAP/SMTP 轮询）。Cron 调度用一个 30 秒轮询的调度器驱动定时任务，触发方式是拉起一个全新的 `ohmo --print` 子进程而不是复用 gateway 的运行时池——这意味着即使 gateway 没在跑，定时提醒依然能正常工作。

Autopilot 一章是全课程唯一同时横跨 Python 后端和 React 前端的文章：一个十三态的任务状态机（`RepoTaskStatus`）配合一份 JSON 快照，快照导出不靠独立调度器，而是挂在任何会改变卡片状态的操作尾部——`snapshot.json` 天然"最多落后一次状态变更"。课程还挖到一处真实的实现缺陷：`_render_dashboard_html()` 的文档字符串声称"只在输出目录没有预构建页面时才写入"，但实际代码是无条件覆盖 `index.html`，意味着本地手动构建出的完整仪表盘会在下一次任意状态变更时被静默替换回极简 fallback 页——一个写文档时的意图和写代码时的实现出现偏差的真实案例。前端 `vite.config.ts` 把构建产物直接输出到 `docs/autopilot`，配合一份共享的 JSON 契约实现前后端解耦，甚至可以直接发布成 GitHub Pages 静态站点——零运维成本，但代价是页面只在挂载时拉取一次数据，不是真正的实时推送。

## 可以提炼的通用设计原则

1. **"壳"与"心脏"分离能显著降低理解一个大型 Agent 引擎的门槛，但要看清楚哪层真的可替换、哪层只是转发**：`QueryEngine` 和 `run_query()` 的分工让读者不必被一个上千行的文件规模吓住——真正的循环逻辑很短，篇幅大头是各种收尾和辅助函数。
2. **复用外部生态已经验证过的凭据，而不是发明一套新认证体系，是"复刻型"项目独有的巧思**：Claude/Codex Subscription 直接读已登录 CLI 工具的凭据文件，用户不需要为一个新工具单独开一个 API key。
3. **用环境变量驱动行为分支，是"同一套循环、两种人格"最廉价的实现方式，但要小心继承链上的递归污染**：coordinator 派生 worker 时会显式把 `CLAUDE_CODE_COORDINATOR_MODE` 清零写进子进程环境，防止子代理误以为自己也该是编排者。
4. **两套同名但语义不同的概念，是快速迭代代码库里的常态，读代码不能只读名字**：`TeamRegistry`(内存，coordinator 用) 和 `TeamFile`(持久化，swarm 用) 只是共享了"团队"这个词，本课程多处用 grep 而非猜测来验证这类关系是否真的成立。
5. **一份共享的 JSON 快照契约，比强行让前后端共享类型定义更轻量，代价是"宽进严出"和非实时**：Autopilot 的仪表盘甚至不需要常驻服务，付出的代价是页面只在挂载时拉取一次。
6. **文档/docstring 和真实实现之间出现偏差是常态而非例外，验证比信任更重要**：本课程在写作过程中发现的几处真实差距——`sandbox` 的 `extra_allowed` 未被真正传入、Autopilot 的 dashboard HTML 会被静默覆盖、`gateway/bridge.py` 并未如预期复用 `openharness.bridge`——都不是靠读文档发现的，而是靠动手 grep 和读实现代码才浮出水面。这种"先假设、再验证、发现不成立就改写"的过程，本身就是阅读任何真实代码库时最该养成的习惯。

## 进阶练习方向

1. **画一遍再对照一遍**：脱离源码，自己画一遍 `run_query()` 的时序图，标出四种终止路径，再用 `grep -n` 核对每一步对应的真实代码位置。
2. **跑通两条 Provider Workflow**：本地分别配置一次 `Claude Subscription` 和一个 `OpenAI-Compatible API` profile，对照第 03 章讲的 `credential_slot` 隔离机制，观察两个 profile 的凭据是否真的互不影响。
3. **接一个新 Channel**：照着 `channels/impl/base.py` 的三个抽象方法，尝试给 `ohmo` 接入一个课程没覆盖过的 IM 平台，实际感受"接入一个新平台需要写多少代码"。
4. **验证课程指出的几个真实瑕疵**：比如 `sandbox` 的 `extra_allowed` 参数是否真的没被任何调用点传入、Autopilot 的 `index.html` 是否真的会在下一次状态变更后被覆盖——自己动手复现一遍，比只读结论印象更深。
5. **补一次四方对比**：挑一两个本课程对比表里的维度，回头重读 PI / DeepSeek Harness / Hermes Agent 对应章节，看看能不能在表格之外补充出更细的差异点。

## 小结

OpenHarness 的价值不在于"又一个能聊天的 Agent"，而在于它示范了另一种做 Agent Harness 的路径——不追求另起炉灶的架构哲学，而是把一个已经被验证过的产品（Claude Code）的工具协议、权限模型、Skills/Plugins 规范尽可能贴身复刻，然后在这个坚实的地基上，长出 `ohmo` 这样面向个人助理场景的、Claude Code 本身没有的东西。读完这门课程，你拿到的不只是"OpenHarness 内部长什么样"，还有一份关于"复刻一个成熟产品时,到底该复刻到多细、又该在哪里开始走自己的路"的真实参考样本。建议把四门课程对照着读完——同一类问题的四种真实答案放在一起看，收获会比单独读任何一套都大。
