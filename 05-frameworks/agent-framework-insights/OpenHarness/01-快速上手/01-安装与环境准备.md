# 安装与环境准备

> OpenHarness 的安装脚本表面上是一个常见的"一键安装"套路，但它悄悄做了一件容易被忽略的设计决策：把 IM channel 依赖（Slack、Telegram、Discord、飞书）直接塞进了核心依赖列表，而不是做成可选 extra。这不是疏忽，而是为 `ohmo` 这个后续才登场的个人 Agent App 提前铺路——你在装 `oh` 的时候，其实已经把 `ohmo` 需要的一切都装好了。

## 学习目标

- 理解 `curl ... install.sh | bash` 一键安装脚本每一步具体做了什么，而不是把它当黑盒。
- 弄清 `--from-source` 和 `--with-channels` 两个参数的真实语义——包括后者为什么已经是一个"名存实亡"的兼容性开关。
- 理解 `uv sync --extra dev` 本地开发方式和一键安装脚本的关系：两者面向的是不同的目标用户。
- 看清 `pyproject.toml` 里依赖分层的真实结构：哪些依赖是"核心"、哪些是给 `ohmo` channel 用的，以及它们为什么被放在了同一层。
- 认识 `openharness`/`oh`/`openh`/`ohmo` 四个可执行入口分别指向什么、彼此是什么关系。

## 背景与设计动机

多数 CLI 项目的安装脚本只关心一件事：把可执行文件放到 `PATH` 里。但 OpenHarness 要解决的问题更复杂一些——它既要装一个纯 Python 的 Agent Harness（`oh`），又要装一个依赖 Node.js/React 前端的终端 UI，还要为后续可能启动的个人 Agent 网关（`ohmo`）预留 IM 平台的 SDK。如果按照"核心先装、其他按需再装"的直觉去设计，用户装完 `oh` 之后想试试 `ohmo` 的 Telegram/Slack 集成，就会撞上"缺依赖，重新 pip install"的体验断层。

`pyproject.toml` 里的依赖列表给出了这套设计的答案：

```toml
# pyproject.toml
dependencies = [
    "anthropic>=0.40.0",
    "openai>=1.0.0",
    "rich>=13.0.0",
    "prompt-toolkit>=3.0.0",
    "textual>=0.80.0",
    "typer>=0.12.0",
    "pydantic>=2.0.0",
    "httpx>=0.27.0",
    "websockets>=12.0",
    "mcp>=1.0.0",
    "pyperclip>=1.9.0",
    "pyyaml>=6.0",
    "questionary>=2.0.1",
    "watchfiles>=0.20.0",
    "croniter>=2.0.0",
    "slack-sdk>=3.0.0",
    "python-telegram-bot>=21.0.0",
    "discord.py>=2.0.0",
    "lark-oapi>=1.5.0",
]

[project.optional-dependencies]
dev = [
    "pexpect>=4.9.0",
    "pytest>=8.0.0",
    "pytest-asyncio>=0.23.0",
    "pytest-cov>=5.0.0",
    "ruff>=0.5.0",
    "mypy>=1.10.0",
]
```

注意这份列表里没有一个叫 `channels` 的 extra。`slack-sdk`、`python-telegram-bot`、`discord.py`、`lark-oapi`——这些原本"看起来就该是可选依赖"的 IM SDK，被直接写进了顶层 `dependencies`，和 `anthropic`、`typer`、`textual` 平起平坐。`[project.optional-dependencies]` 里唯一存在的分组是 `dev`，专门给贡献者用的测试和 lint 工具链（`pytest`、`ruff`、`mypy` 等）。

这解释了 `scripts/install.sh` 里一段容易让人困惑的提示：

```bash
# scripts/install.sh
--with-channels) WITH_CHANNELS=true ;;
...
if [ "$WITH_CHANNELS" = true ]; then
    step "Channel dependencies"
    info "--with-channels is no longer required; common IM channel dependencies are installed by default."
fi
```

`--with-channels` 参数依然被脚本接受、依然会被解析，但它触发的实际动作只是打印一句"这个参数已经不需要了"。这是一个刻意保留的向后兼容退路——早期版本可能确实把 channel 依赖做成了可选安装，后来做了合并，但脚本没有直接删除这个参数并报错，而是选择"接受、告知、什么都不做"。这种处理方式值得留意：它避免了老用户脚本里残留的 `--with-channels` 直接导致安装失败，用一次友好的提示完成了迁移。

## 核心机制详解

### 一键安装脚本的十个步骤

`scripts/install.sh` 的整体结构是十个顺序执行的 step，每一步都有明确的失败退出路径。按顺序拆开看：

**第 1-2 步：环境探测**，判断操作系统（Linux/macOS/WSL/Windows Git Bash）和 Python 版本（要求 `>= 3.10`），找不到符合条件的 `python3`/`python` 就直接退出并给出对应发行版的安装建议：

```bash
# scripts/install.sh
for cmd in python3 python; do
    if command -v "$cmd" &>/dev/null; then
        PY_VER=$("$cmd" --version 2>&1 | grep -oE '[0-9]+\.[0-9]+\.[0-9]+' | head -1)
        PY_MAJOR=$(echo "$PY_VER" | cut -d. -f1)
        PY_MINOR=$(echo "$PY_VER" | cut -d. -f2)
        if [ "${PY_MAJOR}" -ge 3 ] && [ "${PY_MINOR}" -ge 10 ]; then
            PYTHON_CMD="$cmd"
            break
        fi
    fi
done
```

**第 3 步：检查 Node.js（`>= 18`）**。这一步的失败**不会中止安装**，只会打印警告并把 `NODE_OK` 置为 `false`——这是个很关键的细节，说明 React TUI 是一个可降级的可选能力，而不是硬性前置条件。没有 Node.js，`oh` 这个纯 Python 包依然能装、依然能跑，只是终端 UI 那条路径会在后面的步骤里被跳过。

**第 4 步：创建虚拟环境并安装包本体**。这里没有直接往用户的系统 Python 里 `pip install`，而是先在 `~/.openharness-venv` 建一个独立虚拟环境，所有后续的 `pip install` 都发生在这个虚拟环境内部：

```bash
# scripts/install.sh
VENV_DIR="$HOME/.openharness-venv"
...
if [ ! -f "$VENV_DIR/bin/activate" ]; then
    info "Creating virtual environment at ${VENV_DIR}..."
    "$PYTHON_CMD" -m venv "$VENV_DIR"
fi
source "$VENV_DIR/bin/activate"
```

这是为了绕开 PEP 668（externally-managed-environment）在较新 Linux 发行版上对系统 Python 的写保护——脚本注释里直接写明了这一点。`--from-source` 和默认的 `pip install openharness-ai` 都发生在这个隔离的虚拟环境里，两者唯一的区别是前者先 `git clone` 到 `~/.openharness-src` 再 `pip install -e .`（可编辑安装，适合贡献者边改代码边测），后者直接从 PyPI 拉正式发布的 `openharness-ai` 包。

**第 5 步**只是打印上文提到的那句 `--with-channels` 兼容性提示，不做任何实际安装动作。

**第 6 步：按需安装 React TUI 的 npm 依赖**，只有在第 3 步探测到可用 Node.js、且 `frontend/terminal/package.json` 存在时才会执行 `npm install`：

```bash
# scripts/install.sh
if [ "$NODE_OK" = true ]; then
    if [ -d "$FRONTEND_DIR" ] && [ -f "$FRONTEND_DIR/package.json" ]; then
        step "Installing React TUI dependencies"
        (cd "$FRONTEND_DIR" && npm install --no-fund --no-audit --silent)
    fi
fi
```

**第 7 步**建立 `~/.openharness/`、`~/.openharness/skills/`、`~/.openharness/plugins/` 三个目录——这是 OpenHarness 后续读取用户级配置、技能和插件的固定位置。

**第 8 步**是整个脚本里比较值得玩味的一步：把虚拟环境里的三个可执行文件软链接到 `~/.local/bin`：

```bash
# scripts/install.sh
BIN_DIR="$HOME/.local/bin"
mkdir -p "$BIN_DIR"
ln -snf "$VENV_DIR/bin/oh" "$BIN_DIR/oh"
ln -snf "$VENV_DIR/bin/ohmo" "$BIN_DIR/ohmo"
ln -snf "$VENV_DIR/bin/openharness" "$BIN_DIR/openharness"
```

英文版 README 的更新日志里专门提到过这个设计的由来：早期版本是把虚拟环境的 `bin` 目录直接前置进 `PATH`，但这样做会把 Conda 管理的 shell 环境"污染"掉（虚拟环境里的 `python`、`pip` 会意外地抢占 Conda 环境里的同名命令）。改成软链接单个可执行文件到 `~/.local/bin`，规避了这个副作用，同时依然让 `oh`/`ohmo`/`openharness` 全局可用。

**第 9-10 步**分别验证安装是否成功、把 `~/.local/bin` 加入到 `.zshrc`/`.bashrc`/`.bash_profile`/fish config 里，且带幂等检测（已经配置过就跳过，不会重复追加）。

### `--from-source` 与 `--with-channels`：两个参数的真实语义

把两个参数放在一起看会更清楚它们分别解决什么问题：

- `--from-source` 改变的是**安装来源**：从 GitHub 克隆源码、可编辑模式安装,这是给需要改代码、提 PR 的贡献者用的路径，`pip install -e .` 意味着你对 `src/openharness` 或 `ohmo/` 目录里代码的修改会立刻在下一次 `oh` 调用中生效，不需要重新打包。
- `--with-channels` 改变的**本应是安装范围**（是否装 IM SDK），但因为这些依赖已经被合并进核心依赖列表，它现在唯一的效果只是打印一条提示信息。

这也是为什么本篇开头说这不是疏忽：把 `ohmo` 所需的 channel 依赖前置进核心依赖，意味着任何装了 `oh` 的用户，理论上都已经具备了直接跑通 `ohmo init && ohmo config` 走 Telegram/Slack/Discord/飞书 配置向导的能力，不需要额外一轮安装。这是"先装好基础设施，用不用是另一回事"的取舍——用磁盘和安装时间换取后续切换到 `ohmo` 时的零摩擦体验。

### `uv sync --extra dev`：另一条更适合贡献者的路径

`README.zh-CN.md` 和 `CONTRIBUTING.md` 给出的本地运行方式和一键安装脚本是两条并行、而非互斥的路径：

```bash
# README.zh-CN.md / CONTRIBUTING.md
git clone https://github.com/HKUDS/OpenHarness.git
cd OpenHarness
uv sync --extra dev
uv run oh
```

`uv sync --extra dev` 对应的正是 `pyproject.toml` 里 `[project.optional-dependencies]` 下的 `dev` 分组——`pexpect`、`pytest`、`pytest-asyncio`、`pytest-cov`、`ruff`、`mypy`。这条路径面向的是想要跑测试、跑 lint、参与开发的贡献者，`uv` 会在项目目录下管理一个独立的虚拟环境（而不是像安装脚本那样落在 `~/.openharness-venv`），`uv run oh` 直接在这个项目本地环境里执行，改代码后无需任何额外操作即可复现效果。`CONTRIBUTING.md` 里补充了如果还要动 React 终端 UI，需要额外单独进 `frontend/terminal` 跑一次 `npm ci`：

```bash
# CONTRIBUTING.md
cd frontend/terminal
npm ci
cd ../..
```

一键安装脚本面向的是终端用户，追求"复制一行命令就能用"；`uv sync --extra dev` 面向的是贡献者，追求"和仓库保持同步、随时能跑测试"。两者共用同一份 `pyproject.toml` 依赖定义，只是使用了不同的安装/隔离策略。

### 四个可执行入口：一套壳，两个应用

`pyproject.toml` 的 `[project.scripts]` 段落定义了打包后实际会生成的命令行入口：

```toml
# pyproject.toml
[project.scripts]
openharness = "openharness.cli:app"
oh = "openharness.cli:app"
openh = "openharness.cli:app"
ohmo = "ohmo.cli:app"
```

`openharness`、`oh`、`openh` 三个名字指向的是**同一个** Typer 应用对象——`openharness.cli:app`。它们不是三个不同的程序，只是同一个 CLI 的三个别名。这种"多别名指向同一入口"的做法主要是为了适配不同平台/习惯：`oh` 最短最顺手,是日常使用的默认选择；`openharness` 是完整的、语义清晰的包名，适合脚本里显式调用；`openh` 则是英文版 README 里特别提到的 Windows PowerShell 变体——因为 `oh` 在 PowerShell 里会被内置的 `Out-Host` 别名抢占，所以 Windows 用户需要用 `openh` 才能跑到正确的程序。

`ohmo` 则指向一个完全不同的入口——`ohmo.cli:app`,这是 `ohmo/` 目录下独立的 Typer 应用。`[tool.hatch.build.targets.wheel]` 里的 `packages = ["src/openharness", "ohmo"]` 也印证了这一点：`ohmo` 不是 `openharness` 包内部的一个子命令或子模块,而是被单独列为一个顶层包，和 `openharness` 并列打包进同一个 wheel。这个包结构上的独立性,正是后面第 05 篇要展开的"`ohmo` 是基于 OpenHarness 构建的应用,不是 core 的一个 mode"这句话在物理层面的体现——这里先记住这个结构性事实，细节留到那一篇。

## 常见问题/易踩坑

- **装完之后 `oh` 命令找不到**：多半是 `~/.local/bin` 还没进 `PATH`。脚本已经尝试自动写入常见的 shell 配置文件，但需要重启 shell 或手动 `source` 一次配置文件才会生效。
- **Windows PowerShell 下 `oh` 命令行为异常**：这不是 bug，是 `Out-Host` 别名冲突，改用 `openh` 即可。
- **以为不加 `--with-channels` 就不能用 `ohmo` 的 Telegram/Slack 功能**：不成立。这些依赖从 `pyproject.toml` 的角度看本来就是核心依赖的一部分，加不加这个参数结果完全一样。

## 小结

一键安装脚本的十个步骤本质上是在处理三类差异：Python 版本兼容性（虚拟环境 + PEP 668 规避）、Node.js 的可选降级（React TUI 装不上不影响核心功能）、以及全局命令的干净注册（软链接到 `~/.local/bin` 而非污染 `PATH`）。而 `pyproject.toml` 里"IM channel 依赖直接进核心依赖"的选择，是为下一篇要讲的交互体验、以及第 05 篇要讲的 `ohmo` 铺的路。下一篇《快速开始：CLI 与 TUI 速览》会从安装完成之后的第一次 `oh` 说起，看看交互式会话、非交互单次查询、以及三种输出格式分别是怎么工作的。
