# 子代理执行后端:进程内与子进程两种模式

> `registry.py` 探测出的两种主流后端——`InProcessBackend` 和 `SubprocessBackend`——回答的是同一个接口(`TeammateExecutor`)下的同一个问题:"怎么把一个队员真正跑起来",但选择了两种几乎相反的隔离策略。子进程后端把队员做成一个完全独立的操作系统进程,复用 `BackgroundTaskManager` 这套现成的进程生命周期管理;进程内后端把队员做成当前事件循环里的一个 `asyncio.Task`,靠 `contextvars` 做身份隔离,连一次进程启动的开销都省掉。本篇拆开两者的真实实现,并且会指出一个容易被忽略的事实:coordinator 模式下的 `agent` 工具其实从不使用 in_process 后端——原因写在代码注释里,而不是靠猜。

## 学习目标

- 理解 `SubprocessBackend.spawn()` 如何复用 `BackgroundTaskManager`,以及为什么它要绕开 shell、直接用 argv 列表拉起子进程(issue #230 的 Windows Git Bash 问题)。
- 理解 `spawn_utils.py` 里启动一个队员要准备的三类东西:可执行文件路径解析、CLI 参数继承、环境变量转发,并弄清每一类"要转发什么"背后的真实故障场景。
- 理解 `InProcessBackend` 如何用 `TeammateAbortController`(双信号:优雅取消 + 强制取消)和 `ContextVar` 做并发身份隔离,以及它的 spawn/shutdown 生命周期。
- 弄清两种后端各自的隔离代价与启动开销取舍,以及 `agent_tool.py` 为什么显式硬编码只用子进程后端。
- 理解 `lockfile.py`(跨平台排他锁)和 `permission_sync.py`(leader-worker 权限审批协议)分别解决并发场景下的什么问题。

## 背景与设计动机

一个队员本质上是"另一份独立运行的模型对话循环",让它真正跑起来至少要解决三件事:进程/协程怎么起、启动时要继承父进程的哪些配置、运行过程中权限审批和输出怎么和 leader 交互。子进程和进程内两种后端在"进程/协程怎么起"这一步选择不同,但后两件事——`spawn_utils.py` 的参数/环境变量继承逻辑、`permission_sync.py` 的审批协议——是共享的,不因后端而异。这种分层设计的好处是:换后端只影响"用什么原语跑起来",不影响"跑起来之后队员该有什么行为"。

## 核心机制详解

### 子进程后端:复用 `BackgroundTaskManager`

`SubprocessBackend.spawn()` 把队员包装成一次 `manager.create_agent_task()` 调用,底层就是第四篇要讲的通用后台任务管理器:

```python
# src/openharness/swarm/subprocess_backend.py:67-98(节选)
command: str | None = config.command
if command is None:
    # Direct-exec argv list — no shell, no quoting required. This
    # avoids Git Bash on Windows being unable to exec a Windows-
    # pathed python interpreter when bash is itself launched via
    # asyncio.create_subprocess_exec (see issue #230).
    extra_env = build_inherited_env_vars()
    teammate_cmd = get_teammate_command()
    if (teammate_cmd.endswith("python") or teammate_cmd.endswith("python3")
        or teammate_cmd.endswith("python.exe") or "/python" in teammate_cmd
        or "\\python" in teammate_cmd.lower()):
        argv = [teammate_cmd, "-m", "openharness", "--task-worker"] + flags
    else:
        argv = [teammate_cmd, "--task-worker"] + flags

manager = get_task_manager()
record = await manager.create_agent_task(
    prompt=config.prompt, description=f"Teammate: {agent_id}",
    cwd=config.cwd, task_type=config.task_type, model=config.model,
    command=command, argv=argv, env=extra_env,
)
```

只有当调用方没有显式传 `config.command` 时,才会自己拼 argv 并注入继承的环境变量——如果调用方指定了自定义命令,代码选择"尊重调用方的选择,不再自作主张塞环境变量",注释里写得很直白:这是为了保持和修复前行为一致,不擅自加戏。`send_message()` 把消息序列化成一行 JSON 写入子进程的 stdin;`shutdown()` 调用 `manager.stop_task()`,并且专门 `except ValueError` 处理"任务已经结束"的情况——不把这种正常状态当成错误往上抛。

`SubprocessBackend` 自己只维护一个 `agent_id -> task_id` 的映射,所有真正的进程管理(启动、stdin 写入、stdout 收集、终止)都甩给 `BackgroundTaskManager`——这意味着子进程后端跑起来的队员天然是可以被 `task_get`/`task_list`/`task_output`/`task_stop` 这几个工具查询和操作的,因为它们指向的是同一个任务管理器实例。

### `spawn_utils.py`:启动一个队员需要准备什么

启动一个队员分三类准备工作,全部集中在这个模块里。

**可执行文件解析**——`get_teammate_command()` 按优先级决定用什么命令拉起队员:

```python
# src/openharness/swarm/spawn_utils.py:83-106(节选)
def get_teammate_command() -> str:
    override = os.environ.get(TEAMMATE_COMMAND_ENV_VAR)
    if override:
        return override
    if sys.executable:
        return sys.executable
    entry_point = shutil.which("openharness")
    if entry_point:
        return entry_point
    return "python"
```

顺序是:显式的 `OPENHARNESS_TEAMMATE_COMMAND` 环境变量覆盖 > 当前 Python 解释器(`sys.executable`,保证队员用的是和 leader 完全相同的 venv/可编辑安装源码树)> PATH 上的 `openharness` 入口点 > 裸的 `"python"` 兜底。优先选当前解释器而不是 PATH 上的入口点,是为了避免开发环境下"leader 跑的是本地源码树、队员却启动了 pip 安装的旧版本"这种不一致。

**CLI 参数继承**——`build_inherited_cli_flags()` 把 leader 当前会话里的关键设置转发给队员:权限模式(`--dangerously-skip-permissions` 或 `--permission-mode acceptEdits`,但 `plan_mode_required` 为真时会抑制 bypass,因为计划模式的安全约束优先级更高)、模型覆盖(值为 `"inherit"` 时不传,让队员走环境变量继承父级模型)、系统提示(`--system-prompt` 或 `--append-system-prompt`,取决于 `system_prompt_mode`)、settings 路径、插件目录列表、teammate_mode。所有值都经过 `shlex.quote()` 转义,防止拼进 shell 命令时被注入。

**环境变量转发**——`build_inherited_env_vars()` 转发一份精心列出的白名单变量。列表本身就是一份"踩过的坑"清单,每一类都带着注释说明原因:

```python
# src/openharness/swarm/spawn_utils.py:22-80(节选)
_TEAMMATE_ENV_VARS = [
    # --- API provider selection -------------------------------------------
    # Without these, teammates would default to the wrong endpoint provider
    # and fail all API calls (analogous to GitHub issue #23561 in the TS source).
    "ANTHROPIC_API_KEY", "ANTHROPIC_BASE_URL", ...
    # --- Upstream proxy settings ------------------------------------------
    # The parent's MITM relay is reachable from teammates on the same
    # container network. Forward proxy vars so teammates route
    # customer-configured traffic through the relay for credential injection.
    "HTTPS_PROXY", "https_proxy", "HTTP_PROXY", "http_proxy", "NO_PROXY", "no_proxy",
    # --- CA bundle overrides ----------------------------------------------
    "SSL_CERT_FILE", "NODE_EXTRA_CA_CERTS", "REQUESTS_CA_BUNDLE", "CURL_CA_BUNDLE",
    ...
]
```

模块开头的注释解释了为什么需要这份显式白名单而不是让子进程自然继承环境:*"tmux 可能会起一个全新的登录 shell,不会继承父进程环境"*——如果队员是被 tmux 拉起来的一个新 pane,它跑的是一个新的登录 shell,默认不带父进程的任何环境变量。`build_inherited_env_vars()` 无条件加两个变量:`OPENHARNESS_AGENT_TEAMS=1` 标记"我是队员",以及 `CLAUDE_CODE_COORDINATOR_MODE=0`——后者是防止队员被错误地也当成一个 coordinator:leader 若开着 coordinator 模式,这个标记本该只属于 leader,不能被子进程原样继承,否则队员会递归地把自己当成协调者去派生更多子任务。

### 进程内后端:`ContextVar` 隔离并发身份

`InProcessBackend` 走的是完全不同的路子——不开新进程,而是用 `asyncio.create_task()` 在当前事件循环里跑一个协程。并发场景下多个队员的身份要互不干扰,靠的是 `contextvars.ContextVar`(Python 版的 Node `AsyncLocalStorage`):

```python
# src/openharness/swarm/in_process.py:173-188
_teammate_context_var: ContextVar[TeammateContext | None] = ContextVar(
    "_teammate_context_var", default=None
)

def get_teammate_context() -> TeammateContext | None:
    return _teammate_context_var.get()

def set_teammate_context(ctx: TeammateContext) -> None:
    _teammate_context_var.set(ctx)
```

`asyncio.create_task()` 会自动拷贝当前的 `Context`,所以每个新建的 Task 从一开始就带着自己独立的一份 ContextVar 状态——不需要显式加锁,任何在这个 Task 内运行的代码调用 `get_teammate_context()` 都能拿到正确的身份,不会读到兄弟队员的数据。取消信号则用一个双信号控制器:

```python
# src/openharness/swarm/in_process.py:77-97(节选)
def request_cancel(self, reason: str | None = None, *, force: bool = False) -> None:
    self._reason = reason
    if force:
        self.force_cancel.set()
        self.cancel_event.set()  # Also set graceful so both checks fire
    else:
        self.cancel_event.set()
```

`cancel_event` 是"优雅取消"——队员在当前工具调用跑完之后自己检查这个标志退出;`force_cancel` 是"强制取消"——直接调用 `asyncio.Task.cancel()` 立刻中断协程。`shutdown()` 的默认行为是先请求优雅取消并 `asyncio.wait_for` 等一个超时窗口,超时了再退化成强制取消:

```python
# src/openharness/swarm/in_process.py:566-580(节选)
entry.abort_controller.request_cancel(reason="graceful shutdown")
try:
    await asyncio.wait_for(asyncio.shield(entry.task), timeout=timeout)
except asyncio.TimeoutError:
    entry.abort_controller.request_cancel(reason="timeout — forcing", force=True)
    entry.task.cancel()
    with contextlib.suppress(asyncio.CancelledError):
        await entry.task
```

队员协程自身(`start_in_process_teammate()`)无论正常结束还是异常退出,`finally` 块里都会向 leader 的 mailbox 写一条 `idle_notification`,即使这一步本身出错也会被 `contextlib.suppress(Exception)` 吞掉——保证清理逻辑不会因为通知失败而崩溃。运行期间,`_drain_mailbox()` 在每轮工具调用之间检查队员自己的 inbox:收到 `shutdown` 消息就请求取消并结束循环,收到 `user_message` 就塞进 `ctx.message_queue`,由 `_run_query_loop()` 在下一次循环时当作新的一轮用户输入注入进对话。

### 两者的取舍,以及 `agent_tool.py` 的真实选择

两种后端的取舍很直观:子进程隔离性强(完全独立的地址空间、崩溃不影响 leader)但每次启动都要付出一次完整的 Python 解释器 + harness 初始化开销;进程内后端零进程启动开销,但和 leader 共享同一个事件循环——如果队员的某个工具调用是同步阻塞的重活,会连带卡住 leader 和其他队员。此外,`in_process` 后端只在 POSIX 平台(`get_platform_capabilities().supports_swarm_mailbox` 为真,即 macOS/Linux/WSL)才会被注册进 `BackendRegistry`,Windows 上默认不可用。

但真正有意思的是:coordinator 模式下模型唯一能调用的委派工具——`agent_tool.py`——从不让 `registry.detect_backend()` 自动选择,而是硬编码只用子进程后端,并且把原因写在了注释里:

```python
# src/openharness/tools/agent_tool.py:61-66(节选)
# Use subprocess backend so spawned agents are registered in
# BackgroundTaskManager and are pollable by the task tools.
# in_process tasks return asyncio-internal IDs that task tools
# cannot query, and subprocess is always available on all platforms.
registry = get_backend_registry()
executor = registry.get_executor("subprocess")
```

原因是可查询性,而不是隔离性:`in_process` 后端产生的 task_id 是 asyncio 内部标识,`task_get`/`task_list`/`task_output` 这几个模型可调用的工具(第四篇细讲)完全没有办法用它去查状态或拉输出;子进程后端的每个队员天生就是 `BackgroundTaskManager` 里的一条记录,和这些工具共享同一份状态,模型侧的委派体验才是一致的。`in_process` 后端目前更多是给 swarm 的可视化/tmux 面板场景准备的执行原语,而不是 coordinator 派活的默认路径。

### `lockfile.py` 和 `permission_sync.py` 在并发场景下分别解决什么

`lockfile.py` 本身只是一层向后兼容的转发,真正的实现在 `openharness/utils/file_lock.py`:posix 下用 `fcntl.flock`,Windows 下用 `msvcrt.locking`,统一封装成一个上下文管理器 `exclusive_file_lock(lock_path)`。它解决的是"多个进程/协程对同一份共享 JSON 状态做读-改-写时怎么不互相踩踏"——mailbox 的每次写入、`permission_sync.py` 里 pending → resolved 的移动,都是先拿这把锁再动文件。

`permission_sync.py` 解决的是另一层问题:worker 遇到一个需要审批的工具调用时,怎么把这个请求转发给 leader、又怎么等到 leader 的裁决。它提供了两条并行的实现路径——文件目录式(`pending/`/`resolved/` 两个目录 + 排他锁 + 原子重命名)和 mailbox 式(直接往 leader 的 inbox 写一条 `permission_request` 消息)。文件目录式的核心是 `resolve_permission()`:

```python
# src/openharness/swarm/permission_sync.py:504-543(节选,_sync_resolve_permission)
with exclusive_file_lock(lock_path):
    if not pending_path.exists():
        return False
    ...
    resolved_request = SwarmPermissionRequest(..., status="approved" if resolution.decision == "approved" else "rejected", ...)
    tmp_path.write_text(json.dumps(resolved_request.to_dict(), indent=2), encoding="utf-8")
    os.replace(tmp_path, resolved_path)
    try:
        pending_path.unlink()
    except OSError:
        pass
```

worker 侧则要么轮询 `read_resolved_permission(request_id)`,要么(mailbox 路径下)`poll_permission_response()` 每 0.5 秒检查自己的 inbox。另外一个值得注意的细节是 `handle_permission_request()` 里的只读工具白名单:`_READ_ONLY_TOOLS`(`read_file`、`glob`、`grep`、`web_fetch` 等)会被直接自动批准,完全不经过 leader——只有真正可能有副作用的工具调用才会触发这一整套审批协议,减少不必要的往返等待。

## 常见问题/易踩坑

- **子进程后端为什么不用 shell 字符串**:`spawn_utils.py` 生成的是 argv 列表而不是拼接后的 shell 命令,原因(见 `subprocess_backend.py` 的注释)是 Windows 下 Git Bash 无法可靠地 exec 一个 Windows 路径形式的 Python 解释器,尤其是当 Git Bash 自身又是通过 `asyncio.create_subprocess_exec` 启动的时候——绕开 shell 直接 `exec` 整个问题类别都不存在了。
- **进程内后端队员崩溃不会传染给 leader,但 `finally` 块必须自己兜住**:`start_in_process_teammate()` 捕获了 `Exception`(但重新抛出 `asyncio.CancelledError`),并且清理逻辑本身也用 `contextlib.suppress(Exception)` 包了一层——双重保险防止一个队员的异常波及整个事件循环。
- **权限只读白名单是硬编码的,不是动态推导的**:`_READ_ONLY_TOOLS` 是一份固定的工具名集合,新增只读工具需要显式加进这个 frozenset,不会自动从工具的其他属性(比如 `is_read_only()`)推导。

## 小结

两种后端在"进程/协程怎么起"这一层做出了相反的选择,但共享同一套"启动前要准备什么"(`spawn_utils.py`)和"运行期间怎么和 leader 交互"(`permission_sync.py` + `mailbox.py`)的逻辑。`agent_tool.py` 硬编码只用子进程后端这个细节,提示了一个更大的主题:swarm 层提供的是通用的执行原语,而"这些原语具体怎么被上层的委派系统调用"是另一层的决策。下一篇就转向那一层——`coordinator/` 目录下的 coordinator 模式,看它如何在 `agent` 工具之上,用预定义的角色模板和一套结构化的工作流系统提示,把"单个 Agent 编排一整个团队"这件事变成可复用的模式。
