# 消息状态机、上下文管理与成本跟踪

> `ConversationMessage` 只有 `"user"` / `"assistant"` 两种角色，工具调用与工具结果都以类型化内容块的形式塞进这两种角色的消息里——这个看似简单的表示,撑起了整个引擎对"历史该怎么演进""什么时候该压缩""花了多少 token"这三件事的判断依据。压缩逻辑虽然被 README 归在"Memory / Session"名下，但实际代码就趴在 `services/compact/` 里，并且是 `engine/query.py` 每一轮循环开始时都会主动调用的——它不是一个游离于主循环之外的旁路系统,而是核心循环的一部分。

## 学习目标

- 读懂 `ConversationMessage` / `ContentBlock` 的真实定义，理解为什么工具结果被表示成 `"user"` 角色消息里的一个内容块，而不是独立的第三种角色。
- 理解 `sanitize_conversation_messages()` 要修复的具体病态场景——一次被中断的会话恢复后，消息历史可能处于什么样的"半成品"状态。
- 弄清楚 `has_pending_continuation()` 如何判断一个会话是否可以"接着刚才的工具调用继续"而不是重新发起一轮用户输入。
- 通读 `services/compact` 里自动压缩的完整级联策略：token 估算 → 阈值判断 → 微压缩 → 上下文折叠 → 会话记忆压缩 → 全量 LLM 摘要，理解为什么这是一个"先便宜后昂贵"的级联，而不是一步到位调 LLM。
- 理解 `UsageSnapshot` / `CostTracker` 这一层做的其实是 token 计数而不是货币成本，以及 token 估算（用于压缩决策）和 Provider 返回的真实用量（用于计费）为什么是两套独立的数字。

## 背景与设计动机

一个 Agent 循环如果只考虑"这一轮怎么跑",很快就会撞上三类现实问题:

- **消息历史不是永远干净的**。用户可能在工具调用还没执行完时就中断了进程，重启后加载出来的历史里可能有一条 `assistant` 消息发起了工具调用、却没有对应的 `tool_result`——这种"半成品"状态如果原样发给 Provider,大概率会被直接拒绝。
- **上下文窗口是有限的**，而多轮工具调用天然会不断往历史里堆内容（尤其是 `read_file`、`bash`、`grep` 这类会返回大段文本的工具）。如果每次都等到 Provider 报"上下文超限"才处理，用户体验会很差；但如果每次都不计成本地调一次 LLM 做摘要，又太贵太慢。
- **成本需要被追踪**，但"追踪"这件事本身不能反过来影响主循环的决策路径——压缩阈值判断用的 token 数字，和最终展示给用户的计费数字，理应是两套独立的估算与真实数据,不能混为一谈。

`oh` 对这三个问题的回应，分别体现为 `sanitize_conversation_messages()`、`services/compact` 的级联压缩策略、以及 `UsageSnapshot`/`CostTracker` 这一对轻量级容器。三者共享同一份消息表示（`ConversationMessage`），这也是为什么要先把消息模型讲透。

## 核心机制详解

### ConversationMessage：两种角色，四种内容块

```python
# src/openharness/engine/messages.py
class TextBlock(BaseModel):
    type: Literal["text"] = "text"
    text: str

class ImageBlock(BaseModel):
    type: Literal["image"] = "image"
    media_type: str
    data: str
    source_path: str = ""

class ToolUseBlock(BaseModel):
    type: Literal["tool_use"] = "tool_use"
    id: str = Field(default_factory=lambda: f"toolu_{uuid4().hex}")
    name: str
    input: dict[str, Any] = Field(default_factory=dict)

class ToolResultBlock(BaseModel):
    type: Literal["tool_result"] = "tool_result"
    tool_use_id: str
    content: str
    is_error: bool = False
    result_metadata: dict[str, Any] = Field(default_factory=dict)

ContentBlock = Annotated[
    TextBlock | ImageBlock | ToolUseBlock | ToolResultBlock,
    Field(discriminator="type"),
]

class ConversationMessage(BaseModel):
    role: Literal["user", "assistant"]
    content: list[ContentBlock] = Field(default_factory=list)
```

四种内容块用 Pydantic 的 `discriminator="type"` 组成一个可辨识联合，这意味着从 JSON 反序列化时 Pydantic 会自动按 `type` 字段路由到正确的子类型——这对会话持久化/恢复（第六篇的话题）很关键，也是为什么第二篇里能看到每个 Provider 适配器都要用 `isinstance(block, ToolResultBlock)` 这样的模式匹配来区分内容块。

角色只有两种，是这套表示里最值得注意的设计选择：`ToolResultBlock` 不是独立的第三种角色（不像 OpenAI 协议里有专门的 `role="tool"`），而是塞进一条 `role="user"` 的消息里——这是 Anthropic Messages API 的原生形状。上一篇看到的 `_convert_messages_to_openai()`、`_convert_messages_to_codex()`，本质上都是在把这个"两角色 + 类型化内容块"的模型，重新拆解成各自协议要求的形状。选择 Anthropic 的表示作为内部标准而不是发明一套厂商中立的新格式，是一个务实的决定——它天然贴合 `oh` 自己最常用的 Anthropic/Claude 路径，代价则转嫁给了其他协议的适配器去做拆包/合并。

`ConversationMessage` 上还挂了几个只读的便捷属性——`.text`（拼接所有 `TextBlock`）、`.tool_uses`（过滤出所有 `ToolUseBlock`）、`.is_effectively_empty()`（判断消息是否没有任何实质内容）。`run_query()` 在判断"模型是否还要调工具"时用的就是 `final_message.tool_uses`；判断"模型是否返回了一条空消息该被丢弃"用的就是 `is_effectively_empty()`——这两个判断都在上一篇看到过，它们的实现就藏在这个模型类里。

### sanitize_conversation_messages：修复被中断会话留下的破损尾巴

```python
# src/openharness/engine/messages.py
def sanitize_conversation_messages(messages: list[ConversationMessage]) -> list[ConversationMessage]:
    """Drops legacy empty assistant messages and trims malformed trailing tool
    turns, such as an assistant ``tool_use`` message that never received a
    matching user ``tool_result`` response."""
    sanitized: list[ConversationMessage] = []
    pending_tool_use_ids: set[str] = set()
    pending_tool_use_index: int | None = None

    for message in messages:
        if message.role == "assistant" and message.is_effectively_empty():
            continue

        tool_uses = message.tool_uses if message.role == "assistant" else []
        tool_results = [b for b in message.content if isinstance(b, ToolResultBlock)] if message.role == "user" else []

        matched_pending_tool_results = False
        if pending_tool_use_ids:
            result_ids = {block.tool_use_id for block in tool_results}
            if message.role != "user" or not pending_tool_use_ids.issubset(result_ids):
                if pending_tool_use_index is not None and pending_tool_use_index < len(sanitized):
                    sanitized.pop(pending_tool_use_index)
                pending_tool_use_ids = set()
                pending_tool_use_index = None
            else:
                matched_pending_tool_results = True
                pending_tool_use_ids = set()
                pending_tool_use_index = None
        ...
        sanitized.append(message)
        if tool_uses:
            pending_tool_use_ids = {block.id for block in tool_uses}
            pending_tool_use_index = len(sanitized) - 1

    if pending_tool_use_ids and pending_tool_use_index is not None and pending_tool_use_index < len(sanitized):
        sanitized.pop(pending_tool_use_index)
    return sanitized
```

这个函数处理的是一个非常具体的真实场景：会话在"助手发起了工具调用，但工具结果还没写回历史"这个时间窗口内被中断（进程崩溃、用户强制退出），下次加载历史时，最后一条消息是一个带 `tool_uses` 的 `assistant` 消息，但它期待的 `tool_result` 永远不会来了。如果原样把这样的历史发给 Provider，Anthropic/OpenAI 一类严格校验"每个 `tool_use` 必须有匹配 `tool_result`"的 API 会直接拒绝整个请求。

函数用一个"悬挂指针"模式解决这个问题：遍历过程中用 `pending_tool_use_ids` 记录"当前正在等待结果的工具调用 ID 集合"、`pending_tool_use_index` 记录这条 `assistant` 消息在输出列表里的位置。如果紧跟着的下一条消息不是携带了**全部**匹配 `tool_result` 的 `user` 消息（`pending_tool_use_ids.issubset(result_ids)`），就说明这次工具调用没有被正确响应,直接把这条挂起的 `assistant` 消息从输出里删掉（`sanitized.pop(pending_tool_use_index)`）。循环结束后还有一次收尾检查——如果历史的最后一条消息本身就是一个仍在等待结果的 `tool_use` 消息，同样要删掉。

这个函数在 `QueryEngine.submit_message()` 和 `continue_pending()` 里都会在处理历史之前先跑一遍（见第一篇），这不是可选的防御性编程，而是"支持从任意中断点恢复会话"这个功能能够成立的前提条件。

### has_pending_continuation：区分"新一轮输入"与"接着未完成的工具循环走"

```python
# src/openharness/engine/query_engine.py
def has_pending_continuation(self) -> bool:
    """Return True when the conversation ends with tool results awaiting a follow-up model turn."""
    if not self._messages:
        return False
    last = self._messages[-1]
    if last.role != "user":
        return False
    if not any(isinstance(block, ToolResultBlock) for block in last.content):
        return False
    for msg in reversed(self._messages[:-1]):
        if msg.role != "assistant":
            continue
        return bool(msg.tool_uses)
    return False
```

这个判断和 `sanitize_conversation_messages()` 修复的是同一类中断场景的另一面：如果中断发生在"工具已经执行完、结果已经写回历史，但还没来得及把结果喂给模型做下一轮推理"这个时间点，历史本身其实是完整且合法的——最后一条消息是携带 `tool_result` 的 `user` 消息，倒数第二条 `assistant` 消息确实发起过对应的工具调用。这种情况下不需要用户重新说话，只需要调用 `QueryEngine.continue_pending()`（第一篇提到过，不追加新用户消息、直接把现有历史交给 `run_query()`）就能让循环从正确的位置续上。`has_pending_continuation()` 就是判断"当前是否处于这种可续跑状态"的谓词，供上层 UI 决定要不要在恢复会话时自动续跑一次。

### 自动压缩：先便宜后昂贵的级联策略

`services/compact/__init__.py` 的头部注释写得很直白："Faithfully translated from Claude Code's compaction system"——这是一套移植自 Claude Code 的压缩系统，虽然 README 把它归在"Memory / Session"能力清单下，但它的调用入口就在 `engine/query.py::run_query()` 每一轮循环最开始的地方（见第一篇），不是记忆子系统里一个独立运行的旁路,而是核心循环主动驱动的一步。

第一步是估算当前对话占用了多少 token：

```python
# src/openharness/services/compact/__init__.py
TOKEN_ESTIMATION_PADDING = 4 / 3
_DEFAULT_VISION_IMAGE_TOKEN_ESTIMATE = 3_072

def estimate_message_tokens(messages: list[ConversationMessage]) -> int:
    total = 0
    image_token_estimate = _vision_token_budget_per_image()
    for msg in messages:
        for block in msg.content:
            if isinstance(block, TextBlock):
                total += estimate_tokens(block.text)
            elif isinstance(block, ToolResultBlock):
                total += estimate_tokens(block.content)
            elif isinstance(block, ToolUseBlock):
                total += estimate_tokens(block.name)
                total += estimate_tokens(str(block.input))
            elif isinstance(block, ImageBlock):
                total += image_token_estimate
    return int(total * TOKEN_ESTIMATION_PADDING)
```

底层的 `estimate_tokens()` 定义在 `services/token_estimation.py`，是一个极简的字符数启发式：

```python
# src/openharness/services/token_estimation.py
def estimate_tokens(text: str) -> int:
    """Estimate tokens from plain text using a rough character heuristic."""
    if not text:
        return 0
    return max(1, (len(text) + 3) // 4)
```

这不是真正的分词器（不同模型的 tokenizer 完全不同），就是"约 4 字符 1 token"的经验估算，`services/compact` 里又在此基础上统一乘了 `TOKEN_ESTIMATION_PADDING = 4/3` 的安全冗余系数——宁可高估也不要低估，因为这个数字唯一的用途是**决定要不要触发压缩**，估算偏保守最多是"压缩得早一点"，估算偏激进则可能真的把上下文塞爆。这也是为什么它和下面要讲的 `UsageSnapshot`（Provider 返回的真实计费用量）是两套完全独立的数字——一个用于流程控制决策，一个用于呈现给用户的真实开销，两者故意没有被合并成一套"权威 token 数"。

阈值本身怎么算：

```python
# src/openharness/services/compact/__init__.py
AUTOCOMPACT_BUFFER_TOKENS = 13_000
MAX_OUTPUT_TOKENS_FOR_SUMMARY = 20_000

def get_autocompact_threshold(model, *, context_window_tokens=None, auto_compact_threshold_tokens=None) -> int:
    if auto_compact_threshold_tokens is not None and auto_compact_threshold_tokens > 0:
        return int(auto_compact_threshold_tokens)
    context_window = get_context_window(model, context_window_tokens=context_window_tokens)
    reserved = min(MAX_OUTPUT_TOKENS_FOR_SUMMARY, 20_000)
    effective = context_window - reserved
    return effective - AUTOCOMPACT_BUFFER_TOKENS
```

阈值 = 上下文窗口 − 为摘要输出预留的空间（最多 20000）− 再留一道 13000 token 的缓冲带。这个"双重缓冲"的设计意图很清楚：压缩本身要调一次 LLM 生成摘要，这次调用也需要输出 token 配额，如果等到上下文真正塞满才触发压缩，压缩请求本身可能都发不出去；`AUTOCOMPACT_BUFFER_TOKENS` 这道额外缓冲带则是给"估算不精确"留出的容错空间。`auto_compact_threshold_tokens` 可以由用户在 `ProviderProfile` 里显式配置（第二篇提到过这个字段），覆盖掉自动计算的默认值。

真正的级联发生在 `auto_compact_if_needed()` 里，按"越便宜越先尝试"的顺序排列：

```python
# src/openharness/services/compact/__init__.py（节选，保留级联结构）
async def auto_compact_if_needed(messages, *, api_client, model, state, ...):
    if not force and not should_autocompact(messages, model, state, ...):
        return messages, False

    # 1. 微压缩：清空旧工具结果的内容，不调 LLM
    messages, tokens_freed = microcompact_messages(messages)
    if tokens_freed > 0 and not should_autocompact(messages, model, state, ...):
        return messages, True

    # 2. 上下文折叠：截断单条超大内容块
    context_collapsed = try_context_collapse(messages, preserve_recent=preserve_recent)
    if context_collapsed is not None:
        messages = context_collapsed
        if not force and not should_autocompact(messages, model, state, ...):
            return messages, True

    # 3. 会话记忆压缩：确定性摘要，不调 LLM
    session_memory = try_session_memory_compaction(messages, preserve_recent=..., trigger=trigger, metadata=carryover_metadata)
    if session_memory is not None:
        state.compacted = True
        ...
        return build_post_compact_messages(session_memory), True

    # 4. 全量压缩：调 LLM 生成结构化摘要
    result = await compact_conversation(messages, api_client=api_client, model=model, ...)
    state.compacted = True
    return build_post_compact_messages(result), True
```

四步分别是：

1. **微压缩**（`microcompact_messages`）——只清空旧的、可压缩类工具（`read_file`/`bash`/`grep`/`glob`/`web_search`/`web_fetch`/`edit_file`/`write_file`）的结果内容，替换成一句 `[Old tool result content cleared]`，保留最近 `DEFAULT_KEEP_RECENT=5` 个不动。完全不调用模型，纯粹是本地字符串操作，是级联里最便宜的一步。
2. **上下文折叠**（`try_context_collapse`）——针对个别异常巨大的单条内容块做截断，同样不调模型。
3. **会话记忆压缩**（`try_session_memory_compaction`）——为较早的消息生成一份确定性的、逐条摘要文本（`_summarize_message_for_memory()` 对每条消息取前 160 字符），拼成一段"Session memory summary"文本替换掉这些消息，仍然不调用 LLM，只有当生成的摘要确实比原始消息更紧凑（`estimate_message_tokens(provisional) < estimate_message_tokens(messages)`）才会采用。
4. **全量压缩**（`compact_conversation`）——只有前三步都不足以让 token 数降到阈值以下时，才真正调用一次 LLM，用专门设计的压缩提示词（见下）生成结构化摘要。

每一步之后都会重新判断 `should_autocompact()`，一旦某一步已经让 token 数落回阈值以下就立即返回，不再往下走更昂贵的步骤——这正是"先便宜后昂贵"级联的核心逻辑：**大多数时候，压缩根本不需要走到第 4 步**。

全量压缩用的提示词值得一看,因为它直接决定了摘要质量：

```python
# src/openharness/services/compact/__init__.py
BASE_COMPACT_PROMPT = """\
Your task is to create a detailed summary of the conversation so far. ...

Then, produce a structured summary inside <summary> tags with these sections:
1. **Primary Request and Intent**: ...
2. **Key Technical Concepts**: ...
3. **Files and Code Sections**: Every file examined or modified, with specific code snippets and line numbers.
4. **Errors and Fixes**: ...
5. **Problem Solving**: ...
6. **All User Messages**: ...
7. **Pending Tasks**: ...
8. **Current Work**: ...
9. **Optional Next Step**: ...
"""
```

这份提示词要求模型先在 `<analysis>` 标签里做逐轮梳理，再在 `<summary>` 标签里按九个固定小节输出结构化摘要——`format_compact_summary()` 事后会把 `<analysis>` 部分整个丢弃，只保留 `<summary>` 内容拼进新的历史。九个小节里"Files and Code Sections"要求带具体路径和行号、"Pending Tasks"要求列出还没做完的事——这些字段设计得很像是给"压缩之后还要能无缝接着干活"这个目标量身定做的,而不是一份泛泛的对话总结。

还有一条独立于主动检查的**被动兜底路径**：第一篇提到 `run_query()` 在捕获到"prompt too long"类异常时，会以 `trigger="reactive"`、`force=True` 强制走一次压缩再重试——这条路径复用的是同一个 `auto_compact_if_needed()` 函数，只是跳过了 `should_autocompact()` 的前置判断（`force=True` 直接进入级联），处理的是"token 估算失准、真实请求已经被 Provider 拒绝"这个估算兜不住的场景。

压缩过程本身的进度通过 `CompactProgressEvent` 实时流式暴露出来：

```python
# src/openharness/engine/stream_events.py
@dataclass(frozen=True)
class CompactProgressEvent:
    phase: Literal[
        "hooks_start", "context_collapse_start", "context_collapse_end",
        "session_memory_start", "session_memory_end",
        "compact_start", "compact_retry", "compact_end", "compact_failed",
    ]
    trigger: Literal["auto", "manual", "reactive"]
    ...
```

九个 `phase` 取值精确对应级联里的每一步，`trigger` 字段区分这次压缩是主动检查触发、用户手动触发、还是被动兜底触发——这让 UI 层能给用户展示"正在折叠上下文""正在生成摘要"这类具体的进度信息，而不是一个笼统的转圈图标。`AutoCompactState`（`compacted`/`turn_counter`/`consecutive_failures`）作为跨轮次持久化的状态，还带了一道保险：`MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3`，连续压缩失败超过这个次数就放弃自动压缩，避免在一个持续失败的压缩尝试上无限循环消耗时间和 token。

### 成本跟踪：只算 token，不算钱

```python
# src/openharness/api/usage.py
class UsageSnapshot(BaseModel):
    input_tokens: int = 0
    output_tokens: int = 0

    @property
    def total_tokens(self) -> int:
        return self.input_tokens + self.output_tokens

# src/openharness/engine/cost_tracker.py
class CostTracker:
    """Accumulate usage over the lifetime of a session."""

    def __init__(self) -> None:
        self._usage = UsageSnapshot()

    def add(self, usage: UsageSnapshot) -> None:
        self._usage = UsageSnapshot(
            input_tokens=self._usage.input_tokens + usage.input_tokens,
            output_tokens=self._usage.output_tokens + usage.output_tokens,
        )

    @property
    def total(self) -> UsageSnapshot:
        return self._usage
```

`CostTracker` 这个名字听起来像是要算美元开销，但它的字段只有 `input_tokens`/`output_tokens`——它做的是 token 计数累加，货币成本换算（如果有）留给更上层按模型定价表去做，这里刻意不掺入价格假设，避免"引擎核心"和"计费策略"绑死。`add()` 方法的写法也符合仓库的不可变风格：不是原地修改 `self._usage.input_tokens += ...`，而是整个构造一个新的 `UsageSnapshot` 替换掉旧的引用。

这份用量数字的来源，是第二篇看到的每个 Provider 适配器在流式响应结束时产出的 `ApiMessageCompleteEvent.usage`——它是 Provider 自己在响应里报告的真实用量（比如 Anthropic SDK 的 `final_message.usage`），是**权威值**，不是估算。数据流是：适配器解析出 `UsageSnapshot` → `run_query()` 通过 `yield (event, usage)` 的元组把它和 `AssistantTurnComplete` 一起交出 → `QueryEngine.submit_message()` 在消费流时调用 `self._cost_tracker.add(usage)` 累加 → `QueryEngine.total_usage` 属性对外暴露跨整个会话生命周期的累计值。

这条链路和前面讲的"压缩用的 token 估算"是两条完全独立的路径：一条用近似值驱动"要不要压缩"这个流程控制决策，容错空间大、更新频繁（每轮循环开始都会重新估算一次当前全部历史）；另一条用 Provider 返回的精确值驱动"这个会话到底花了多少 token"这个面向用户的统计展示，只在每次请求真正完成后更新一次。两者从未被合并成一套数字，这本身就是一处值得记住的设计取舍。

## 小结

`ConversationMessage` 用"两角色 + 类型化内容块"的极简表示撑起了整个消息状态机，`sanitize_conversation_messages()` 和 `has_pending_continuation()` 分别处理了"历史带着病态尾巴需要清理"和"历史完整但循环需要续跑"这两种不同的中断恢复场景。上下文压缩虽然实现细节很庞大（`services/compact/__init__.py` 一个文件就有 1700 多行），但整体策略是清晰的四级级联——微压缩、上下文折叠、会话记忆压缩、全量 LLM 摘要——每一级都比前一级更贵，只在前一级不够用时才继续往下走。成本跟踪这一层刻意保持简单：只做 token 计数的不可变累加，把估算（用于流程控制）和真实用量（用于统计展示）严格分开。

下一篇转向另一条完全独立的关注点：这一切之所以能跑起来，前提是引擎手里握着一个有效的模型访问凭据。`oh` 支持两类截然不同的认证模式——标准 OAuth（GitHub Copilot）和"复用外部 CLI 工具已登录凭据"（Claude Subscription / Codex Subscription）——第四篇就拆解这套认证体系，看清楚"不用单独为 `oh` 付费开一个 API Key，只要本地登录过 Claude Code 或 Codex CLI 就能直接用"这句承诺背后的具体实现。
