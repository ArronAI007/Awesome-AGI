# 配置与路径解析体系

> OpenHarness 的配置体系比它的文档措辞更朴素:`paths.py` 的文档字符串说自己"遵循 XDG 规范",实际实现却是一个更简单的单根目录模型——`~/.openharness/` 一个目录装下配置、数据、日志,靠三个独立的环境变量分别覆盖,而不是真正拆到 `~/.config`、`~/.local/share`、`~/.cache` 三处。配置优先级链(CLI > 环境变量 > 配置文件 > 默认值)也不是写在某个抽象的"合并器"里,而是分散在 `load_settings()`(文件 + 环境变量)和 `merge_cli_overrides()`(CLI 参数)两个函数里,由各个调用点自己决定要不要叠加 CLI 层。这篇把这套朴素但精确的机制过一遍。

## 学习目标

- 弄清楚 `config/paths.py` 里"类 XDG"路径解析的真实实现:一个可覆盖的根目录 + 若干子目录,而不是三份独立的标准目录。
- 理解 `config/settings.py` 顶部注释声明的四层优先级,分别对应代码里的哪几个函数调用。
- 认识 `Settings` 模型里的 Provider Profile 机制——同一份配置文件如何在 Anthropic API、Claude 订阅、Codex、Copilot、Kimi、Gemini 等十余种供应商之间切换,以及"扁平字段"和"profile 字典"之间是怎么互相同步的。
- 弄清楚 `config/schema.py` 这个文件其实不是主配置的 schema,而是 `ohmo` 频道适配器专用的一小撮兼容性模型。
- 知道仓库里只有一份全局 `settings.json`,不存在项目级配置文件覆盖全局配置这回事,project 相关的路径解析服务的是另一类需求。

## 背景与设计动机

一个既要支持"纯 API Key 直连 Anthropic",又要支持"复用已有的 Claude/Codex 订阅""复用 GitHub Copilot 订阅""接入 Kimi/Gemini/MiniMax/DashScope 等国内外任意 OpenAI 兼容供应商"的 CLI 工具,配置系统面临一个典型张力:用户既希望有一套"当前生效的模型/供应商/API Key"这样扁平、好读好改的顶层字段,又需要能保存"我配过好几套供应商,随时切换"这种多份配置共存的能力。如果只做扁平字段,切换供应商就要手动改一堆字段;如果只做纯粹的 profile 字典,任何一个只想临时改一下 `model` 的脚本都要先理解 profile 概念。

OpenHarness 的解法是让两者同时存在,并显式维护它们之间的同步关系:`Settings` 模型上既有 `model`/`provider`/`api_format`/`base_url` 这些扁平字段(兼容早期"没有 profile 概念"时期的调用方),又有 `profiles: dict[str, ProviderProfile]` 和 `active_profile: str` 这套完整的多配置存档;`materialize_active_profile()` 负责把 profile 投影回扁平字段,`sync_active_profile_from_flat_fields()` 负责反过来把扁平字段的改动折叠回 profile。路径解析这一侧则简单得多——没有多层级覆盖的诉求,只需要保证"默认能用、想改能用环境变量改"就够了。

## 核心机制详解

### `paths.py`:一个可覆盖的根目录,三个独立覆盖的子目录

模块的文档字符串这样写:

```python
# src/openharness/config/paths.py
"""Path resolution for OpenHarness configuration and data directories.

Follows XDG-like conventions with ~/.openharness/ as the default base directory.
"""

_DEFAULT_BASE_DIR = ".openharness"
_CONFIG_FILE_NAME = "settings.json"
```

但落到具体函数,"类 XDG"其实只体现在**每一类目录都可以被一个专属的环境变量单独覆盖**这一点上,并不是真正把配置、数据、缓存分别放进 XDG 规定的三个不同的操作系统标准目录:

```python
# src/openharness/config/paths.py
def get_config_dir() -> Path:
    """Return the configuration directory, creating it if needed.

    Resolution order:
    1. OPENHARNESS_CONFIG_DIR environment variable
    2. ~/.openharness/
    """
    env_dir = os.environ.get("OPENHARNESS_CONFIG_DIR")
    config_dir = Path(env_dir) if env_dir else Path.home() / _DEFAULT_BASE_DIR
    config_dir.mkdir(parents=True, exist_ok=True)
    return config_dir


def get_data_dir() -> Path:
    """Resolution order:
    1. OPENHARNESS_DATA_DIR environment variable
    2. ~/.openharness/data/
    """
    env_dir = os.environ.get("OPENHARNESS_DATA_DIR")
    data_dir = Path(env_dir) if env_dir else get_config_dir() / "data"
    data_dir.mkdir(parents=True, exist_ok=True)
    return data_dir


def get_logs_dir() -> Path:
    """Resolution order:
    1. OPENHARNESS_LOGS_DIR environment variable
    2. ~/.openharness/logs/
    """
    env_dir = os.environ.get("OPENHARNESS_LOGS_DIR")
    logs_dir = Path(env_dir) if env_dir else get_config_dir() / "logs"
    logs_dir.mkdir(parents=True, exist_ok=True)
    return logs_dir
```

真正的 XDG Base Directory 规范会要求配置进 `$XDG_CONFIG_HOME`(默认 `~/.config`)、数据进 `$XDG_DATA_HOME`(默认 `~/.local/share`)、缓存进 `$XDG_CACHE_HOME`(默认 `~/.cache`)——三个默认值分散在用户目录的不同位置。OpenHarness 的实现更接近"单一命名空间目录"模型:默认情况下配置、数据、日志全部挤在同一个 `~/.openharness/` 下面(数据和日志是它的子目录),只有当用户显式设置了三个 `OPENHARNESS_*_DIR` 环境变量之一时,对应的那一类才会被搬到别处。这个设计对单用户 CLI 工具是合理的取舍——用户几乎不需要关心"配置和数据分开放"这件事,`rm -rf ~/.openharness` 就能干净地清掉这个工具留下的一切痕迹,这比要去三个不同的标准目录里分别清理更符合"个人开发者工具"的使用直觉。三个独立环境变量的存在,则是留给需要精细控制的场景(比如把体积可能变大的 `data/`——里面存会话历史、任务输出——单独挂到另一块磁盘)。

在这四个"全局"函数之外,`paths.py` 剩下的十几个函数全部是**按项目 cwd 派生的路径**,统一挂在调用方传入的工作目录下的 `.openharness/` 子目录里:

```python
# src/openharness/config/paths.py
def get_project_config_dir(cwd: str | Path) -> Path:
    """Return the per-project .openharness directory."""
    project_dir = Path(cwd).resolve() / ".openharness"
    project_dir.mkdir(parents=True, exist_ok=True)
    return project_dir


def get_project_issue_file(cwd: str | Path) -> Path:
    return get_project_config_dir(cwd) / "issue.md"

def get_project_autopilot_registry_path(cwd: str | Path) -> Path:
    return get_project_autopilot_dir(cwd) / "registry.json"
```

这一组函数解析出的路径全部落在**当前项目目录**下,存的是 `issue.md`(当前 issue 上下文)、`pr_comments.md`(PR 评论上下文)、`autopilot/registry.json`(仓库自动巡检的任务队列)这类**项目专属的运行状态**,不是配置。全局的用户设置只有一份、只存在用户主目录下——这两套 `.openharness/` 目录(`~/.openharness/` 和 `<project>/.openharness/`)容易被同名误导成"全局配置 vs 项目配置覆盖"的关系,但实际上它们管的是完全不同的两类东西:前者是"这个 CLI 工具的用户级配置",后者是"这个项目的 Agent 运行状态"。

### `settings.py`:四层优先级分别落在哪两个函数里

模块顶部的文档字符串直接声明了完整的优先级链:

```python
# src/openharness/config/settings.py
"""Settings model and loading logic for OpenHarness.

Settings are resolved with the following precedence (highest first):
1. CLI arguments
2. Environment variables (ANTHROPIC_API_KEY, OPENHARNESS_MODEL, etc.)
3. Config file (~/.openharness/settings.json)
4. Defaults
"""
```

第 3、4 层("配置文件"和"默认值")以及**第 2 层("环境变量")**,全部在 `load_settings()` 一个函数内完成——它先用 `Settings()` 的 Pydantic 默认值兜底,再用文件内容覆盖,最后套一层 `_apply_env_overrides()`:

```python
# src/openharness/config/settings.py
def load_settings(config_path: Path | None = None) -> Settings:
    if config_path is None:
        from openharness.config.paths import get_config_file_path
        config_path = get_config_file_path()

    if config_path.exists():
        raw = json.loads(config_path.read_text(encoding="utf-8"))
        settings = Settings.model_validate(raw)
        ...
        return _apply_env_overrides(settings.materialize_active_profile())

    settings = Settings()
    ...
    return _apply_env_overrides(settings.materialize_active_profile())
```

第 1 层("CLI 参数")不在 `load_settings()` 里,而是每个调用点自己决定要不要在拿到的 `Settings` 上再叠一层 `merge_cli_overrides()`。真实调用点分布在三处,风格完全一致:

```python
# src/openharness/cli.py
settings = load_settings().merge_cli_overrides(
    model=model, max_turns=max_turns, base_url=base_url,
    system_prompt=system_prompt, api_key=api_key,
    api_format=api_format, permission_mode=permission_mode, effort=effort,
)
```

```python
# src/openharness/ui/runtime.py
def current_settings(self):
    """Return the effective settings for this session.

    We persist most settings to disk (``~/.openharness/settings.json``), but
    CLI options like ``--model``/``--api-format`` should remain in effect for
    the lifetime of the running process. Without this overlay, issuing any
    slash command (e.g. ``/fast``) would refresh UI state from disk and
    "snap back" the model/provider to whatever is stored in the config file.
    """
    return load_settings().merge_cli_overrides(**self.settings_overrides)
```

`RuntimeBundle.current_settings()` 上的这段注释解释了为什么 CLI 覆盖不能被直接落盘、只能作为一层运行时叠加:如果 `--model` 传入的值直接写进了 `settings.json`,那么会话进行到一半执行 `/fast` 这类会重新触发 `load_settings()` 的斜杠命令时,就会把用户在这次启动时临时指定的模型"弹回"配置文件里保存的那个——`merge_cli_overrides` 因此被设计成每次都在"刚读到的文件内容"上重新叠加一遍 CLI 覆盖,而不是把 CLI 覆盖一次性写死进内存里的某个全局单例。

`merge_cli_overrides` 自己的实现也值得看一眼,因为它不是简单的字段覆盖:

```python
# src/openharness/config/settings.py
def merge_cli_overrides(self, **overrides: Any) -> Settings:
    """Return a new Settings with CLI overrides applied (non-None values only)."""
    updates = {k: v for k, v in overrides.items() if v is not None}
    permission_mode = updates.pop("permission_mode", None)
    ...
    if "model" in updates and isinstance(updates["model"], str):
        updates["model"] = strip_ansi_escape_sequences(updates["model"])
    if "effort" in updates and isinstance(updates["effort"], str):
        updates["effort"] = "xhigh" if updates["effort"].strip().lower() == "max" else updates["effort"].strip().lower()
    merged = apply_permission_mode(self.model_copy(update=updates))
    ...
```

`None` 值会被过滤掉而不是覆盖成 `None`——这保证了"用户没有传这个 CLI 参数"和"用户显式传了空值"是可区分的,前者不产生任何覆盖效果;`model` 字段会先过一遍 `strip_ansi_escape_sequences`,这是因为某些终端环境下环境变量或粘贴输入可能带着 ANSI 转义序列(比如 `\x1b[1m`),不清理的话会直接污染发给模型 API 的请求。

`_apply_env_overrides` 里同样能看到一条不那么直觉的细节——`OPENHARNESS_*` 前缀的环境变量和裸的 Provider 原生环境变量(`ANTHROPIC_MODEL`、`ANTHROPIC_BASE_URL`、`OPENAI_BASE_URL`)优先级并不相同:

```python
# src/openharness/config/settings.py
def _apply_env_overrides(settings: Settings) -> Settings:
    """
    Provider-scoped env vars (``ANTHROPIC_BASE_URL``, ``ANTHROPIC_MODEL``,
    ``OPENAI_BASE_URL``) only apply when the active profile does *not*
    explicitly configure the corresponding field.  ``OPENHARNESS_*`` env vars
    always override (explicit user intent).
    """
    ...
    openharness_model = os.environ.get("OPENHARNESS_MODEL")
    if openharness_model:
        updates["model"] = strip_ansi_escape_sequences(openharness_model)
    elif not profile_has_explicit_model:
        anthropic_model = os.environ.get("ANTHROPIC_MODEL")
        if anthropic_model:
            updates["model"] = strip_ansi_escape_sequences(anthropic_model)
```

`OPENHARNESS_MODEL` 这种带项目前缀的环境变量被注释明确标注为"用户的显式意图",永远生效;而 `ANTHROPIC_MODEL`、`ANTHROPIC_BASE_URL` 这类供应商原生环境变量(很多人的 shell 里可能因为用别的工具而长期设置着)只在当前激活的 profile **没有**显式配置对应字段时才生效——这是为了防止一个为了别的工具设置的 `ANTHROPIC_BASE_URL`,意外劫持了 OpenHarness 里已经明确配置好的某个 profile。

### Provider Profile:扁平字段与多配置存档的双向同步

`Settings` 上同时存在两套描述"用哪个供应商、哪个模型"的字段——旧的扁平字段和新的 profile 字典:

```python
# src/openharness/config/settings.py
class Settings(BaseModel):
    api_key: str = ""
    model: str = "claude-sonnet-4-6"
    base_url: str | None = None
    api_format: str = "anthropic"
    provider: str = ""
    active_profile: str = "claude-api"
    profiles: dict[str, ProviderProfile] = Field(default_factory=default_provider_profiles)
    ...
```

内置的 profile 目录覆盖了十余种真实供应商配置,每一条都是一个完整可用的 `ProviderProfile`:

`load_settings()` 在返回前调用 `materialize_active_profile()`,保证消费方读到的扁平字段(`settings.model`、`settings.provider`)永远和当前激活的 profile 保持一致;`save_settings()` 在写盘前调用 `sync_active_profile_from_flat_fields()`,保证如果调用方是直接改了扁平字段(比如某段旧代码 `settings.model = "xxx"` 然后调 `save_settings`),这个改动会被正确折叠回 `profiles[active_profile]` 里,而不是产生"扁平字段和 profile 字典各说各话"的不一致状态。这一对方法的存在,本质上是给"从纯扁平字段演化到 profile 系统"这次架构升级留的兼容层——`sync_active_profile_from_flat_fields` 的 docstring 直接承认了这一点。

### `schema.py`:一个容易被误认为"主配置 schema"的小文件

`config/schema.py` 只有 120 行,乍看名字容易让人以为它是 `Settings` 的 JSON Schema 或者校验层,但它的文档字符串直接把范围划清楚了:

```python
# src/openharness/config/schema.py
"""Compatibility channel config models.

These models keep the synced channel adapters importable while the main
OpenHarness settings system evolves independently.
"""

class Config(_CompatModel):
    channels: ChannelConfigs = Field(default_factory=ChannelConfigs)
    providers: ProviderConfigs = Field(default_factory=ProviderConfigs)
```

这里的 `Config`/`ChannelConfigs` 描述的是 Telegram、Slack、Discord、飞书、钉钉、Email、QQ、Matrix、WhatsApp 等聊天频道适配器各自需要的凭证字段(token、app_id、webhook 密钥等),真正的消费方是 `ohmo/gateway/config.py`——`ohmo` 的网关层需要知道"这个飞书 bot 的 app_secret 是什么""这个 Telegram bot 允许哪些用户发消息"这类频道级配置,而不是 `openharness` 主配置(模型、供应商、权限模式)的一部分。`BaseChannelConfig` 上的 `allow_from` 字段还带着一条明确写在注释里的安全默认值:

```python
# src/openharness/config/schema.py
class BaseChannelConfig(_CompatModel):
    enabled: bool = False
    # Secure default: enabling a channel does not automatically trust every
    # remote sender. Operators must explicitly allow specific identities, or
    # intentionally set ["*"] when they want open access.
    allow_from: list[str] = Field(default_factory=list)
```

启用一个频道不等于信任这个频道上的任何人——`allow_from` 默认是空列表,必须显式列出允许的身份,或者显式设成 `["*"]` 才算"我知道自己在做什么、要开放访问"。这是一条对聊天机器人这类"任何认识 bot 账号的人都能给它发消息"场景很关键的默认拒绝策略。

## 常见问题/易踩坑

- **不要把 `config/schema.py` 当成 `Settings` 的校验 schema 去找**:它只服务于 `ohmo` 的频道适配器,`Settings` 本身的字段校验就是 Pydantic 模型自身的类型标注,没有独立的 JSON Schema 文件。
- **不存在"项目级 `settings.json` 覆盖全局配置"这回事**:`get_project_config_dir(cwd)` 返回的 `<project>/.openharness/` 目录里放的是 issue 上下文、PR 评论上下文、autopilot 状态,不是配置覆盖层;修改模型/供应商配置永远只有 `~/.openharness/settings.json`(或 `OPENHARNESS_CONFIG_DIR` 指向的路径)这一份文件。
- **改了 `settings.model` 却发现 `/fast` 之类命令后又变回旧值**:检查是不是漏掉了 `merge_cli_overrides` 这一层——`load_settings()` 每次都从磁盘重新读,CLI/运行时的临时覆盖必须每次显式叠加,不会自动"粘"在某次调用结果上。

## 小结

OpenHarness 的路径解析用一个可整体搬迁、按需拆分的单根目录模型,换来了"删一个目录就是干净卸载"的简单心智模型;配置优先级链虽然文档里写成四层,但代码上其实只有两个关键函数——`load_settings()` 吃进文件和环境变量,`merge_cli_overrides()` 按调用点各自决定要不要再叠一层 CLI 覆盖。Provider Profile 系统则用"扁平字段 + profile 字典 + 两个双向同步方法"的组合,在保持旧调用方兼容的前提下,撑起了十余种供应商、含订阅复用在内的切换能力。下一篇是这一章的收尾——测试策略与工程规范,会讲清楚 `uv run pytest` 覆盖的常规测试和 `scripts/` 下那批需要真实 API Key 才能跑的端到端脚本之间是怎么分层的,以及 CI 里 ruff/mypy/前端类型检查各自把关到什么程度。
