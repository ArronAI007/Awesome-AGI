# 测试策略与工程规范

> `uv run pytest -q` 在 CI 里几秒钟就能跑完,但 `tests/` 目录里其实藏着几个需要真实模型 API Key、需要一个只存在于原作者机器上的绝对路径(`/home/tangjiabin/AutoAgent`)才会真正执行的"重量级"集成测试——它们没有被搬到别处,而是留在 `tests/` 里,靠 `pytest.mark.skipif` 在没有满足条件时安静跳过。`scripts/` 目录下则是另一批完全不在 `pytest` 默认发现路径里的端到端脚本,专门用来对着真实 API、真实 Docker、真实 TTY 跑一遍完整场景。这篇把这套三层测试策略,以及 `ruff`/`mypy` 在 CI 里"严格配置、宽松执行"的现状讲清楚。

## 学习目标

- 理解 `pyproject.toml` 里 `testpaths = ["tests"]` 这一行,如何把 `tests/` 和 `scripts/` 划成两个默认发现范围完全不同的测试空间。
- 认清 `tests/` 目录内部其实混杂着"总会跑的快速测试"和"靠 `skipif` 自我豁免的真实 API 集成测试"两类文件,学会用 `pytest.mark.skipif` 的条件表达式区分它们。
- 弄清楚 `scripts/test_harness_features.py`、`test_real_skills_plugins.py` 这类脚本存在的设计意图——用真实模型跑一遍真实 skill/plugin,验证的是文档和示例的可用性,而不是代码路径的单元正确性。
- 通过 `scripts/test_docker_sandbox_e2e.py` 的双模式设计(既能 `python3` 直接跑,也能被 `pytest` 收编但按 Docker 可用性自动跳过),理解一个测试脚本如何同时服务两种使用场景。
- 读懂 CI 的三个并行 job(`python-tests`、`python-quality`、`frontend-typecheck`)各自的把关范围,以及 `mypy strict = true` 为什么目前不是必须通过的门禁。

## 背景与设计动机

OpenHarness 面对一个几乎所有"用 LLM 驱动的 Agent 框架"都会遇到的测试困境:框架本身的很多正确性,只有接上一个真实模型、真实跑一轮完整对话之后才能验证——工具是否真的被模型正确调用、hook 是否真的在模型触碰到某个操作时被触发、skill 是否真的被模型找到并使用。这类验证天然需要一个可用的 API Key、可能需要几十秒到几分钟的真实网络往返,不可能作为每次 `git push` 都要跑的默认测试套件的一部分——否则 CI 会变得又慢又不稳定(模型输出的不确定性会带来天然的 flaky)。

但完全不做这类验证也不行,因为很多问题只在"模型真的按预期使用了某个工具"这个层面才会暴露。OpenHarness 的解法不是把这两类测试彻底分离到互不相干的目录,而是用一套**分层但共存**的策略:绝大多数测试留在 `tests/` 目录、用 mock 或本地可控的输入跑纯粹的单元/集成测试,由 `testpaths = ["tests"]` 保证它们是 `uv run pytest` 默认就会跑的部分;少数几个真正需要真实模型的"大场景"测试同样物理放在 `tests/` 里,但顶着 `pytest.mark.skipif` 自我豁免,让它们在没有满足条件的环境里(包括绝大多数贡献者的机器和 CI)默默跳过而不是报错;真正大批量的、面向真实模型/真实 Docker/真实终端的端到端验证,则搬到 `testpaths` 覆盖不到的 `scripts/` 目录,变成需要显式调用才会执行的"仪式性"验证脚本。这套分层没有用任何测试框架的高级特性(比如 pytest 的 marker 体系配合 `-m "not slow"` 这种筛选惯用法),而是直接用文件路径和 `skipif` 条件表达式手工划界——朴素,但每一条边界都能在源码里直接读出来。

## 核心机制详解

### `testpaths = ["tests"]`:一条分界线划开两个世界

`pyproject.toml` 里配置 pytest 的部分只有三行:

```toml
# pyproject.toml
[tool.pytest.ini_options]
testpaths = ["tests"]
asyncio_mode = "auto"
```

`testpaths = ["tests"]` 意味着裸的 `uv run pytest`(或 `pytest`)只会在 `tests/` 目录下发现测试,`scripts/` 目录下那些文件名同样以 `test_` 开头的脚本(`test_harness_features.py`、`test_cli_flags.py` 等)**根本不在默认收集范围内**。`asyncio_mode = "auto"` 则是因为 OpenHarness 的核心逻辑几乎全是 `async def`(引擎循环、工具执行、流式事件),这个配置让 `pytest-asyncio` 自动识别并运行所有异步测试函数,不需要给每个测试函数手工加 `@pytest.mark.asyncio`。

`tests/` 目录下有 103 个测试文件、约 27100 行代码,子目录基本和 `src/openharness/` 的子包一一对应(`test_engine/`、`test_tools/`、`test_sandbox/`、`test_swarm/` 等),这是最常见的"测试目录结构映射源码目录结构"惯例。`tests/conftest.py` 全文只有一个 autouse fixture:

```python
# tests/conftest.py
"""Shared test fixtures."""

import pytest_asyncio
from openharness.tasks.manager import shutdown_task_manager


@pytest_asyncio.fixture(autouse=True)
async def _reset_background_task_manager():
    yield
    await shutdown_task_manager()
```

这个 fixture 揭示了一个真实的测试隔离问题:`openharness.tasks.manager` 里维护着一个进程级的后台任务管理器(单例),如果不在每个测试结束后主动 `shutdown_task_manager()`,上一个测试留下的后台任务/事件循环状态就可能污染下一个测试——`autouse=True` 保证了这一步不需要每个测试文件自己记得去做,而是全局兜底。

### `tests/` 内部真正的分野:`skipif` 划出的"真实 API"孤岛

`tests/` 目录并不是铁板一块的"全是快速单元测试"。仔细看几个体量较大的文件(`test_untested_features.py`、`test_real_large_tasks.py`、`test_merged_prs_on_autoagent.py`、`test_hooks_skills_plugins_real.py`),它们的文档字符串直接写明了自己需要真实 API:

```python
# tests/test_real_large_tasks.py
"""Real large tasks that exercise multiple OpenHarness features together.

Each task is a realistic multi-turn scenario that combines 3+ features,
running on the AutoAgent codebase (an unfamiliar project) with real Kimi K2.5 API.

Run: python tests/test_real_large_tasks.py
"""
```

它们把大部分测试函数都标上了 `pytest.mark.skipif`,条件是**一个硬编码的绝对路径是否存在**:

```python
# tests/test_real_large_tasks.py / test_hooks_skills_plugins_real.py / test_merged_prs_on_autoagent.py
@pytest.mark.skipif(not Path("/home/tangjiabin/AutoAgent").exists(), reason="Needs real API + AutoAgent")
```

`/home/tangjiabin/AutoAgent` 显然是原作者本机上一个具体开发者账号下、检出了 `AutoAgent`(一个约 1.7 万行的 Python 项目,用作"陌生代码库"测试素材)的路径——这条路径在几乎所有其他人的机器和 CI 环境上都不存在,于是这些测试在 `uv run pytest -q` 跑起来时会被**安静跳过**而不是报错或失败。这不是一种严谨的"环境探测"写法(更规范的做法通常是检查环境变量或某个可配置的 fixture),但它确实达到了目的:这批测试留在版本库里作为"如何用真实场景验证一整套功能组合"的可读文档和回归基准,同时不会拖慢或搞崩任何人的常规测试运行。

`test_untested_features.py` 的 skip 条件写得稍微完善一点,同时检查工作区路径和 API Key 是否存在:

```python
# tests/test_untested_features.py
API_KEY = os.environ.get(
    "ANTHROPIC_API_KEY",
    "sk-Ue1kdhq9prvNwuwySlzRtWVD7ek0iJJaHyPdKDa3ecKLwYuG",
)
BASE_URL = os.environ.get("ANTHROPIC_BASE_URL", "https://api.moonshot.cn/anthropic")
MODEL = os.environ.get("ANTHROPIC_MODEL", "kimi-k2.5")
...
_SKIP_REAL_API = not WORKSPACE.exists() or not API_KEY

@pytest.mark.skipif(_SKIP_REAL_API, reason="Needs real API + AutoAgent")
def test_xxx(): ...
```

这里能读出一个值得留意的细节:`API_KEY` 的 `os.environ.get` 调用带了一个**硬编码的默认值**,而不是在环境变量缺失时返回空字符串——这意味着 `_SKIP_REAL_API` 里的 `not API_KEY` 这个条件事实上永远不会因为"没设置 `ANTHROPIC_API_KEY`"而成立,真正起作用的只有 `not WORKSPACE.exists()`。这几个文件把测试用的 API Key 直接以字面量形式提交进了版本库,这是复用这套脚本时需要留意的一点——如果要在自己的环境里跑这类测试,应当用自己的环境变量覆盖它,而不是依赖源码里遗留的默认值仍然有效。

### `scripts/`:完全脱离 `testpaths` 的端到端验证层

`scripts/` 目录下有 8 个 `test_*.py` 文件,合计约 3200 行,它们的共同点是文件头部都直接写明了运行方式,而且几乎全部要求真实模型:

```python
# scripts/test_harness_features.py
"""E2E tests for Harness features: retry, skills, parallel tools, path permissions.

Uses kimi model for real API calls.
"""
```

```python
# scripts/test_real_skills_plugins.py
"""E2E tests using REAL skills and plugins from anthropics/skills and compatible plugin repos.

Tests skill loading, plugin loading, command execution, hook execution with kimi model.
"""

SKILLS_REPO = Path("/tmp/anthropic-skills/skills")
PLUGINS_REPO = Path("/tmp/openharness-test-plugins/plugins")
```

`test_real_skills_plugins.py` 的设计意图和 `tests/` 里那批 `skipif` 测试不同——它验证的不是"某个内部函数在给定输入下返回预期输出",而是**"把 `anthropics/skills` 这个真实的官方 skill 仓库原样丢进 OpenHarness,模型真的能发现、加载并使用它们吗"**。这类测试的价值在于捕捉"单元测试全绿,但真实生态系统的产物用不起来"这类问题——比如某个 skill 的 frontmatter 格式和 OpenHarness 的解析器有细微差异、某个 plugin 目录结构假设和实际加载逻辑对不上。这种问题只有真的拿外部真实产物跑一遍才能发现,mock 掉的单元测试天然覆盖不到。这些脚本内部统一用同一个模式驱动被测对象——直接 `subprocess.run` 拉起真实的 `oh` 命令行,而不是在进程内 import 调用:

```python
# scripts/test_harness_features.py / test_real_skills_plugins.py 共同模式
def _run_oh(*args: str, timeout: int = 90) -> subprocess.CompletedProcess:
    cmd = [sys.executable, "-m", "openharness", *args]
    return subprocess.run(
        cmd, capture_output=True, text=True, timeout=timeout,
        env=_env(), cwd=str(PROJECT_ROOT),
    )
```

这保证了测试验证的是用户实际会敲的那条命令行路径,而不是绕过 CLI 解析、绕过进程边界之后的"内部近似"。

`scripts/react_tui_e2e.py` 走得更远,用 `pexpect` 驱动一个真正带 TTY 的子进程,这正是第 02 篇讲过的 Ink 前端依赖 raw-mode stdin 这件事在测试层面的对应验证——普通的 `subprocess.run` 拿到的是管道而不是伪终端,测不出交互式 TUI 在真实终端下的行为:

```python
# scripts/react_tui_e2e.py
"""Scripted React TUI end-to-end checks using the real CLI entrypoint."""

import pexpect
```

`scripts/test_docker_sandbox_e2e.py` 则展示了一种"双栖"写法——同一个文件既可以被直接执行,也可以被 `pytest` 收编,靠模块级 `pytestmark` 按运行时环境自动跳过:

```python
# scripts/test_docker_sandbox_e2e.py
"""End-to-end tests for the Docker sandbox backend.

These tests require a running Docker daemon. They exercise the full container
lifecycle: image build, container start, command execution, file isolation,
network isolation, resource limits, and cleanup.

Run directly:
    python3 scripts/test_docker_sandbox_e2e.py

Or via pytest (skipped automatically when Docker is unavailable):
    uv run pytest scripts/test_docker_sandbox_e2e.py -v
"""

_DOCKER = shutil.which("docker")
...
pytestmark = pytest.mark.skipif(not _DOCKER_OK, reason=_SKIP_REASON)
```

因为 `testpaths = ["tests"]` 把 `scripts/` 排除在默认发现范围外,这个文件永远不会被裸的 `uv run pytest -q` 意外收集到——必须像 CONTRIBUTING.md 示范的那样显式指向它,`pytestmark` 才有机会生效。这是"默认跑得快、需要时才跑重的"这条设计原则,在文件路径这一层面上的落实。

### CI 的三条并行流水线:各自的把关范围

`.github/workflows/ci.yml` 定义了三个互相独立、并行执行的 job,每一个对应仓库里的一类文件:

```yaml
# .github/workflows/ci.yml
jobs:
  python-tests:
    strategy:
      matrix:
        python-version: ["3.10", "3.11"]
    steps:
      - run: uv sync --extra dev
      - run: uv run pytest -q

  python-quality:
    steps:
      - run: uv sync --extra dev
      - run: uv run ruff check src tests scripts

  frontend-typecheck:
    defaults:
      run:
        working-directory: frontend/terminal
    steps:
      - run: npm ci
      - run: npx tsc --noEmit
```

`python-tests` 在 Python 3.10 和 3.11 两个版本矩阵上跑 `pytest -q`——对应 `pyproject.toml` 里 `requires-python = ">=3.10"` 声明的最低支持版本,矩阵测试确保不会引入只在某一个 Python 版本下才成立的语法或标准库行为。`python-quality` 只跑 `ruff check`,范围覆盖 `src`、`tests`、`scripts` 三个目录——**包括** `scripts/` 里那些不会被 `pytest` 收集的文件,说明"静态检查"和"测试执行"两件事在这里被分别对待:一个文件即使从不会被真正跑起来,依然要求语法/风格上是干净的。`frontend-typecheck` 是唯一涉及 Node/TypeScript 的 job,只做 `tsc --noEmit`——只验证类型能通过编译检查,不产出任何构建产物,也不跑前端的单元测试(`ModalHost.test.tsx`、`MarkdownText.test.tsx`、`PromptInput.test.ts` 这几个测试文件的存在说明前端有自己的测试,但 CI 里没有专门跑它们的 job)。

### `ruff`/`mypy`:配置严格,执行宽松

`pyproject.toml` 里两个静态检查工具的配置本身都不算宽松:

```toml
# pyproject.toml
[tool.ruff]
line-length = 100
target-version = "py311"

[tool.mypy]
python_version = "3.11"
strict = true
```

`mypy` 的 `strict = true` 是 mypy 里能打开的最严格档位,理论上要求所有函数签名都有完整类型标注、不允许隐式 `Any` 等等。但对照 CI 配置和 `CONTRIBUTING.md` 会发现一个明显的落差——**`mypy` 从未出现在 `ci.yml` 的任何一个 job 里**,`CONTRIBUTING.md` 对它的措辞也很克制:

```markdown
<!-- CONTRIBUTING.md -->
- If you are improving type coverage, feel free to run `uv run mypy src/openharness`, but it is not yet a required green check for the whole repo.
```

这是一种诚实的中间状态:类型标注这件事被认为值得做、配置也按最严格的标准写好了,但整个代码库还没有达到"全量跑一遍 `mypy --strict` 能保持绿色"的程度,所以没有把它接入 CI 强制门禁,而是留给愿意贡献类型改进的人自愿去跑。`ruff` 则相反——配置本身只设置了 `line-length` 和 `target-version`,没有显式打开任何 `select` 规则集(意味着用的是 ruff 的默认规则档位,不是刻意收紧过的定制规则集),但它确确实实被接入了 `python-quality` job,是一条会真正拦截 PR 的门禁。类似地,`pytest-cov>=5.0.0` 作为 dev 依赖出现在 `pyproject.toml` 里,但翻遍 CI 配置和 `CONTRIBUTING.md` 找不到任何 `--cov` 调用——覆盖率工具装好了,却没有被接进任何门禁或报告流程。这些细节合在一起描绘出一个真实项目的常见状态:工具链准备得比实际强制执行的标准更超前一步,严格配置先写好占位,再随着项目成熟度慢慢收紧成硬门禁。

### `CONTRIBUTING.md` 里对贡献者的期望

贡献者被要求在本地跑一遍和 CI 完全一致的三条检查:

```bash
# CONTRIBUTING.md
uv run ruff check src tests scripts
uv run pytest -q
```

```bash
cd frontend/terminal
npx tsc --noEmit
```

以及一条不涉及自动化检查、但明确写进流程的人工要求——"为用户可见的变更在 `CHANGELOG.md` 的 `Unreleased` 章节下加一条简短说明"。这把"改了什么、为什么改、怎么验证的"这套要求,从单纯的自动化门禁扩展到了需要人工判断的部分——`CONTRIBUTING.md` 特别提到,如果一个 issue/PR 主要是文档或维护性质,应该显式说明这一点以便被正确归类为文档 PR,这类软性流程约束本身也是"工程规范"的一部分,不是所有质量控制都能靠 CI 脚本自动化完成。

## 常见问题/易踩坑

- **裸跑 `pytest` 不会覆盖 `scripts/` 目录**:`testpaths = ["tests"]` 明确把它排除在外,如果想连带跑 `scripts/test_docker_sandbox_e2e.py` 这类文件,必须显式传路径。
- **`tests/` 目录跑得快不代表所有测试都跑了**:留意 `pytest.mark.skipif` 装饰的那批文件,它们大概率因为缺一个特定的本机路径或环境变量而被跳过,`pytest -q` 的输出里这些会显示为 `s`(skipped)而不是失败,容易被忽略。
- **不要直接复用 `tests/` 里那几个硬编码的 API Key 默认值**:它们只是历史遗留的兜底默认值,复用这套脚本前应该用自己的 `ANTHROPIC_API_KEY`/`ANTHROPIC_BASE_URL` 环境变量覆盖,不应该假设源码里的默认值仍然有效或应该继续被使用。
- **`mypy strict = true` 目前不是能拿来当"仓库类型安全"证据的门禁**:它没有接入 CI,大段代码库可能还无法在 `--strict` 下全绿,提交 PR 时不需要为此负责,除非你恰好在做类型标注改进。

## 小结

OpenHarness 的测试策略没有依赖复杂的 marker/tag 体系,而是用"目录归属 + `skipif` 条件表达式"这两个朴素手段划出了三层:`tests/` 下 103 个文件构成默认必跑的快速回归集,其中夹杂着几个靠硬编码路径自我豁免的真实 API 集成测试;`scripts/` 下的端到端脚本完全脱离 `pytest` 默认发现范围,专门用真实模型、真实 Docker、真实 TTY 验证"文档里说的能用" 这件事本身。CI 的三条流水线各自把关源码质量、测试通过、前端类型正确性,而 `mypy strict` 这样配置严格但尚未强制执行的工具,则诚实地反映了一个仍在演进中的代码库的真实状态。这一章到此收尾——下一章会一头扎进 Agent 核心循环,也就是驱动整个 OpenHarness 对话流程的 `QueryEngine`。
