# 多级权限模式与审批流程

> `PermissionChecker.evaluate()` 的方法体只有五十多行,但它的分支顺序本身就是一份设计文档:敏感路径保护先于一切模式判断执行,`denied_tools`/`allowed_tools`/`path_rules`/`denied_commands` 这些用户配置的规则又先于 `FULL_AUTO`/`PLAN`/`DEFAULT` 三档权限模式生效。也就是说,"允许什么"从来不是一个单一开关决定的,而是一条越往后越粗粒度的判定链——细粒度规则可以推翻粗粒度模式,但没有任何模式能推翻内置的凭据保护。理解这条链的顺序,比记住三档模式的名字更重要。

## 学习目标

- 弄清 OpenHarness 的三档权限模式(`default`/`plan`/`full_auto`)在 `PermissionChecker.evaluate()` 里各自对应哪条分支,以及它们和 `is_read_only`、`path_rules`、`denied_commands` 之间的优先级关系。
- 理解内置的 `SENSITIVE_PATH_PATTERNS` 为什么被放在整个判定链的最前面,以及它和用户自定义 `path_rules` 的分工差异。
- 弄清"要求用户确认"和"直接拒绝"这两种拒绝方式在代码里是两条不同的路径,并理解这个区分带来的一个真实的边界情况。
- 追踪一次工具调用从 `PermissionChecker.evaluate()` 返回 `requires_confirmation=True` 开始,到用户在界面上点下 Allow/Deny,再到结果送回执行循环的完整链路。
- 理解 `/permissions`、`/plan` 这类斜杠命令为什么要把权限模式写回 `settings.json` 并重建 `PermissionChecker`,而不是只改一个内存标志位。

## 背景与设计动机

一个能自主调用 Bash、编辑文件、发起网络请求的 Agent,天然存在一个矛盾:你希望它足够自主,能连续完成十几步操作而不用每一步都停下来问你;但你又不希望它在你没意识到的情况下执行一条 `rm -rf` 或者把凭据文件读出来发到某个 URL。这不是"要不要装安全机制"的问题,而是"把自主性和可控性这条轴上的旋钮拧到哪个刻度"的问题——不同任务、不同信任程度,理想的刻度是不一样的。

OpenHarness 把这个刻度做成了三档可切换的权限模式,而不是一个二元开关。同时,它没有把所有判断都塞进这一个模式变量里,而是在模式之上叠了几层更细粒度的规则:内置的凭据路径保护(任何模式都不能绕过)、用户配置的工具黑白名单、路径规则、命令拒绝模式。这样设计的好处是,即使用户为了效率把模式调到最宽松的 `full_auto`,像 `~/.ssh/id_rsa` 这样的路径依然会被挡下来——粗粒度的"自主性刻度"和细粒度的"硬性红线"是两套独立的机制,不会互相削弱。

## 核心机制详解

### 三档权限模式:一个 Enum,三种执行策略

```python
# src/openharness/permissions/modes.py:1-14
"""Permission mode definitions."""

from __future__ import annotations

from enum import Enum


class PermissionMode(str, Enum):
    """Supported permission modes."""

    DEFAULT = "default"
    PLAN = "plan"
    FULL_AUTO = "full_auto"
```

这个文件本身极简——它只声明了三个值,不包含任何行为。行为全部在 `PermissionChecker.evaluate()` 里,这意味着"模式叫什么名字"和"模式做什么"是彻底分离的两件事,后者可以独立演化而不用碰这个枚举。三档模式对应的直觉是:

- **`default`**(默认档):只读工具直接放行,变更类工具需要用户确认。这是"Agent 可以自己看,但改东西前要问一句"的常态。
- **`plan`**:只读工具依然放行,但变更类工具被**直接拒绝**,不会弹确认框。这是给"先规划、后执行"这类工作流用的——用户想让 Agent 先把改动方案想清楚,再决定要不要放开手脚。
- **`full_auto`**:除了内置的敏感路径保护和用户显式 `denied_tools`/`denied_commands` 规则外,其余全部放行,不再逐条确认。这是"我信任这个任务,不想被打断"的场景,典型用例是下面会提到的 autopilot 后台执行(`src/openharness/autopilot/service.py:66` 里 `permission_mode` 的默认值就是 `"full_auto"`——无人值守的后台执行本来就没有人可以点 Allow,所以只能走这一档)。

### 判定链:`PermissionChecker.evaluate()` 的分支顺序

三档模式只是判定链末尾的兜底逻辑。完整的判定顺序在 `checker.py` 里一次性写死,理解这个顺序比理解任何一个分支单独的含义都重要:

```python
# src/openharness/permissions/checker.py:75-156(节选,已省略部分实现细节)
def evaluate(
    self,
    tool_name: str,
    *,
    is_read_only: bool,
    file_path: str | None = None,
    command: str | None = None,
) -> PermissionDecision:
    """Return whether the tool may run immediately."""
    # 1. 内置敏感路径保护——任何模式、任何用户配置都不能覆盖
    if file_path:
        for candidate_path in _policy_match_paths(file_path):
            for pattern in SENSITIVE_PATH_PATTERNS:
                if fnmatch.fnmatch(candidate_path, pattern):
                    return PermissionDecision(allowed=False, reason=...)

    # 2. 显式工具黑名单
    if tool_name in self._settings.denied_tools:
        return PermissionDecision(allowed=False, reason=f"{tool_name} is explicitly denied")

    # 3. 显式工具白名单
    if tool_name in self._settings.allowed_tools:
        return PermissionDecision(allowed=True, reason=f"{tool_name} is explicitly allowed")

    # 4. 路径规则(path_rules)
    if file_path and self._path_rules:
        ...

    # 5. 命令拒绝模式(denied_commands)
    if command:
        ...

    # 6. full_auto:放行一切(前提是没被 1-5 挡下)
    if self._settings.mode == PermissionMode.FULL_AUTO:
        return PermissionDecision(allowed=True, reason="Auto mode allows all tools")

    # 7. 只读工具:任何模式下都直接放行
    if is_read_only:
        return PermissionDecision(allowed=True, reason="read-only tools are allowed")

    # 8. plan 模式:直接拒绝,不给确认机会
    if self._settings.mode == PermissionMode.PLAN:
        return PermissionDecision(allowed=False, reason="Plan mode blocks mutating tools until the user exits plan mode")

    # 9. default 模式:拒绝,但标记为"可以询问用户"
    return PermissionDecision(allowed=False, requires_confirmation=True, reason=...)
```

把这九步拆开看,会发现三档模式实际只出现在第 6、8、9 步——也就是链条的最后三分之一。前五步(敏感路径、黑名单、白名单、路径规则、命令拒绝模式)对所有模式一视同仁。这个顺序直接决定了几个不那么直觉但很关键的行为:

- `allowed_tools` 白名单(第 3 步)排在 `full_auto`(第 6 步)之前生效,但也排在敏感路径检查(第 1 步)之后——也就是说,即便你把某个工具显式加入白名单,只要它这次调用命中了 `~/.ssh/*` 这类内置模式,依然会被第 1 步拦下。白名单能覆盖的是模式判断,覆盖不了凭据保护。
- 只读工具(第 7 步)在 `plan` 模式下依然可以执行——`plan` 挡住的是"变更",不是"读取"。这是它能被称作"先规划"模式的原因:Agent 在 plan 模式下可以自由读文件、跑只读的 grep/glob,但写文件、跑变更类 Bash 命令会被挡。
- `PermissionDecision` 有 `allowed` 和 `requires_confirmation`两个独立字段,而不是一个三态枚举。`plan` 模式返回的是 `allowed=False, requires_confirmation=False`(第 8 步没有设置这个字段,默认值是 `False`)——即彻底拒绝,不会弹出确认框;`default` 模式返回的是 `allowed=False, requires_confirmation=True`(第 9 步)——拒绝立即执行,但把决定权交给用户。这两种"拒绝"在下游的处理逻辑完全不同,下一节会看到。

### 内置敏感路径保护:模式管不到的一层

```python
# src/openharness/permissions/checker.py:14-37
SENSITIVE_PATH_PATTERNS: tuple[str, ...] = (
    "*/.ssh/*",
    "*/.aws/credentials",
    "*/.aws/config",
    "*/.config/gcloud/*",
    "*/.azure/*",
    "*/.gnupg/*",
    "*/.docker/config.json",
    "*/.kube/config",
    "*/.openharness/credentials.json",
    "*/.openharness/copilot_auth.json",
)
```

注释写得很直接:这是"针对 LLM 指挥的、或者 prompt injection 驱动的凭据访问"的纵深防御。它覆盖的场景是——不管用户把权限模式调到多宽松、不管 Agent 是被正常指令驱动还是被注入的恶意内容诱导,只要目标路径匹配这些 glob 模式,直接拒绝,连 `requires_confirmation` 都不给。这条规则甚至排在用户自己的 `denied_tools`/`allowed_tools` 之前生效,意味着它是整个权限系统里唯一一层"用户配置也无法关闭"的保护。

值得注意的是路径匹配的实现细节:

```python
# src/openharness/permissions/checker.py:159-169
def _policy_match_paths(file_path: str) -> tuple[str, ...]:
    """Return path forms that should participate in policy matching.

    Directory-scoped tools like ``grep`` and ``glob`` may operate on a root such
    as ``/home/user/.ssh``. Appending a trailing slash lets glob-style deny
    patterns like ``*/.ssh/*`` and ``/etc/*`` match the directory root itself.
    """
    normalized = file_path.rstrip("/")
    if not normalized:
        return (file_path,)
    return (normalized, normalized + "/")
```

这个函数解决的是一个容易被忽略的边界情况:`grep`/`glob` 这类工具接收的往往是一个目录根路径(比如直接把 `/home/user/.ssh` 当作搜索根),而不是某个具体文件。如果只用原始路径去匹配 `*/.ssh/*`,`/home/user/.ssh` 本身(没有尾部内容)是匹配不上的——`fnmatch` 要求 `*` 之后至少还有点什么。所以这里同时生成"原路径"和"原路径+尾随斜杠"两种形式参与匹配,确保目录根本身也能命中规则,不给"直接把 `.ssh` 整个目录当 root 传进去"这种绕过方式留缝隙。

### `path_rules` 与 `denied_commands`:用户自定义的细粒度规则

`path_rules` 允许用户在 `default`/`full_auto` 之外,针对具体路径追加允许或拒绝规则:

```python
# src/openharness/permissions/checker.py:49-54
@dataclass(frozen=True)
class PathRule:
    """A glob-based path permission rule."""

    pattern: str
    allow: bool  # True = allow, False = deny
```

在 `evaluate()` 里,只有 `allow=False` 的规则会产生实际效果(第 108-117 行):

```python
# src/openharness/permissions/checker.py:108-117
if file_path and self._path_rules:
    for candidate_path in _policy_match_paths(file_path):
        for rule in self._path_rules:
            if fnmatch.fnmatch(candidate_path, rule.pattern):
                if not rule.allow:
                    return PermissionDecision(
                        allowed=False,
                        reason=f"Path {file_path} matches deny rule: {rule.pattern}",
                    )
```

这里有一个容易读漏的细节:`PathRule` 结构体虽然定义了 `allow` 字段,但循环体里只处理 `not rule.allow` 的情况——`allow=True` 的规则被解析进了 `self._path_rules` 列表,却不会在这一步产生任何"放行"效果。换句话说,`path_rules` 目前的实际语义是一个纯粹的**路径黑名单**,`allow: True` 这个字段目前更多是为配置文件保留的表达能力(比如未来做白名单模式的开关),不代表现在写一条 `allow: true` 的规则就能让某个路径绕过 `plan` 模式或者 `denied_tools`。

`denied_commands` 的实现更简单,一条 `fnmatch` 直接匹配整条命令字符串:

```python
# src/openharness/permissions/checker.py:119-126
if command:
    for pattern in getattr(self._settings, "denied_commands", []):
        if isinstance(pattern, str) and fnmatch.fnmatch(command, pattern):
            return PermissionDecision(
                allowed=False,
                reason=f"Command matches deny pattern: {pattern}",
            )
```

用 `fnmatch`(shell 通配符)而不是正则或者对命令做语法解析,意味着这层防护本质上是启发式的——想用 `rm -rf /` 这种字面量模式挡住"删除根目录"很容易,但 Bash 是图灵完备的,任何基于字符串匹配的黑名单都可以被换一种写法绕过(比如变量拼接、编码、alias)。这条规则和敏感路径保护不是一回事:后者是"绝对生效的凭据保护",前者是"帮用户挡住常见误操作的启发式规则",不应该把它当作对抗恶意输入的边界。

### 从"需要确认"到用户看到弹窗:执行循环怎么接手

`PermissionChecker.evaluate()` 只是给出一个 `PermissionDecision`,真正决定"接下来发生什么"的是调用它的执行循环。这段逻辑在 `engine/query.py` 的 `_execute_tool_call()` 里:

```python
# src/openharness/engine/query.py:926-966(节选)
_file_path = _resolve_permission_file_path(context.cwd, tool_input, parsed_input)
_command = _extract_permission_command(tool_input, parsed_input)
decision = context.permission_checker.evaluate(
    tool_name,
    is_read_only=tool.is_read_only(parsed_input),
    file_path=_file_path,
    command=_command,
)
if not decision.allowed:
    if decision.requires_confirmation and context.permission_prompt is not None:
        if context.hook_executor is not None:
            await context.hook_executor.execute(
                HookEvent.NOTIFICATION,
                {
                    "event": HookEvent.NOTIFICATION.value,
                    "notification_type": "permission_prompt",
                    "tool_name": tool_name,
                    "reason": decision.reason,
                },
            )
        confirmed = await context.permission_prompt(tool_name, decision.reason)
        if not confirmed:
            return ToolResultBlock(
                tool_use_id=tool_use_id,
                content=decision.reason or f"Permission denied for {tool_name}",
                is_error=True,
            )
    else:
        return ToolResultBlock(
            tool_use_id=tool_use_id,
            content=decision.reason or f"Permission denied for {tool_name}",
            is_error=True,
        )
```

这里印证了前面提到的两种拒绝路径的分野:只有 `requires_confirmation=True`(也就是 `default` 模式下的变更类工具)才会走到 `context.permission_prompt(...)` 这条弹窗询问的分支;`plan` 模式的拒绝、`denied_tools`/`denied_commands`/敏感路径的拒绝,`requires_confirmation` 都是 `False`,会直接落入 `else` 分支,把 `decision.reason` 作为一条 `is_error=True` 的工具结果直接返回给模型——模型看到的是一条报错,不会有人被问到。

在真正弹窗之前,还有一次 `HookEvent.NOTIFICATION` 钩子调用——这让第 04 章讲过的 hooks 系统可以在"即将向用户展示批准弹窗"这个时间点插入自定义逻辑(比如往外部系统推一条通知),它和权限系统的联动只到这一步为止,不参与批准结果本身的判断。另外值得一提的是,权限检查发生在 `PRE_TOOL_USE` 钩子之后——`_execute_tool_call()` 一开始就会跑一次 `PRE_TOOL_USE`,如果钩子本身选择 block,权限检查根本不会被执行到,这是两层独立的门,顺序是钩子先行。

`context.permission_prompt` 的类型定义很简单:

```python
# src/openharness/engine/query.py:53
PermissionPrompt = Callable[[str, str], Awaitable[bool]]
```

一个接受 `(tool_name, reason)`、返回 `bool` 的异步回调——执行引擎不关心这个回调背后是命令行提示、TUI 弹窗还是 Web 界面的一次网络往返,它只关心最后拿到一个 `True`/`False`。

### 谁在实现这个回调:两套真正在用的交互实现

仓库里 `src/openharness/ui/permission_dialog.py` 是一个非常简短的实现:

```python
# src/openharness/ui/permission_dialog.py:1-14
"""Interactive permission prompt."""

from __future__ import annotations

from prompt_toolkit import PromptSession


async def ask_permission(tool_name: str, reason: str) -> bool:
    """Prompt the user to approve a mutating tool."""
    session = PromptSession()
    response = await session.prompt_async(
        f"Allow tool '{tool_name}'? [{reason}] [y/N]: "
    )
    return response.strip().lower() in {"y", "yes"}
```

但顺着调用关系往下查会发现一个值得指出的事实:这个 `ask_permission` 函数在整个源码树里没有被任何地方 `import` ——它符合 `PermissionPrompt` 的签名,读起来也像是权限确认的"标准实现",但实际运行时没有任何代码路径会调用到它。真正被接到 `context.permission_prompt` 上的,是另外两套各自面向不同界面形态的实现:

TUI(Textual)界面里,`PermissionScreen` 是一个真正的模态弹窗组件,支持鼠标点击和键盘快捷键:

```python
# src/openharness/ui/textual_app.py:47-85(节选)
class PermissionScreen(ModalScreen[bool]):
    """Simple approval modal for mutating tools."""

    BINDINGS = [
        Binding("escape", "deny", "Deny"),
        Binding("y", "allow", "Allow"),
        Binding("n", "deny", "Deny"),
    ]

    def compose(self) -> ComposeResult:
        yield Container(
            Static(Panel.fit(f"Allow tool [bold]{self._tool_name}[/bold]?\n\n{self._reason}",
                              title="Permission Required")),
            Horizontal(
                Button("Allow", id="allow", variant="success"),
                Button("Deny", id="deny", variant="error"),
                classes="permission-actions",
            ),
        )

    def action_allow(self) -> None:
        self.dismiss(True)
```

而 `_ask_permission` 把这个模态屏幕的结果通过一个 `asyncio.Future` 桥接回 `permission_prompt` 期望的协程返回值:

```python
# src/openharness/ui/textual_app.py:270-285(节选)
async def _ask_permission(self, tool_name: str, reason: str) -> bool:
    return bool(await self._open_modal(PermissionScreen(tool_name, reason)))

async def _open_modal(self, screen: ModalScreen) -> object:
    loop = asyncio.get_running_loop()
    future: asyncio.Future[object] = loop.create_future()

    def _done(result: object) -> None:
        if not future.done():
            future.set_result(result)

    self.push_screen(screen, callback=_done)
    return await future
```

Web/React 前端走的是另一套跨进程通道,`backend_host.py` 的 `_ask_permission` 把请求包装成一条 `modal_request` 事件推给前端,再挂一个带超时的 `Future` 等前端把用户的选择回传回来:

```python
# src/openharness/ui/backend_host.py:762-782(节选)
async def _ask_permission(self, tool_name: str, reason: str) -> bool:
    async with self._permission_lock:
        request_id = uuid4().hex
        future: asyncio.Future[bool] = asyncio.get_running_loop().create_future()
        self._permission_requests[request_id] = future
        await self._emit(
            BackendEvent(
                type="modal_request",
                modal={"kind": "permission", "request_id": request_id,
                       "tool_name": tool_name, "reason": reason},
            )
        )
        try:
            return await asyncio.wait_for(future, timeout=300)
        except asyncio.TimeoutError:
            log.warning("Permission request %s timed out after 300s, denying", request_id)
            return False
        finally:
            self._permission_requests.pop(request_id, None)
```

三种形态(orphaned 的 prompt_toolkit 版本、Textual 模态屏幕、Web 端跨进程事件)背后是同一个抽象:一个 `(tool_name, reason) -> bool` 的异步回调,执行循环完全不关心它具体怎么呈现给人。这也是为什么 `_execute_tool_call()` 那段代码可以写得那么干净——它只依赖 `PermissionPrompt` 这一个类型别名,UI 细节被彻底挡在了执行引擎之外。300 秒超时并默认拒绝也是一个值得注意的设计:弹窗如果一直没人处理,系统不会无限期挂起等待,而是选择更保守的一侧(拒绝),避免一个卡住的确认框把整个 Agent 会话冻结。

### 模式切换:写回持久化配置,而不是内存标志

`/permissions` 和 `/plan` 两个斜杠命令是用户主动切换模式的入口:

```python

    return CommandResult(message=f"Permission mode set to {label}", refresh_runtime=True)
```

三件事同时发生:把新模式写进 `Settings` 对象、调用 `save_settings()` 落盘到配置文件、用新配置重建一个 `PermissionChecker` 并通过 `context.engine.set_permission_checker()` 换掉引擎里那个旧的检查器实例。`PermissionChecker` 本身是一个轻量、无状态的对象(构造函数只是把 `path_rules` 解析成 `PathRule` 列表),所以"重建"的成本很低,不需要考虑复用。

这里还有一个和权限模式强相关、但值得单独指出的事实:OpenHarness 的系统提示词会显式包含当前权限模式的文字说明,并且随着模式切换而重新生成:

```python
# src/openharness/prompts/context.py:80-99(节选)
def _build_permission_mode_section(settings: Settings) -> str:
    mode = settings.permission.mode
    if mode == PermissionMode.PLAN:
        guidance = ("Plan mode is enabled. Treat this session as read-only planning and analysis. "
                    "Do not call mutating tools such as file writes, edits, package installs, "
                    "state-changing shell commands, or task-spawning actions unless the user exits plan mode.")
    elif mode == PermissionMode.FULL_AUTO:
        guidance = ("Full-auto permission mode is enabled. You may use mutating tools when they are "
                    "necessary for the user's request, while still keeping changes scoped and intentional.")
    else:
        guidance = ("Default permission mode is enabled. Read-only tools can run directly; "
                    "mutating tools may require explicit user approval.")
    return f"# Current Permission Mode\n{guidance}"
```

也就是说,模型确确实实"知道"自己当前处于哪一档权限模式——这不只是一个执行期才生效的门控,还是写进上下文、指导模型主动决策的显式信息。`plan` 模式下模型被告知"不要调用变更类工具",这比单纯依赖执行期拒绝更进一步:理想情况下,模型会先自我约束,减少无谓的"尝试变更—被拒绝—重试"的来回,权限检查器则是这层自我约束失效或被绕过时的兜底。测试用例 `tests/test_ui/test_runtime_plan_mode.py` 也直接断言了 `/plan on` 之后 `bundle.engine.system_prompt` 里出现了 `"Plan mode is enabled"` 字样,确认这个联动是被有意维护的行为,不是偶然产生的副作用。

## 常见问题/易踩坑

**`enter_plan_mode`/`exit_plan_mode` 这两个工具本身,是否也会被 `plan` 模式挡住?** 从代码读到的现象是:会。`ExitPlanModeTool`/`EnterPlanModeTool` 都没有覆写 `BaseTool.is_read_only()`,而基类的默认实现返回 `False`(`src/openharness/tools/base.py:46-49`)。按照上面梳理的判定链,在 `plan` 模式下这两个工具会落到第 8 步——`plan` 模式的分支不检查 `requires_confirmation`,直接返回 `allowed=False`。也就是说,如果模型试图通过调用 `exit_plan_mode` 这个工具来"请求"退出 plan 模式,这次调用本身会被同一套 plan 模式规则拦下,模型收到的是一条报错,而不是退出成功的确认。目前真正能让会话退出 `plan` 模式的路径,是用户主动执行 `/plan off` 或 `/permissions default` 这类斜杠命令——这两条命令走的是 `commands/registry.py` 里直接调用 `context.engine.set_permission_checker()` 的路径,不经过 `PermissionChecker.evaluate()`,自然不受这条规则约束。读这段代码时值得留意:一个名字里写着"允许退出某种模式"的工具,不代表它在语义上被排除在该模式的门控之外——除非显式把它标成只读或者加入 `allowed_tools`。

**`SandboxFilesystemSettings` 里配置的 `allow_read`/`allow_write` 等字段,会不会影响这里讲的权限判定?** 不会。它们是给下一篇要讲的沙箱系统用的,和这里的 `PermissionChecker`/`path_rules` 是两套完全独立的机制,不要把两者的配置项混在一起理解。

## 小结

OpenHarness 的权限系统不是一个单一的"允许/拒绝"开关,而是一条有明确优先级的判定链:内置的敏感路径保护在最前面,任何模式都无法覆盖;用户配置的工具黑白名单、路径规则、命令拒绝模式排在中间,可以在模式之上做更细粒度的收紧;`default`/`plan`/`full_auto` 三档模式在最后兜底,分别对应"变更需确认""变更直接拒绝""变更直接放行"三种自主性刻度。`requires_confirmation` 这个字段把"拒绝"进一步拆成"可以问用户"和"没得商量"两种,只有前者才会触发 `permission_prompt` 回调——这个回调背后连接的是 Textual 模态弹窗或者 Web 端的跨进程 `modal_request` 事件,而不是仓库里那个看起来像标准实现、实际上没被任何代码引用的 `permission_dialog.py`。模式切换本身走的是持久化配置加重建检查器的路径,并且会同步进系统提示词,让模型对自己当前的权限边界有显式认知。

这一层进程内的权限判定,本质上和 Hermes 课程里讲过的"批准门"一样,防的是合作模式下的误操作,而不是一个主动对抗的模型。真正把"变更类工具"和宿主机文件系统、网络之间划出一条操作系统级边界的,是下一篇要讲的沙箱执行系统——Docker 后端如何隔离文件系统和网络,以及 `path_validator.py` 在容器边界之外还额外做了哪一层校验。
