# 协议代码生成:TypeBox 到 JSON Schema 再到 Swift

> OpenClaw 要同时给一个 TypeScript 后端(Gateway)、一个 Swift 写的 macOS App、一个 Swift 写的 iOS App、一个 Kotlin 写的 Android App 供货,四端都要理解同一份 WebSocket 协议里的每一个消息类型。如果协议类型在四个代码库里各自手写一份,版本一旦往前走,四份手写类型必然逐渐漂移,某个客户端迟早会在某个字段上悄悄解析错误。OpenClaw 的解法是:协议只有一个源头——`packages/gateway-protocol` 里用 TypeBox 写的 schema——JSON Schema、Swift 模型、Kotlin 模型全部是从这一个源头自动生成的派生物,而且 CI 会用 `git diff --exit-code` 强制校验生成结果和已提交代码完全一致。这篇讲清楚这条代码生成链路的真实实现依据。

## 学习目标

- 理解 `docs/concepts/architecture.md`"Protocol typing and codegen"一节描述的三段式链路:TypeBox schema 定义协议 → 生成 JSON Schema → 生成 Swift 模型。
- 找到这条链路在仓库里的真实落点:`packages/gateway-protocol`(协议单一源头)、`scripts/protocol-gen.ts`(JSON Schema 生成)、`scripts/protocol-gen-swift.ts`(Swift 生成)、`scripts/protocol-gen-kotlin.ts`(Kotlin 生成)。
- 理解"协议定义单一数据源,多语言客户端类型自动派生"这个设计对于一个要同时服务 TypeScript 后端和多个原生 App 的项目意味着什么,以及 CI 如何强制这条链路不漂移。
- 理解生成代码在这个仓库里的特殊地位——它既不是手写源码,也不是可以被死代码检测工具随意标记删除的产物。

## 背景与设计动机

`docs/concepts/architecture.md` 用三句话概括了这套机制:

```text
## Protocol typing and codegen

- TypeBox schemas define the protocol.
- JSON Schema is generated from those schemas.
- Swift models are generated from the JSON Schema.
```

TypeBox 是一个 TypeScript 库,它的特点是:用它写出来的 schema 对象在运行时**本身就是符合 JSON Schema 规范的普通 JavaScript 对象**,同时又能在编译期通过 TypeBox 的类型推导得到对应的静态 TypeScript 类型。这意味着"用 TypeBox 定义协议"这一件事,天然同时产出了两样东西:给 TypeScript 编译器用的静态类型,以及可以直接序列化输出的 JSON Schema 文档——不需要额外的转换步骤,TypeBox schema 对象本身既是数据又是类型。

这个特性正是整条代码生成链路能够成立的基础:协议只需要用 TypeBox 写一遍,TypeScript 侧立刻拿到类型安全和运行时校验能力,同时这份 schema 又可以原样序列化成 JSON Schema 文档,再喂给下游的代码生成器,产出 Swift、Kotlin 等其他语言的类型定义。对于一个要同时服务后端和多个原生客户端的协议来说,这消灭了"协议改了一个字段,四个代码库要分别手动同步"这个最容易出错的环节。

## 核心机制详解

### 协议的单一源头:`packages/gateway-protocol`

`packages/gateway-protocol/package.json` 的描述写得很直接:

```json
{
  "name": "@openclaw/gateway-protocol",
  "description": "Typed schemas and runtime validators for the OpenClaw Gateway WebSocket protocol",
  "keywords": ["gateway", "openclaw", "protocol", "typebox", "websocket"],
  "files": ["dist", "LICENSE", "README.md", "CHANGELOG.md", "protocol.schema.json"]
}
```

`keywords` 里直接写着 `typebox`,`files` 字段里则声明了这个包对外发布的产物里包含一份 `protocol.schema.json`——也就是说,这个包不仅仅是给 TypeScript 代码用的类型定义,它同时把生成好的 JSON Schema 文档作为发布内容的一部分,供任何需要理解 OpenClaw Gateway 协议的下游消费者(不管是不是 TypeScript 项目)直接读取。

包内的 `src/schema/` 目录下有几十个按领域拆分的 schema 文件(`agent.ts`、`approvals.ts`、`artifacts.ts`、`audit.ts` 等等),`src/schema/protocol-schemas.ts` 把它们汇总成一个 `ProtocolSchemas` 对象,这个对象就是整条代码生成链路真正的输入源头。

### 第一段:TypeBox → JSON Schema

`scripts/protocol-gen.ts` 是这条链路的第一段,它的核心逻辑非常简洁:

```typescript
import { ProtocolSchemas } from "../packages/gateway-protocol/src/schema/protocol-schemas.js";
import { listCoreGatewayMethodMetadata } from "../src/gateway/methods/core-descriptors.js";
import { writeGeneratedOutput } from "./lib/generated-output-utils.mts";
import {
  assertProtocolSchemaDocument,
  buildProtocolSchemaDocument,
} from "./lib/protocol-schema-document.mts";

function main() {
  const document = buildProtocolSchemaDocument({
    methods: listCoreGatewayMethodMetadata(),
    schemas: ProtocolSchemas,
  });
  assertProtocolSchemaDocument(document);
  const result = writeGeneratedOutput({
    check: false,
    next: JSON.stringify(document, null, 2),
    outputPath: resolveOutputPath(process.argv.slice(2)),
    repoRoot,
  });
  ...
}
```

它把 `ProtocolSchemas`(TypeBox schema 集合)和 Gateway 方法元数据(`listCoreGatewayMethodMetadata()`,即所有 RPC 方法的签名信息)组合成一份完整的协议文档,序列化写入 `dist/protocol.schema.json`。脚本里的一处注释很能说明这份 JSON Schema 文档在整个链路里的分量:

> The artifact is a build output with no committed baseline, so this contract check is the only guard between a degraded registry and the published schema; a regenerate-then-diff guard on it can never fail.

因为这份文档是纯构建产物,不像 Swift/Kotlin 那样有一份提交进版本控制的基线可以做 `git diff` 比对,所以 `assertProtocolSchemaDocument` 这个运行期契约检查就成了唯一能拦住"协议注册表退化"的防线——它在生成的那一刻直接校验文档结构是否完整自洽,而不是依赖事后 diff。

### 第二段:同一份 schema → Swift 模型

`scripts/protocol-gen-swift.ts` 是第二段,值得注意的是它的输入不是上一步产出的 `protocol.schema.json` 文件,而是**直接从同一个 `ProtocolSchemas` 源头再次读取**——因为 TypeBox schema 对象本身已经具备 JSON Schema 的结构形态,生成 Swift 的脚本可以绕过"先读文件再解析"这一步,直接在内存里对同一份 schema 对象做遍历:

```typescript
import { ErrorCodes } from "../packages/gateway-protocol/src/schema/error-codes.js";
import { ProtocolSchemas } from "../packages/gateway-protocol/src/schema/protocol-schemas.js";
import {
  MIN_CLIENT_PROTOCOL_VERSION,
  MIN_NODE_PROTOCOL_VERSION,
  PROTOCOL_VERSION,
} from "../packages/gateway-protocol/src/version.js";

const outPaths = [
  path.join(
    repoRoot, "apps", "shared", "OpenClawKit",
    "Sources", "OpenClawProtocol", "GatewayModels.swift",
  ),
];

const header = `// Generated by scripts/protocol-gen-swift.ts — do not edit by hand
// swiftlint:disable file_length
import Foundation

public let GATEWAY_PROTOCOL_VERSION = ${PROTOCOL_VERSION}
public let GATEWAY_MIN_PROTOCOL_VERSION = ${MIN_CLIENT_PROTOCOL_VERSION}
public let GATEWAY_MIN_NODE_PROTOCOL_VERSION = ${MIN_NODE_PROTOCOL_VERSION}
...`;
```

这段代码把三件事绑定在了一起写进生成的 Swift 文件头部:协议版本号常量(`PROTOCOL_VERSION`、`MIN_CLIENT_PROTOCOL_VERSION`、`MIN_NODE_PROTOCOL_VERSION`)、从 `ErrorCodes` 派生出的 `ErrorCode` 枚举、以及后面几千行由 schema 遍历生成的 Swift `struct`/`enum` 定义。输出路径 `apps/shared/OpenClawKit/Sources/OpenClawProtocol/GatewayModels.swift` 落在 `apps/shared/OpenClawKit`——这是 macOS App 和 iOS App 共用的 Swift 包,意味着这一份生成文件同时服务两个原生客户端,而不需要为 macOS 和 iOS 分别生成两份。

文件头部的注释"Generated by scripts/protocol-gen-swift.ts — do not edit by hand"是一条清晰的信号:这个 `.swift` 文件虽然确实以源码形式提交进了 Git 仓库(Swift 工具链没有像 TypeScript 那样成熟的"从非 Swift 源直接生成类型"集成方式,所以生成结果需要落盘成真实的 `.swift` 文件参与编译),但它的可编辑权属于生成脚本,不属于人。

### 第三段:同一份 schema → Kotlin 模型

`scripts/protocol-gen-kotlin.ts` 是这条链路里容易被忽略的第三段——Android App 同样需要理解 Gateway 协议,`package.json` 里的脚本条目证实了它和 Swift 生成走的是完全对称的路径:

```json
"protocol:gen": "node --import ./scripts/tsx.mjs scripts/protocol-gen.ts",
"protocol:gen:swift": "node --import ./scripts/tsx.mjs scripts/protocol-gen-swift.ts",
"protocol:gen:kotlin": "node --import ./scripts/tsx.mjs scripts/protocol-gen-kotlin.ts",
```

生成的 Kotlin 文件落在 `apps/android/app/src/main/java/ai/openclaw/app/gateway/GatewayProtocol.kt` 和同目录下的 `OpenClawProtocolConstants.kt`——同一套协议源头,这次派生出的是 Android 客户端需要的 Kotlin 数据类。这说明 `docs/concepts/architecture.md` 里"Swift models are generated from the JSON Schema"这句概括其实是简化描述,完整图景是:**一份 TypeBox schema,三条并行的生成路径,分别产出 JSON Schema 文档、Swift 模型、Kotlin 模型**,共同服务后端、macOS/iOS、Android 三类消费者。

### 用 `git diff --exit-code` 强制"生成结果不漂移"

光有生成脚本还不够——如果没有人记得在改协议之后重新跑一遍生成命令,提交进仓库的 `GatewayModels.swift`、`GatewayProtocol.kt` 就会和最新的 TypeBox schema 脱节。`package.json` 里的 `protocol:check` 脚本把生成、校验、diff 比对串成了一条流水线:

```json
"protocol:check": "pnpm protocol-registry:check && pnpm protocol:gen && pnpm protocol:check:swift && pnpm protocol:gen:kotlin && node --import ./scripts/tsx.mjs scripts/check-protocol-since.mts && git diff --exit-code -- apps/shared/OpenClawKit/Sources/OpenClawProtocol/GatewayModels.swift apps/android/app/src/main/java/ai/openclaw/app/gateway/GatewayProtocol.kt apps/android/app/src/main/java/ai/openclaw/app/protocol/OpenClawProtocolConstants.kt",
"protocol:check:swift": "node --import ./scripts/tsx.mjs scripts/protocol-gen-swift.ts --check",
"protocol:check:kotlin": "pnpm protocol:gen:kotlin && git diff --exit-code -- apps/android/app/src/main/java/ai/openclaw/app/gateway/GatewayProtocol.kt apps/android/app/src/main/java/ai/openclaw/app/protocol/OpenClawProtocolConstants.kt",
```

这条命令链的逻辑是:先重新生成一遍 Swift 和 Kotlin 模型,再用 `git diff --exit-code` 检查生成结果和已提交文件是否完全一致——只要有任何差异(意味着有人改了协议 schema 却忘了重新生成,或者手改了生成文件),这个检查就会以非零退出码失败。这把"生成代码必须和源头保持同步"从一条君子协定,变成了一条 CI 会主动拦截的硬性约束。

有意思的是,这份生成出来的 Swift 文件在 CI 里还享受一种特殊待遇——`docs/ci.md` 提到了 iOS/macOS 侧的死代码检测(Periphery)如何对待它:

> Standalone Periphery workflows enforce zero dead-code findings for the iOS and macOS apps... Its generated `OpenClawProtocol/GatewayModels.swift` schema contract is retained as generator-owned code rather than treated as app-local dead code.

Periphery 是一个扫描 Swift 项目、找出未被使用的声明的静态分析工具。一份自动生成的协议文件里,天然会包含一些当前版本客户端暂未用到、但协议层面确实存在的类型或字段(比如某个字段只有下一个版本的某个客户端才会读)——如果把这些声明当成"死代码"删掉,下次协议生成时又会把它们加回来,循环拉扯。CI 把这份文件标记为"generator-owned code",意味着死代码检测的判断标准对它单独放宽:它的存在理由不取决于当前 App 代码是否引用了它,而取决于它是否忠实反映了协议源头。

## 常见问题/易踩坑

- **不要直接手改 `GatewayModels.swift` 或 `GatewayProtocol.kt`**:文件头部的"do not edit by hand"注释不是客套话——`protocol:check` 会在 CI 里用 `git diff --exit-code` 把手改的内容和重新生成的结果做比对,手改会在下一次协议变更的 PR 里被直接冲掉或报错。
- **修改协议之后必须记得跑 `pnpm protocol:gen` / `protocol:gen:swift` / `protocol:gen:kotlin`**:三条生成路径是并行、独立的,改了 TypeBox schema 之后,JSON Schema、Swift、Kotlin 三份产物都需要重新生成并一起提交,漏掉任何一份都会在 CI 的 `protocol:check` 阶段被拦下。
- **不要把生成出来的协议文件当作可以被死代码工具随意清理的对象**:它的"未被使用"状态可能只是因为当前客户端版本还没跟上协议的最新能力,而不是真的多余。

## 小结

OpenClaw 用 TypeBox 把协议定义收敛成唯一的一个源头,再用三条并行的生成脚本(`protocol-gen.ts`、`protocol-gen-swift.ts`、`protocol-gen-kotlin.ts`)分别派生出 JSON Schema 文档、macOS/iOS 共用的 Swift 模型、Android 的 Kotlin 模型,并用 `git diff --exit-code` 把"生成结果必须和协议源头同步"这条约束做成了 CI 硬性检查。对于一个要同时服务 TypeScript 后端和三个原生客户端代码库的项目来说,这条链路消灭了"协议改了一个字段,四份手写类型定义逐渐漂移"这个最容易出错、也最难被发现的隐患。
