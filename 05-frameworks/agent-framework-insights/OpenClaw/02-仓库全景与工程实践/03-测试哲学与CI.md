# 测试哲学与 CI

> `src/gateway` 一个目录就有 2639 个文件,`extensions/` 挂着 155 个插件,`.github/workflows/` 下堆着 105 个工作流文件——一个体量这么大的仓库,如果每次改动都要求全量跑一遍测试和 lint,反馈循环会慢到没法用。OpenClaw 的应对方式不是"买更快的机器",而是一整套"变更范围识别 + 分层测试 + 按需申请隔离环境"的工程纪律:`check:changed`/`test:changed` 只对你实际改动的范围做检查,真正需要脏机器、真实安装、Docker、跨平台这类"环境本身就是证据的一部分"的场景才申请 Crabbox/Testbox 这样的远程沙箱。这篇讲清楚这套分层逻辑,以及它背后"不要为了凑测试覆盖率去写只是镜像实现的测试"这条更根本的原则。

## 学习目标

- 理解 `AGENTS.md`"Commands And Validation"一节定义的日常验证顺序:`pnpm check:changed` → `pnpm test:changed`/`pnpm test <path>` → 按需扩大范围。
- 理解 `pnpm changed:lanes --json` 在这套体系里扮演的角色——先看清一次改动触发了哪些"架构 lane",再决定要跑哪些检查。
- 理解 Crabbox 与 Testbox 分别是什么、什么时候才应该申请它们,以及为什么不能把它们当成通用算力来用。
- 理解"不要为了满足清单去写只是镜像实现的测试"这条原则在实践中意味着什么。
- 对 OpenClaw 的 CI 工作流体系有一个粗略但准确的分类印象,而不是试图记住全部 105 个工作流文件。

## 背景与设计动机

对一个体量巨大、每天都有大量并发 PR 的仓库来说,"测试要不要跑全量"从来不是非黑即白的选择。全量跑一遍意味着诚实但昂贵——CI 时间可能长达数十分钟甚至更久;只跑改动相关的测试则意味着快但有遗漏风险。OpenClaw 的答案是把这个决策拆成两层:本地开发循环里,默认只针对"变更范围"做检查,把全量验证留给显式的、有意为之的场景;CI 层面则用一个叫 `preflight` 的前置任务对 diff 做分类,决定这次 CI 要跑图里的哪些分支,而不是无脑跑满整张作业图。

第二个背景是"测试即证据"这个理念本身。`AGENTS.md` 里反复出现"proof"这个词——测试不是为了让某个覆盖率数字好看,而是为了证明一个具体的行为改动是正确的。这直接导向了两条彼此呼应的规则:一是"不要写只是镜像实现的测试"(这类测试除了让覆盖率上升之外不提供任何真实保护),二是"环境本身是证据的一部分时才用远程沙箱"(如果一个 bug 只在全新安装、Docker 容器、或者真实桌面环境里才能复现,本地 mock 环境提供的测试通过与否根本不构成证据)。

## 核心机制详解

### 日常验证的三级台阶

`AGENTS.md` 的"Commands And Validation"一节把日常验证流程写得非常具体:

> Start with `pnpm check:changed` and focused `pnpm test <path-or-filter>` or `pnpm test:changed`. Use `pnpm changed:lanes --json` to inspect scope. Worktrees may use `node scripts/check-changed.mjs` and `node scripts/run-vitest.mjs` to avoid pnpm reconciliation when dependencies are ready.

`docs/reference/test.md` 把这套顺序进一步落成一张"Routine local order":

1. `pnpm test:changed` —— 变更范围内的 Vitest 证明。
2. `pnpm test <path-or-filter>` —— 针对一个文件、目录或显式目标。
3. `pnpm test` —— 只有确实需要跑全量本地 Vitest 套件时才用。

配套的 `package.json` 脚本印证了这套分层的具体实现:

```json
"changed:lanes": "node scripts/changed-lanes.mjs",
"check:changed": "node scripts/check-changed.mjs",
"test:changed": "node --import ./scripts/tsx.mjs scripts/test-projects.mts --changed origin/main",
"test:coverage:changed": "node scripts/run-vitest.mjs run --config test/vitest/vitest.unit.config.ts --coverage --changed origin/main"
```

`check:changed` 不只是跑测试——文档里说它"Runs the local changed formatting/typecheck/lint/guard plan, including targeted Vitest owner tests for selected paths",也就是把格式化、类型检查、lint、以及各种项目自定义的 guard 脚本(比如导入环检查、废弃 API 使用检查)全部按变更范围过滤后跑一遍,是本地开发循环里第一道、也是最便宜的一道关卡。`changed:lanes --json` 则是一个纯粹的侦察工具——"Shows the architectural lanes triggered by the diff against `origin/main`",在真正跑检查之前,先让你知道这次改动命中了哪些架构分区(比如是否碰到了 gateway 事件目录、是否影响了移动端协议覆盖),这对于判断"我这次改动到底需要多广的验证范围"是一个很实用的前置信息。

### "不要写镜像实现的测试"

`AGENTS.md` 里紧跟着命令说明之后,有一条经常被忽略但分量很重的规则:

> Do not write tests for reversible, low-impact changes that merely mirror the implementation. Tests must meaningfully protect behavior. Use `$test-audit` when writing, changing, or reviewing tests.

这句话反对的是一类具体的反模式——为了让某个改动"看起来有测试覆盖",写一个断言逻辑几乎就是把实现代码原样复制一遍的测试(比如实现里写 `return a + b`,测试就写 `expect(add(a,b)).toBe(a+b)` 而不构造任何有意义的边界场景)。这种测试唯一的效果是让改动之后如果实现被重构,测试也要跟着改,除此之外不提供任何真实的回归保护。规则要求的是"测试必须有意义地保护行为"——换句话说,写测试之前先问一句:如果这段实现被写错了,这个测试真的会失败吗?如果答案是"不一定",这个测试就没有存在的必要。

紧接着的一条规则进一步说明了"该测什么、测到什么程度"要跟着改动本身的性质走,而不是套用一个固定清单:

> Run tests appropriate to the change and complete required checks. Once those pass, broaden or repeat testing only when new changes, failures, or unresolved concerns justify it; otherwise, continue toward completing the task.

也就是说,测试范围本身是有终止条件的——该测的测完、该过的检查过了,就该继续推进任务,而不是不断加测、不断扩大范围以求"绝对安全感"。

### Crabbox 与 Testbox:什么时候才该申请远程沙箱

`docs/reference/test.md` 的开篇给出了一条清晰的分界线:

> Agent sessions run trusted development tests, changed gates, typecheck/lint, and builds locally by default, broadening only when the touched contract requires it. Never execute untrusted repository tooling locally. Use Crabbox when the environment is part of the proof: clean-machine, install/package, Docker, E2E, live, desktop, or cross-platform work, or when the operator explicitly requests remote proof. Do not use Crabbox merely as generic compute offload.

这里的核心判断标准是:**只有当"环境本身就是要证明的东西的一部分"时,才需要 Crabbox**。举例来说,如果你要验证一个全新安装流程是否正常工作,本地开发机器上早已装好的各种依赖、缓存、历史状态本身就会污染这个证明——你需要一台真正干净的机器。同理,验证打包、Docker 镜像、桌面应用行为、跨平台兼容性,这些场景里"在什么样的环境下跑"本身就是断言的一部分,本地 mock 无法替代。反过来,如果一个改动只是纯逻辑修改,本地已经能够完整证明,就不应该把 Crabbox 当成"我想要更多算力"的通用出口去申请。

Crabbox 和 Testbox 不是同一个东西,但经常一起出现:

- **Crabbox**:一个独立的命令行工具/CLI(有自己的仓库 `openclaw/crabbox`),负责按需申请远程沙箱机器、同步代码、执行命令、回收资源,文档里的 `node scripts/crabbox-wrapper.mjs run/warmup/stop` 是 OpenClaw 对它的封装脚本。
- **Testbox**:Crabbox 支持的其中一种 provider/workflow,文档里写道"The repository default is `blacksmith-testbox`, with `.github/workflows/ci-check-testbox.yml` owning its prepared environment"——它是一个**预先配置好、承载凭证的**远程执行环境。正因为它会"hydrate credentials"(挂载凭证),文档特别强调:

> The configured Testbox workflow hydrates credentials, so untrusted contributor or fork code must use secretless fork CI or sanitized direct AWS Crabbox instead.

也就是说,Testbox 因为携带了凭证,只能用于可信代码;来自不受信任贡献者或 fork 的代码,必须走不带凭证的 fork CI,或者经过审查、隔离过的直接 AWS Crabbox 路径,绝不能让未经审查的代码触碰到挂载了凭证的执行环境。这是一条纯粹的安全边界,而不是性能或便利性的考虑。

OpenClaw 还专门做了插件化封装——`extensions/crabbox` 是一个 bundled 插件(`@openclaw/crabbox-provider`),它的插件说明写着"Cloud worker provider backed by the Crabbox CLI",意味着 Crabbox 不只是内部 CI 工具,还被产品化成了一种可配置的云端 worker 后端,供 OpenClaw 自身的 agent 任务调度使用。

懒加载而非预热也是这套体系的一条明确原则:

> Do not pre-warm for anticipated work. Acquire the backend lazily when the first environment-sensitive command is ready, reuse the returned `tbx_...` id for later remote commands, sync the current checkout on every run, and stop it before handoff.

不要因为"接下来可能需要"就提前申请远程环境,而是在真正需要一个环境敏感命令时才申请,申请之后尽量复用同一个 lease 处理后续的相关命令,用完主动释放。

### CI 流水线:先分类,再决定跑什么

`.github/workflows/` 目录下有 105 个工作流文件,`docs/ci.md` 把它们的调度逻辑总结成一句话:

> `preflight` classifies the diff and turns expensive lanes off when only unrelated areas changed.

这条规则和本地开发的 `check:changed`/`test:changed` 是同一套思路在 CI 层面的镜像——先识别这次 PR 改了什么范围,再决定图里哪些昂贵的作业(比如全套原生 App 构建、跨平台矩阵测试)需要被点亮,而不是每次 PR 都无条件跑满整张作业图。`docs/ci.md` 的 Pipeline overview 表格里能看到具体的分层结构,几个代表性的作业:

| Job | 作用 | 触发条件 |
|---|---|---|
| `preflight` | 识别变更范围,构建 CI manifest | 所有非草稿 push/PR |
| `security-fast` | 私钥检测、变更工作流的 zizmor 审计、生产锁文件审计 | 所有非草稿 push/PR |
| `build-artifacts` | 构建 `dist/`、Control UI、启动内存检查 | Node 相关变更 |
| `checks-node-*` | 变更目标的 Node 测试(PR 上是变更测试,`main` 上是紧凑分片) | Node 相关变更 |
| `macos-swift` / `ios-build` / `android` | 各原生平台的 lint 与构建 | 对应平台相关变更 |
| `openclaw/ci-gate` | 最终聚合门禁:要求 preflight 和 security 通过,拒绝任何非预期跳过或失败 | 每次 CI 运行 |

`openclaw/ci-gate` 作为唯一的强制分支保护检查,把前面所有分散的作业结果聚合成一个单一的通过/失败信号——这让分支保护规则不需要随着作业图的演化而不断更新required checks 列表,新增一个作业只需要让它汇入 `ci-gate` 的聚合逻辑即可。

值得一提的是,`main` 分支上还有一套"双槽位、按 run 编号奇偶分配"的调度策略,目的是让最多两条集成流水线同时存在、互不阻塞:

> Canonical `main` pushes use a two-slot pipeline keyed by run-number parity, so at most two integration runs overlap. Each slot is non-canceling and keeps one coalesced pending tip: a new merge replaces that slot's older pending run instead of canceling work that already registered a Blacksmith matrix.

这解决的是一个具体的资源浪费问题——如果每次 `main` 上的新 push 都取消上一次还在跑的 CI,那些已经注册了昂贵矩阵作业的运行就白跑了;双槽位设计让"新的 push 替换掉同一槽位里还没跑的那个 pending 提交",而不是打断已经在执行的运行。

## 常见问题/易踩坑

- **不要把 Crabbox/Testbox 当成"我想要更多 CPU"的出口**:判断标准是"这次验证是否需要环境本身作为证据的一部分",而不是"本地机器跑得慢"。
- **来自不可信来源的代码永远不能触碰挂载了凭证的 Testbox**:必须走 secretless fork CI 或经过审查的隔离 AWS Crabbox 路径,这是安全边界而不是流程建议。
- **`check:changed` 和 `test:changed` 不是同一件事的两个别名**:前者是格式化/类型检查/lint/guard 的变更范围检查,后者是变更范围的 Vitest 证明,文档明确要求两者搭配使用,而不是二选一。
- **不要为了凑覆盖率写镜像实现的测试**:写测试前先确认"实现写错了,这个测试真的会失败吗"。

## 小结

OpenClaw 用"变更范围优先、环境按需申请、测试证明行为而非凑覆盖率"三条原则,把一个体量巨大的仓库的验证成本控制在了可持续的范围内:本地开发循环默认只检查变更范围,`changed:lanes` 让你在动手之前先看清改动命中了哪些架构分区;Crabbox/Testbox 只在环境本身构成证据时才被申请,且严格区分可信/不可信代码的执行边界;CI 层面的 `preflight` 把同样的"先分类再决定跑什么"逻辑搬到了流水线调度上,`ci-gate` 把上百个分散作业聚合成一个稳定的门禁信号。下一篇转向另一条贯穿 TypeScript 后端与四个原生 App 的工程链路——协议是如何用 TypeBox 定义一次、再自动派生出 JSON Schema、Swift、Kotlin 多份客户端类型的。
