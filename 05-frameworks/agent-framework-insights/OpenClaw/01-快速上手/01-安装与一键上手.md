# 安装与一键上手

> `curl -fsSL https://openclaw.ai/install.sh | bash` 这一句话看起来只是“装个 CLI”，但它背后串起来的是一条明确的单向流水线：确认 Node 运行时安全（避开有 SQLite WAL 重置漏洞的版本）→ 装 OpenClaw → 跑 `openclaw onboard` 验证一次真实的模型补全 → 落地一个常驻的 Gateway 服务。理解这条流水线在哪一步做了什么决定，比记住某一个安装命令更重要——因为 OpenClaw 的整个产品形态，都建立在“一台宿主机上有且只有一个 Gateway 长期运行”这条设计原则之上。

## 学习目标

- 分清 `install.sh`/`install.ps1`（一键安装脚本，自动装 Node）与直接 `npm install -g openclaw`（自己管理 Node，需要理解 `--allow-scripts=openclaw` 在防什么）这两条安装路径的本质区别。
- 读懂 `openclaw onboard --install-daemon` 这一句命令实际做了哪几件事：验证推理可用性、准备 workspace、配置 Gateway、安装后台服务。
- 知道为什么 OpenClaw 要求 Node 22.22.3+/24.15+/25.9+，而不是“随便一个新版本就行”。
- 能用 `openclaw gateway status` 和 `openclaw dashboard` 两条命令验证安装是否真正成功，而不是仅凭命令没报错就下结论。
- 建立“一台宿主机只应该有一个 Gateway”这条从 README、SECURITY.md、CLI 文档里反复出现的设计原则，为后面理解 Gateway 架构（第 03 章）打下前提。

## 背景与设计动机

OpenClaw 的产品定位是“跑在你自己设备上、接入你已经在用的聊天软件的 AI 助理”，核心是一个叫 **Gateway** 的常驻控制平面（README 原话：*“It connects models, tools, messaging channels, and optional companion apps through one Gateway”*）。这意味着安装这一步的真正目标，不是“把二进制文件放到磁盘上”，而是要在目标机器上稳稳当当地跑起来**一个**长期存活的进程，管理会话、工具、事件和各个消息通道的连接。

正因为 Gateway 是单一控制平面，安装脚本才会做很多看起来“多此一举”的事情：检测并按需安装 Node（因为 Gateway 依赖 Node 内置的、经过 WAL 重置修复的 SQLite 实现）、在 npm 12 的脚本白名单机制下显式放行 OpenClaw 的生命周期脚本、安装完成后立刻跑一次 `openclaw doctor --fix` 做配置体检。这些步骤背后的逻辑是一致的：**先把运行时环境的正确性钉死，再谈业务配置**——因为一旦 Gateway 带着损坏的 SQLite 库或者错误的 Node 版本跑起来，后续所有的会话、配对、密钥状态都建立在不可靠的地基上。

VISION.md 里把这条思路说得更直接：“OpenClaw is currently terminal-first by design. This keeps setup explicit: users see docs, auth, permissions, and security posture up front.” 也就是说，安装/引导这一步刻意不做“魔法式”的一键黑盒，而是让你在过程中看到每一次模型鉴权、每一次安全提示。这也是为什么 `openclaw onboard` 的引导流程会在配置任何 Channel 之前，先强制跑通一次真实的模型补全——这条约束我们会在第 4 篇细讲。

## 核心机制详解

### 三条安装路径，一个共同终点

OpenClaw 官方文档把安装方式分成了三类。`docs/install/installer.md` 用一张表总结了三个安装脚本各自的职责：

> | Script | Platform | What it does |
> | --- | --- | --- |
> | `install.sh` | macOS / Linux / WSL | Installs Node if needed, installs OpenClaw via npm (default) or git, can run onboarding. |
> | `install-cli.sh` | macOS / Linux / WSL | Installs Node + OpenClaw into a local prefix (`~/.openclaw`) via npm or git. No root required. |
> | `install.ps1` | Windows (PowerShell) | Installs Node if needed, installs OpenClaw via npm (default) or git, can run onboarding. |

最常见的是第一种：

```bash
# macOS / Linux / WSL2
curl -fsSL https://openclaw.ai/install.sh | bash
```

```powershell
# Windows PowerShell
iwr -useb https://openclaw.ai/install.ps1 | iex
```

`install.sh` 的执行流程被拆成四个明确阶段（`docs/install/installer.md`）：检测操作系统 → 确保有一个受支持的 Node 运行时（缺失时 macOS 走 Homebrew 装 Node 26，Linux 走 NodeSource 装 Node 24 LTS）→ 确保 Git 存在 → 安装 OpenClaw 本体，默认走 npm 全局安装，`--install-method git` 则会克隆仓库、用 pnpm 构建、把包装脚本装到 `~/.local/bin/openclaw`。安装完成后，脚本还会做一轮“售后”：对已配置好的安装，尝试刷新并重启已加载的 Gateway 服务，并跑一次修复性的 `openclaw doctor`；对未配置的全新安装，则直接拉起引导流程。

如果你已经自己管理 Node，可以跳过安装脚本直接用包管理器：

```bash
npm install -g openclaw@latest --allow-scripts=openclaw
openclaw onboard --install-daemon
```

`README.md` 对这条命令有一个前提条件：“That command is for npm 12 or npm 11.16+. On npm 11.15 and earlier, omit `--allow-scripts=openclaw`.”——理解 `--allow-scripts` 在防什么，需要看 `docs/install/index.md` 里的说明：

> npm 12 blocks unapproved package lifecycle scripts by default. The `--allow-scripts=openclaw` option explicitly allows OpenClaw's `preinstall` and `postinstall` steps; without it, npm reports them as `blocked because they are not covered by allowScripts`.
>
> npm 11.16 accepts the option but otherwise only warns that the scripts are `not yet covered by allowScripts` and still runs them. npm 11.15 and earlier have neither the policy nor the option, so their command must be unflagged.

也就是说，`--allow-scripts=openclaw` 不是一个可有可无的性能选项，而是 npm 12 引入的供应链安全机制在 OpenClaw 这一侧的必要配合：npm 12 默认拦截任何包的生命周期脚本（`preinstall`/`postinstall`），OpenClaw 恰好需要这些脚本来完成安装期的必要工作（比如拉起 onboarding），所以必须显式在命令行里“点名放行”这一个包，而不是全局关闭这层保护。文档里还专门提醒了一个容易踩的坑：npm 11.16 建议你运行的 `npm approve-scripts openclaw` 命令，对全局安装其实是失效的，会报 `ENOMATCH No installed packages match: openclaw`。

### 为什么 Node 版本被锁得这么死

`SECURITY.md` 对 Node 版本的要求写得很具体：

> OpenClaw requires **Node.js 22.22.3+, Node.js 24.15+, or Node.js 25.9+**. Node 24 is the recommended default runtime for new installs. These minimum versions include the upstream SQLite WAL-reset corruption fix; Node 23 is unsupported. The minimum supported Node 22 version also includes important security patches:
>
> - CVE-2025-59466: async_hooks DoS vulnerability
> - CVE-2026-21636: Permission model bypass vulnerability

这条约束解释了一个现象：为什么 `install.sh` 在 Alpine/musl Linux 上不是简单调用 `apk add nodejs`，而是要“verifies the actual linked SQLite version”，必要时改用官方 `node:26-alpine` 容器或换 glibc 主机。OpenClaw 的会话、配对、密钥状态几乎全部落在 SQLite（`~/.openclaw/state/openclaw.sqlite`）里，一个链接了有 WAL 重置漏洞的 SQLite 库的 Node 运行时，足以在高并发写入下悄悄损坏这个状态库。这也是为什么安装脚本宁可多花几步去校验“你这个 Node 实际链接的 SQLite 是不是安全版本”，而不是只看 `node --version` 的数字。

### `openclaw onboard --install-daemon`：引导流程做了什么

安装完成后，`README.md` 给出的下一步是：

```bash
openclaw onboard --install-daemon
```

`docs/start/onboarding-overview.md` 把引导阶段拆成了“先建立推理、后配置其余”两段：

> The guided inference phase establishes only:
>
> 1. **Model provider and auth** — detected access or a verified provider sign-in, API key, or token
> 2. **Verified inference** — a real completion on the default agent's effective model
>
> After that completion passes, OpenClaw can configure the workspace, Gateway, Gateway service, channels, agents, plugins, and other optional features.

也就是说，`onboard` 不是一次性把所有配置都写好，而是有一道硬性的“先决条件”：任何模型提供方的选择，都必须先跑通一次真实的补全请求才算数（这条设计我们会在第 4 篇展开）。`--install-daemon` 这个 flag 的作用是让 onboarding 在推理验证通过之后，顺带把 Gateway 安装成后台服务——macOS 上是 LaunchAgent，Linux/WSL2 上是 systemd user unit，原生 Windows 上是 Scheduled Task（`docs/start/getting-started.md`）：

> This installs a LaunchAgent on macOS, a systemd user unit on Linux and WSL2, or a Scheduled Task on native Windows (with a per-user Startup-folder login item as the fallback if task creation is denied).

不加这个 flag 也可以完成 onboarding，只是 Gateway 会停留在前台运行（你在终端里按 Ctrl+C 就会把它杀掉），配置本身照样保存。`getting-started.md` 里对这一点写得很清楚：*“The Gateway runs in this terminal until you press Ctrl+C; your config stays saved.”*——这也印证了 OpenClaw 的一个一贯原则：配置持久化和进程生命周期是两件独立的事，杀掉前台 Gateway 不等于丢配置。

### 验证安装：两条命令，两个层面

安装/引导跑完之后，官方给出的验证方式是两条命令的组合：

```bash
openclaw gateway status
openclaw dashboard
```

`openclaw gateway status` 验证的是“服务层”：`docs/cli/gateway.md` 里说明它默认会同时检查 launchd/systemd/schtasks 这类原生服务状态，以及一次可选的连通性/鉴权探测；健康的基线输出应该是 `Runtime: running`、`Connectivity probe: ok`。`getting-started.md` 补了一个具体期望值：*“You should see the Gateway listening on port 18789.”*——`18789` 是 OpenClaw Gateway 的默认 WebSocket 端口，后面几篇会反复看到这个数字。

`openclaw dashboard` 验证的则是“应用层”：它会打开浏览器里的 Control UI，并且这个过程本身就是一次安全握手。`docs/cli/dashboard.md` 解释了这个“一次性配对链接”的机制：

> Open the Control UI with a short-lived, one-time owner pairing link. A successful handoff gives that signed browser a durable administrator device credential, so reopening the dashboard does not depend on the shared Gateway token.

换句话说，`openclaw dashboard` 不只是“打开一个网页”，它是在给这个浏览器颁发一枚长期有效的管理员级设备凭证，之后这个浏览器再打开 Control UI 就不再依赖共享的 Gateway token。`getting-started.md` 给的最终验收标准也很朴素：“Type a message in the Control UI chat and you should get an AI reply.”——发一条消息、收到回复，才算这一章真正走完。

### 一台宿主机，一个 Gateway

这条原则在多处文档里被反复强调，不是随口一提的建议，而是贯穿整个安全模型的前提。`README.md` 的架构一句话概括是：*“the same gateway runs as a personal assistant on one laptop or as a shared team deployment”*——注意措辞是“the same gateway”，而不是“多个 gateway 协同”。`SECURITY.md` 在信任模型一节写得更直白：

> Recommended mode: one user per machine/host (or VPS), one gateway for that user, and one or more agents inside that gateway.
> ... OpenClaw can technically run multiple gateway instances on one machine, but recommended operations are clean separation by trust boundary.

`docs/gateway/index.md`（Gateway 运维手册）也重申了同一件事：“Most installs should run one gateway per machine. A single gateway can host multiple agents and channels. You only need multiple gateways when you intentionally want isolation or a rescue bot.” 也就是说，“多加几个 agent”从来不是“多起几个 Gateway”的理由——一个 Gateway 内部本来就可以承载多个 agent、多个 channel。这条原则会在第 03 章讲 Gateway 架构时被反复引用，因为它直接决定了会话、鉴权、状态存储都以“每 Gateway 一份”为单位设计。

### 不想用命令行：桌面 App 也是一种“安装”

如果你更习惯普通应用那样点开安装、而不是敲终端命令，OpenClaw 也提供了原生桌面客户端。`docs/install/index.md` 列出了两条路径：

> - **Windows**: the Windows Hub companion app — a signed installer you download and run like any Windows app, with setup, tray status, chat, and node mode.
> - **macOS**: the macOS menu bar app — download the `.dmg` (preferred) or `.zip` asset, then install and launch **OpenClaw.app**.
>
> Both desktop apps can provision a local Gateway during first-run setup, or connect to an existing remote Gateway.

这句话里“provision a local Gateway during first-run setup, or connect to an existing remote Gateway”值得留意——桌面 App 本身不是 Gateway 的替代品，它要么在首次启动时帮你在本机拉起一个 Gateway，要么直接连接一个已经在别处跑着的 Gateway。这再次印证了本篇反复强调的一点：不管入口是 CLI、网页仪表盘还是原生 App，Gateway 才是真正承载状态和逻辑的那一个进程，其余的都只是“怎么把它跑起来、怎么连上它”的不同方式。

### 校验安装本身：一组更基础的自检命令

`openclaw dashboard` 验证的是“整个链路能不能正常对话”，但如果连 CLI 本身是否装对都不确定，`docs/install/index.md` 给出了一组更基础的自检：

```bash
openclaw --version      # confirm the CLI is available
openclaw doctor         # check for config issues
openclaw gateway status # verify the Gateway is running
```

`openclaw doctor` 值得单独说一句：它不只是“报错”，很多历史遗留的配置写法（比如老版本的字段名）会被它自动识别并给出修复建议，`openclaw doctor --fix` 甚至可以直接应用这些修复。VISION.md 里专门强调了这条工程纪律：“When a config change makes existing user config invalid, the same change needs a doctor migration. `openclaw doctor --fix` should detect the old shape, explain it, back it up when needed, and rewrite it to the canonical format.”——也就是说，配置格式的每一次破坏性变更，都必须配一条自动迁移路径，这也是为什么升级 OpenClaw 通常不需要担心手工修复配置文件。

## 常见问题/易踩坑

- **在 npm 11.15 及更早版本上也加了 `--allow-scripts=openclaw`**：这个参数在旧版本 npm 上根本不存在这套脚本审批机制，加了反而可能报错或被忽略；按官方说明，npm 11.15 及更早版本应该省略这个参数。
- **以为装了一次 Gateway 服务，多加几个 agent 就该再装一个 Gateway**：不需要，一个 Gateway 本来就能承载多个 agent 和多个 channel；只有明确需要隔离（比如给不同信任边界的用户分别提供服务）时才考虑多 Gateway，而且要各自配置独立的端口、状态目录和 workspace。
- **`openclaw gateway status` 显示服务在跑，就以为安装完全成功**：这只证明了“服务层”健康，真正验证“模型能不能正常应答”要靠 `openclaw dashboard` 打开 Control UI 并实际发一条消息，两层缺一不可。

## 小结

一键安装脚本的价值不在于省掉了几条命令，而在于它把“Node 运行时安全→OpenClaw 本体安装→推理验证→Gateway 服务化”这条有严格先后依赖的流水线固化了下来；`openclaw onboard --install-daemon` 之所以要先跑通一次真实补全再谈其余配置，也是因为 OpenClaw 把“Gateway 是唯一控制平面”当成了整个安全与架构设计的起点。下一篇会把镜头从“怎么装起来”转向“装起来之后有哪些入口能跟它对话”——CLI 的整体命令版图、Control UI 和 TUI 各自扮演什么角色，以及它们为什么本质上都只是 Gateway 的客户端。
