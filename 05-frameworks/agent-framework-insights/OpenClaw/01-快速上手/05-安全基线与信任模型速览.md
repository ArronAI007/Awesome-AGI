# 安全基线与信任模型速览

> “Security in OpenClaw is a deliberate tradeoff: strong defaults without killing capability.”——VISION.md 用这一句话给整个项目的安全哲学定了调。这不是一句公关辞令，而是能在代码和文档里逐条对应上的设计取舍：默认值要足够保守，但不能保守到让操作者做不成真正的工作。在深入 Gateway 协议、工具系统、沙箱机制这些具体子系统之前，先把这套“默认值长什么样”的整体地图看清楚，后面每一章讨论具体机制时，都会默认你已经理解了这里建立的信任边界。

## 学习目标

- 理解 VISION.md 里“strong defaults without killing capability”这句话具体对应哪些代码层面的默认值，而不是把它当成一句空泛的口号。
- 记住三条最基础的信任规则：入站消息默认不可信、工具默认在宿主机上跑（除非配置沙箱）、Gateway 鉴权对本地和远程连接一视同仁。
- 理解 OpenClaw 的“一个信任边界”模型：已鉴权的 Gateway 调用方被视为可信操作者，而不是需要互相隔离的多租户用户。
- 知道插件在这套模型里的位置——装上即信任，和宿主机上的本地代码拥有同等权限。
- 知道 `openclaw security audit` 这一条命令能做什么，把它当成日常自检的起点。
- 明确本篇只建立整体认知，沙箱机制的具体实现（如何隔离、隔离到什么粒度）留给第 10 章深入。

## 背景与设计动机

理解 OpenClaw 的安全模型，首先要理解它面对的是一类特殊的产品形态：一个能执行 shell 命令、读写文件、访问网络的 AI 助理，同时还要通过公网可达的聊天软件接收陌生人的消息。这两件事放在一起，天然存在张力——能力越强，被滥用或被诱导滥用的代价就越大；但如果处处设防到束手束脚，产品就失去了存在的意义。

VISION.md 把这条张力写得非常直白：

> Security in OpenClaw is a deliberate tradeoff: strong defaults without killing capability. The goal is to stay powerful for real work while making risky paths explicit and operator-controlled.
>
> We prioritize secure defaults, but also expose clear knobs for trusted high-power workflows.

“deliberate tradeoff”（刻意的取舍）这个措辞很关键——它承认安全和能力之间没有免费的完美解，OpenClaw 选择的立场是：默认值站在保守的一侧，但每一条收紧的默认值背后都留一个“开关”，让理解风险的操作者可以主动选择更强的能力。这条哲学在整个产品里反复出现：DM 默认要配对审批，但可以显式配成开放；工具默认在宿主机跑，但可以显式配置沙箱；Gateway 默认只监听回环地址，但可以显式配置对外暴露。理解了这条主线，后面看到的每一条具体规则就都有了落点。

## 核心机制详解

### 第一条基线：入站消息默认不可信

README 的 Security 一节把这条基线放在了最前面：

> Treat inbound messages as untrusted input. DM-capable channels pair unknown senders by default; approve a pairing request with `openclaw pairing approve <channel> <code>`.

SECURITY.md 在“Agent and Model Assumptions”一节把这条基线的逻辑基础讲得更完整——不可信的不只是“发消息的人”，连模型本身在这套威胁模型里都不是一个可信主体：

> The model/agent is **not** a trusted principal. Assume prompt/content injection can manipulate behavior. Security boundaries come from host/config trust, auth, tool policy, sandboxing, and exec approvals. Prompt injection by itself is not a vulnerability report unless it crosses one of those boundaries.

这句话里有一个容易被误读的地方：“prompt injection 本身不算漏洞”并不是说 OpenClaw 不在乎提示注入，而是说——防线不应该寄希望于“模型足够聪明、不会被诱导”，而应该建立在模型之外的、确定性的边界上：鉴权、工具策略、沙箱、执行审批。这也是为什么第 3 篇讲的 DM Pairing 要做成协议层面的强制审批，而不是指望模型自己识别出“这条消息看起来像攻击”再拒绝执行——把安全性寄托在模型的判断力上，本身就不是一条可靠的边界。

### 第二条基线：工具默认在宿主机上跑

这是最容易被低估、也是 SECURITY.md 讲得最直白的一条：

> Tools run on the host for the main session unless you configure sandboxing.

对应到具体配置项，SECURITY.md 的“Operator Trust Model”一节给出了确切的默认值：

> Exec behavior is host-first by default: `agents.defaults.sandbox.mode` defaults to `off`.
> `tools.exec.host` defaults to `auto`: sandbox when sandbox runtime is active for the session, otherwise gateway.
> Implicit exec calls (no explicit host in the tool call) follow the same behavior.

翻译成人话：除非你显式打开沙箱模式，否则 agent 调用 `exec` 之类的工具，执行的位置就是 Gateway 进程所在的这台宿主机，拥有和你手动在终端敲命令等价的权限。这不是一个隐藏的疏漏，而是被 SECURITY.md 明确写进“预期行为”里的默认值——报告“host-side exec when sandbox runtime is disabled”这类现象，在官方的安全响应流程里会被直接归类为“documented default behavior”，不算漏洞。这条基线也解释了为什么 README 会把这句提醒和“安全指南、暴露手册、沙箱指南”的链接放在一起：一旦你打算让其他人接触这个 agent，或者把 Gateway 暴露到本机之外，理解“工具默认跑在哪”就成了前置作业。

### 第三条基线：Gateway 鉴权对本地和远程一视同仁

第 2 篇提到过，Control UI 直连本机 Gateway 也逃不过 token/password 校验。macOS 应用引导文档把这条设计原则讲得更明确：

> Gateway auth mode defaults to `token` even for loopback binds, so local WS clients must authenticate.
> Setting `gateway.auth.mode: "none"` lets any local process connect; use that only on fully trusted machines.

也就是说，“这是我自己的电脑，应该默认信任”这种直觉在 OpenClaw 里是被刻意打破的——即便 Gateway 只监听 `127.0.0.1`，默认也要求 token 鉴权，`auth.mode: "none"` 是一个需要显式选择的例外，而不是本机场景下的隐式默认。SECURITY.md 在“Web Interface Safety”一节给出了对应的部署建议：

> Recommended: keep the Gateway **loopback-only** (`127.0.0.1` / `::1`). Config: `gateway.bind="loopback"` (default).
> Do **not** expose it to the public internet (no direct bind to `0.0.0.0`, no public reverse proxy). It is not hardened for public exposure.
> If you need remote access, prefer an SSH tunnel or Tailscale serve/funnel (so the Gateway still binds to loopback), plus strong Gateway auth.

### 一个信任边界，而不是多租户隔离

理解 OpenClaw 安全模型时最容易带偏的一个预设，是把它想象成一个需要在互相不信任的用户之间做隔离的多租户系统。SECURITY.md 在开篇就纠正了这个预设：

> OpenClaw is local-first agent infrastructure for trusted operators; it is not designed as a shared multi-tenant boundary between adversarial users on one gateway.

“Operator Trust Model”一节把这条原则落到了具体的鉴权语义上：

> OpenClaw does **not** model one gateway as a multi-tenant, adversarial user boundary.
> Authenticated Gateway callers are treated as trusted operators for that gateway instance.
> ... Session identifiers (`sessionKey`, session IDs, labels) are routing controls, not per-user authorization boundaries.
> If one operator can view data from another operator on the same gateway, that is expected in this trust model.

推荐的部署形态因此是“一个信任边界一个 Gateway”：

> Recommended mode: one user per machine/host (or VPS), one gateway for that user, and one or more agents inside that gateway.
> If multiple users need OpenClaw, use one VPS (or host/OS user boundary) per user.

这条原则和第 1 篇提到的“一台宿主机一个 Gateway”是同一枚硬币的两面——不仅是运维上的推荐做法，更是安全模型能够成立的前提：一旦某个人通过了 Gateway 的鉴权，他就被当作这个 Gateway 的可信操作者，而不是被进一步细分权限的“某个租户”。如果需要在互相不信任的人之间做隔离，答案不是在同一个 Gateway 内部加隔离逻辑，而是拆成多个 Gateway、多个 OS 用户甚至多台主机。

这条边界延伸到了共享 agent 的场景。“One-User Trust Model”一节指出，多个人共享同一个配了工具的 agent（比如一个共享的 Slack 工作区），意味着这些人共享了这个 agent 被授予的全部工具权限：

> If multiple people can message the same tool-enabled agent (for example a shared Slack workspace), they can all steer that agent within its granted permissions.

### 插件是受信任计算基的一部分

第 3 篇提过 Channel 有 bundled/official/external 三种打包方式，但不管来自哪一层，一旦被装载进 Gateway 进程，插件在信任模型里的地位是完全一致的——SECURITY.md 把这条讲得毫不含糊：

> Plugins/extensions are part of OpenClaw's trusted computing base for a gateway.
> Installing or enabling a plugin grants it the same trust level as local code running on that gateway host.
> Plugin behavior such as reading env/files or running host commands is expected inside this trust boundary.

这意味着“装一个插件”这个动作本身，在安全语义上等价于“往这台机器上添加一段拥有本地代码权限的程序”——不存在某种沙箱把插件天然圈在一个更弱的权限范围里。这也是为什么 VISION.md 会强调“Preferred plugin path is npm package distribution... If you build a plugin, host and maintain it in your own repository”，以及为什么 SECURITY.md 建议“prefer `plugins.allow` to pin explicit trusted plugin ids”——既然装上就等于信任，那么“装了哪些插件”这件事本身就应该被当作一份需要审视的信任清单，而不是随手加加看看。

### 共享 Agent 里的“责任”，是尽力而为而不是硬保证

SECURITY.md 单独用一节“Shared Agents”讲了一条容易被忽视的推论：能操作一个 agent 的人，就能让它做这个 agent 能做的任何事，会话的归属、可见性、在线状态都只是可用性层面的便利功能，不是安全边界：

> Anyone who can operate an agent can make it do anything that agent can do. Session ownership, visibility, and presence are usability features, not security boundaries. Turn attribution is best-effort because steering can merge input into an active turn. Use separate agents or separate gateway/host trust boundaries when operators need real isolation.

“Turn attribution is best-effort”这句话值得多想一层：如果一次对话轮次中途被另一个操作者的输入“引导”介入，系统只能尽力标注是谁说了什么，而不能给出一个无法伪造的强保证。这再次印证了前面反复出现的结论——真正的隔离从来不是靠某个软性的归属标签，而是靠拆分成不同的 agent、不同的 Gateway 或不同的宿主机。

### 一条命令，体检一次

前面几条都是静态的默认值，`openclaw security audit` 则是把这些默认值和你实际配置之间的差异找出来的工具。`docs/gateway/security/index.md` 概括了它的检查范围：

> - **Inbound access** - DM/group policies, allowlists: can strangers trigger the bot?
> - **Tool blast radius** - elevated tools + open rooms: could prompt injection become shell/file/network actions?
> - **Network exposure** - Gateway bind/auth, Tailscale Serve/Funnel, weak/short auth tokens.
> - **Local disk hygiene** - permissions, symlinks, config includes, synced-folder paths.
> - **Plugins** - loading without an explicit allowlist.

同一份文档给出的排查优先级也值得记下来，作为日常自检的顺序参考：

> 1. Anything "open" + tools enabled: lock down DMs/groups first (pairing/allowlists), then tighten tool policy/sandboxing.
> 2. Public network exposure (LAN bind, Funnel, missing auth): fix immediately.
> 3. Browser control remote exposure: treat like operator access (tailnet-only, pair nodes deliberately, no public exposure).
> 4. Permissions: state/config/credentials/auth must not be group/world-readable.
> 5. Plugins: load only what you explicitly trust.

`--fix` 参数会应用一部分“安全”的自动修复（把开放的群组策略收紧为白名单、把状态/配置文件权限修正为 `600`/`700`），但它是“intentionally narrow”——不会替你做需要理解业务上下文的判断，比如要不要开放某个 DM 策略。

### 报告安全问题时，先分清“这是不是一个边界被突破”

SECURITY.md 用了相当大的篇幅列举“通常不算漏洞”的模式，核心判断标准出现了很多次：是否有一条**已记录的信任边界**被绕过（鉴权、审批、沙箱、白名单），而不是单纯“某个强大的能力被使用了”。比如，一个已认证的操作者故意使用一个本地 shell 功能、或者一个受信插件在被安装后执行了本地命令，这些都被明确列为“预期内的可信操作者行为”，而不是漏洞。这条标准和本篇的主线是同一件事——先划清“谁是可信操作者、工具默认跑在哪、鉴权覆盖到哪些连接”，才能判断一个具体现象究竟是在预期之内，还是真正突破了边界。

## 常见问题/易踩坑

- **把“我的电脑只有我自己用”当成 Gateway 可以不设鉴权的理由**：即便是纯本机场景，默认的 `token` 鉴权模式依然生效，`gateway.auth.mode: "none"` 是一个需要你显式选择、且官方明确提示“only on fully trusted machines”的例外，不是本机场景的隐式默认。
- **把“工具默认在宿主机跑”误当成一个可以直接上报的漏洞**：这是 SECURITY.md 明确写下的预期默认行为，真正需要处理的是“要不要为这个 agent 打开沙箱”，而不是把默认值本身当作缺陷去报告。
- **以为同一个 Gateway 上的不同 session/操作者之间存在租户级隔离**：不存在，`sessionKey` 只是路由标识，不是鉴权边界；如果确实需要隔离互不信任的人，唯一支持的做法是拆分成独立的 Gateway、独立的 OS 用户或主机。

## 小结

OpenClaw 的安全默认值可以归纳成三句话：入站消息不可信，所以陌生发送者要先过配对这道闸；工具默认跑在宿主机上，所以要不要隔离是一个需要主动做出的选择而不是隐藏的疏漏；Gateway 鉴权不区分本地远程，一视同仁地把“通过鉴权”等同于“可信操作者”——而不是搭建一套多租户式的细粒度权限体系。这三条基线，加上“插件即信任”和“一次 `security audit` 体检”这两个操作性工具，构成了在深入任何具体子系统之前就应该建立起来的整体认知。下一章会把镜头从“怎么用起来、默认值是什么”切换到“这个项目本身是怎么被组织和构建出来的”——拆开这个 pnpm monorepo 的仓库全景，看看 `src/`、`packages/`、`extensions/`、四个原生 App 分别承担什么角色，以及这套规模巨大的代码库背后的工程实践。
