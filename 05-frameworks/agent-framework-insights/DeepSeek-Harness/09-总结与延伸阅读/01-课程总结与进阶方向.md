# 课程总结与进阶方向

> 回顾整套课程串起了 DeepSeek Harness(`dsh`)的哪些层次,把它放到 Claude Code / Codex CLI / `pi` 这个坐标系里看看架构哲学的差异,老实聊一聊这套重框架路线的代价,最后给出几条继续深入的路径。

## 学习目标

- 用一张分层地图把前面九章讲过的所有主题重新串成一个整体心智模型,而不是九篇互相独立的笔记。
- 理解 dsh 在架构哲学上相对于 Claude Code / Codex CLI / `pi` 的独特之处——以及这种独特性从何而来、边界在哪里。
- 直面这套架构选择带来的真实成本,不只是复述"优点"。
- 拿到几条可以直接上手的进阶阅读路径和练习方向,知道接下来该点开哪个文件、哪篇文档。

## 全景回顾:一张分层地图

如果把这九章内容压缩成一张图,大致是这样的(从入口到内核,再到能力扩展与跨语言边界,最后落到治理规则):

```
┌───────────────────────────────────────────────────────────────┐
│ 入口层        CLI(apps/cli) / Web UI(packages/client 40+ 叶子包) │  01 章
│              Profile 装配、Provider 配置、权限预设                │
├───────────────────────────────────────────────────────────────┤
│ 工程地图层     219 个可发布叶子包 / 49 个能力分类目录               │  02 章
│              pnpm workspace、Host / Client 双面构建、CI 门禁      │
│              vendoring 治理(vendor/ 下的 Cordis 生态)             │
├───────────────────────────────────────────────────────────────┤
│ 框架基石层     Cordis:Context / Service / Plugin / Typed Events │  03 章
│              Profile → Bundle → Preset 的装配链路                │
├───────────────────────────────────────────────────────────────┤
│ Agent 内核层   ReactLoopAgent 的 kick → turn → step             │  04 章
│              事件溯源会话日志、流式管道、上下文压缩、错误重试与取消     │
├───────────────────────────────────────────────────────────────┤
│ 能力扩展层     Capability Seam 三元结构                          │  05 章
│              (抽象座 Service Definition / 实现 Provider / 消费者 Tool)│
│              工具注册与执行管线、权限审批与多沙箱后端、内置工具全解析    │
├───────────────────────────────────────────────────────────────┤
│ 跨语言与部署层  native/landlock-run(纯 C11)、python/sdk(NDJSON-RPC)│  06 章
│               Host/Client Typert 类型安全 RPC、SDK-ACP、Hooks 兼容 │
├───────────────────────────────────────────────────────────────┤
│ 编排层        Subagent 委派、Workflow 引擎与 Ralph 循环             │  07 章
│              Skill 技能系统与动态插件自举                          │
├───────────────────────────────────────────────────────────────┤
│ 治理层        测试哲学(per-file 100% 覆盖率)、AGENTS.md 强制规范     │  08 章
│              Postmortem 文档体系、防御性编程模式                    │
└───────────────────────────────────────────────────────────────┘
```

### 这张图想说明的一件事

dsh 不是"一个 Agent 循环外面裹了一层壳",而是**先把一套通用插件框架(Cordis)立起来,再用同一种三元结构(座/实现/消费者)把几十个能力域都摆进这套框架里,Agent 循环本身只是这套框架里的一个消费者**。

这也是为什么课程要专门用第 03 章讲 Cordis——如果跳过它直接看第 04～07 章,会发现每个能力域的代码都长得很像"依赖注入 + 事件系统",但看不懂为什么大家都长这个样子。反过来,08 章讲的治理规则(逐文件覆盖率、Registrations-are-effects、Model-visible⟺logged)不是空喊口号,它们是能撑住"几十个能力域各自独立演化、还能互相插拔"这套复杂度的配套设施——没有严格的治理,插件化架构很容易演变成"表面模块化、实际互相耦合"的烂摊子。

### 图里每一层对应的"如果只记一句话"

- **入口层**:用户看到的只是 CLI 或网页,但背后已经在跑 Profile 装配——这是理解后面所有章节的第一道门槛,因为几乎所有能力都是"按 Profile 决定装不装"而不是"写死在代码里"。
- **工程地图层**:两级目录(一级分类、二级叶子包)不是随意的文件组织,是"能力座与实现分离"这条架构原则在文件系统上的直接投影。
- **框架基石层**:Context/Service/Plugin 这三个词一旦在脑子里成型,后面看到的所有 `ctx.xxx` 都不再是魔法,而是"某个服务契约被某个 Provider 满足了"。
- **Agent 内核层**:会话是 append-only 的事件日志,消息历史是从日志派生出来的视图,不是被单独维护的另一份状态——这条设计决策贯穿了压缩、Checkpoint、重试的所有实现细节。
- **能力扩展层**:座/实现/消费者三元结构第一次出现在 03 章是抽象概念,到 05 章变成具体的、可以在几十个包里反复认出来的代码形态。
- **跨语言与部署层**:边界不是"抛个 JSON 过去就完事",native 侧是手写系统调用的独立可执行文件,Python 侧是把整套 Node 运行时打成单文件 exe 当子进程用。
- **编排层**:子代理、Workflow、Skill 三者都在回答同一个问题——"一个 Agent 不够用的时候,复杂度应该以什么形式被组织起来",答案分别是"再开一个 Agent""写一段编排脚本""按需加载一份技能包"。
- **治理层**:所有前面的灵活性,都是靠这一层的强制规则(而不是靠自觉)撑住的。

值得说明一点:第 05 章之后的很多细节(比如各个 Provider 具体怎么实现、Workflow 引擎脚本的完整语法)本课程只挑了有代表性的路径讲透,不追求覆盖 219 个叶子包里的每一个——这也是为什么后面会给出"按兴趣分流"的进阶路径,而不是建议每个人都从头读到尾。

## 与同类项目的对比:架构哲学的分野

把 dsh 放进"编码 Agent Harness"这个产品品类里看,几个可比对象是 Claude Code、OpenAI 的 Codex CLI,以及姊妹课程讲的 `pi`。先说清楚边界:本课程没有拿到 Claude Code 和 Codex CLI 的源码做逐行分析,下面关于它们的判断只基于公开可观察的行为、官方文档描述的可扩展机制(hooks、MCP、subagent、skills 之类),以及 dsh 自己选择去兼容它们生态的事实——这部分的确定性明显低于对 dsh 和 `pi` 源码的判断,标了"未深入验证"的地方请读者自行核实。

### dsh vs `pi`:重框架 + 能力 Seam,还是精简核心 + TS 扩展点

这是本课程能给出最有把握的对比,因为两边源码都被系统读过。

| 维度 | `pi` | dsh |
|---|---|---|
| 核心组织方式 | Agent 运行时(`packages/agent`)本身就是最小稳定核心 | Cordis 插件框架先立起来,Agent 循环只是框架里的一个消费者 |
| 能力接入方式 | TypeScript 扩展在生命周期节点挂钩 | 每个能力域拆成"抽象座 + Provider + 消费者"三元结构 |
| 多模型差异 | 收敛成一层统一适配接口(`packages/ai`) | 同样收敛成 LLM 能力座,但作为几十个能力域中的一个,不是特例 |
| 安全隔离 | 不做进核心,交给外部容器化(Gondolin/Docker/OpenShell) | 直接做成核心的一部分:sandbox mode + approval policy + permission preset 三个旋钮 |
| 会话持久化 | JSONL 追加写入,天然支持分支 | append-only 事件日志,消息历史从日志派生,压缩靠"替换 surface 区间"而非删除日志 |
| 包的规模感 | 十余个包,基本能整体记在脑子里 | 219 个叶子包分布在 49 个分类目录下,需要专门的导航约定 |

两条路线不是谁更"对",而是对"复杂度放在哪里"给出了不同答案——`pi` 把复杂度尽量推到核心之外,核心本身可以在一次坐下阅读里看完;dsh 把"如何组织复杂度"这件事本身框架化了,代价是必须先学会这套框架,好处是几十个能力域被迫用同一种语言描述,新增一个能力域时"该怎么拆"这个设计问题已经被框架提前回答掉了。

如果只用一句话总结:`pi` 证明了"核心极简 + 外围可插拔"也能撑起一个功能完整的编码 Agent;dsh 证明了"把插件化本身框架化,套用到几十个能力域"也能撑起一个功能更庞杂、生态野心更大的编码 Agent——两者都成立,选哪条路取决于你更看重"新人多快能看懂核心"还是"几十人团队同时改几十个能力域时会不会互相踩脚"。

### dsh vs Claude Code / Codex CLI:插件框架内置,还是留出集成缝隙

从 dsh 第 06 章讲到的"兼容 Claude Code / Codex 的 Hooks 生态桥接层"能看出一件事——dsh 团队显然认为 hooks 这种"在关键节点插入外部脚本"的集成模式已经是这类工具的事实标准,值得专门做一层兼容适配,而不是要求生态迁移到 dsh 自己的插件写法上。

这从侧面说明,Claude Code / Codex CLI 对外暴露的扩展面,给人的感觉更接近"在一个相对封闭的核心外面开若干个标准化的钩子",而不是像 dsh 这样把"整个运行时都是插件"作为架构起点。但这只是一个基于集成层设计做出的推断,本课程**没有**深入验证 Claude Code / Codex CLI 内部是否也存在类似 Cordis 的插件内核——它们完全可能在内部也有一套自己的抽象层,只是没有对外暴露成"用户可以直接写插件替换任意能力域"的样子。这一点留给读者自己去查证,不在这里下结论。

能确定的是:dsh 选择主动兼容它们的生态约定(而不是反过来要求生态适配 dsh),这本身释放了一个信号——一个 developer preview 阶段的新项目,即便架构上足够激进,在"如何不让已有用户觉得陌生"这件事上依然是务实的。

## 这套架构的代价与权衡

彻底剖析不能只挑好听的说,dsh 这套选择也有实打实的代价,课程在讲具体机制时基本没展开讲,这里集中说一下。

### Cordis 学习曲线是真实存在的门槛

Context / Service / Plugin / Typed Events 这套心智模型,对一个只想"加个新工具"的开发者来说是额外的一层抽象——`pi` 的读者理论上可以直接打开 Agent 主循环的源码从头读到尾,dsh 的读者必须先在第 03 章把 Cordis 的四个核心概念嚼透,否则后面看到的每一段"能力扩展"代码都只是"看起来像依赖注入,但说不清楚为什么这么写"。这不是三言两语能省略的一步,课程专门用一整章去打这个基础,本身就是这个代价的证明。对于团队里经验较浅的成员,这道门槛意味着"能独立改一个新能力域"和"刚入职能看懂代码"之间会有明显的时间差。

### Host/Client 强制类型分离,换来干净边界,也换来额外构建流程

两个独立的 TS Program 避免了 Cordis Context 类型污染到浏览器端,这个设计意图是清晰且合理的;但代价是任何跨越 Host/Client 边界的新功能,都必须走"定义 RPC 契约 → 用 Typert 生成代码 → Host/Client 两侧各自实现"这一整套流程,比在单一 TS Program 里直接共享类型定义要慢、要多一层心智负担。对于一个还在 developer preview 阶段、迭代速度诉求很高的项目,这笔账值不值,见仁见智——它更像是"提前为规模化付了一笔保险费",在包和团队规模还小的阶段,这笔保险费的性价比不一定划算。

### 逐文件 100% 覆盖率的门槛,连它自己都要开例外

`AGENTS.md` 里写得很直接:`pnpm run test:coverage` 是 CI 覆盖率门禁,`packages/*/*/src` 逐文件 100%。但从 `vitest.config.ts` 引用的 `scripts/coverage-exempt.ts` 能看到,项目专门维护了一份"重量级测试套件豁免名单"——意味着这条规则并非没有代价的免费午餐,一些集成性很强、跑起来很"重"的测试确实很难无脑塞进逐文件 100% 的框架里,只能开豁免通道来平衡覆盖率诉求和 CI 时长。这条规则值得学,但落地时要有心理预期:它会明显拖慢一部分改动的合入速度,团队需要不断维护"哪些确实该豁免、哪些是在偷懒"的边界,这本身也是一项持续的治理成本。

### 219 个叶子包的导航成本,是一种隐性认知负担

相比 `pi` 十几个包基本能整体记在脑子里,dsh 想找一个具体实现,先要弄清楚"应该去哪个分类目录、这个能力域下哪个后缀对应哪种实现"——`-local`、`-sandbox`、`-e2b`、`tool-*` 这类命名约定需要专门学习才能不靠猜。这在工具链完善(IDE 跳转、`ripgrep`)、且已经熟悉命名规则的团队内部问题不大,但对第一次进入这个仓库的新人,确实需要额外的适应期,这也是课程要专门用第 02 章讲"仓库全景"的原因——如果没有这张地图,新人大概率会在 `packages/` 目录下迷路很久才能找到自己要改的那一个包。

### developer preview 阶段的现实:社区目前只能"用",不能直接"改核心"

`CONTRIBUTING.md` 写得很坦白:项目还在早期阶段,暂不接受外部 PR,鼓励的贡献方式是写插件、写教程、在生态层面参与,而不是给核心仓库提交代码。这对本课程读者是一个务实的提醒:如果学完这套架构是想给 dsh 核心贡献代码,目前这条路暂时走不通;更现实的路径是把学到的设计范式用在自己的项目里,或者在 `dsh-plugin` 这个生态标签下做点什么。这也意味着,dsh 现阶段的"重框架"投入,更多是团队自己在为未来的规模化下注,外部读者暂时只能旁观和借鉴,还谈不上共建。

## 延伸阅读与一手资料

- 仓库根目录治理文档:`AGENTS.md`(强制规则,包括覆盖率门禁、Registrations-are-effects、Model-visible⟺logged)、`CONTRIBUTING.md`(贡献边界)、`THIRD_PARTY_NOTICES.md`。
- Cordis 框架本身:`vendor/cordis` 源码,以及 `docs/cordis-tutorial/`、`docs/cordis-api/` 两组文档。
- 子系统级设计文档:`docs/subsystems/*.md`,覆盖 core、session、approval、typert、goal、attachment 等几十个子系统,是比源码注释更系统的一手资料,且由脚本从源码同步生成,基本不会和代码脱节。
- Cookbook 系列(`docs/cookbook/`):`adding-a-tool.md`、`adding-a-package.md`、`adding-a-vendored-package.md`、`adding-an-llm-adapter.md`、`extension-cookbook.md` 等,是"我要做 X,该 touch 哪些文件"这类问题最直接的答案。
- Postmortem 系列(`docs/postmortem/`):目前公开的几篇涵盖 ACP 默认导出丢失注入、JS 表达式意外关闭文件系统工具、Web Agent GUI 反馈闭环、Landlock 部分通知误判子进程失败——比任何架构文档都更真实地展示"设计决策为什么长这样"。
- 跨语言边界的落地代码:`native/landlock-run`(纯 C11)、`python/sdk` 与 `python/sdk-runtime`(单文件可执行运行时的部署根)。
- 安全模型相关包:`packages/sandbox/{sandbox,sandbox-local,sandbox-policy,sandbox-windows-acl}`、`packages/e2b`、`packages/interaction/{permission-presets,user-approval}`。

## 进阶阅读路径:按兴趣分流

不同方向的读者,接下来值得优先点开的东西不太一样,不建议每个人都从头读到尾:

- **想写新工具的人**:回头精读第 05 章提到的 Capability Seam 三元结构在某一个具体能力域(比如 `packages/fs`)里的落地,然后打开 `docs/cookbook/adding-a-tool.md`——它就是按"写一个新工具需要 touch 哪些文件"的顺序组织的,比反过来从源码里摸索效率高得多。
- **想理解安全模型的人**:重点看 `packages/sandbox/` 下的几个叶子包和 `packages/e2b`,再对照 `native/landlock-run` 的纯 C 实现感受一下"为什么这一个后端要单独拿出来手写系统调用"。`docs/postmortem/0004-landlock-partial-notice-misclassified-child-failures.md` 值得专门读一遍——它记录了一次真实的沙箱边界误判事故,比任何设计文档都更能说明"安全模型的边界条件到底有多难界定对/错"。
- **想理解权限审批交互的人**:`packages/interaction/permission-presets` 和 `packages/interaction/user-approval` 两个包,配合前端的 `packages/client/ui-permission-presets`,能看到"一次性升级授权"这个机制从后端到前端是怎么串起来的。
- **想给自己产品引入类似架构的人**:不要直接抄 dsh 的能力域拆分,应该从 Cordis 框架本身入手——先在一个小项目里把 Context / Service / Plugin 三个概念用透,再考虑要不要把"座/实现/消费者"三元结构套到自己的能力域上。跨语言边界部分,`packages/typert` 是理解"如何在编译期生成类型安全 RPC"的最小切入点。
- **想搞清楚 dsh 是怎么一步步变成现在这样的人**:把 `docs/postmortem/` 整个系列读完,很多看起来"故意设计成这样"的防御性代码,其实是从某一次真实故障里长出来的。

## 进阶练习方向

几个可以直接动手、不需要等所有章节都写完就能开始的练习:

1. **画一张事件溯源时序图**:挑 Agent 内核层(04 章)提到的 `kick → turn → step` 驱动路径,不看源码先凭记忆画一遍,再回头对照实际代码检查遗漏的分支(重试、取消、压缩触发时机)。
2. **写一份"假想 Provider 需要实现哪些接口"的清单**:选一个能力域(比如会话存储或凭证管理),读它的抽象座包,列出如果要新增一个假想的 Provider(比如把会话存到别的存储引擎),必须实现哪些方法——不必真正写代码,重点是理清"座"定义的契约边界。
3. **追一次跨 Host/Client 的调用链路**:找一个具体的前端交互(比如某个设置项的保存),从 `packages/client` 侧的调用一路跟到 Typert 生成的契约,再跟到 `packages/host` 侧的实现,画出完整的调用链路图。
4. **读一篇 Postmortem 并还原因果链**:选 `docs/postmortem/` 里任意一篇,尝试用自己的话画出"设计假设 → 触发条件 → 表现出的症状 → 根因 → 修复方案"这条链路,再对照原文检查理解是否准确。
5. **本地跑一次覆盖率门禁,感受一下代价**:克隆仓库后跑一次 `pnpm run test:coverage`,观察它对某个你故意改动过的文件是怎么报告缺口的,体会一下"逐文件 100%"在真实项目里到底是什么感觉,而不是只停留在文字描述上。

## 小结

00 章开篇说,这套课程的目标是"从会用到懂原理,最终具备阅读、扩展、甚至改造这套编码 Agent 引擎的能力"。走到这里,如果前面九章的内容基本跟下来了,应该已经具备了这个能力的大部分要素——能看懂 Cordis 的插件语言,能在几十个能力域里认出同一套三元结构,能大致判断一次改动应该动 Host 侧还是 Client 侧,也知道去哪找工具、找沙箱实现、找故障复盘。

dsh 这套架构最值得记住的,不是它某一个具体的技术选型(用 Cordis、用 Typert、用 Landlock),而是它展示了"把插件化本身当作一个可以被框架化、被推广到几十个能力域的设计问题"这件事是可行的——代价也是真实的,上一节已经老实聊过。读懂这套代码,拿到的不只是一个开源 Agent 项目的使用手册,更是一份"当系统复杂度注定要变大时,可以怎么组织复杂度"的参考答案之一。它不是唯一的答案——`pi` 那份"核心精简"的参考答案同样成立——但正因为两条路线都真实存在、都能跑起来,对照着读才更有意思。

希望这套课程能帮你把这份参考答案读懂、用上,也希望你在自己的项目里,能更清醒地在"重框架"和"精简核心"之间做出适合自己团队的选择,而不是盲目照抄任何一边。Into the unknown——这是 dsh 团队自己在 `CONTRIBUTING.md` 结尾留下的一句话,拿来作为这套课程的结尾也挺合适。
