# 权限预设与个性化配置

> "沙箱模式"和"审批策略"在 `dsh` 里从来不是一个开关，而是两个完全独立、可以任意组合的旋钮：`sandbox` 决定工具能碰哪些文件，`approval` 决定敏感操作要不要先问人。`workspace-write`、`danger-full-access` 这些"预设"只是把这两个旋钮打包成用户可见的几个常见组合，本质上是一层"体验糖衣"，而不是权限系统本身。理解这层解耦，才能看懂为什么切换一个预设背后其实触发了两次独立的会话事件。

## 学习目标

- 理解 `SandboxMode`（`read-only`/`workspace-write`/`danger-full-access`）和 `ApprovalPolicy`（`ask`/`never`）是两个正交的独立配置，`permission-presets` 只是把它们打包成用户可选的预设。
- 读懂 `PermissionPresetService` 如何把"选中一个预设"翻译成两条独立的会话事件（`sandbox/mode` + `approval/policy`），以及"自定义组合"（`custom`）状态怎么被识别出来。
- 理解 `ApprovalService.request()` 的完整决策路径：`never` 策略如何在分发事件之前就短路决策，`ask` 策略如何通过 Cordis 的 waterfall 事件征询已注册的应答者。
- 知道 `/permission` 命令的作用，以及权限预设的默认值实际来自 `dsh-base` 的 `cordis.patch.yml`，而不是 `permission-presets` 包自己内置的默认表。
- 了解 `cordis.yml`/`cordis.patch.yml` 补丁机制里 `!!js` 表达式如何让权限默认值随部署环境变量变化。

## 背景与设计动机

一个编码 Agent 能执行 shell 命令、改写文件，如果"允许它做什么"和"要不要在做之前问一下人"被绑在同一个开关上，产品能提供的组合就会非常有限——要么完全信任、要么完全不信任，中间状态很难表达（比如"允许它随便读写工作区文件，但涉及工作区之外的路径必须先问我"）。`dsh` 的答案是把这两个维度彻底拆开成两个独立的能力 Seam：`packages/sandbox/sandbox` 只回答"这次执行的文件效应范围是什么"，`packages/interaction/user-approval` 只回答"这次操作要不要先问人"。`permission-presets` 是在这两者之上叠的一层，用来把几种常见组合（比如"工作区可写 + 遇到升级请求就问"）暴露成用户点一下就能切换的选项，但底层写入的永远是两条独立的知识。

## 核心机制详解

### 两个正交的旋钮：`SandboxMode` 与 `ApprovalPolicy`

沙箱模式的完整词汇表只有三个值：

```typescript
// packages/sandbox/sandbox/src/index.ts
/**
 * File-effect policy for confined processes. `read-only` permits only required
 * sinks such as `/dev/null`; `workspace-write` also permits the workspace and a
 * backend-defined temp area; `danger-full-access` bypasses confinement. Network
 * and process visibility are outside this vocabulary.
 */
export type SandboxMode = 'read-only' | 'workspace-write' | 'danger-full-access'
```

它只回答"文件效应"这一个维度（网络访问、进程可见性都不在这套词汇表管辖范围内）。真正执行沙箱包裹的是一个抽象 Provider：

```typescript
// packages/sandbox/sandbox/src/index.ts
export abstract class SandboxProvider extends Service {
  /**
   * Wrap `argv` so it executes confined under `policy` on this host; the
   * caller spawns the returned argv in place of its own.
   */
  abstract confine(argv: readonly string[], policy: SandboxPolicy): ConfinedArgv
}
```

`confine()` 的注释特意强调"必须返回真正强制隔离的 argv，或者直接拒绝执行；静默地不加隔离直接放行是被禁止的"——这是一条 fail-closed 的硬约束：没有可用的沙箱后端（比如缺少 bubblewrap、Landlock 内核支持、`sandbox-exec`）时，`confine()` 必须抛出 `SandboxUnavailableError`，绝不能悄悄退化成不隔离直接跑命令。

审批策略的词汇表更简单，只有两个值：

```typescript
// packages/interaction/user-approval/src/index.ts
/**
 * - `'ask'` (the default) — delegate to the composed answerers; with none
 *   composed the chain falls through to the fail-closed `'unavailable'`.
 * - `'never'` — never prompt anyone: every ask resolves `'rejected'`
 *   deterministically. The strict headless stance (CI, unattended runs) ...
 */
export type ApprovalPolicy = 'ask' | 'never'
```

这两套词汇表分别活在 `packages/sandbox` 和 `packages/interaction/user-approval` 两个独立的包里，互不 import 对方——`permission-presets` 是唯一同时认识两者、把它们打包在一起的地方。

### `PermissionPresetService`：把两个旋钮打包成用户可选项

`permission-presets` 包的模块注释直接点明了这层解耦：

```typescript
// packages/interaction/permission-presets/src/index.ts
/**
 * User-facing permission presets over the independent sandbox-mode and
 * approval-policy knobs. A switch records the selected preset, then writes
 * changed knobs through their canonical setters. Execution, prompt narration,
 * and replay keep reading their knob folds. ...
 */
```

一个预设的定义只有两个必填字段：

```typescript
// packages/interaction/permission-presets/src/index.ts
export interface PresetSpec {
  /** The `sandbox/mode` value the preset writes through. */
  sandbox: SandboxMode
  /** The `approval/policy` value the preset writes through. */
  approval: ApprovalPolicy
  name?: string
  description?: string
}
```

包自己的 schema 内置了两个默认预设：

```typescript
// packages/interaction/permission-presets/src/index.ts（节选）
static Config: z<Config> = z.object({
  presets: z.dict(z.object({ ... })).default({
    'workspace-write': {
      sandbox: 'workspace-write', approval: 'ask',
      name: 'workspace-write', description: 'Write inside the workspace and permitted temporary directories; wider retries require approval.',
    },
    'danger-full-access': {
      sandbox: 'danger-full-access', approval: 'never',
      name: 'danger-full-access', description: 'Full file access without approval prompts.',
    },
  }),
  defaultPreset: z.string(),
})
```

但实际跑起来的 `dsh`（`dsh-base` bundle）在这份内置默认之上又叠了一层部署级覆盖,多加了一个 `read-only` 预设，并且把 `sandbox-policy`、`approval` 两个底层服务的默认值绑定到同一个环境变量上：

```yaml
# packages/bundle/base/cordis.patch.yml（节选）
- id: sandbox-policy
  name: '@deepseek-ai/dsh-sandbox-policy'
  config:
    mode: !!js process.env.DSH_PERMISSION_MODE ?? 'workspace-write'
    workspaceRoot: !!js process.cwd()

- id: approval
  name: '@deepseek-ai/dsh-user-approval'
  config:
    policy: !!js "(process.env.DSH_PERMISSION_MODE ?? 'workspace-write') === 'danger-full-access' ? 'never' : 'ask'"

- id: permission
  name: '@deepseek-ai/dsh-permission-presets'
  config:
    presets:
      read-only:
        sandbox: read-only
        approval: ask
      workspace-write:
        sandbox: workspace-write
        approval: ask
      danger-full-access:
        sandbox: danger-full-access
        approval: never
```

这段配置本身就是"预设只是组合糖衣"最直接的证据：`sandbox-policy` 和 `approval` 两个底层服务各自读取同一个 `DSH_PERMISSION_MODE` 环境变量算出自己的默认值,而 `permission` 这一行只是声明了三个"名字 → 组合"的映射表，供用户在运行时切换,并不参与"进程刚启动时默认用哪个组合"的决策——那件事完全是前两行各自独立算出来的。

真正把"切换预设"翻译成会话状态的地方是 `PermissionPresetService.apply`：

```typescript
// packages/interaction/permission-presets/src/index.ts（节选）
private apply(session: Session, name: string, setApproval: (policy: ApprovalPolicy) => void): void {
  const spec = this.resolve(name)
  if (this.current(session.events) !== name) {
    session.append('permission/preset', { preset: name })
  }
  const events = session.events
  if (spec.sandbox !== (effectiveSandboxMode(events) ?? this.ctx.shell.sandboxMode)) {
    setSandboxMode(session, spec.sandbox)
  }
  if (spec.approval !== (effectiveApprovalPolicy(events) ?? this.ctx.approval.config.policy ?? 'ask')) {
    setApproval(spec.approval)
  }
}
```

切一次预设，最多向会话日志追加三条独立事件：`permission/preset`（记录"用户选了哪个预设名字"这件事本身，纯审计用途，从不进入模型看到的上下文）、`sandbox/mode`、`approval/policy`（这两条才是真正被执行侧读取的知识）。**只有真的发生变化的知识才会追加事件**——如果新预设的 `sandbox` 值和当前生效值相同，就不会多写一条 `sandbox/mode`。

反过来，"当前处于哪个预设"是一个纯粹的推导结果，而不是存储值：

```typescript
// packages/interaction/permission-presets/src/index.ts（节选）
private derive(state: KnobState): string {
  const sandbox = state.sandbox ?? this.ctx.shell.sandboxMode
  const approval = state.approval ?? this.ctx.approval.config.policy ?? 'ask'
  const matches = (spec: PresetSpec): boolean => spec.sandbox === sandbox && spec.approval === approval
  if (state.preset !== null) {
    const spec = this.presets[state.preset]
    if (spec !== undefined && matches(spec)) return state.preset
  }
  for (const [name, spec] of Object.entries(this.presets)) {
    if (matches(spec)) return name
  }
  return CUSTOM_PRESET
}
```

如果用户手动把 `sandbox/mode` 和 `approval/policy` 分别调成了预设表里任何一项都对不上的组合（比如自己把沙箱设成 `read-only` 但审批设成 `never`），系统不会报错，而是把当前状态标记成 `CUSTOM_PRESET`（渲染成 UI 上的"Custom"选项）——这正是因为两个旋钮从设计上就是可以独立调整的，预设表只是覆盖了其中几种"常见组合"，不是唯一合法状态空间。

### `ApprovalService`：`ask` 与 `never` 的真实决策路径

审批服务的核心方法 `request()` 有一条明确的前置约束——只能在一个已经打开的 turn 内部发起：

```typescript
// packages/interaction/user-approval/src/index.ts（节选）
async request(req: ApprovalRequest): Promise<ApprovalOutcome> {
  const session = req.agent.session
  if (!hasOpenTurn(session.events)) {
    throw new Error(
      'approval.request() outside an open turn: the approval/asked + approval/decided audit pair '
      + 'must be turn-enclosed ...',
    )
  }
  const id = ApprovalRequestId(randomUUID())
  session.append('approval/asked', { id, toolName: req.toolName, ... })
  const outcome = await this.decide(req, session)
  session.append('approval/decided', { id, outcome })
  return outcome
}
```

每一次询问都会在会话日志里留下一对`approval/asked` + `approval/decided`审计事件——这也是"Model-visible ⟺ logged"规则的延伸：即便审批结果本身不会进模型的对话上下文,它依然必须是可以从日志重放出来的事实。真正的决策在 `decide()` 里，`never` 策略被特意放在**分发任何事件之前**就短路掉：

```typescript
// packages/interaction/user-approval/src/index.ts（节选）
private async decide(req: ApprovalRequest, session: Session): Promise<ApprovalOutcome> {
  const signal = req.signal
  if (signal?.aborted) return 'cancelled'
  // The 'never' policy is decided HERE, before any dispatch: a listener
  // registered with `prepend: true` after this service mounts would sit
  // ahead of any gate LISTENER, so a listener-shaped gate cannot keep the
  // documented promise that 'never' rejects deterministically regardless
  // of registration order — only the service's own request path can.
  if (this.effectivePolicy(session) === 'never') return 'rejected'
  const answer: Promise<ApprovalOutcome> = Promise.resolve().then(
    () => this.ctx.waterfall(
      scopeTarget(this, req.agent), 'approval/request', req,
      () => Promise.resolve<ApprovalOutcome>('unavailable'),
    ),
  ).then(
    outcome => OUTCOMES.includes(outcome) ? outcome : 'unavailable',
    () => 'unavailable',
  )
  ...
}
```

这段注释解释了一个很容易被忽略的设计细节：如果"`never` 拒绝一切"是靠注册一个优先级最高的事件监听器来实现的，那么任何后来注册了 `prepend: true` 的监听器理论上都可能插到它前面,让"`never` 绝对拒绝"这个承诺被绕开。所以这条判断被写死在 `ApprovalService.request()` 自己的方法体里，而不是作为一个"网关监听器"注册进事件系统——只有服务自己的调用路径才能保证这个决策绝对发生在任何插件监听器之前。

只有 `ask` 策略才会真正走到 `ctx.waterfall('approval/request', ...)` 这条分发链——`waterfall` 是 Cordis 的一种事件分发模式（`docs/cordis-primer.md` 里"环绕式中间件"，监听器可以调用 `next()` 委托下一个，或者直接返回结果短路），任何插件都可以注册一个 `approval/request` 的应答者来决定"允许一次"还是"拒绝"；如果没有任何应答者注册（比如一个裸的无 UI 部署），waterfall 链最终会落到默认的 `() => Promise.resolve('unavailable')`——**没有人能回答的问题，默认结果是拒绝，而不是放行**，这是另一处 fail-closed 的具体体现。

### `/permission` 命令：唯一的写入口

会话内切换预设的入口是一个内置命令，注册代码同样在 `permission-presets` 里：

```typescript
// packages/interaction/permission-presets/src/index.ts（节选）
commandCtx.commands.register({
  name: 'permission',
  description: 'Switch the permission preset (sandbox mode + approval policy)',
  input: { hint: '<preset>' },
  handler: ({ agent, rawInput }) => {
    const name = rawInput.trim()
    if (name === '') {
      return { kind: 'success', text: `current preset ${this.current(agent.session.events)} (available: ${this.names.join(', ')})` }
    }
    if (!this.names.includes(name)) {
      return { kind: 'error', text: `unknown preset "${name}" (available: ${this.names.join(', ')})` }
    }
    this.apply(agent.session, name, (policy) => { this.ctx.approval.setPolicy(agent, policy) })
    return { kind: 'success', text: `preset ${name}` }
  },
})
```

不带参数的 `/permission` 会打印当前生效的预设名（可能是 `custom`）和全部可选预设；带一个预设名参数就会触发上一节讲的 `apply()` 写入路径。Web UI 里设置页面的权限切换控件，最终提交的正是这一条命令行文本。

### `cordis.yml`/`cordis.patch.yml`：部署侧覆盖默认值的机制

到这里已经能看到，权限的默认组合在两个层面都可以覆盖：`permission-presets` 包自己内置了两个默认预设,而 `dsh-base` 的 `cordis.patch.yml` 又重新声明了一份带 `read-only` 的三项表,并让底层默认值随 `DSH_PERMISSION_MODE` 变化。这靠的正是第 03 篇讲过的补丁叠加机制——`cordis.patch.yml` 里每一行都是"用 `id` 定位到某个已装配的插件行，整体替换它的 `config`"。`docs/cordis-primer.md` 的 Loader Configuration 一节说明了 `!!js` 表达式的求值时机：

```markdown
`@deepseek-ai/cordis-plugin-include` parses `!!js` into expression nodes. Loader interpolates
an entry's `config` (after declared injections activate, against that plugin context —
`ctx.serviceName`) and its `disabled` field (at every mount decision, against the loader
context); Include preserves nested row expressions until target activation.
```

也就是说 `!!js process.env.DSH_PERMISSION_MODE ?? 'workspace-write'` 这类表达式，是在这一行对应的插件真正被激活装配时才求值的，而不是在 YAML 被解析的那一刻——这也是为什么它能读到 `process.env`、能引用 `ctx.webStartup` 之类"只有到那个装配阶段才存在"的运行时对象。一个部署方如果想把整台机器的默认权限锁定成 `read-only`，不需要改任何源码，只需要在自己的 `$DSH_HOME/cordis.patch.yml`（Home 级用户层，第 03 篇讲过它排在 Profile 自己的层之后）里针对 `permission` 这一行的 `id` 覆盖一次 `defaultPreset` 字段即可。具体 `cordis.patch.yml` 支持哪些补丁操作（`insert`/按 `id` 覆盖 `config`/`disabled`），本文未逐一展开，可参考 `docs/architecture.md` 与 `docs/cordis-primer.md` 中的补丁算法说明。

## 常见问题/易踩坑

- **以为切换预设就是改一个字段**：实际上是同时（最多）写三条独立会话事件，`permission/preset` 只是审计记录，真正生效的是 `sandbox/mode` 和 `approval/policy`——如果只关心"这次执行到底是什么权限"，应该读后两者的折叠结果，而不是 `permission/preset`。
- **手动分别调整了沙箱模式和审批策略，发现界面显示"Custom"**：这是预期行为，不是 bug——两个旋钖本来就可以独立调整,只有当前组合正好匹配预设表里的某一项时才会显示具体预设名。
- **以为 `never` 策略是靠注册了一个高优先级监听器实现的**：不是,它被硬编码在 `ApprovalService.request()` 自己的决策路径里，任何监听器都无法绕开这个短路判断,这是刻意的设计。
- **没有配置任何应答者，审批请求却被直接拒绝而不是报错**：这是 fail-closed 策略的体现——`waterfall` 链条走到底找不到应答者时，默认结果是 `'unavailable'`（最终归一化为拒绝），而不是抛异常或放行。

## 小结

`dsh` 的权限系统把"能碰什么文件"（`SandboxMode`）和"要不要先问人"（`ApprovalPolicy`）拆成两个完全独立的 Seam，`permission-presets` 只是在这两者之上叠了一层用户可切换的组合表，实际的默认值又可以在 `dsh-base` 的 `cordis.patch.yml` 里按部署环境变量重新声明。这套"预设 → sandbox mode + approval policy"的组合旋钮设计还只是全貌的一半——本篇看到的 `ApprovalService` 只回答"允许一次还是拒绝"，还没有涉及"模型主动申请把权限临时放宽一级"这件事怎么被安全地处理；`packages/sandbox/sandbox/src/escalation.ts` 里的 `WIDER_MODES`/`ESCALATION_TARGETS` 已经埋好了这条"升级（escalation）"路径的词汇表，第 05 章"权限审批与沙箱体系"会继续深入这套机制的完整实现。
