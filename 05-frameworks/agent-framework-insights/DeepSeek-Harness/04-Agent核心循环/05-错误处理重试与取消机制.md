# 错误处理、重试与取消机制

> `dsh` 把"模型请求失败了怎么办"这个问题拆成了两个完全独立的关注点：一个是**分类**——任何失败,无论来自网络、adapter、还是 provider 返回的错误体,最终都要被规约成一份携带稳定 `code` 的结构化 `LlmFailure`；另一个是**策略**——`llm-retry` 插件挂在 `agent/request-error` 这个 waterfall 钩子上,用指数退避加抖动的算法决定要不要再来一次,而且**重试这个决策本身也会被写进会话日志**,可以被完整回放。与此同时,取消（`AbortSignal`）贯穿从 Provider 到 Agent Loop 的每一层,而工具调用的并发上限则是一个完全独立的、和 provider 限流无关的调度参数。本篇把这几条线分别理清楚,并且如实说明一件容易被想当然认为存在、但代码里其实没有实现的机制。

## 学习目标

- 理解 `LlmFailure`/`LlmError`/`HarnessError` 三层结构如何把"任意来源的失败"规约成一份可路由、可持久化的结构化数据。
- 通读 `llm-retry` 插件的 `localDelay()` 指数退避算法与抖动计算,理解 `retry`（重试轮次）为什么从会话日志里的历史 `llm/retry` 事件反查而不是维护一个内存计数器。
- 理解重试决策"先落盘、再等待、再放行"的三段式（`llm/retry` → `cancellableDelay` → `llm/retry-started`）如何让整个重试过程本身可以被回放和审计。
- 理解 `AbortSignal` 如何从 `ReactLoopAgent.cancel()` 一路贯穿到 provider adapter 的 `fetch`,以及 `AgentCancelCause` 四种取消原因分别对应什么场景。
- 理解工具调用并发度控制（`maxParallelToolCalls`、`isConcurrencySafe`）和 provider 级别的请求限流是两个完全不同的问题——并如实确认后者在当前代码库里没有找到实现。

## 背景与设计动机

一次模型请求失败,可能来自完全不同的层次：DNS 解析失败、TCP 连接被拒绝、TLS 握手失败（这些会被 Node 的 `fetch` 统一包成一个语义模糊的 `TypeError: fetch failed`）；HTTP 层返回了非 2xx 状态码,body 里可能有也可能没有结构化的错误信息；SSE 流中途断线;流看起来正常但语义上违反协议（比如 EOF 之前没有 `[DONE]`）；空闲太久触发本地看门狗超时;调用方主动取消。如果每一层都各自处理自己的失败逻辑,上层的重试策略就没法用一套统一的规则来决定"这个失败该不该重试、该等多久"。

`dsh` 的解法是让**每一个可能失败的层次都收敛到同一份结构**（`LlmFailure`——一个只有 `message`/`code`/`status?`/`providerRetryAfterMs?`/`requestId?` 五个字段的普通对象),上层的重试/取消/压缩恢复逻辑（第四篇讲的 `agent/request-error` 钩子）永远只需要认得这一份结构,不需要关心失败具体源自 fetch 的哪一层。

## 核心机制详解

### LlmFailure / LlmError / HarnessError：三层结构化失败

最底层是 `HarnessError`（`packages/llm/llm/src/error.ts`）——整个代码库所有自定义错误的公共基类,只比标准 `Error` 多了一个字段:

```typescript
// packages/llm/llm/src/error.ts
export class HarnessError extends Error {
  readonly code: string
  constructor(message: string, code: string, options?: ErrorOptions) {
    super(message, options)
    this.code = code
    this.name = new.target.name
  }
}
```

`LlmError` 继承 `HarnessError`,额外携带一份可序列化、可持久化的 `failure` 快照:

```typescript
// packages/llm/llm/src/index.ts
export class LlmError extends HarnessError {
  readonly failure: LlmFailure
  constructor(message: string, code: string, options?: LlmErrorOptions) {
    super(message, code, options)
    this.name = 'LlmError'
    this.failure = Object.freeze({
      message, code,
      ...options?.status === undefined ? {} : { status: options.status },
      ...options?.providerRetryAfterMs === undefined ? {} : { providerRetryAfterMs: options.providerRetryAfterMs },
      ...options?.requestId === undefined ? {} : { requestId: options.requestId },
    })
  }
}
```

```typescript
// packages/llm/llm/src/types.ts
export interface LlmFailure {
  readonly message: string
  readonly code: string
  readonly status?: number
  readonly providerRetryAfterMs?: number
  readonly requestId?: ProviderRequestId
}
```

`code` 是唯一应该被拿来做路由判断的字段——第三篇看到的 `httpErrorCode()`（DeepSeek adapter）会把 401/403 映射成 `AUTH`,429 映射成 `RATE_LIMIT`,配额相关的错误文案（正则匹配)映射成 `QUOTA`,上下文超限的文案映射成 `CONTEXT_WINDOW_EXCEEDED`,5xx 映射成 `SERVER`,其余 4xx 映射成 `HTTP_${status}`。这份映射发生在 adapter 层,再往上,任何消费者（重试插件、压缩插件、UI）都只需要认得这些稳定字符串,不需要去解析人类可读的 `message` 文本——这条规则在代码注释里被反复强调:"route on this, never by parsing `message`"。

对于不是从 `LlmError` 抛出来的任意值（比如第三方 SDK 抛出的错误,或者一个裸字符串),`normalizeLlmFailure()`（`packages/llm/llm/src/adapter-failure.ts`）负责兜底规约:

```typescript
// packages/llm/llm/src/adapter-failure.ts
export function normalizeLlmFailure(value: unknown): LlmFailure {
  const error = value instanceof Error ? value : new HarnessError(thrownMessage(value), 'UNKNOWN', { cause: value })
  const carried = ownFailureSnapshot(error)
  if (carried !== undefined && carried.code === ownErrorCode(error)) return carried
  return Object.freeze({ message: errorMessage(error), code: harnessErrorCode(error) })
}
```

只有当一个跨包传递过来的错误对象自身携带的 `failure` 快照,和它自身携带的 `code` 字段互相印证一致时,才会被信任直接复用；否则统一退化成 `{ message, code: 'UNKNOWN' }`（如果不是 `HarnessError` 的实例）——这是"永远不要信任外部抛出的、未经验证的结构"这条原则在错误处理路径上的体现。

### llm-retry：指数退避 + 抖动,以及"重试决策本身可回放"

`packages/llm/llm-retry/src/index.ts` 挂在 `agent/request-error` 这个 waterfall 钩子上（和第四篇的压缩溢出恢复挂在同一个钩子,谁先注册谁先决定要不要处理这次失败）。核心的延迟计算:

```typescript
// packages/llm/llm-retry/src/index.ts
function localDelay(config: ResolvedRetryPolicy, retry: number, random: () => number): number {
  const exponent = Math.min(retry - 1, 1024)
  const exponential = Math.min(config.initialDelayMs * 2 ** exponent, config.maxDelayMs)
  const jitter = 1 - config.jitterRatio + 2 * config.jitterRatio * random()
  return Math.min(exponential * jitter, config.maxDelayMs)
}
```

默认参数（`packages/llm/llm/src/retry-policy.ts`）是 `initialDelayMs = 500`、`maxDelayMs = 10_000`、`jitterRatio = 0.1`、普通模式 `maxRetries = 2`,默认可重试的 `code` 集合是 `[EMPTY_RESPONSE, RATE_LIMIT, SERVER, TIMEOUT, TRANSPORT]`——注意 `AUTH`/`INVALID_CREDENTIAL`/`CONTEXT_WINDOW_EXCEEDED` 都不在这份默认列表里,因为这些失败**不会因为多试一次就自己变好**。延迟计算是"指数增长的基础延迟 × 一个围绕 1 上下浮动 `jitterRatio` 的随机系数",并且始终不超过 `maxDelayMs` 的硬上限——`Math.min(retry - 1, 1024)` 这个防御是为了避免 `2 ** exponent` 在重试次数极大时算出 `Infinity`。

比较特别的是 **重试轮次不是一个内存变量,而是从会话日志里查出来的**：

```typescript
// packages/llm/llm-retry/src/index.ts
const priorPolicyRetry = agent.session.events.findLast((event): event is SessionEvent<'llm/retry'> =>
  event.type === 'llm/retry'
  && event.data.turn === turn && event.data.step === step
  && event.data.provider === provider && event.data.policyKey === policyKey,
)
const previousRetry = priorPolicyRetry?.data.retry ?? 0
if (policy.mode === 'normal' && previousRetry >= policy.maxRetries) return next()
const retry = previousRetry + 1
```

`retryPolicyKey()` 把当前生效的重试策略（mode、maxRetries、retryableCodes、退避参数）序列化成一个字符串键,一起存进日志——这意味着"如果两次请求之间策略配置变了（比如用户中途改了 provider 的 `retryableCodes`）,旧的重试计数不会被新策略继续沿用"，因为查找条件里包含了 `policyKey` 的精确匹配。这个设计的直接好处是：**进程重启后重新走到同一个 turn/step,不会凭空重置重试计数**——重试轮次和会话历史一样,是从日志里可靠重建出来的派生状态,而不是一份进程内存独有、重启就丢失的临时计数。

真正执行一次重试等待的 `backoff()` 函数,把整个过程拆成了三段,中间的等待可以被取消:

```typescript
// packages/llm/llm-retry/src/index.ts
async function backoff(agent, turn, step, failure, provider, policy, policyKey, retry, retryId, delayMs, signal): Promise<RequestErrorAction> {
  const fusedSignal = AbortSignal.any([signal, lifetime.signal])
  if (fusedSignal.aborted) return
  agent.session.append('llm/retry', { retryId, turn, step, provider, mode: policy.mode, policyKey, retry, /* maxRetries?, */ delayMs, failure })
  if (!await cancellableDelay(delayMs, fusedSignal)) return
  agent.session.append('llm/retry-started', { retryId, turn, step, retry })
  return { kind: 'retry' }
}
```

**第一步先把"决定要重试、要等多久"这个决策本身落盘**（`llm/retry` 事件),第二步才真正去等待（`cancellableDelay`,内部用 `AbortSignal` 监听中途取消),第三步等待真正结束后再落一条 `llm/retry-started` 确认"这次重试真的要发生了",然后才把 `{ kind: 'retry' }` 交还给 `step()` 的重试循环。这个顺序的价值在回放场景里很直观：即使进程在等待期间崩溃,日志里也能看到"当时决定要重试、等了多久、但没等到确认就中断了"这一完整过程,不会留下一段无法解释的空白。

`cancellableDelay()` 本身是一个标准的、可被 `AbortSignal` 提前打断的定时器封装:

```typescript
// packages/llm/llm-retry/src/index.ts
function cancellableDelay(delayMs: number, signal: AbortSignal): Promise<boolean> {
  if (signal.aborted) return Promise.resolve(false)
  return new Promise((resolve) => {
    const timer = setTimeout(() => { signal.removeEventListener('abort', onAbort); resolve(true) }, delayMs)
    function onAbort(): void { clearTimeout(timer); resolve(false) }
    signal.addEventListener('abort', onAbort, { once: true })
  })
}
```

另外还有一种 `mode: 'always'` 策略——"无限重试直到成功、取消或插件被卸载",专门给一些明确希望"网络抖动我不管,反正给我重试到底"的部署场景使用；它的处理路径会先让 `next()`（更外层的监听器,比如压缩恢复插件)有机会先处理这次失败,只有 `next()` 明确判定"不重试"时,才轮到 `always` 策略自己接管。

### AbortSignal：贯穿全链路的取消信号

取消信号从最外层的 `Agent.cancel()` 开始:

```typescript
// packages/core/agent-loop/src/agent.ts
cancel(cause: AgentCancelCause, options: CancelOptions = {}): void {
  if (!options.keepInbox) {
    this.inbox.clear()
    if (this.phase.kind !== 'idle') this.phase.wakeRequested = false
  }
  if (this.phase.kind !== 'idle') this.phase.abort.abort(cause)
}
```

```typescript
// packages/core/session/src/types.ts
export type AgentCancelCause =
  | { readonly kind: 'user' }
  | { readonly kind: 'parent' }
  | { readonly kind: 'hook'; readonly reason: string }
  | { readonly kind: 'disposed' }
```

四种取消原因分别对应四类场景：`user`（用户主动点了停止）、`parent`（父级会话/子代理被取消,连带打断)、`hook`（某个插件钩子主动决定要中断,携带一个人类可读的 `reason`)、`disposed`（agent 整个生命周期被销毁)。第一篇讲过,`phase.abort` 是当前活动（`running` 或 `maintenance`)专属的 `AbortController`,`cancel()` 只会打断"当前这一个",不会误伤下一次唤醒——这也是为什么 `turn()` 每次成功进入下一轮时都会 `phase.abort = new AbortController()` 换一个全新的信号。

这个信号一路贯穿到最底层：`step()` 里的 `signal` 会被塞进 `buildRequest()` 组装出的 `GenerateOptions.signal`;`LlmRuntime.stream()` 把它原样转发给 adapter;`DeepSeekAdapter.stream()` 内部会把它和空闲看门狗自己的信号用 `AbortSignal.any()` 融合,再传给 `fetch()` 的 `signal` 选项,一旦用户取消,进行中的 HTTP 请求会被浏览器/Node 运行时真正中断,不是"逻辑上假装取消了,底层连接还挂着"。工具执行侧同样如此——第一篇的 `tool-calls.ts` 里,`executeToolCalls()` 收到的 `signal` 一旦变成 `aborted`,`runGroup()` 会停止启动新的调用、drain 掉已经在跑的调用,并对每一个"model 发起了调用但根本没机会开始执行"的调用记录一条结构化的合成失败结果:

```typescript
// packages/core/agent-loop/src/tool-calls.ts
function appendSkippedToolCall(session: Session, turn: number, step: number, block: ToolCallBlock): void {
  const callSeq = appendToolCall(session, turn, step, block)
  appendToolResult(session, turn, step, block, {
    content: [{ type: 'text', text: 'Error: tool call aborted before dispatch' }],
    isError: true,
    error: { message: 'tool call aborted before dispatch', info: { name: 'AbortError', code: TOOL_ABORTED_BEFORE_DISPATCH } },
  }, callSeq)
}
```

**即使一次调用因为取消从未真正开始执行,日志里也会补一条"这条调用曾经存在过、但被取消了"的合成结果**——这保证了每一条 `tool/call` 事件永远都能在日志里找到与它配对的 `tool/result`,不会留下悬空的调用记录,回放时不会遇到"这个 callId 到底有没有结果"的歧义。

### 工具调用并发度：maxParallelToolCalls 与 isConcurrencySafe

工具调用的并发上限是一个和 provider 限流完全独立的参数——它限制的是"同一个 agent 步骤里,最多同时有几个工具调用在跑",而不是"多久能发一次模型请求"。默认值定义在 `packages/core/agent-loop/src/constants.ts`:

```typescript
// packages/core/agent-loop/src/constants.ts
export const DEFAULT_MAX_PARALLEL_TOOL_CALLS = 10
```

`packages/core/agent-loop/src/index.ts` 把它做成一个部署级可配置项,并在解析时做了严格校验:

```typescript
// packages/core/agent-loop/src/index.ts
function resolveMaxParallelToolCalls(value: number | undefined): number {
  const maxParallelToolCalls = value ?? DEFAULT_MAX_PARALLEL_TOOL_CALLS
  if (!Number.isInteger(maxParallelToolCalls) || maxParallelToolCalls < 1) {
    throw new Error('maxParallelToolCalls must be a positive integer')
  }
  return maxParallelToolCalls
}
```

第一篇提到的 `tool-calls.ts` 里的 `runGroup()`,用这个上限维护一个"滚动池"（rolling pool）：

```typescript
// packages/core/agent-loop/src/tool-calls.ts
const { maxParallelToolCalls } = ctx.agentLoop.config
// ...
const fillPool = async (): Promise<void> => {
  while (!aborted && nextToStart < group.length && inFlight.size < maxParallelToolCalls) {
    const nextCall = group[nextToStart]!
    if (nextToStart > 0 && mode === 'parallel' && ctx.tools.executionMode(nextCall.exec).kind !== 'parallel') break
    await startCall(nextToStart)
    nextToStart++
    // ...
  }
}
```

只要 `inFlight`（正在执行中的调用）数量还没到上限,就持续从待启动队列里拉新的调用进来启动——但每次要启动下一个之前,会重新检查一遍这个调用当下的并发分类（`ctx.tools.executionMode()`),如果它从"可并行"变成了"需要独占"，滚动池会立刻停止继续填充,等当前批次排空,把这个独占调用当成一个新的屏障来处理。一个具体调用是否"可并行"由工具自己声明:

```typescript
// packages/core/tools/src/index.ts
export type ToolExecutionMode =
  | { kind: 'parallel' }
  | { kind: 'exclusive' }

executionMode(exec: ToolExecutionInput): ToolExecutionMode {
  const tool = this.resolveExecution(exec.name, exec.agent, exec.parent !== undefined)
  if (!tool?.isConcurrencySafe) return { kind: 'exclusive' }
  try {
    const concurrencySafe: unknown = tool.isConcurrencySafe(exec.arguments)
    return concurrencySafe === true ? { kind: 'parallel' } : { kind: 'exclusive' }
  } catch {
    return { kind: 'exclusive' }
  }
}
```

默认是 `exclusive`（保守）——只有工具显式实现了 `isConcurrencySafe(arguments)` 且针对**这次具体的参数**返回 `true`,才会被归类为可并行。这里的关键细节是它是一个**基于参数的谓词函数**而不是一个静态标记：同一个工具,对不同的调用参数可能给出不同的并发分类（比如"读文件"永远安全,但"写文件"要看写的是不是同一个路径）。任何异常（谓词函数自己抛错）都会被兜底成最保守的 `exclusive`。

### 如实说明：provider 级别的请求限流

素材和许多同类系统的直觉都会假设"既然有重试策略,应该也有一个主动的 QPS/并发限流器,防止把 provider 的速率限制打爆"。但在这份代码库里检索 `rate limit`/`QPS`/`throttle` 相关的实现（`packages/llm` 全目录),能找到的只有 `RATE_LIMIT` 这个**被动的错误码**——它是 provider 返回 429 之后被识别、进而触发重试等待的结果,不是任何一处主动预测"接下来可能超限、提前放慢发送速度"的限流器。也就是说,**`dsh` 目前的策略是完全被动响应式的**：先把请求发出去,如果 provider 说"你太快了"（429/`RATE_LIMIT`),再按上面讲的指数退避策略等一等重试,而不存在一个提前节流、主动控制发送速率的组件。这一点在扩展系统或者接入自己的 provider 时值得留意——如果确实需要主动限流,目前需要自己在 provider adapter 或者更上层的封装里补上,而不能依赖框架内建的某个隐藏机制。

## 小结

- 任何来源的失败最终都规约成一份携带稳定 `code` 的 `LlmFailure`,重试、压缩恢复、UI 展示都只认这个字段,不解析人类可读的错误文案。
- `llm-retry` 的重试延迟是指数退避加随机抖动，重试轮次从会话日志里的历史 `llm/retry` 事件反查而不是内存计数,重试决策本身先落盘、再等待、再确认,让整个过程可以被完整回放。
- `AbortSignal` 从 `Agent.cancel()` 一路贯穿到 provider 的 `fetch` 调用和工具执行的滚动池,`AgentCancelCause` 用四种判别值明确记录取消的真实来源；被取消的工具调用即使从未开始执行,也会补一条合成的失败结果,保证调用与结果永远配对。
- 工具调用的并发上限（`maxParallelToolCalls`，默认 10）和工具的 `isConcurrencySafe` 参数谓词共同决定一批调用是走并行滚动池还是退化成独占屏障；这与 provider 请求速率限流是两个不同问题——当前代码库里只有被动的 `RATE_LIMIT` 重试响应,没有找到主动的 QPS 限流实现。
