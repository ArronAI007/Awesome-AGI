# 工具注册与执行管线

> 一个工具从"某个插件调用 `ctx.tools.register()`"到"模型的一次 `toolCall` 变成一条 `tool/result` 事件"之间,要经过一条固定的三段瀑布流水线——`tools/pre-execute` → 单调 Guard → `tools/execute` → `tools/post-execute` → `finalizeContent` → `tools/result`。这条流水线是所有权限检查、沙箱拦截、审批弹窗、超时重试、结果改写的唯一插入点,也是 dsh 用"一个注册表 + 一套调度器"取代"每个工具各写一套校验逻辑"的核心机制。本篇沿着真实源码把这条流水线拆开,并专门讲清楚 Code Mode(`run_code`)这条让模型"写代码调用工具"的另类分发路径。

## 学习目标

- 理解 `ToolDefinition` 接口的完整契约:`output`(规范输出)、`execute`、`finalizeContent`、`isConcurrencySafe`、`presentCall`/`presentResult` 各自的职责边界。
- 理解 `ToolRuntime.register()` 在注册时做的三类校验:输出契约校验、`timeoutMs` 校验、保留名 `run_code` 校验。
- 理解 `executeToolCalls` 调度器如何用"并行池(bounded rolling pool)"和"独占屏障(exclusive barrier)"两种模式调度一批工具调用,以及为什么执行可以并发而策略、结果、上下文必须保持模型原始顺序。
- 通读 `tools/pre-execute` → Guard → `tools/execute` → `tools/post-execute` 四个阶段的真实实现,理解每个阶段能做什么、不能做什么。
- 理解 Code Mode 这条"模型只能调用 `run_code`,真正的工具调用从程序体内部发起"的另类分发路径,以及"containment 不等于 security boundary"这句代码原话背后的安全含义。

## 背景与设计动机

模型返回的 `toolCall` 只是一个工具名加一段 JSON 参数,谁都不能保证这个调用"应该被执行"——可能命中了沙箱策略要求先审批,可能撞上了另一个正在写同一个文件的并发调用,可能这一步刚好被用户按下了终止键。如果把这些检查散落在每个工具的 `execute()` 内部,权限逃逸和逻辑不一致几乎是必然的。

dsh 的做法是把"要不要执行""怎么执行""执行完要不要改写结果"拆成三个独立的、可插拔的扩展点,由 `ToolRuntime` 统一编排,工具本身只需要负责"给定合法参数,怎么产出结果"这一件事。官方文档 `docs/tool-execution-pipeline.md` 用一张 Mermaid 图总结了这条流水线:

> `tools/pre-execute` waterfall(瀑布式事件)首先运行,随后是单调守卫,然后运行 `tools/execute` 和 `tools/post-execute` waterfall;这三个 waterfall 可以改写一次调用。由定义自身控制的 `finalizeContent` 和 `tools/result` 在此之后运行。

"waterfall"是 Cordis 的一种事件分发模式:多个监听器按注册顺序依次处理同一个值,每个监听器可以调用 `next()` 把值传给下一个,也可以直接返回自己的决定截断链条——这正是权限插件、钩子桥接插件能够在不修改 `ToolRuntime` 源码的前提下,插入自己的检查逻辑的机制。

## 核心机制详解

### `ToolDefinition`:一个工具必须声明的完整契约

`packages/core/tools/src/index.ts` 里的 `ToolDefinition` 接口是每个工具注册时必须满足的形状:

```typescript
// packages/core/tools/src/index.ts
export interface ToolDefinition extends ToolSchema {
  readonly output: ToolOutputDefinition
  execute(args: unknown, exec: ToolRunContext): Promise<unknown>
  finalizeContent?(exec: Readonly<ToolExecution>, result: Readonly<ToolExecutionResult>): ContentBlock[] | undefined
  timeoutMs?: number
  isConcurrencySafe?(args: unknown): boolean
  presentCall?(args: unknown): ToolCallView | undefined
  presentResult?(args: unknown, result: ToolResult): ToolResultView | undefined
}
```

其中 `ToolOutputDefinition`(即 `output` 字段)是这套设计里最不寻常的一处约定:

```typescript
export interface ToolOutputDefinition {
  readonly schema: JsonSchemaNode
  render(args: unknown, value: JsonValue): ContentBlock[]
  presentationMeta?(args: unknown, value: JsonValue): JsonValue
}
```

工具的 `execute()` 不直接返回模型看到的文本内容,而是返回一个**规范化的 JSON 值**(`value`),这个值必须满足 `output.schema` 声明的 JSON Schema;真正喂给模型的文本内容,是 `output.render(args, value)` 这个纯函数对这个规范值的一次投影。这个"值与展现分离"的设计带来两个直接好处:一是 Code Mode 下模型写的程序拿到的是结构化的 `value`(可以直接取字段做逻辑判断),而不是一段格式化文本;二是 `render` 是纯函数,同一个历史结果可以在会话重放(replay)时被重新渲染,而不需要重新执行工具。

`isConcurrencySafe` 是调度器判断"这次调用能不能和别的调用并行跑"的唯一依据,而且是**故意收紧的**:

```typescript
executionMode(exec: ToolExecutionInput): ToolExecutionMode {
  const tool = this.resolveExecution(exec.name, exec.agent, exec.parent !== undefined)
  if (!tool?.isConcurrencySafe) return { kind: 'exclusive' }
  try {
    const concurrencySafe: unknown = tool.isConcurrencySafe(exec.arguments)
    return concurrencySafe === true ? { kind: 'parallel' } : { kind: 'exclusive' }
  } catch {
    return { kind: 'exclusive' }
  }
}
```

只有精确等于 `true` 才会被判定为可并行;未声明、抛异常、返回任何非 `true` 的值,统统 fail-closed 成 `exclusive`。`packages/fs/tool-fs/src/read.ts` 里 `read` 工具的声明是这套机制里最简单的例子:

```typescript
// packages/fs/tool-fs/src/read.ts
isConcurrencySafe: () => true,
```

`read` 是纯读取、零副作用,所以无条件返回 `true`;而像 `edit`/`write` 这类会修改文件的工具则完全不声明这个方法,默认走独占路径——这不是遗漏,而是"默认拒绝并发"的安全姿态。

### `ToolRuntime.register()`:注册时的三类强制校验

`register()` 在把工具塞进注册表之前,会做三件事(节选自 `packages/core/tools/src/index.ts`):

```typescript
register(definition: ToolDefinition): () => void {
  const name = definition.name
  const output = (definition as Partial<ToolDefinition>).output
  if (output === undefined || typeof output !== 'object'
    || typeof output.render !== 'function'
    || (output.presentationMeta !== undefined && typeof output.presentationMeta !== 'function')) {
    throw new TypeError(`tool "${name}" must declare output { schema, render, presentationMeta? }`)
  }
  assertSupportedJsonSchema(output.schema)
  const timeoutMs = definition.timeoutMs
  if (timeoutMs !== undefined && (!Number.isFinite(timeoutMs) || timeoutMs <= 0)) {
    throw new TypeError(`tool "${name}" timeoutMs must be a positive finite number`)
  }
  if (name === RUN_CODE_NAME) {
    throw new Error(`tool name "${RUN_CODE_NAME}" is reserved for the Code Mode presentation transport and cannot be registered or shadowed`)
  }
  return this.layers.effect(this.ctx, layer => layer.tools.insert(name, definition), { label: 'tools.register()' })
}
```

第一类校验保证"输出契约"这件事不是可选的——没有声明合法的 `output.schema`/`render` 就直接 `throw`,不给工具留下"先跑起来再说"的空子。第二类校验保证 `timeoutMs`(如果声明了)是一个正的有限数字,避免一个写错的 `NaN` 或负数在超时策略里造成难以调试的行为。第三类校验保护的是 `run_code` 这个保留名——它是 Code Mode 的传输通道,任何插件都不能注册或覆盖同名工具,这个检查发生在**注册时**而不是执行时,把潜在的命名冲突尽早暴露出来。

`register()` 返回值是一个精确的 disposer 函数,底层走的是 `this.layers.effect(...)`——这是 dsh 的 scope(作用域)机制:全局注册和某个 agent 的 `agent.ctx` 注册各自落在不同的层,查找时"最具体者胜出"(scope 内注册会遮蔽同名的全局注册)。这也是为什么 `ToolRuntime` 还提供了 `restrict()`(给单个 scope 的全局工具集合做白/黑名单过滤)和 `guard()`(注册一个只能拒绝、不能强行放行的单调检查函数)两个配套 API——它们和 `register()` 共享同一套按 scope 分层的存储,但服务的目的不同:`register` 决定"这个工具存在不存在",`restrict` 决定"这个 scope 能不能看见它",`guard` 决定"看见了能不能真的跑"。

### 三段瀑布流水线:从 `pre-execute` 到 `result`

一次工具调用真正进入执行,要依次穿过 `prepareExecution` → `dispatchScheduledExecution` → `finalizeScheduledExecution`(或跳过 post 的 `finishScheduledExecution`)三个内部阶段。先看第一段——`tools/pre-execute` 加单调 Guard(节选自 `packages/core/tools/src/index.ts`):

```typescript
private async prepareExecution<T>(input: ToolExecutionInput, next: ...): Promise<T> {
  const created = this.createExecution(input)
  if (created.kind !== 'ready') return next(created)
  const exec = created.exec
  if (this.callerCancelled(exec)) {
    return next({ kind: 'final-result', exec, result: toolAbortedBeforeDispatchResult() })
  }
  const carrier = scopeTarget(this, exec.agent)
  const gate = await this.ctx.waterfall(
    carrier, 'tools/pre-execute', exec,
    () => Promise.resolve<PreToolDecision>({ kind: 'allow' }),
  )
  const askResolution = gate.kind === 'ask'
    ? await this.serviceAsk(exec, gate)
    : { decision: gate, approvalCancelled: false }
  const denialReason = askResolution.decision.kind === 'allow'
    ? this.guardReason(exec)
    : askResolution.decision.reason
  if (denialReason !== undefined) {
    return await next({ kind: 'post-result', exec, result: this.materializeFinalResult({
      content: [{ type: 'text', text: `Error: ${denialReason}` }], isError: true, error: { message: denialReason },
    }) })
  }
  return await next({ kind: 'dispatch', exec })
}
```

这里有一个容易忽略但很关键的顺序:`tools/pre-execute` 这个**可扩展**的 waterfall 先跑,拿到 `allow`/`deny`/`ask` 三种决策之一;如果是 `ask`,交给 `ctx.approval`(第三篇会详细展开)去问人;只有在这一切都通过之后,才轮到 `guardReason(exec)`——也就是通过 `ctx.tools.guard()` 注册的**单调守卫**。这个顺序保证了守卫检查的是"已经通过扩展策略"的调用,而且守卫本身"只能拒绝、不能强行放行"——`guardReason` 遍历所有已注册的 guard,任何一个返回拒绝理由就立即生效,没有哪个 guard 能把别的 guard 的拒绝翻转回允许。这条不变式在类型上也有体现:

```typescript
export type ToolGuard = (execution: Readonly<ToolExecution>) => string | undefined
```

返回 `string` 就是拒绝,返回 `undefined` 就是"我没意见",没有第三种"我强制允许"的返回值可选。

第二段是 `tools/execute`(环绕分发),真正调用工具体的 `execute()`:

```typescript
private async dispatchScheduledExecution(exec: ToolRunContext): Promise<ScheduledToolDispatch> {
  const mutableExec = exec as MutableToolRunContext
  const carrier = scopeTarget(this, exec.agent)
  const result = await this.ctx.waterfall(
    carrier, 'tools/execute', mutableExec,
    () => this.dispatchToolBody(mutableExec),
  )
  // ...合并 deferContext() 收集的 additionalContexts...
  return { kind: 'post-result', result: /* ... */ }
}
```

`tools/execute` 是一个"环绕"(around)式 waterfall——一个监听器可以在调用 `next()` 前后插入自己的逻辑(比如统计耗时、失败重试),`next()` 最终落到 `dispatchToolBody`,也就是真正执行工具体的地方。第三段 `tools/post-execute` 则在工具体产出结果之后运行,可以 `accept`(原样接受)、`replace`(替换部分展现内容)或 `block`(把结果转成一条纠正性的错误反馈)——这是"结果观察者"们(比如 spill 策略,把过大的文本结果换成一个"预览+定位符")介入的唯一入口。

三段瀑布之后,`finishScheduledExecution` 会先对结果做一次无损 JSON 快照(`materializeFinalResult`),再调用工具自己注册的 `finalizeContent`(如果有)做最后一次同步转换,最后才触发只读的 `tools/result` 通知——这也是为什么 `finalizeContent` 的 JSDoc 强调它"必须是全函数、绝不能抛异常":它是整条流水线里**唯一**一个在"结果已经确定"之后还能碰内容的钩子,如果它自己出错,没有更下游的兜底了。

### 调度器:并行池与独占屏障

`packages/core/agent-loop/src/tool-calls.ts` 里的 `executeToolCalls` 负责把一个 assistant 步骤里的一批 `toolCall` 分组调度。它的核心思路是"按连续同质分组":

```typescript
// packages/core/agent-loop/src/tool-calls.ts
let next = 0
while (next < planned.length) {
  const first = planned[next]!
  const mode = ctx.tools.executionMode(first.exec).kind
  const group = mode === 'parallel' ? planned.slice(next) : [first]
  const outcome = await runGroup(ctx, turn, step, group, mode, signal, acceptContext)
  next += outcome.consumed
  // ...
}
```

如果排在最前面的调用是 `exclusive`,这一组就只有它自己一个,单独跑完才轮到下一个;如果是 `parallel`,这一组就先把从当前位置到末尾的所有调用都纳入候选,但**候选归候选,真正会不会一起跑还要在 `runGroup` 里逐个重新判定**——这是文档注释里"later calls are reclassified before start"这句话的来源:注册表状态可能在两次调用之间发生变化(比如一个前面的调用触发了权限降级),所以"是否并行"不是一次性决定,而是每次要启动下一个调用前都重新问一次。

`runGroup` 内部维护一个"填充池"(`fillPool`),核心逻辑是:

```typescript
const fillPool = async (): Promise<void> => {
  while (!aborted && nextToStart < group.length && inFlight.size < maxParallelToolCalls) {
    const nextCall = group[nextToStart]!
    if (nextToStart > 0 && mode === 'parallel'
      && ctx.tools.executionMode(nextCall.exec).kind !== 'parallel') break
    await startCall(nextToStart)
    nextToStart++
    await commitReady()
    if (signal.aborted) aborted = true
  }
}
```

`maxParallelToolCalls`(默认值 10,定义在 `packages/core/agent-loop/src/constants.ts` 的 `DEFAULT_MAX_PARALLEL_TOOL_CALLS`)是并发池的容量上限;一旦发现下一个候选调用被重新分类为非并行,填充立即停止——这一批已经在跑的调用会继续跑完,但不会再有新的调用加入同一批。这就是"bounded rolling pool"(有界滚动池)和"exclusive barrier"(独占屏障)两个词的准确含义:并行池有容量上限、会随注册表状态动态收缩;独占屏障则强制单个调用独占一整个调度周期,前后两端都不会有其他调用与它重叠。

真正体现"执行可以乱序完成,但结果必须按模型原始顺序落盘"的,是 `commitReady`:

```typescript
const commitReady = async (): Promise<void> => {
  while (committed < group.length) {
    const slot = slots[committed]
    if (slot === undefined) break
    // ...finalize 或 finish...
    appendToolResult(session, turn, step, call!.block, result, callSeqs[committed]!)
    committed++
  }
}
```

`slots` 数组按调用在这一批里的**原始下标**存放结果,`committed` 只会在"下一个待提交的槽位已经就位"时才前进一格。也就是说,即便调用 3 比调用 1 先执行完,调用 3 的结果也必须等调用 1、2 都落盘之后才能落盘——`while (committed < group.length)` 加上 `if (slot === undefined) break` 这两行,就是维持模型侧上下文顺序一致性的全部机制。

### 呈现与执行分离:`presentCall`/`presentResult` 不参与流水线

容易和 `output.render` 搞混的是 `ToolDefinition` 上另外两个可选方法——`presentCall`/`presentResult`。它们**不在**上面讲的三段瀑布流水线里,不会影响任何一次调用的执行结果,唯一的作用是告诉 UI"这次调用/这次结果应该长什么样"。`packages/core/tools/src/presentation.ts` 的模块文档说得很明确:

```typescript
// packages/core/tools/src/presentation.ts
/**
 * Tool render-intent vocabulary: the provider-neutral types a tool declares via
 * `ToolDefinition.presentCall`/`ToolDefinition.presentResult` to say how one of its calls
 * renders in a UI (an editor's tool-call card, a CLI log line).
 */
```

`packages/shell/tool-bash/src/index.ts` 里 `bash` 工具的实现是个很直观的例子:

```typescript
// packages/shell/tool-bash/src/index.ts
function presentBashCall(args: BashCallArgs): GenericCallView | TerminalCallView {
  if (args.run_in_background === true) {
    return { card: 'generic', title: args.command, kind: 'execute', rawInput: args.command,
      content: [{ type: 'text', text: args.description }] }
  }
  return { card: 'terminal', title: args.command, description: args.description,
    ...args.workdir !== undefined ? { cwd: args.workdir } : {} }
}

function presentBashResult(args: unknown, result: ToolResult): ToolResultView | undefined {
  const block = result.content.length === 1 ? result.content[0] : undefined
  if (block === undefined || block.type !== 'text') return undefined
  const raw = block.text
  const isBackground = /* ... */
  if (isBackground || result.isError) {
    return { card: 'generic', content: [{ type: 'text', text: `\`\`\`console\n${raw.replace(/\n+$/, '')}\n\`\`\`` }] }
  }
  const { body, ...exit } = parseExitStatus(raw)
  return { card: 'terminal', output: body, ...exit }
}
```

同样是一次 `bash` 调用,后台运行时呈现成一个通用卡片(`card: 'generic'`),前台运行时呈现成一个带退出码"药丸"的终端卡片(`card: 'terminal'`)——但无论呈现成什么样,`execute()` 真正返回给模型的规范值(`output.schema` 约束的那个 JSON)完全不受影响。这条分离的价值在于**会话重放**:`presentCall`/`presentResult` 被要求是纯函数、只依赖 `args`(和 `presentResult` 额外依赖的 `result`),这意味着 UI 可以在实时执行时调用它们渲染卡片,也可以在重放一段历史会话日志时用完全相同的函数重新渲染出一模一样的卡片——不需要重新执行工具体,自然也不会有"重放时又跑了一次 `bash` 命令"这种副作用重演的风险。`edit` 工具的 `presentResult`(`packages/fs/tool-fs/src/edit.ts`)是另一处印证:它从 `result.meta`(工具结果里那个不透明的、随会话持久化的展现数据)里取出上一节 `computeHunkDiffs` 算好的 diff 数组直接渲染,而不是重新读一次文件去对比——`meta` 字段正是为了让"结果时算一次、之后随便重放多少次"这条原则能落地而存在的。

### Code Mode:另一条分发路径

以上讲的是"模型直接命名一个工具"的默认路径。dsh 还支持一种叫 Code Mode 的替代表现形式:`ctx.tools` 的 `mode` 配置一旦设为 `'code'` 或 `'both'`,模型看到的就不再是每个工具各自的 schema,而是一份生成的 SDK 说明("像写代码一样调用这些函数")加一个唯一可直接调用的工具——`run_code`。`packages/core/tools/src/code-mode.ts` 里的注释说得很直接:

```typescript
// packages/core/tools/src/code-mode.ts
/**
 * Code Mode `run_code` transport. Programs call the registry's agent-visible
 * tools through nested executions scheduled under the native concurrency
 * contract; each sub-dispatch is logged for reconstruction, while only the
 * outer curated result enters model history.
 */
export const RUN_CODE_NAME = 'run_code'
```

模型在 `code` 模式下调用 `run_code`,参数是一段 TypeScript(或 Python)程序体;这段程序在一个隔离的运行时里执行,程序内部调用 `await tools.name(args)` 时,并不是本地函数调用,而是重新进入 `ToolRuntime` 的调度器,走一遍完整的 `prepare` → `dispatch` → `finalize` 三段(和模型直接发起调用完全相同的策略、沙箱、审批检查),只是这一次的"发起者"变成了正在运行的程序而不是模型本身:

```typescript
// packages/core/tools/src/code-mode.ts(节选)
const prepared = await scheduler.prepare(input)
if (prepared.kind === 'dispatch') {
  this.flight = scheduler.dispatch(prepared.exec).then((dispatchOutcome) => {
    parked = { kind: dispatchOutcome.kind, exec: prepared.exec, result: dispatchOutcome.result }
    this.settled = true
  })
  return
}
```

每一次子调用都会记一对 `tool/code-dispatch-start` + `tool/code-dispatch` 日志事件,方便会话重放时重建程序内部到底发起了哪些调用,但这些子调用**不会**进入模型的对话历史——真正进入模型历史的,只有 `run_code` 这次调用自己的最终结果(程序打印或 `return` 的内容)。这也是 Code Mode 的核心价值:模型可以在一次调用里串联多个工具、做条件判断和循环,而不必把每一步的中间结果都塞进上下文窗口。

### "Containment,不是 security boundary"

Code Mode 的程序要在哪里跑?dsh 目前唯一发布的后端是 `packages/code-runtime/code-runtime-worker-thread`,用 Node 的 `worker_threads.Worker` 给每次运行开一个全新的 worker 线程。这个包的模块文档写得非常直白:

```typescript
// packages/code-runtime/code-runtime-worker-thread/src/index.ts
/**
 * Worker-thread code runtime: a fresh worker runs each host-type-stripped TypeScript program
 * and bridges bindings over its message port. This is containment, not a security boundary:
 * model code has bash-equivalent trust despite an empty environment, a heap cap, measured
 * event-loop busy-time and wall-time budgets, and termination that also stops synchronous loops.
 */
```

翻译过来就是:worker 线程提供的是资源层面的**约束**(containment)——独立的 V8 isolate、空环境变量、堆内存上限(`maxOldGenerationSizeMb`)、基于事件循环忙时间测量的计算预算(`computeMs`)、绝对墙钟超时(`maxWallMs`)、以及能强行终止同步死循环的硬终止——但它**不是**一道安全边界(security boundary)。`CodeRuntime` 这个 Service Definition 的 JSDoc 把这句话说得更绝对:

```typescript
// packages/code-runtime/code-runtime/src/index.ts
/**
 * The execution substrate, as a lowercase identifier. Informational, not
 * gating — a descriptor so deployments and diagnostics can tell backends
 * apart, not a security claim. Well-known values: `'worker-thread'`,
 * `'process'`, `'container'`.
 */
abstract readonly isolation: string
```

也就是说,模型在 `run_code` 里写的程序,信任级别和它直接调用 `bash` 工具执行一条命令是**对等的**("bash-equivalent trust")——两者都假定调用方(模型)可能是恶意或出错的,真正的安全边界永远在更下层的沙箱(`ctx.sandbox`)和文件系统围栏(`ctx.fs`)上,而不是代码执行运行时本身。`code-runtime` 包的 README 也补了一句直白的话:"只有 worker-thread 这一个后端已发布——`process`/`container` 只是声明了的、尚无实现的 `isolation` 枚举值,真正的硬安全边界要等一个容器后端"。这提醒我们不要把"跑在一个独立线程/进程里"和"这段代码是安全的"划等号——containment 解决的是资源耗尽和无限循环的问题,不是恶意逃逸的问题。

## 常见问题/易踩坑

**Q:`tools/pre-execute` 里的 `ask` 决策和 `tools/post-execute` 里的 `block` 决策看起来都是"拒绝",有什么本质区别?**

`ask` 发生在工具体执行**之前**,交给 `ctx.approval` 问人,问的结果只有"允许一次"或者拒绝——工具体从未被调用过,不会产生任何副作用。`block` 发生在工具体已经**执行完**之后,是对一个已经产生的结果的事后否决,通常伴随着"把结果换成一段纠正性的反馈文本"(比如"你写的这段内容触犯了某条策略,请修改后重试"),模型看到的是一个 `isError: true` 的结果,但底层的副作用(如果工具体确实做了什么)已经发生了。这也是为什么"能不能提前拦截"的判断逻辑应该尽量放在 `pre-execute`/Guard 而不是 `post-execute`——`post-execute` 只适合处理"必须先看到结果才能判断"的场景(比如结果内容过大需要 spill、结果内容需要脱敏)。

**Q:一个工具如果同时声明了 `finalizeContent` 和依赖 `tools/post-execute` 改写结果,两者的执行顺序是怎样的?**

`tools/post-execute` 先跑,`finalizeContent` 后跑——`finishScheduledExecution` 的实现里是先 `postExecute()`,再对结果调用 `applyFinalContent()`(内部才是 `finalizeContent`)。这个顺序的含义是:插件级别的横切策略(post-execute)有机会在工具自己的最终内容转换之前先动一次结果,但 `finalizeContent` 永远是整条链路上**最后**碰内容的地方,且注册表在调用开始时就已经把这个回调"快照"下来——即便执行过程中工具被注销或替换,已经开始的这次调用依然会用开始时捕获到的那个 `finalizeContent` 收尾,不会中途换掉。

**Q:`maxParallelToolCalls` 和 `maxParallelSubCalls`(Code Mode 里 `run_code` 子调用的并发上限)是不是同一个配置?**

不是,但默认值恰好都是 10。`maxParallelToolCalls` 属于 `packages/core/agent-loop`,控制的是模型一次 assistant 消息里直接发起的一批 `toolCall` 的并行池容量;`maxParallelSubCalls` 属于 `packages/core/tools` 的 `ToolRuntime` 配置,控制的是一个 `run_code` 程序内部通过 `await tools.name(args)` 发起的子调用能有多少个同时在飞。两者是完全独立的两层调度容量,一个部署完全可以把外层调到 4、内层调到 20(或者反过来),取决于"模型直接发起的调用"和"程序内部串联的调用"各自的并发特性。

## 小结与思考题

一次工具调用的完整生命周期可以归纳为:模型(或 Code Mode 程序)发起调用 → `createExecution` 分配调用身份、做参数无损快照 → `tools/pre-execute` 瀑布(可 `allow`/`deny`/`ask`)→ 单调 Guard(只能拒绝)→ `tools/execute` 瀑布环绕真正的工具体 → `tools/post-execute` 瀑布(可接受/替换/拦截)→ `finalizeContent` 做最后一次内容转换 → `tools/result` 只读通知。调度层面,并行池按注册表的实时状态动态收缩、独占屏障强制串行,但无论执行顺序如何交错,提交到会话日志、反馈给模型的结果永远保持调用发起时的原始顺序。Code Mode 复用了这套完全相同的流水线,只是把"发起者"从模型换成了一段在隔离 worker 里运行的程序——隔离解决的是资源问题,不是信任问题。

思考题:

1. `tools/pre-execute` 和 `guard()` 都能拒绝一次调用,为什么 dsh 要设计成两条独立的机制,而不是把所有拒绝逻辑都塞进 `tools/pre-execute` 一个瀑布里?
2. 如果要新增一种"工具调用必须在 5 秒内响应,否则自动重试一次"的横切策略,应该挂在 `tools/pre-execute`、`tools/execute` 还是 `tools/post-execute` 上?为什么其它两个位置做不到或者不合适?
