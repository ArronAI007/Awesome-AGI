# 权限审批与沙箱体系

> dsh 把"要不要限制文件访问""要不要弹窗问人""默认给哪一档权限"拆成了三个各自独立、各自持久化的旋钮——`sandbox/mode`、`approval/policy`、`permission/preset`——而不是一个笼统的"权限等级"开关。四种平台各自用不同的内核机制(bwrap、Seatbelt、Landlock、Windows 受限令牌)兑现同一份"read-only / workspace-write / danger-full-access"契约,一次升级请求必须先过严格单向递增表、再过人工审批,才能拿到一次性的更宽权限。本篇把这套体系的旋钮关系、平台实现、升级流程和 E2B 远程替代路径依次讲清楚。

## 学习目标

- 理解 `sandbox/mode`、`approval/policy`、`permission/preset` 三个旋钮各自的职责边界,以及它们如何通过会话事件持久化、可重放。
- 通读 `SandboxProvider`/`SandboxPolicyService`/`ApprovalService`/`PermissionPresetService` 四个 Service 的真实实现,理解"策略解析"和"策略执行"是如何被拆到不同层的。
- 理解 dsh 在 Linux/macOS/Windows 三个平台上分别选用 bwrap、Landlock、Seatbelt、Windows ACL 四种沙箱实现的取舍,以及 Windows 方案已知的强制力缺口。
- 理解沙箱升级(escalation)机制的完整流程:严格单向递增表、审批请求、一次性授权。
- 了解 E2B 这条把 `ctx.fs`/`ctx.subprocess` 换成远程 microVM 后端的替代路径,以及 dsh 与 Claude Code/Codex 相比在"权限档位"和"编辑回滚"上的两点差异。

## 背景与设计动机

"给不给这条命令写文件的权限"和"要不要为这次操作弹窗问用户"其实是两个完全独立的问题:一个命令可能被沙箱允许执行,但部署方仍然希望每一次都有人确认;反过来,一个部署可能完全不想弹窗(比如 CI 无人值守场景),但仍然需要沙箱把破坏性操作限制在工作区之内。如果把这两件事合并成一个"权限等级",要么会出现"CI 场景下想要严格沙箱但不能有弹窗"这种表达不出来的组合,要么就要为每一种组合单开一个特殊等级,越加越乱。

dsh 的解法是把它们拆成三个正交的持久化事件——`sandbox/mode`(文件效果模式)、`approval/policy`(要不要走审批)、`permission/preset`(面向用户的"套餐"记录,把前两者打包成一个好记的名字)——每一个都可以独立读取、独立切换,`permission/preset` 只是一层方便用户操作的糖衣。三者都通过会话事件写入,天然可重放:恢复一个历史会话时,重新回放事件日志就能得到当时生效的确切权限状态,不需要额外的快照机制。

## 核心机制详解

### 旋钮一:`sandbox/mode`——文件效果模式

`ctx.sandboxPolicy`(`packages/sandbox/sandbox-policy/src/index.ts`)是这个旋钮的策略归宿。它不做任何实际的沙箱包装,只负责"给定一次调用,解析出这次调用应该用哪个模式、哪个工作区根目录":

```typescript
// packages/sandbox/sandbox-policy/src/index.ts
export class SandboxPolicyService extends Service {
  static Config: z<Config> = z.object({
    mode: z.union(['read-only', 'workspace-write', 'danger-full-access'] as const).default('read-only'),
    workspaceRoot: z.string(),
  })

  resolve(request: SandboxPolicyRequest = {}): SandboxExecutionPolicy {
    const { session } = request
    return {
      mode: request.mode ?? (session === undefined ? undefined : this.overrideOf(session)) ?? this.defaultMode,
      workspaceRoot: resolveWorkspaceRoot(session?.header.cwd ?? this.workspaceRoot),
      ...session === undefined ? {} : { sessionId: session.id },
    }
  }
}
```

优先级链写得很清楚:一次调用如果带了显式的、经过审批的 `mode` override,它优先;否则看会话自己的 `sandbox/mode` 事件历史(`overrideOf`,内部就是折叠 `effectiveSandboxMode(session.events)`);最后才落到部署配置的 `defaultMode`——**部署默认值是 `read-only`**,这是一处刻意的"failsafe 默认"选择:一个没有显式声明"我允许工作区可写"的部署,永远从最保守的模式起步。

真正把这个模式**兑现**成一次具体的进程限制,是另一个独立的 seam——`ctx.sandbox`(`packages/sandbox/sandbox/src/index.ts`)。`SandboxProvider` 的契约只有一个方法:

```typescript
// packages/sandbox/sandbox/src/index.ts
export abstract class SandboxProvider extends Service {
  abstract confine(argv: readonly string[], policy: SandboxPolicy): ConfinedArgv
}
```

`confine` 接收调用方即将 spawn 的原始 argv,返回一个包裹过的新 argv,调用方直接拿新 argv 去 spawn。这个方法的 JSDoc 特别强调"必须返回强制生效的 argv 或者在包装/运行时 fail closed;绝不允许静默地直通不加沙箱的原始命令"——`SandboxUnavailableError` 就是这条 fail-closed 承诺的具体载体:找不到可用的沙箱后端时,dsh 选择直接拒绝执行,而不是退化成"不沙箱化也照样跑"。

### 旋钮二:`approval/policy`——要不要走审批

`ctx.approval`(`packages/interaction/user-approval/src/index.ts`)只有两档:

```typescript
// packages/interaction/user-approval/src/index.ts
export type ApprovalPolicy = 'ask' | 'never'
```

`'ask'` 是默认值,交给已注册的"回答者"(answerer,比如某个 UI 插件)去决定;没有回答者时 fail-closed 成 `'unavailable'`。`'never'` 是**确定性拒绝**——不经过任何 waterfall 分发,直接返回 `'rejected'`:

```typescript
private async decide(req: ApprovalRequest, session: Session): Promise<ApprovalOutcome> {
  const signal = req.signal
  if (signal?.aborted) return 'cancelled'
  if (this.effectivePolicy(session) === 'never') return 'rejected'
  // ...才进入 approval/request waterfall...
}
```

代码注释解释了为什么这个检查必须写在 `decide()` 内部而不是作为一个监听器:"一个用 `prepend: true` 注册、排在这个检查之前的监听器,如果是一个 listener 形态的门,就没法保证 `'never'` 无条件拒绝这个文档化的承诺——只有这个服务自己的请求路径能保证"。这是"确定性"这个词的真正含义:`'never'` 策略下的拒绝结果在代码路径上就不可能被任何后注册的插件绕过,这正是无人值守 CI 场景需要的强保证。

**关键事实:`ApprovalOutcome` 的取值只有四种,里面没有"永久允许"**:

```typescript
// packages/interaction/user-approval/src/types.ts(经 index.ts 重导出)
const OUTCOMES: readonly ApprovalOutcome[] = ['allowed-once', 'rejected', 'cancelled', 'unavailable']
```

`allowed-once` 明确是"一次性"的——没有一个 `allowed-forever` 或类似的档位。这意味着每一次需要审批的操作都要重新走一遍审批流程,不存在"用户批准一次,后续所有类似操作自动放行"的机制。

### 旋钮三:`permission/preset`——把前两者打包成套餐

`ctx.permissionPresets`(`packages/interaction/permission-presets/src/index.ts`)不引入新的强制力,它只是把 `sandbox/mode` 和 `approval/policy` 的组合包装成一个用户友好的名字,默认表:

```typescript
// packages/interaction/permission-presets/src/index.ts
}).default({
  'workspace-write': {
    sandbox: 'workspace-write', approval: 'ask',
    name: 'workspace-write', description: 'Write inside the workspace and permitted temporary directories; wider retries require approval.',
  },
  'danger-full-access': {
    sandbox: 'danger-full-access', approval: 'never',
    name: 'danger-full-access', description: 'Full file access without approval prompts.',
  },
}),
```

切换一个 preset,底层是连续写两个知识产权独立的事件:

```typescript
private apply(session: Session, name: string, setApproval: (policy: ApprovalPolicy) => void): void {
  const spec = this.resolve(name)
  if (this.current(session.events) !== name) {
    session.append('permission/preset', { preset: name })
  }
  if (spec.sandbox !== (effectiveSandboxMode(events) ?? this.ctx.shell.sandboxMode)) {
    setSandboxMode(session, spec.sandbox)
  }
  if (spec.approval !== (effectiveApprovalPolicy(events) ?? this.ctx.approval.config.policy ?? 'ask')) {
    setApproval(spec.approval)
  }
}
```

`permission/preset` 事件本身只是"日志用户意图"——真正生效的仍然是紧随其后写入的 `sandbox/mode` 和 `approval/policy` 事件。这也解释了为什么会存在一个 `CUSTOM_PRESET = 'custom'` 的特殊值:如果两个旋钮当前的实际取值凑不出表里任何一行(比如用户手动把 sandbox 调到了 `read-only` 但 approval 还留在 `never`),`derive()` 就会返回 `'custom'`——这不是一个可以切换到的目标,只是"当前状态无法归类到任何已知套餐"的诚实汇报。

### 四种平台的沙箱实现对比

`ctx.sandbox` 的本地实现 `LocalSandboxProvider`(`packages/sandbox/sandbox-local/src/index.ts`)按平台选择一条"运行器链"(runner chain):

```typescript
// packages/sandbox/sandbox-local/src/index.ts
const PLATFORM_CHAINS: Record<string, readonly SelectedRunner['runner'][]> = {
  linux: ['bwrap', 'landlock'],
  darwin: ['seatbelt'],
  win32: ['windows-acl'],
}
```

Linux 有两个候选,按声明顺序做**功能性探测**(真的 spawn 一次极简进程验证内核/工具是否可用)来仲裁:优先 bubblewrap(`bwrap`,基于 mount namespace,profile 语义最贴近 dsh 的模式词汇),探测失败才退到 `landlock-run`(基于 Landlock LSM,不需要 mount 权限,更适合受限容器环境)。macOS 和 Windows 各只有一个候选,不需要探测,选中即用,执行期失败再 fail closed。四条链各自的 profile 构造(`packages/sandbox/sandbox-local/src/profiles.ts`):

```typescript
// packages/sandbox/sandbox-local/src/profiles.ts
export function bwrapProfileArgs(policy: SandboxPolicy): string[] {
  const args = ['--ro-bind', '/', '/', '--dev', '/dev', '--proc', '/proc', '--die-with-parent']
  if (policy.mode === 'workspace-write') {
    args.push('--tmpfs', '/tmp')
    args.push('--bind', policy.workspaceRoot, policy.workspaceRoot)
  }
  return args
}

export function seatbeltProfileArgs(policy: SandboxPolicy): string[] {
  const forms = ['(version 1)', '(allow default)', '(deny file-write*)', `(allow file-write* (literal ${sbplString('/dev/null')}))`]
  const roots = writableRoots(policy)
  if (roots.length > 0) {
    forms.push(`(allow file-write* ${roots.map(root => `(subpath ${sbplString(root)})`).join(' ')})`)
  }
  return ['-p', forms.join(' ')]
}
```

`bwrap` 用 mount bind 把整个根文件系统只读挂载,再把工作区目录额外 bind 成可写;`seatbelt`(macOS 的 `sandbox-exec -p`,SBPL profile 语言)反过来是"默认允许,显式拒绝文件写入,再对工作区路径开白名单"。两种截然不同的策略语言,最终都要收敛到同一份"read-only / workspace-write / danger-full-access"契约上——这正是 seam 抽象在起作用:`ctx.sandbox.confine()` 的调用方完全不需要知道 SBPL 和 bwrap 的 mount 参数语法差在哪里。

四条链的**强制完整性**(`SandboxEnforcement`,只有 `'full'` 和 `'partial'` 两档)并不一致:

```typescript
// packages/sandbox/sandbox-local/src/index.ts
const STATIC_ENFORCEMENT: Record<SelectedRunner['runner'], SandboxEnforcement> = {
  bwrap: 'full',
  landlock: 'full',
  seatbelt: 'full',
  // WRITE_RESTRICTED needs Everyone in both restricting lists for process
  // initialization. An external object that grants Everyone write access
  // therefore remains writable, and NTFS hard links can alias a granted
  // workspace file to a path outside it.
  'windows-acl': 'partial',
}
```

Windows 方案(`packages/sandbox/sandbox-windows-acl`)用的是"受限令牌"(restricted token)运行子进程,配合 ACL(访问控制列表)显式授予工作区的写权限。代码注释直接写明了它的两个已知缺口:Windows 的 `WRITE_RESTRICTED` 令牌机制要求进程初始化阶段的两个"限制列表"里都保留 `Everyone` 组,这意味着任何本来就对 `Everyone` 开放写权限的外部对象仍然可写;另外 NTFS 的硬链接(hard link)可以让同一个文件对象在授权路径之外别名出现,从而绕开路径层面的授权检查。这不是实现疏漏,而是 Windows ACL 模型本身的结构性限制——所以 `windows-acl` 在强制完整性上被诚实地标记为 `'partial'`,而不是伪装成 `'full'`。四条链各自的"拒绝方言"(denial signature,即拒绝发生时 stderr 里会出现的特征字符串)也不同:

```typescript
const DENIAL_SIGNATURES = {
  bwrap: ['read-only file system'],
  landlock: ['permission denied'],
  seatbelt: ['operation not permitted'],
  'windows-acl': ['access is denied', 'access to the path', 'permission denied'],
} as const
```

这份表存在的意义是让上层(比如 `tool-bash`)能够从一次失败的命令输出里,准确判断"这是沙箱拒绝了文件操作"还是"命令自己执行失败了"——如果匹配了对应后端的拒绝方言,才会在模型看到的结果里附加 `[sandbox: file access denied under <mode> mode]` 这个标准化标记,而不是把两种性质完全不同的失败混为一谈。

### 文件系统层的第二道防线:进程内的路径围栏

沙箱运行器解决的是"进程级别能不能碰某个路径",但 dsh 在文件系统 Provider 内部还叠加了一层**进程内**的二次防护——`packages/fs/fs-sandbox/src/containment.ts` 的 `isPathUnder`:

```typescript
// packages/fs/fs-sandbox/src/containment.ts
export async function isPathUnder(
  path: string, root: string,
  caseSensitive = process.platform !== 'win32',
): Promise<boolean> {
  if (isLexicallyUnder(path, root, caseSensitive)) return true
  const rootInfo = await statIfPresent(root)
  if (!rootInfo) return false
  let ancestor = path
  while (true) {
    const ancestorInfo = await statIfPresent(ancestor)
    if (ancestorInfo && sameIdentity(ancestorInfo, rootInfo)) return true
    const parent = dirname(ancestor)
    if (parent === ancestor) return false
    ancestor = parent
  }
}
```

先走词法前缀比较(把目标路径和根目录字符串比较是否有前缀关系),如果字符串不匹配,再退而求其次,沿着目标路径的每一级祖先目录做文件系统身份(`dev`+`ino`)比较——这一步专门是为了识别 Windows 上"长文件名/8.3 短文件名"或大小写差异造成的路径别名,不让字符串层面的伪装绕过围栏。这道防线和 `ctx.sandbox` 的进程级隔离是互补关系:一个在内核/OS 层拦截 `open()` 系统调用,一个在 Node 进程内部对"这次要写的目标到底是不是工作区内的路径"做二次校验,两者叠加才是 dsh 对"workspace-write"这个词的完整承诺。

### 让模型知道自己处在什么权限下:系统提示词里的策略陈述

三个旋钮的当前取值,不只是内部策略检查用的状态,还会被翻译成一段自然语言,拼进每次请求的系统提示词里,让模型对自己的处境有明确认知,而不是只能通过"试了才知道被拒绝"来摸清边界。`SandboxPolicyService` 的构造函数里注册了这样一段:

```typescript
// packages/sandbox/sandbox-policy/src/index.ts
ctx.inject(['systemPrompt'], (scope: Context) => {
  scope.systemPrompt.context({
    name: 'sandbox:policy',
    order: 110,
    text: (context) => {
      const session = context.agent?.session
      return session === undefined ? '' : renderPolicyContext(this.resolve({ session }))
    },
  })
})

function renderPolicyContext(policy: SandboxExecutionPolicy): string {
  switch (policy.mode) {
    case 'read-only':
      return 'Current DSH file policy: read-only. ... Do not refuse a required modification from this policy alone: try an available tool normally and follow any denial and escalation guidance it returns.'
    case 'workspace-write':
      return `Current DSH file policy: workspace-write. Any available operation enforced by the DSH file sandbox may modify files under the session workspace: ${JSON.stringify(policy.workspaceRoot)}. ...`
    case 'danger-full-access':
      return 'Current DSH file policy: danger-full-access. The DSH file sandbox does not restrict file modifications by available operations.'
  }
}
```

这段陈述**每次请求都重新按当前策略生成**,而不是写死在系统提示词的静态部分——这样切换 `sandbox/mode` 之后,模型在下一步就能读到更新后的陈述,不需要重启会话。特别值得注意的是 `read-only` 分支的最后一句:"不要仅凭这条策略陈述就拒绝执行一个必要的修改——正常尝试可用的工具,并遵循它返回的拒绝与升级指引"。这是一处刻意的措辞选择:系统提示词只负责**告知**当前处于什么模式,不负责**替模型做决策**——真正"这次操作行不行"的判断权始终留在执行时的沙箱强制和审批流程手里,模型不应该因为读到"当前是 read-only"就自己提前放弃尝试,毕竟同一轮里升级机制随时可能让这次操作变得可行。`ApprovalService` 也用同样的模式挂了一段 `approval:policy` 陈述,`'never'` 策略下明确告诉模型"不要发起沙箱升级请求(不要设置 `sandbox_permissions`)"——因为在 `'never'` 策略下,升级请求百分之百会在审批这一步被确定性拒绝,提前把这个事实告诉模型可以避免一轮无意义的尝试。

### 升级机制(Escalation):从拒绝到一次性放宽

工具被沙箱拒绝之后,模型可以在**同一轮**里附带升级请求重试同一个调用。这条流程的核心是"严格单向递增表",定义在 `packages/sandbox/sandbox/src/escalation.ts`:

```typescript
// packages/sandbox/sandbox/src/escalation.ts
export const WIDER_MODES: Record<string, readonly SandboxMode[]> = {
  'read-only': ['workspace-write', 'danger-full-access'],
  'workspace-write': ['danger-full-access'],
}

export const ESCALATION_TARGETS: readonly SandboxMode[] = ['workspace-write', 'danger-full-access']
```

`WIDER_MODES` 是**执行期**才会查的表——"从 `read-only` 只能升到 `workspace-write` 或 `danger-full-access`,从 `workspace-write` 只能升到 `danger-full-access`"这条规则故意不写进工具的 schema 枚举(`ESCALATION_TARGETS` 是给 schema 用的,是"这个部署可能升到的全部目标"的静态并集),因为 schema 是注册表级别全局共享的,而"从哪个模式升级"是每次调用的运行期事实——两者必须分开校验。真正的判定在 `approveEscalation`:

```typescript
// packages/sandbox/sandbox/src/escalation.ts
export async function approveEscalation<A, C>(request: EscalationRequest, approval: EscalationApproval<A, C>): Promise<SandboxMode> {
  const { requestedMode: mode, effectiveMode, justification, subject } = request
  if (!(WIDER_MODES[effectiveMode] ?? []).includes(mode as SandboxMode)) {
    throw new Error(`sandbox escalation to "${mode}" is not strictly wider than this call's current "${effectiveMode}" mode`)
  }
  if (approval.approver === undefined) {
    throw new Error(`sandbox escalation to "${mode}" requires approval, but no approval service is composed`)
  }
  const outcome = await approval.approver.request({
    agent: approval.agent, toolName: approval.toolName, callId: approval.callId,
    reason: `escalate sandbox to ${mode}: ${justification}`,
  })
  switch (outcome) {
    case 'allowed-once': return mode as SandboxMode
    case 'rejected': throw new Error(`the user rejected escalating this ${subject} to "${mode}"`)
    // ...
  }
}
```

完整顺序是:先做严格单向递增校验(不满足直接拒绝,连审批都不问),再检查有没有配置审批服务和调用方 agent(缺任何一个都直接拒绝),最后才真正发起 `ctx.approval.request(...)`。批准的结果只是**这一次调用**的 `mode` override,不会写回会话级别的 `sandbox/mode` 事件——下一次同样的命令如果再被拒绝,还要再走一次完整的升级流程。`packages/shell/tool-bash/src/index.ts` 里 `bash` 工具的描述文本把这套流程翻译成了给模型看的操作指引,核心是"不要先去聊天里问权限,直接重试触发的审批弹窗就是用户同意的方式;一次被拒绝的升级对这条命令是终局的——停下来解释,不要绕路"。

### E2B:把整个能力域换成远程 microVM

以上讲的都是"同一台机器上共享内核和文件系统"的沙箱方案。dsh 还提供了一条完全不同的路径——`packages/e2b`,把 `ctx.fs` 和 `ctx.subprocess` 两个 seam 的 Provider 都换成基于 E2B 云端 microVM 的实现(`fs-e2b`、`subprocess-e2b`),背后由 `E2BRuntime`(`packages/e2b/e2b/src/index.ts`)统一持有一个共享的 E2B SDK 句柄:

```typescript
// packages/e2b/e2b/src/index.ts
export interface Config {
  apiKey?: string
  cwd?: string
  timeoutMs?: number
}
```

这条路径和 `packages/sandbox` 系列的关键差异是:`sandbox`/`fs-sandbox` 依然和宿主共享内核与文件系统,只是限制了能碰到的路径范围;E2B 则是彻底换了一个执行环境——文件系统和进程都实际运行在远程的 Linux microVM 里,宿主机完全不会被触碰到。这再次印证了第一篇讲的类推:`ctx.fs` 和 `ctx.subprocess` 都是 seam,`fs-e2b`/`subprocess-e2b` 只是又一对新的 Provider,消费方(`tool-fs`、`bash-local`)不需要感知这个差异。

### 与 Claude Code/Codex 相比的两点差异

调研过程中注意到两处和一些同类工具不同的设计:一是 `ApprovalOutcome` 的取值确实没有"永久允许"这一档,每次审批都是一次性的;二是全仓库搜索 `undo_edit`、`apply_patch`、`multi_edit` 均无命中,dsh 的编辑工具没有提供撤销(undo)能力,安全网是下一篇会讲到的"乐观并发版本控制"(先读后写、写入带版本号校验),而不是"记录历史然后可以撤销"。这两点都是根据源码搜索得出的调研发现,具体的设计取舍原因源码注释里没有直接说明,不确定是有意为之还是尚未实现,这里只如实陈述现象,不做过度推测。

## 常见问题/易踩坑

**Q:`sandbox/mode` 调到 `workspace-write` 之后,是不是工作区里所有文件都可以随便改?**

不完全是。`workspace-write` 只是把"可写范围"从空集扩大到"工作区根目录加平台临时目录",并不代表沙箱内部没有更细粒度的限制——比如 `fs-observation-policy` 的"先读后写"CAS 检查(第四篇会详细展开)仍然要求写入前必须先观察过目标文件的版本,这条检查和 `sandbox/mode` 是完全独立的两层。同样,`workspace-write` 也不代表工作区之外**绝对**不可写——如果沙箱后端本身强制不完整(比如 Windows ACL 方案标记为 `partial`),理论上仍然存在通过已有的 `Everyone` 权限或硬链接绕过的余地。"模式名字听起来涵盖的范围"和"实际的强制完整性"是两个独立的问题,后者要看 `SandboxEnforcement` 的取值。

**Q:审批请求(`approval/asked`)和沙箱升级请求(escalation)是一回事吗?**

不是一回事,但升级请求最终会**借用**审批这个 seam。审批(`ctx.approval`)是一个通用机制,任何工具都可以在自己的 `tools/pre-execute` 里返回 `{ kind: 'ask' }` 来触发一次审批;沙箱升级(`approveEscalation`)是专门给"沙箱拒绝之后想更宽权限重试"这一个场景设计的更高层封装,它在校验完严格单向递增之后,内部调用的正是 `ctx.approval` 的 `request()` 方法。可以理解成审批是通用的"问人"基础设施,升级是这套基础设施在沙箱场景下的一个专用调用方——两者的关系类似第一篇讲的 seam 和其消费方。

**Q:为什么升级批准之后,`mode` override 不直接写回 `session.append('sandbox/mode', ...)`,变成会话级别的新常态?**

因为升级请求的措辞和校验逻辑通篇强调的都是"这一次"(`allowed-once`、"a one-shot retry"、"consumed by the one call that asked")。如果批准结果写回会话级别的持久事件,等价于把一次性的人工确认变成了永久性的权限提升,这正是审批机制想要避免的——`ApprovalOutcome` 里没有"永久允许"这一档不是疏漏,是刻意的设计立场,升级机制的"一次性"完全是这条立场在沙箱场景下的自然推论。如果确实想要"以后都用更宽的模式",正确的路径是通过 `/permission` 命令或者 `PermissionPresetService.set()` 显式切换会话的 `sandbox/mode`,让这次变更成为一条可审计的、独立的会话事件,而不是依附在某一次工具调用的升级批准上。

## 小结与思考题

dsh 的权限体系由三个正交旋钮构成:`sandbox/mode` 决定文件效果的强制范围,`approval/policy` 决定要不要走人工审批,`permission/preset` 只是把两者打包成方便切换的套餐。所有旋钮都通过会话事件持久化,天然可重放。四个平台各自用完全不同的内核机制兑现同一份三档契约,强制完整性诚实地区分 `full` 与 `partial`(Windows 方案因 `Everyone` 例外和硬链接别名被标记为 `partial`)。升级机制要求严格单向递增加人工审批,批准结果只对这一次调用生效。E2B 提供了一条把整个执行环境换到远程 microVM 的替代路径。

思考题:

1. `approval/policy` 的 `'never'` 档位选择在 `decide()` 内部硬编码检查,而不是注册一个优先级最高的 `approval/request` 监听器。如果确实需要给某个特殊场景开一个"'never' 策略下仍允许某类操作通过"的例外,应该怎么设计,才不破坏"`'never'` 无条件拒绝"这条文档化的承诺?
2. Windows ACL 方案的两个已知缺口(`Everyone` 例外、NTFS 硬链接别名)都是"外部对象已经存在的宽松权限无法被沙箱收紧"这一类问题。如果要进一步收紧这个方案的强制力,可能需要在 `confine()` 之外的哪个环节(比如工作区初始化、文件创建时)补一道检查?
