# 安装与环境准备

> Hermes Agent 号称"随处运行"——本篇讲清楚它在 Linux/macOS/WSL2/Termux/原生 Windows 五种平台上分别是怎么落地的，尤其是原生 Windows 支持背后的具体工程手段，这是它区别于同类项目的一处亮点。

## 学习目标

- 掌握 Linux/macOS/WSL2/Termux 下的一键安装命令，以及它背后大致做了什么
- 理解原生 Windows（不依赖 WSL）安装的技术实现：便携版 Git 而非单纯 MinGit、无需管理员权限
- 知道 `hermes` 命令背后真正的可执行文件长什么样,以及 Windows 上的编码兼容层做了什么
- 了解贡献者/开发者的推荐安装路径与其背后的一条重要安全约束
- 知道卸载 / 重装时哪些数据会被保留

## 一键安装：Linux / macOS / WSL2 / Termux

Hermes 官方提供一条 curl 一键脚本，覆盖 Linux、macOS、WSL2 和 Android（Termux）：

```bash
curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash
```

安装完成后：

```bash
source ~/.bashrc    # 重新加载 shell（或 source ~/.zshrc）
hermes              # 开始对话！
```

这条脚本（`scripts/install.sh`，近 3700 行）背后做的事情，和仓库里给贡献者/开发者用的 `setup-hermes.sh` 是同一套思路，核心步骤包括：

1. **检测/安装 [uv](https://docs.astral.sh/uv/)**——Astral 出品的 Rust 编写的 Python 包管理器。脚本会依次检查 `uv`、`~/.local/bin/uv`、`~/.cargo/bin/uv`，都找不到才去下载官方安装脚本自装。
2. **确保 Python 3.11**：不依赖系统 Python，而是用 `uv python find 3.11` / `uv python install 3.11`,由 uv 自己下载和管理这个版本,避免"系统 Python 版本不对"的经典坑。
3. **创建虚拟环境**并按平台安装依赖——Termux 走 stdlib 的 `venv` + `pip`（因为 uv 在 Android 上支持有限）,桌面/服务器则优先用 `uv sync --extra all --locked` 走**哈希校验安装**（`uv.lock` 记录了每个传递依赖的 SHA256,一旦某个依赖在供应链攻击中被替换,哈希不匹配会直接拒绝安装）,失败再降级为不做哈希校验的 `pip install -e ".[all]"`。
4. **可选安装 ripgrep**（更快的文件搜索）和 **ffmpeg**（TTS 语音消息转码）。
5. 生成 `.env`（`chmod 600`,仅当前用户可读写）,把 `hermes` 命令软链接进 `~/.local/bin`（Termux 是 `$PREFIX/bin`）并写入 shell 配置文件的 PATH。
6. 把仓库自带的 Skills 同步进 `~/.hermes/skills/`。

Termux 上还有一处细节：安装器会装一个**精简依赖集** `.[termux]`,而不是完整的 `.[all]`,因为完整依赖集会拉取一批 Android 不兼容的语音相关依赖。

## 原生 Windows：PowerShell 一键脚本

Hermes 最值得单独说一说的是**原生 Windows 支持**——不需要 WSL,CLI、gateway、TUI、工具全部原生跑在 Windows 上。安装方式是在 PowerShell 里执行：

```powershell
iex (irm https://hermes-agent.nousresearch.com/install.ps1)
```

这条命令背后是 `scripts/install.ps1`,一个 5000 行的脚本,拆成几十个职责单一的函数（`Install-Uv`、`Install-Git`、`Install-SystemPackages`、`Install-Dependencies`、`Install-HermesCommandLaunchers` 等）。其中最值得展开的是 **Git Bash 的处理**——因为 Hermes 的 `bash` 工具（执行 shell 命令的内置工具）在 Windows 上依赖一个可用的 `bash.exe`。

官网 README 的说法是安装器会带上"一个便携版 Git Bash（MinGit）",但读 `Install-Git` 函数的真实实现会发现更精确的版本:

```powershell
# scripts/install.ps1 (Install-Git 函数注释节选)
# **Why PortableGit, not MinGit:**  MinGit is the minimal-automation
# distribution and ships ONLY ``git.exe`` -- no bash, no POSIX utilities.
# Hermes needs ``bash.exe`` to run shell commands.  PortableGit is the
# full Git for Windows distribution without the installer UI; it ships
# ``git.exe`` + ``bash.exe`` + ``sh``, ``awk``, ``sed``, ``grep``, ``curl``,
# ``ssh``, etc. in ``usr\bin\``.
```

也就是说,64 位/ARM64 机器上装的其实是完整的 **PortableGit**（Git for Windows 的免安装版,自带 `bash.exe` 和一整套 POSIX 工具）,只有在检测到 32 位 Windows 时才退化为 **MinGit**（因为 PortableGit 不提供 32 位构建）,并明确警告"32 位机器上 bash 相关功能不可用"。这批文件被解到 `%LOCALAPPDATA%\hermes\git`,**不需要管理员权限,完全独立于系统已装的 Git**——脚本还特意跳过了 `winget` 安装路径,理由是"系统 Git 处于半安装状态时 winget 经常失败",而自己管理一份独立副本"坏了直接删掉 `%LOCALAPPDATA%\hermes\git` 重装即可恢复"。如果机器上已经有可用的系统 Git,安装器会优先探测并复用它。

同一个函数里还会做一次**探测**（`Test-GitBashCompatibility`）,确认这个 bash 真的能启动 MSYS 程序,而不是findet 到一个残破的 Git 安装。

安装器同时负责：

- 用 `uv`（Windows 版）配好 Python 3.11 环境;
- 检测/安装 Node.js（浏览器工具需要）;
- 用 `winget`/`choco`/`scoop` 之一装好 ripgrep、ffmpeg（找不到包管理器则跳过并提示手动安装）;
- 把 `hermes` 命令的启动器安装好、写入用户级 PATH。

安装完成后按提示重启终端,运行 `hermes` 即可开始对话。

### 排错:杀毒软件误报 uv.exe

一个值得知道的真实坑:部分杀毒软件（Windows Defender、Bitdefender 等）的 ML 引擎会把 `%LOCALAPPDATA%\hermes\bin\uv.exe` 误判为恶意软件并隔离——本质是"未签名的、会联网下载安装包的 Rust 二进制"这个行为模式容易触发启发式规则。这是已知的上游问题（可参考 astral-sh/uv 的 issue #13553、#15011、#10079）,官方 README 给出了用 `gh attestation verify` 核验签名、以及把整个 `bin` 文件夹（而非某个文件哈希,因为 `uv` 每次更新哈希都会变)加入杀毒软件白名单的具体步骤。

## `hermes` 命令背后是什么

无论装在哪个平台,最终的 `hermes` 可执行文件本身极薄——它只是把控制权移交给 `hermes_cli.main`:

```python
# hermes（仓库根目录,无扩展名的可执行脚本）
#!/usr/bin/env python3
"""
Hermes Agent CLI launcher.

This wrapper should behave like the installed `hermes` command, including
subcommands such as `gateway`, `cron`, and `doctor`.
"""

if __name__ == "__main__":
    from hermes_cli.main import main
    main()
```

真正有意思的是每个入口模块顶部都会先 `import hermes_bootstrap`（`hermes_bootstrap.py`）。这个模块只在 Windows 上生效,解决两个长期存在的 Python-on-Windows 编码坑:

1. Windows 控制台默认绑定的是本地代码页（比如美区英文系统的 `cp1252`）,导致 `print("café")` 直接抛 `UnicodeEncodeError`;
2. `subprocess` 派生的子进程默认继承同样的编码,沙箱工具、委派子代理、linter 子进程都可能因此崩溃。

`hermes_bootstrap.py` 在所有其他 import 之前,把 `PYTHONUTF8=1`、`PYTHONIOENCODING=utf-8` 设进环境变量（供子进程继承）,并对当前进程的 `stdout`/`stderr`/`stdin` 调用 `reconfigure(encoding="utf-8", errors="replace")`。它在 POSIX 系统上完全是空操作——"POSIX 系统 99% 情况下默认已经是 UTF-8,不应该去动用户可能特意配置过的 `LANG`/`LC_*`"。这个模块同时也是 `sys.path` 加固（防止用户项目目录下的 `utils/`、`proxy/` 之类同名包顶替掉 Hermes 自己的顶层模块）和不可变 Docker 镜像下"lazy 依赖"重新挂载的入口——这些细节会在后面工程实践章节展开,这里只需要知道:**每个 Hermes 入口点导入的第一行几乎总是 `import hermes_bootstrap`**。

## 贡献者/开发者安装路径

如果你打算读源码或提交 PR,官方推荐的方式不是随手 `git clone` 到任意目录,而是先跑标准安装器,再进入它创建的托管 checkout:

```bash
curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash
cd "${HERMES_HOME:-$HOME/.hermes}/hermes-agent"
uv pip install -e ".[all,dev]"
scripts/run_tests.sh
```

如果你确实需要一次性 clone（比如 CI、临时复现问题）,README 给出的手动路径里有一条容易被忽略但很重要的注释:

> Create the venv outside the cloned source tree — a venv inside the directory the agent operates from can be wiped by a relative-path command the agent runs against its own checkout, destroying the running runtime mid-session.

也就是说**虚拟环境必须建在被 Agent 操作的代码目录之外**,因为 Agent 本身有权限对它工作的目录执行相对路径命令——如果 venv 就放在这个目录里,一次看似无害的清理操作就可能把正在运行的 Python 运行时自己删掉。

## Nix 支持（可选）

仓库根目录还有一份 `flake.nix`,基于 `flake-parts` + `uv2nix` 组织,提供了声明式的开发环境和可安装包,并且导出了 `homeManagerModules` 供 Home Manager 用户直接复用配置。这是给已经在用 NixOS/Nix 生态、希望声明式管理 Hermes 环境的用户的备选项,本课程后续不会展开,感兴趣可以直接读 `nix/` 目录下的几个模块文件。

## 卸载与数据保留

无论用哪种方式安装,Hermes 的个人数据都集中存放在 `HERMES_HOME` 指向的目录——POSIX 系统默认是 `~/.hermes`,原生 Windows 默认是 `%LOCALAPPDATA%\hermes`,WSL2 则仍然遵循 Linux 的 `~/.hermes`。卸载 CLI 本体不会清空这个目录,配置、凭证、会话、Skills 都还在,重装/升级可以放心操作。`HERMES_HOME` 这个环境变量在第 05 篇（Profile 与个性化配置）里还会深入讲——它正是 Hermes 支持"多实例隔离"的核心机制。

## 小结与思考题

Hermes 的安装体验刻意做到了"平台无关":Linux/macOS/WSL2/Termux 走同一条 curl 一键脚本,原生 Windows 走独立的 PowerShell 脚本,但两者背后的设计目标一致——用 `uv` 托管 Python 版本、用锁文件做供应链加固、把命令软链接/启动器装进用户级目录而不依赖系统权限。原生 Windows 支持的关键工程手段是自带一份独立的 PortableGit（而非 README 简化描述的"MinGit"）,以及 `hermes_bootstrap.py` 这个在所有入口点最先被 import 的 UTF-8/`sys.path` 加固层。

思考题:

1. `install.ps1` 为什么宁可自己下载管理一份 PortableGit,也不用 `winget install Git.Git`?如果换成你来设计,还能想到哪些场景会让"复用系统包管理器"变得不可靠?
2. `hermes_bootstrap.py` 里 `harden_import_path()` 要解决的问题（用户项目目录下的同名包顶替 Hermes 自身模块）在 PI 这样的 TypeScript 项目里是否也会存在?为什么 Python 项目对这类问题格外敏感?
3. 贡献者安装文档里"venv 不能建在 Agent 操作的目录内"这条注释,你能想到 Hermes 自身还有哪些功能（比如后面会讲到的执行后端、worktree）也可能触发类似的自毁风险吗?
