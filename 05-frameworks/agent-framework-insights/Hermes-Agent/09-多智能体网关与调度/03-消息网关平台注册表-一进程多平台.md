# 消息网关平台注册表——一进程多平台

> hermes-agent 的 gateway 是一个单一长驻进程,却要同时接 Telegram、Discord、Slack、WhatsApp、Signal、Email 等二十多个消息平台的收发。如果每接入一个新平台就往 gateway 核心加一个 `elif platform == Platform.XXX`,核心文件会无限膨胀,而且每加一个平台都要改动、重新测试同一个核心函数。hermes-agent 的做法是引入一张显式的平台适配器注册表(`gateway/platform_registry.py`),让插件平台"自己举手注册",gateway 优先查注册表、查不到才退回旧的 if/elif 链——新旧两条路径长期共存,没有一次性推翻重写。这正是"渐进式重构"在真实工程里的样子。本篇拆开这套注册表的机制,并简单点一下"一进程多平台"背后那些运维级问题(排空、重启风暴、会话恢复、投递账本)分别由哪个文件兜底。

## 学习目标

- 理解 `_create_adapter()` 里"先查 `platform_registry`,查不到再退回内置 if/elif"这条查找顺序,以及为什么这是一种可以长期共存、不需要一次性迁移的渐进式重构范例。
- 理解 `PlatformEntry` 这个数据类如何用一堆可选回调字段(`check_fn`/`ensure_deps_fn`/`validate_config`/`standalone_sender_fn`……)把"一个平台适配器需要向 gateway 声明的所有东西"收敛成一份显式契约,而不是靠 gateway 反过来猜。
- 理解"被动依赖探测"(`check_fn`)与"主动依赖安装"(`ensure_deps_fn`)为什么要拆成两个字段而不是一个——理解错误合并会导致的两种真实故障(状态页触发 pip 安装、依赖永远装不上)。
- 理解注册表的"延迟加载"(deferred loader)设计:为什么内置平台插件不能在发现阶段就 eager import,以及一次真正的平台查找如何触发一次性加载并让并发查找者共享同一个加载事件。
- 弄清 `scope` 隔离的作用——为什么插件平台的注册要按 `HERMES_HOME` 分区域,而不是全进程共享一张表。
- 知道"一进程多平台"背后还有哪些运维级问题需要专门文件兜底(排空控制、重启风暴熔断、会话数据库恢复、投递账本),以及它们分别解决什么故障场景——不需要逐行看实现,能说出问题类型即可。

## 一个 gateway 进程,二十多个平台适配器

`gateway/run.py` 里的 `GatewayRunner._create_adapter()` 是每个平台适配器真正被实例化的地方。它的注释直接写明了查找顺序:

```python
# gateway/run.py:16750-16760(节选)
def _create_adapter(
    self,
    platform: Platform,
    config: Any
) -> Optional[BasePlatformAdapter]:
    """Create the appropriate adapter for a platform.

    Checks the platform_registry first (plugin adapters), then falls
    through to the built-in if/elif chain for core platforms.
    """
```

这句话背后是一个真实的历史演进:Telegram、Discord、Slack、WhatsApp(桥接版)、Signal、Email、飞书、企业微信、Matrix、Mattermost 等等平台的适配器代码,如今全部住在 `plugins/platforms/<name>/` 目录下,作为插件通过注册表自注册;而 `_create_adapter()` 里残留的 if/elif 分支,只剩下少数几个尚未迁移成插件的"核心"平台——WhatsApp Cloud API、Signal(内置版)、微信、API Server、Webhook、MSGraph Webhook、BlueBubbles、QQ 机器人、元宝:

```python
# gateway/run.py:16770-16791(节选)
try:
    from gateway.platform_registry import platform_registry
    if platform_registry.is_registered(platform.value):
        adapter = platform_registry.create_adapter(platform.value, config)
        if adapter is not None:
            adapter.gateway_runner = self
            return adapter
        # Registered but failed to instantiate — don't silently fall
        # through to built-ins (there are none for plugin platforms).
        logger.error(...)
        return None
except Exception as e:
    logger.debug("Platform registry lookup for '%s' failed: %s", ...)
# Fall through to built-in adapters below

if platform == Platform.WHATSAPP_CLOUD:
    ...
elif platform == Platform.SIGNAL:
    ...
elif platform == Platform.WEIXIN:
    ...
```

这里有一个容易忽视但很关键的细节:**如果注册表里确实登记了这个平台名字、但适配器构造失败,代码不会静默跌落到 if/elif 链**——因为对一个插件平台而言,if/elif 链里本来就没有它的分支,跌落下去只会白白多算一轮判断再返回 `None`。只有"注册表压根不认识这个平台名字"时,才有意义去试试内置分支。这是"查找优先级"和"失败即终止"两条规则的组合,避免了一种隐蔽的静默失败——适配器明明注册了却构造出错,不该被误判成"这平台走的是老路径,应该看看内置分支"。

## `PlatformEntry`:把适配器需要声明的一切收敛成一份契约

新增一个平台适配器需要向 gateway 交代很多事情:依赖有没有装好、配置合不合法、要不要主动装依赖、认证走哪个环境变量、cron 投递怎么找默认频道、消息长度上限是多少……如果这些散落在 gateway 到处判断"这是不是 Telegram""这是不是 Slack",核心代码会变成一堆平台专属的特判。`PlatformEntry` 把这些全部收敛成一份数据类的字段:

```python
# gateway/platform_registry.py:63-77(节选)
@dataclass
class PlatformEntry:
    """Metadata and factory for a single platform adapter."""
    name: str
    label: str
    adapter_factory: Callable[[Any], Any]
    check_fn: Callable[[], bool]
    validate_config: Optional[Callable[[Any], bool]] = None
    ensure_deps_fn: Optional[Callable[[], bool]] = None
    is_connected: Optional[Callable[[Any], bool]] = None
    required_env: list = field(default_factory=list)
    install_hint: str = ""
    setup_fn: Optional[Callable[[], None]] = None
    source: str = "plugin"
    ...
```

除了这些,`PlatformEntry` 还声明了 `parse_target_ref_fn`(平台自己的目标寻址语法,比如 `fmsg:@alice@example.com`)、`apply_yaml_config_fn`(平台自己把 `config.yaml` 翻译成环境变量/`extra` 字段的逻辑)、`standalone_sender_fn`(cron 进程和 gateway 进程分离部署时,不经过活的适配器对象也能发消息)等十几个可选字段——**每一个字段都是"平台插件可以自己实现的一个可选能力",gateway 核心代码只需要按字段名调用,完全不需要知道具体是哪个平台**。这是"用数据契约替代类型判断"的一个直接体现:新增一个平台从来不需要改 `PlatformEntry` 或 `PlatformRegistry` 本身,只需要按契约填好一份新的 `PlatformEntry` 实例。

`register_platform()` 是插件侧真正调用的入口,以 Telegram 插件为例:

```python
# plugins/platforms/telegram/adapter.py:11038-11055(节选)
def register(ctx) -> None:
    """Plugin entry point — called by the Hermes plugin system."""
    ctx.register_platform(
        name="telegram",
        label="Telegram",
        adapter_factory=_build_adapter,
        check_fn=telegram_deps_present,
        ensure_deps_fn=check_telegram_requirements,
        is_connected=_is_connected,
        required_env=["TELEGRAM_BOT_TOKEN"],
        install_hint="Run `hermes setup` to install Telegram support.",
        setup_fn=interactive_setup,
        apply_yaml_config_fn=_apply_yaml_config,
        allowed_users_env="TELEGRAM_ALLOWED_USERS",
        allow_all_env="TELEGRAM_ALLOW_ALL_USERS",
        cron_deliver_env_var="TELEGRAM_HOME_CHANNEL",
        standalone_sender_fn=_standalone_send,
        max_message_length=4096,
        emoji="✈️",
    )
```

而 `PluginContext.register_platform()`(`hermes_cli/plugins.py`)只是把这些参数原样打包成一个 `PlatformEntry(source="plugin", ...)`,再交给全局单例 `platform_registry.register()`——插件本身不直接碰 `PlatformRegistry` 的内部实现。

## 被动探测与主动安装:为什么要拆成两个字段

`check_fn` 和 `ensure_deps_fn` 长得很像,都是"检查/搞定这个平台的依赖",但源码注释专门解释了为什么必须拆成两个独立字段,而不是合而为一:

```python
# gateway/platform_registry.py:78-101(节选,PlatformEntry 字段注释)
# PASSIVE dependency probe: returns True when the platform's dependencies
# are available RIGHT NOW.  Must be side-effect free — it is called from
# status displays (``hermes setup``, ``hermes status``, the dashboard
# readiness probe) and the config enablement pass, none of which may
# trigger a pip install.  Put install logic in ``ensure_deps_fn`` instead.
check_fn: Callable[[], bool]
...
# ACTIVE dependency installer: make the platform's dependencies available,
# installing them (pip / lazy_deps) if needed. ...
#
# Why two fields (#79812): when the ACTIVE installer was registered as
# ``check_fn``, every status display pip-installed SDKs as a side effect
# (desktop boot-loop at 94%, see gateway/config.py enablement comments);
# when the PASSIVE probe was registered instead, ``create_adapter()``
# returned None before ``connect()`` could lazy-install, so the deps
# never installed at all (Teams deadlock).  Splitting the two roles makes
# both call sites correct by construction.
ensure_deps_fn: Optional[Callable[[], bool]] = None
```

这段注释描述的是两个真实踩过的坑:如果把"主动安装"注册成 `check_fn`,状态页(`hermes setup`/`hermes status`/dashboard 就绪探测)每次展示状态都会顺手触发一次 `pip install`,桌面客户端因此卡在启动进度 94% 反复安装;反过来如果只留"被动探测"、没有主动安装钩子,`create_adapter()` 在依赖还没装好时直接返回 `None`,而依赖原本设计成"连接时才惰性安装"(比如 Teams),于是永远没有一个时机真正触发安装,平台死锁在"缺依赖"状态。`create_adapter()` 里对应的调用顺序把这个区别落到了实处——先探测,探测失败且有安装钩子才安装,安装完还失败才真正判定失败:

```python
# gateway/platform_registry.py:585-610(节选,create_adapter)
deps_ok = bool(entry.check_fn())
if not deps_ok and entry.ensure_deps_fn is not None:
    logger.info("Platform '%s' dependencies missing — attempting install...", entry.label)
    deps_ok = bool(entry.ensure_deps_fn())
if not deps_ok:
    hint = f" ({entry.install_hint})" if entry.install_hint else ""
    logger.warning("Platform '%s' requirements not met%s", entry.label, hint)
    return None
```

这是"两个字段各自只在正确的时机被调用"的工程原则——拆分字段本身不是目的,目的是让"状态展示绝不产生副作用"和"真正连接时才允许安装"这两条互相冲突的要求,分别落在两个不会被误用的调用点上。

## 延迟加载:发现阶段只挂"如何加载"的钩子,不真的导入

平台适配器模块往往在模块顶层就 `import` 平台专属的重型 SDK(`discord.py`、`slack_bolt`、飞书 SDK……)。如果插件发现阶段就把所有平台插件都 eager import 一遍,`hermes chat` 这种完全用不到任何 gateway 平台的普通命令,启动时间也会被平摊上好几秒。`PlatformRegistry` 的解法是注册一个"延迟加载器"而不是真正的 `PlatformEntry`:

```python
# gateway/platform_registry.py:250-263(节选,PlatformRegistry.__init__ 注释)
# Deferred platform loaders: name -> zero-arg callable that imports the
# owning plugin module (which calls register() and populates _entries).
#
# Why this exists: platform adapter modules import heavy, platform-
# specific SDKs at module level ... Eagerly loading all ~20 bundled
# platform plugins at plugin-discovery time added several seconds to
# *every* `hermes` invocation ... Discovery now registers a cheap
# deferred loader per platform; the real module is imported only when a
# registry lookup actually asks for that platform (gateway start, cron
# delivery, `hermes setup`/`gateway status`, send_message).
```

真正触发加载的是 `_resolve()`:第一次有人查某个平台名字时,弹出对应的 `loader` 并执行它(执行期间释放锁,只在记录状态时持锁),`loader` 内部才真正 `import` 插件模块、跑到 `register()`、把占位的 deferred 换成真正的 `PlatformEntry`。并发场景下如果两个线程同时查同一个还没加载的平台,后到的线程不会重复触发加载,而是等第一个加载者的 `threading.Event` 被 `set()`——这是一个典型的"单次执行、多方等待"（single-flight）模式:

```python
# gateway/platform_registry.py:335-348(节选,_resolve)
if event is None and loader is not None:
    event = threading.Event()
    self._inflight[load_key] = event
    self._inflight_loaders[load_key] = loader
    ...
    is_loader = True
if not is_loader:
    event.wait()
    self._resolve(name, active_scope)
    return
```

`register_deferred()` 的文档还补了一句很重要的优先级规则:"一个真正被直接注册的条目(比如一个内置适配器)优先于任何待处理的延迟加载器"——也就是说具体注册永远覆盖占位声明,不会出现"延迟加载器迟迟不触发,真实注册反而被挡住"的倒挂。

## 按 `HERMES_HOME` 分区域的注册作用域

`PlatformRegistry` 内部维护的不是一张全局表,而是"进程全局表 + 按 scope 分区的表"两层结构:

```python
# gateway/platform_registry.py:239-248(节选)
self._entries: dict[str, PlatformEntry] = {}
# Plugin adapters are isolated per resolved HERMES_HOME and overlay the
# process-global entries for lookups in that profile's runtime scope.
self._scoped_entries: dict[str, dict[str, PlatformEntry]] = {}
```

`scope` 默认取 `hermes_home_key()`(即当前 profile 的 `HERMES_HOME`)。这解决的是多 profile 在同一进程里跑(multiplex profiles)时的隔离问题:两个 profile 各自的插件系统可能加载了不同版本、不同配置的同名平台插件(比如都叫 `telegram`,但分别绑定不同的 bot token 和不同的插件版本),它们的注册不应该互相覆盖。查找时先看当前 scope 的表,再看全局表兜底——内置适配器(比如 `gateway/relay/__init__.py` 里直接注册的中继适配器)天然是进程全局的,不需要 scope 区分。

## 插件卸载与热替换:注册表不是只增不减

`PlatformRegistry` 还提供了 `snapshot_registration()`/`restore_registration()` 这一对方法,专门支撑插件的热卸载/替换场景——比如用户在 `hermes plugins` 里禁用/重新启用某个平台插件,或者一个新版本插件覆盖了旧版本再被回滚。这里的核心难点是"识别一致性":卸载操作必须确认它要恢复的确实是自己当初替换掉的那个状态,而不是在它持有引用期间又被别的操作替换过。`restore_registration()` 用身份比较(`is not`)而不是值比较来判断"当前状态是否仍是我离开时的状态",这与许多并发数据结构里的 CAS(compare-and-swap)思路是同一类解法。这部分机制主要服务插件系统自身的生命周期管理,细节不在本篇展开,但值得记住它的存在——它是"注册表允许运行时增删,而不是只在启动时固化一次"的关键支撑。

## 一进程多平台背后的运维问题:点一下即可,不必逐个深入

平台注册表解决的是"网关进程如何发现和实例化适配器",但"一个进程同时扛住二十多个平台"还会遇到一整类运维级问题,分别有专门的文件兜底,不需要逐个讲透,但要知道它们各自对应什么故障场景:

- **`gateway/drain_control.py`**——外部排空控制。dashboard 没有直接调用一个正在跑的 gateway 的通道,所以"开始排空"这个动作走的是文件标记(`.drain_request.json`),gateway 自己的后台 watcher 读到标记就翻转成 `draining` 状态、停止接受新一轮对话。标记带着"实例化 epoch"戳记,专门解决"排空标记写在持久卷上、机器重启后被误当成还在排空"的问题(NS-570 事故:自动更新后的实例因为读到旧标记卡在排空状态约 52 分钟)。
- **`gateway/restart_loop_guard.py`——重启风暴熔断**。如果某个 agent 的一次操作反复触发 gateway 重启(比如一条终端命令杀掉了网关进程),supervisor 的自动重启策略会不断把这个坏会话重放一遍、再次触发重启,陷入死循环。这个模块记录每次"带着中断会话启动"的时间戳,连续启动间隔过短就判定"熔断已触发",当次启动跳过自动恢复那个会话,把人重新拉回决策链路里。
- **`gateway/session_db_recovery.py`——会话数据库恢复**。给每个路径的 `SessionDB` 句柄缓存包一层"可恢复"的健康状态跟踪,记录失败次数和下次重试时间,让某个 profile 的数据库句柄暂时不可用时不会拖垮整个网关,也不会无限重试。
- **`gateway/delivery_ledger.py`——投递账本**。一段已经生成、但还没确认送达消息平台的最终回复,是网关唯一可能"悄无声息丢掉"的东西——这轮对话已经消耗了 token,文本只存在于 Python 的局部变量里,进程在"生成完毕"和"平台确认收到"之间崩溃或计划内重启,文本就没了。这个模块在共享的 `state.db` 里为每条待发送的最终回复记一行状态机(`pending → attempting → delivered/failed`),启动时清理"持有者进程已死"的行并交给网关重新投递,重投递时带着明确的"这是恢复重发"标记,做到诚实的"至少一次"语义而不是悄悄的重复消息。

这四个文件共同说明一件事:**支撑"一进程多平台"的,不只是平台适配器怎么被发现和实例化(注册表解决的问题),还有进程本身的生命周期——重启、排空、崩溃恢复、投递确认——如何在多平台并发的情况下保持诚实和可预测**。

## 小结与思考题

`gateway/platform_registry.py` 是渐进式重构的一个具体范例:内置的少数几个尚未迁移的平台继续走 `_create_adapter()` 里的 if/elif 硬编码链;绝大多数平台(Telegram、Discord、Slack、WhatsApp 桥接版、Signal、Email、飞书、企业微信等)已经迁移成插件,通过 `ctx.register_platform()` 把自己的适配器工厂、依赖探测/安装回调、配置校验、认证环境变量、投递能力等打包成一份 `PlatformEntry`,自注册进全局单例 `platform_registry`。gateway 查找适配器时先查注册表、查不到才退回旧链路,两条路径长期共存,新增平台从来不需要改动核心文件。注册表本身还处理了三类工程难题:被动探测与主动安装必须是两个不同的回调(否则要么状态页产生副作用,要么依赖永远装不上);模块级重量导入必须延迟到真正被查找的那一刻,并发查找者共享同一次加载;多 profile 场景下注册需要按 `HERMES_HOME` 分区域。除此之外,"一进程多平台"还牵出一整类运维问题(排空、重启熔断、会话恢复、投递账本),各自由独立文件兜底。

思考题:

1. `_create_adapter()` 对"注册表里有名字但适配器构造失败"选择直接返回 `None`,而不是退回 if/elif 链再试一次。如果一个插件平台的名字恰好和某个内置 `Platform` 枚举值撞车(比如插件也叫 `signal`),这条"查到即终止"的规则会带来什么后果?你觉得这种命名冲突应该在注册阶段就拒绝,还是允许"后注册者覆盖"?
2. `check_fn`(被动)与 `ensure_deps_fn`(主动)拆分是为了让"状态展示"和"真正连接时安装"分别落在正确的调用点上。如果你要新增一个字段表示"卸载/清理这个平台的依赖",应该给它设计成被动查询还是主动执行?调用时机应该挂在 gateway 生命周期的哪个钩子上?
