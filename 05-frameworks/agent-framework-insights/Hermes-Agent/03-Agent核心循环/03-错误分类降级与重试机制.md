# 错误分类、降级与重试机制

> 一次模型 API 调用可能因为几十种原因失败：限流、鉴权过期、上下文超长、内容审查拒绝、供应商内部错误、SSL 握手失败……hermes-agent 用 `agent/error_classifier.py` 里一个近 2200 行的优先级管线,把任意异常统一规约成一个携带 `reason`/`retryable`/`should_compress`/`should_rotate_credential`/`should_fallback` 五个字段的 `ClassifiedError`。`agent/conversation_loop.py` 里的重试循环只认这五个字段做决策,不需要自己再解析一遍错误文案。本篇梳理这套分类体系,以及分类结果如何驱动重试、凭据轮换与多 provider 降级。

## 学习目标

- 理解 `agent/errors.py`、`agent/error_surface.py`、`agent/error_classifier.py` 三个文件各自的职责边界。
- 掌握 `FailoverReason` 枚举定义的错误分类体系,以及 `ClassifiedError` 携带的"恢复动作提示"字段。
- 读懂 `classify_api_error()` 的优先级管线结构,理解限流/超时/上下文超长/鉴权失败/内容审查等分支各自的判断依据。
- 理解 `TurnRetryState` 如何把十几个"一次性重试守卫"从裸变量收敛成一个数据类,以及重试循环怎么消费分类结果。
- 理解多 provider 降级链(`_fallback_chain`/`_fallback_index`/`_try_activate_fallback`)的触发条件、跳过逻辑与退避策略。

## `agent/errors.py`：极简的独立异常类

这个文件只有 13 行,定义了三个与主分类体系无关的独立异常类：

```python
# agent/errors.py
class SSLConfigurationError(Exception):
    """Raised when SSL/TLS certificate bundle configuration fails."""
    pass


class EmptyStreamError(RuntimeError):
    """Raised when a provider closes a stream without yielding a response."""
    pass


class MoAPresetNotFoundError(ValueError):
    """Raised when a persisted MoA preset no longer exists in config."""
```

它们分别对应"SSL 证书包配置失败"（环境问题,不是 API 错误)、"provider 关闭了流但什么都没返回"（`classify_api_error` 会在别处对这类空流做专门处理)、"MoA(Mixture of Agents)预设配置丢失"。这三个类不参与下面的 `FailoverReason` 分类体系,是独立场景下的轻量信号。

## `agent/error_surface.py`：面向 UI 的错误呈现层

`error_surface.py`（258 行)不做分类判断,只做**面向客户端的呈现映射**。模块 docstring 说得很清楚：

```python
# agent/error_surface.py:1-27（节选）
"""Structured error-surface descriptors for UI clients (Desktop/TUI).

Maps the internal failure taxonomy (``agent.error_classifier.FailoverReason``
values carried in turn results as ``failure_reason``, or raw exceptions from
the turn dispatcher) onto a small, stable wire descriptor:

    {"layer": <ui layer>, "code": <specific code>, "retryable": <bool>}

The *layer* names which part of the stack failed, so clients can say
"Provider error" / "Gateway error" instead of toasting an opaque string...

    provider   — the model/provider API rejected or failed the call
    endpoint   — a user-configured custom/local endpoint failed (transport)
    streaming  — the provider's SSE/stream connection dropped mid-turn
    auth       — authentication/authorization failed
    billing    — credits/quota wall
    gateway    — the local gateway/agent runtime itself errored
    runtime    — agent initialization / local environment failure
    disk       — local disk full / persistence failure

This module is intentionally dependency-light and NEVER raises...
"""
```

它的两个入口函数分别处理两种来源：`build_error_surface_from_result()` 读取 `run_conversation()` 返回结果里已经打好的 `failure_reason`/`error` 字段,把 `FailoverReason` 的 `.value` 字符串映射到 8 种 UI layer 之一;`build_error_surface_from_exception()` 处理"直接从调度器逃逸出来的异常"——先判断异常是否来自已知的 API/传输库(`_API_EXC_MODULE_PREFIXES`,涵盖 openai/httpx/anthropic/botocore/google/grpc/requests/aiohttp/ssl/socket/urllib 等模块前缀),是的话才调用 `classify_api_error()` 走一遍真正的分类管线,否则直接判定为 `LAYER_GATEWAY`("不是 provider 的错,是我们自己调度器的 bug 或环境问题")：

```python
# agent/error_surface.py:233-244（节选）
exc_module = type(exc).__module__ or ""
api_like = exc_module.split(".")[0] in _API_EXC_MODULE_PREFIXES or hasattr(
    exc, "status_code"
)
if not api_like or not isinstance(exc, Exception):
    return _surface(LAYER_GATEWAY, type(exc).__name__, True, provider, model)

from agent.error_classifier import classify_api_error
classified = classify_api_error(exc, provider=provider, model=model)
```

也就是说：**`error_classifier.py` 负责"这次失败到底是什么、该怎么恢复"的内部路由判断,`error_surface.py` 负责把这份内部判断翻译成一份不会 "leak" 内部细节、也绝不会自己再抛异常的稳定 wire 格式给桌面端/TUI 展示**。两者的关系是消费方与生产方——`error_surface.py` 在多处 `import agent.error_classifier`,反过来 `error_classifier.py` 完全不知道 `error_surface.py` 的存在。

## `agent/error_classifier.py`：分类体系

### `FailoverReason`：错误分类枚举

```python
# agent/error_classifier.py:30-79（节选，共约 25 个枚举值）
class FailoverReason(enum.Enum):
    """Why an API call failed — determines recovery strategy."""

    # Authentication / authorization
    auth = "auth"                        # Transient auth (401/403) — refresh/rotate
    auth_permanent = "auth_permanent"    # Auth failed after refresh — abort

    # Billing / quota
    billing = "billing"                  # 402 or confirmed credit exhaustion — rotate immediately
    rate_limit = "rate_limit"            # 429 or quota-based throttling — backoff then rotate
    upstream_rate_limit = "upstream_rate_limit"  # Aggregator 429 — fallback model, key is healthy

    # Server-side
    overloaded = "overloaded"            # 503/529 — provider overloaded, backoff
    server_error = "server_error"        # 500/502 — internal server error, retry

    # Transport
    timeout = "timeout"                  # Connection/read timeout — rebuild client + retry
    ssl_cert_verification = "ssl_cert_verification"  # deterministic per host, fail fast

    # Context / payload
    context_overflow = "context_overflow"  # Context too large — compress, not failover
    payload_too_large = "payload_too_large"  # 413 — compress payload
    image_too_large = "image_too_large"
    image_corrupt = "image_corrupt"

    # Model / provider policy
    model_not_found = "model_not_found"  # 404 or invalid model — fallback to different model
    provider_policy_blocked = "provider_policy_blocked"
    content_policy_blocked = "content_policy_blocked"  # deterministic per-request, don't retry unchanged

    # Request format
    format_error = "format_error"
    invalid_encrypted_content = "invalid_encrypted_content"
    multimodal_tool_content_unsupported = "multimodal_tool_content_unsupported"

    # Provider-specific
    thinking_signature = "thinking_signature"
    long_context_tier = "long_context_tier"
    oauth_long_context_beta_forbidden = "oauth_long_context_beta_forbidden"
    llama_cpp_grammar_pattern = "llama_cpp_grammar_pattern"

    # Catch-all
    unknown = "unknown"                  # Unclassifiable — retry with backoff
```

每个枚举值右侧的注释本身就是"这类错误该怎么恢复"的速查表——这也是这个类的设计初衷,模块 docstring 直接写着："Provides a structured taxonomy of API errors and a priority-ordered classification pipeline that determines the correct recovery action (retry, rotate credential, fallback to another provider, compress context, or abort). Replaces scattered inline string-matching with a centralized classifier."(`agent/error_classifier.py:1-10`)

### `ClassifiedError`：分类结果 + 恢复动作提示

```python
# agent/error_classifier.py:84-101
@dataclass
class ClassifiedError:
    """Structured classification of an API error with recovery hints."""

    reason: FailoverReason
    status_code: Optional[int] = None
    provider: Optional[str] = None
    model: Optional[str] = None
    message: str = ""
    error_context: Dict[str, Any] = field(default_factory=dict)

    # Recovery action hints — the retry loop checks these instead of
    # re-classifying the error itself.
    retryable: bool = True
    should_compress: bool = False
    should_rotate_credential: bool = False
    should_fallback: bool = False
```

`reason` 只是"这是什么错误",真正驱动重试循环行为的是后面四个布尔字段——`retryable`（还要不要重试原样请求)、`should_compress`（要不要先压缩上下文再重试,典型如 `context_overflow`/`payload_too_large`)、`should_rotate_credential`（要不要先轮换凭据池里的下一把 key 再重试,典型如 401)、`should_fallback`（要不要切到降级 provider/model)。这四个字段互不排斥,一次分类可能同时打开多个（比如 401 认证失败会同时标记 `should_rotate_credential=True` 和 `should_fallback=True`——先试轮换,轮换失败再降级)。

### `classify_api_error()`：优先级管线

```python
# agent/error_classifier.py:810-830（节选）
def classify_api_error(
    error: Exception, *, provider: str = "", model: str = "",
    approx_tokens: int = 0, context_length: int = 200000, num_messages: int = 0,
) -> ClassifiedError:
    """Classify an API error into a structured recovery recommendation.

    Priority-ordered pipeline:
      0. Plugin ``transform_api_error_classification`` hooks (first valid result wins)
      1. Special-case provider-specific patterns (thinking sigs, tier gates)
      2. HTTP status code + message-aware refinement
      3. Error code classification (from body)
      4. Message pattern matching (billing vs rate_limit vs context vs auth)
      5. SSL/TLS transient alert patterns → retry as timeout
      6. Server disconnect + large session → context overflow
      7. Transport error heuristics
      8. Fallback: unknown (retryable with backoff)
    """
```

八级优先级里最值得注意的是第 0 级——**插件可以在核心分类逻辑之前介入,既能补充核心逻辑漏判的场景,也能纠正某个 provider 的误判**,回调异常被隔离,不会打断分类流程(`agent/error_classifier.py:916-940`)。第 1 级是"高优先级的特判",比如内容审查拒绝(必须在状态码判断之前拦截,否则一个不带状态码的安全拒绝会被丢进 `unknown` 的可重试桶里、白白浪费重试次数)：

```python
# agent/error_classifier.py:951-956
if any(p in error_msg for p in _CONTENT_POLICY_BLOCKED_PATTERNS):
    return _result(
        FailoverReason.content_policy_blocked,
        retryable=False,
        should_fallback=True,
    )
```

第 2 级 `_classify_by_status()` 是状态码判断的主体,几个关键分支：

```python
# agent/error_classifier.py:1259-1270
if status_code == 401:
    # Not retryable on its own — credential pool rotation and
    # provider-specific refresh (Codex, Anthropic, Nous) run before
    # the retryability check in run_agent.py.  If those succeed, the
    # loop `continue`s.  If they fail, retryable=False ensures we
    # hit the client-error abort path (which tries fallback first).
    return result_fn(
        FailoverReason.auth,
        retryable=False,
        should_rotate_credential=True,
        should_fallback=True,
    )
```

```python
# agent/error_classifier.py:1359-1372（节选，429 分支）
if status_code == 429:
    # Some providers (notably Z.AI / Zhipu) reuse HTTP 429 for
    # server-wide overload — same status code as a true per-credential
    # rate limit, but the credential is valid and the correct recovery
    # is "back off and retry the same key", NOT "rotate the credential".
    if any(p in error_msg for p in _OVERLOADED_PATTERNS):
        return result_fn(FailoverReason.overloaded, retryable=True)
    ...
```

429 分支里这段注释是一个很好的例子,说明"分类不能只看状态码,还要结合错误文案"——同样是 429,一个是"这把 key 被限流了、该轮换/退避",另一个是"整个服务过载了、轮换凭据毫无意义、只能等"。413(payload 过大)、404(区分"模型真的不存在"、"OpenRouter 隐私策略拦截了唯一可用端点"、"模型 id 缺少已知前缀的畸形请求"、"泛型 404 可能只是路由配置错误")等分支也都体现了同一种设计思路：**status code 只是入口,真正的判断依据是状态码 + 错误文案的组合模式**。

context 超长的分类走的是 `context_overflow`/`payload_too_large`,恢复动作是 `should_compress=True` 而非 `should_fallback`——这是 docstring 里特别强调的一点("Context too large — compress, not failover"),因为切换 provider 并不能解决"这段对话历史本身就太长"的问题,只有压缩才是对症的恢复手段。

## 重试循环如何消费分类结果

`agent/conversation_loop.py` 的重试循环在捕获到 API 异常后,第一件事就是分类：

```python
# agent/conversation_loop.py:4779-4795（节选）
classified = classify_api_error(
    api_error,
    provider=getattr(agent, "provider", "") or "",
    model=getattr(agent, "model", "") or "",
    approx_tokens=approx_tokens,
    context_length=_ctx_len,
    num_messages=len(api_messages) if api_messages else 0,
)
logger.debug(
    "Error classified: reason=%s status=%s retryable=%s compress=%s rotate=%s fallback=%s",
    classified.reason.value, classified.status_code,
    classified.retryable, classified.should_compress,
    classified.should_rotate_credential, classified.should_fallback,
)
```

随后依次尝试(每一步失败就 `continue` 到重试循环顶部,重新走一次分类)：凭据池恢复(`agent._recover_with_credential_pool(...)`,传入 `classified.reason`)、图片过大收缩、格式修复……如果这些"针对性恢复"都不适用或都失败了,才会走到 `should_fallback` 驱动的多 provider 降级链(下一节)。

### `TurnRetryState`：把十几个裸变量收敛成一个数据类

在被拆出来之前,单次模型调用尝试内部要做的"一次性恢复守卫"(避免同一种恢复反复触发死循环)曾经是十几个散落在循环体前面的裸布尔局部变量。`agent/turn_retry_state.py` 的模块 docstring 描述了这个历史：

```python
# agent/turn_retry_state.py:1-25（节选）
"""Per-attempt recovery bookkeeping for the conversation turn loop.

The inner retry loop in ``run_conversation`` (``while retry_count <
max_retries``) makes several distinct recovery attempts on a single model API
call: a credential-pool 429 retry, a per-provider OAuth refresh (codex,
anthropic, nous, copilot), a long-context compression restart, a length-
continuation restart, and a handful of format-recovery branches...

Each of those branches is guarded by a one-shot boolean so it fires at most
once per attempt. They used to be ~16 bare ``*_attempted`` / ``has_retried_*``
/ ``restart_with_*`` locals declared inline before the loop and threaded
through its 2,400-line body. ``TurnRetryState`` collapses them into one object
the loop mutates in place (``state.codex_auth_retry_attempted = True``)...
"""
```

```python
# agent/turn_retry_state.py:32-89（节选）
@dataclass
class TurnRetryState:
    # ── Per-provider OAuth / credential refresh guards ───────────────────
    codex_auth_retry_attempted: bool = False
    anthropic_auth_retry_attempted: bool = False
    nous_auth_retry_attempted: bool = False
    copilot_auth_retry_attempted: bool = False
    ...
    # ── Transport / rate-limit recovery ──────────────────────────────────
    primary_recovery_attempted: bool = False
    has_retried_429: bool = False
    # ── Restart signals (read by the outer loop after the attempt) ───────
    restart_with_compressed_messages: bool = False
    restart_with_length_continuation: bool = False
    restart_with_rebuilt_messages: bool = False
    restart_with_redirected_messages: bool = False
```

docstring 里特别说明 `retry_count`/`max_retries`/`max_compression_attempts` 这几个纯粹的循环控制变量**故意**没有收进这个数据类——它们是 `while` 循环本身的机制,不是"恢复策略的记账",放进去只会增加一层无意义的间接。这是一处很清楚的"哪些状态该收敛、哪些不该"的边界判断示范。重试的等待本身使用带随机抖动的退避（`jittered_backoff(retry_count, base_delay=..., max_delay=...)`,`agent/conversation_loop.py:3528`/`6647`),并且等待期间以 0.2 秒为粒度轮询是否有中断/改口请求到来(第四篇会讲这个机制),而不是一次性 `time.sleep(wait_time)` 阻塞整个等待窗口。

## 多 provider 降级：`_fallback_chain` 与 `_try_activate_fallback`

当分类结果的 `should_fallback` 为真、且针对性恢复都已经试过,重试循环会调用 `agent._try_activate_fallback(reason=classified.reason)`——这也是一个转发器,真正的实现在 `agent/chat_completion_helpers.py`：

```python
# agent/chat_completion_helpers.py:2459-2469
def try_activate_fallback(agent, reason: "FailoverReason | None" = None) -> bool:
    """Switch to the next fallback model/provider in the chain.

    Called when the current model is failing after retries.  Swaps the
    OpenAI client, model slug, and provider in-place so the retry loop
    can continue with the new backend.  Advances through the chain on
    each call; returns False when exhausted.
    """
```

它维护两个状态字段：`agent._fallback_chain`（配置好的降级候选列表)和 `agent._fallback_index`（当前已经走到第几个)。每次调用只推进一格,链走完就返回 `False` 让调用方放弃降级：

```python
# agent/chat_completion_helpers.py:2493-2523（节选）
if agent._fallback_index >= len(agent._fallback_chain):
    ...
    return False
fb = agent._fallback_chain[agent._fallback_index]
agent._fallback_index += 1
fb_key = _fallback_entry_key(fb)
unavailable = getattr(agent, "_unavailable_fallback_keys", None)
if fb_key in unavailable:
    logger.debug("Fallback skip: %s previously marked unavailable", fb_key)
    return agent._try_activate_fallback(reason)
fb_provider = (fb.get("provider") or "").strip().lower()
fb_model = (fb.get("model") or "").strip()
if not fb_provider or not fb_model:
    return agent._try_activate_fallback(reason)  # skip invalid, try next
```

值得注意的几个细节：

- **候选跳过是递归自调用,不是简单的 `continue`**——本地不可用(`_fallback_entry_unavailable_without_network`)、配置不完整、已知不可用(`_unavailable_fallback_keys` 缓存),都直接递归调用 `agent._try_activate_fallback(reason)` 跳到下一个候选,而不是把"跳过逻辑"和"生效逻辑"混在一个大 `if/elif` 里。
- **防止降级到"同一个后端"造成死循环**——`agent/backend_identity.py` 的 `BackendIdentity.build()`/`should_skip_candidate()` 判断候选是否在 provider/model/base_url 维度上与当前刚失败的后端等价,是则跳过(`agent/chat_completion_helpers.py:2541-2559`):

```python
current_ident = BackendIdentity.build(
    provider=getattr(agent, "provider", ""), model=getattr(agent, "model", ""),
    base_url=str(getattr(agent, "base_url", "") or ""),
)
fb_ident = BackendIdentity.build(
    provider=fb_provider, model=fb_model, base_url=(fb.get("base_url") or ""),
)
if should_skip_candidate(fb_ident, current_ident):
    logger.warning("Fallback skip: chain entry %s/%s resolves to the same backend...")
    return agent._try_activate_fallback(reason)
```

- **限流/账单类失败会先给主 provider 安排一段指数退避冷却,而不是立即换回**：

```python
# agent/chat_completion_helpers.py:2471-2492（节选）
if reason in {FailoverReason.rate_limit, FailoverReason.billing, FailoverReason.upstream_rate_limit}:
    fallback_already_active = bool(getattr(agent, "_fallback_activated", False))
    current_provider = (getattr(agent, "provider", "") or "").strip().lower()
    primary_provider = ((agent._primary_runtime or {}).get("provider") or "").strip().lower()
    if (not fallback_already_active) or (primary_provider and current_provider == primary_provider):
        backoff_count = getattr(agent, "_rate_limit_backoff_count", 0)
        agent._rate_limit_backoff_count = backoff_count + 1
        backoff_seconds = min(60 * (2 ** backoff_count), 14400)
        agent._rate_limited_until = time.monotonic() + backoff_seconds
```

这段逻辑只在"确实是离开主 provider 时"才启动/延长冷却——如果已经在降级链上再往下走(不是刚刚离开主 provider),就不重置冷却计时,这样主 provider 的冷却窗口不会被后续无关的降级事件意外拉长。冷却时间是标准的指数退避(60s → 2m → 4m → …,上限 4 小时),但触发条件是"连续限流",而不是每次限流都从头计算,首次 429 不会立即把主 provider 打入半小时冷却。

- **成功匹配到候选后,用统一的 `resolve_provider_client()` 走一遍鉴权与客户端构造**(`agent/chat_completion_helpers.py:2564-2610`),包括从降级配置里解析 `api_mode`(比如显式配置的 `provider: anthropic` 会被解析成 `anthropic_messages`,即便用户没有显式写 `api_mode`)、从环境变量或 secret scope 里补齐 API key(比如 Ollama Cloud 端点会自动去读 `OLLAMA_API_KEY`)。降级生效之后,同一次重试循环会带着新的 `agent.provider`/`agent.model`/`agent.base_url` 重新发起请求,对用户表现为"同一轮对话无缝换了一个模型继续"。

## 关键代码解读

三个文件的分工可以概括为一句话：`error_classifier.py` 回答"这是什么错误、该怎么恢复"（生产 `ClassifiedError`),`error_surface.py` 回答"这个错误该用什么样的文案/图标呈现给用户"（消费 `ClassifiedError`/`FailoverReason`,生成稳定的 `{"layer", "code", "retryable"}` 三元组),`errors.py` 只是三个跟主分类体系无关的小异常类。重试循环(`agent/conversation_loop.py` 内部超过 2000 行的 `while retry_count < max_retries` 块)的核心节奏是：**分类 → 按 `should_rotate_credential`/`should_compress`/`should_fallback` 的优先级依次尝试针对性恢复 → 都不适用或都失败则调用 `_try_activate_fallback` 走降级链 → 用新的 provider/model 重新发起请求**,`TurnRetryState` 把"这次尝试有没有已经试过某种恢复"这件事从裸变量收敛成一个可测试的对象。

## 小结与思考题

hermes-agent 用一个约 25 个值的 `FailoverReason` 枚举 + `ClassifiedError` 的四个布尔恢复提示字段,把"错误分类"和"恢复决策"彻底解耦——分类函数只管判断"这是什么",不管"该怎么办",怎么办完全由消费方(重试循环)根据这几个字段自行决定。多 provider 降级链(`_fallback_chain`/`_fallback_index`)通过递归跳过无效/重复/已知不可用的候选、结合 `BackendIdentity` 防止死循环、结合指数退避冷却防止对限流中的主 provider 频繁重试,构成了一套相对完整的自动降级机制。

思考题：

1. `classify_api_error()` 的优先级管线里,插件分类(第 0 级)排在内置的所有分支之前——如果一个第三方插件把某个本该是 `content_policy_blocked`（不可重试)的错误误判成 `unknown`（可重试),会造成什么后果？源码里有没有什么机制能缓解这类误判的影响？
2. `TurnRetryState` 明确不收纳 `retry_count`/`max_retries` 这两个循环控制变量。如果你要新增一种"最多重试 2 次的格式修复"恢复分支,这个"最多 2 次"的计数应该放进 `TurnRetryState` 还是作为独立的裸变量？依据是什么？
3. `_try_activate_fallback` 对限流类失败设置的冷却时间只在"离开主 provider 时"生效——如果用户的降级链里配置了 3 个候选 provider,第 2 个候选也返回了限流错误,这次限流会不会延长第 1 步为主 provider 记的冷却时间？为什么源码要这样设计？
