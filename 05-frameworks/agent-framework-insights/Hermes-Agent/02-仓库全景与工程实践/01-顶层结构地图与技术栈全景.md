# 顶层结构地图与技术栈全景

> hermes-agent 是一个体量远超典型 Agent 项目的仓库:根目录下几个核心 Python 文件动辄万行(`cli.py`
> 102 万字节、`hermes_state.py` 70 万字节),`agent/`、`hermes_cli/`、`tools/` 各有一两百个文件,还并存着
> TypeScript/Ink 终端 UI、Electron 桌面应用、Vite Web 仪表盘、Docusaurus 文档站和一份自研的 C 语言
> SQLite 扩展。在深入任何具体子系统之前,必须先建立一张可靠的顶层地图——不是凭空画的框图,而是逐个
> 目录、逐个入口文件实际 `ls`/读 docstring 核实过的地图,后面每一章讲某个子系统时才知道它在整个仓库里
> 处在什么位置、和谁协作。

## 学习目标

- 记住仓库根目录下每一个顶层目录和关键单文件的职责,能在需要时快速定位到正确的代码位置。
- 理解 hermes-agent 的技术栈全景:Python 核心运行时、TypeScript/Node 前端矩阵、C 原生扩展、Nix/Docker
  两套打包体系分别覆盖什么。
- 理解 `tools/registry.py → model_tools.py → run_agent.py/cli.py` 这条"工具自注册"依赖链的方向。
- 知道 `hermes_state*.py` 为什么拆成五个文件而不是一个,理解 mixin 式模块拆分的意图。
- 建立一张"想读懂某个功能该从哪个目录入手"的速查表,作为后续章节的导航索引。

## 顶层单文件:大多是"核心运行时"级别的模块

除了目录,根目录本身还平铺着一批体量巨大的单文件——AGENTS.md 的 Project Structure 一节把它们称为
"load-bearing entry points"(承重入口点)。逐个读过 docstring/顶部注释后,职责如下:

| 文件 | 体量 | 职责(引自文件内 docstring) |
|---|---|---|
| `run_agent.py` | ~43 万字节 | `AIAgent` 类——核心对话循环、工具分发、会话持久化,AGENTS.md 标注 ~12k LOC |
| `cli.py` | ~102 万字节 | `HermesCLI` 类——交互式 CLI 编排器,AGENTS.md 标注 ~11k LOC |
| `model_tools.py` | ~7.7 万字节 | "工具注册表之上的薄编排层"——触发 `tools/` 下所有模块的自注册发现 |
| `toolsets.py` | ~3.9 万字节 | `TOOLSETS` 字典定义,`_HERMES_CORE_TOOLS` 默认工具集列表 |
| `hermes_state.py` | ~70 万字节 | `SessionDB`——SQLite 会话存储主类,FTS5 全文搜索 |
| `hermes_state_common.py` | — | `SessionDB` 系列 mixin 共享的模块级常量,避免循环导入 |
| `hermes_state_schema.py` | ~7.5 万字节 | Schema 建表、列对齐、FTS DDL 管理(mixin) |
| `hermes_state_search.py` | ~11.6 万字节 | 全文/trigram/中日韩搜索与 FTS 维护(mixin) |
| `hermes_state_portability.py` | ~3.7 万字节 | 会话列表、导出/导入(mixin) |
| `hermes_constants.py` | ~7.3 万字节 | `get_hermes_home()`、`display_hermes_home()`——profile 感知的路径解析 |
| `hermes_logging.py` | ~3.2 万字节 | `setup_logging()`——agent.log/errors.log/gateway.log |
| `batch_runner.py` | ~6 万字节 | 并行批处理跑数据集,产出训练轨迹 |
| `mini_swe_runner.py` | ~2.8 万字节 | 用 Hermes 自己的执行环境(local/docker/modal)跑 SWE 任务,输出 Hermes 轨迹格式 |
| `trajectory_compressor.py` | ~7 万字节 | 训练轨迹压缩——保留首尾轮次,只压缩中间轮次 |
| `toolset_distributions.py` | ~1.2 万字节 | 数据生成时的工具集抽样分布定义 |
| `model_tools.py`/`toolsets.py` 之外 | | |
| `mcp_serve.py` | ~3.8 万字节 | 反向暴露:把 Hermes 自己的消息会话作为 MCP 工具供 Claude Code/Cursor 等客户端调用 |
| `registration_lifecycle.py` | ~4 千字节 | 可替换运行时注册的"所有权租约",区分注册的世代(generation) |
| `hermes_bootstrap.py` | ~1 万字节 | Windows UTF-8 启动引导——修 stdout 编码和子进程编码两个 Windows 老坑 |
| `utils.py` | ~3.7 万字节 | 通用工具函数 |

`hermes_state*.py` 拆成五个文件是一个值得单独记住的设计:`hermes_state.py` 里的 `SessionDB` 是主类,
`_schema`/`_search`/`_portability` 三个文件是**纯 mixin**——docstring 明确写道"这是一个普通 mixin 类,
被 `hermes_state.SessionDB` 消费;它不定义 `__init__`、不持有自己的状态;方法访问的是宿主的
`self._conn`/`self.db_path`/`self._execute_write` 等属性"。之所以还要专门拆出 `hermes_state_common.py`
放"共享的模块级常量",docstring 里写得很直白:是为了让三个 mixin 模块能互相引用常量,而不必导入
`hermes_state`(会形成循环导入)。这是一种常见于超大类拆分的模式:保留一个"胖类"作为对外契约,但把它的
内部实现按关注点切成可以独立读、独立测试的 mixin 文件。

## 技术栈全景:四种语言,分层清晰

```
┌─────────────────────────────────────────────────────────────────┐
│ 应用/交互层                                                       │
│  ui-tui/ (TypeScript + Ink/React)  ── hermes --tui 终端渲染        │
│  apps/desktop/ (Electron + TS)     ── 桌面聊天应用                 │
│  apps/bootstrap-installer/ (Tauri + Rust) ── 图形化安装器          │
│  web/ (Vite + React + TS)          ── hermes dashboard 本地仪表盘  │
│  website/ (Docusaurus + TS)        ── 文档站                      │
├─────────────────────────────────────────────────────────────────┤
│ Python 核心运行时                                                 │
│  run_agent.py / cli.py / model_tools.py / toolsets.py             │
│  agent/ / hermes_cli/ / tools/ / gateway/ / cron/ / plugins/       │
│  hermes_state*.py (SQLite + FTS5 会话存储)                        │
├─────────────────────────────────────────────────────────────────┤
│ 通信/协议桥接层                                                    │
│  tui_gateway/ (Python JSON-RPC，服务 ui-tui)                       │
│  acp_adapter/ (ACP 协议服务端，服务 VS Code/Zed/JetBrains)         │
├─────────────────────────────────────────────────────────────────┤
│ 原生扩展层                                                         │
│  native/fts5_cjk/ (C) ── 自研 SQLite FTS5 中日韩分词扩展            │
├─────────────────────────────────────────────────────────────────┤
│ 打包/部署层                                                        │
│  Docker (Dockerfile + docker-compose*.yml + s6-overlay)            │
│  Nix (flake.nix + nix/*.nix ── 声明式可复现部署)                   │
└─────────────────────────────────────────────────────────────────┘
```

几个容易被忽略但值得记住的细节:

- **Rust 也在仓库里**,只是藏在一个不起眼的位置——`apps/bootstrap-installer/src-tauri`。这是 Tauri 桌面
  安装器("Hermes-Setup")的 Rust 后端,CI 里专门有一条 `rust-tests.yml` 跑 `cargo test`(见第 3 篇)。
- `native/fts5_cjk/` 是仓库里唯一的 C 代码:一个自研的 SQLite FTS5 分词器扩展(`fts5_cjk.c`),为
  `hermes_state_search.py` 的中日韩全文搜索提供底层支持,`build.sh` 负责编译,`vendor/` 目录带了依赖。
- `providers/` 目录很小(只有 `base.py` + `__init__.py` + `README.md`),它只放 `ProviderProfile` 这个
  抽象和注册表本身;具体的 provider 实现("profiles themselves")作为插件活在别处——这是"核心只放契约,
  实现下沉到插件"这套思路在代码组织上的直接体现,后面插件系统一章会展开。
- `apps/` 下三个子应用彼此独立:`desktop` 是 Electron + TypeScript,`bootstrap-installer` 是 Tauri +
  Rust(负责"图形化装 Hermes"这件更轻量的事),`shared` 是它们共用的代码。

## 速查表:想读懂 X 功能,从哪个目录入手

| 我想读懂… | 从这里入手 |
|---|---|
| Agent 的对话循环怎么跑起来的 | `run_agent.py`(`AIAgent` 类)→ `agent/` |
| 一个工具是怎么被模型看到并调用的 | `tools/registry.py` → `model_tools.py` → 具体 `tools/*.py` |
| 某个 slash 命令/CLI 子命令怎么加 | `hermes_cli/commands.py`(注册表)、`hermes_cli/subcommands/` |
| Telegram/Discord/Slack 等平台怎么接进来的 | `gateway/run.py`、`gateway/session.py`、`gateway/platforms/<name>.py` |
| TUI 界面是怎么渲染的 | `ui-tui/src/`(Ink 前端)+ `tui_gateway/`(Python JSON-RPC 后端) |
| 桌面应用怎么打包、怎么跟后端通信 | `apps/desktop/`(Electron)、`apps/desktop/src/plugins/hermes-bots/` |
| 会话是怎么存储和搜索的 | `hermes_state.py` + 四个 `hermes_state_*.py` mixin |
| 一个新能力该加在哪一层(Skill/工具/插件/MCP) | AGENTS.md "Footprint Ladder" 一节(见本章第 4 篇) |
| 技能(Skill)是怎么被发现、加载、自我改进的 | `skills/`、`optional-skills/`、AGENTS.md "Skills" 一节 |
| 插件怎么写 | `plugins/<name>/`、`hermes_cli/plugins.py`(`PluginManager`) |
| MCP 服务器怎么接入 | `optional-mcps/<name>/`、AGENTS.md 里 MCP catalog 相关小节 |
| 定时任务/Cron 怎么跑的 | `cron/scheduler.py`、`cron/jobs.py` |
| 终端命令实际在哪个环境执行(本地/Docker/SSH/云沙箱) | `tools/environments/`(`local.py`/`docker.py`/`ssh.py`/`modal.py`/`daytona.py`/`singularity.py`/`vercel_sandbox.py`) |
| 训练数据/轨迹是怎么生成和压缩的 | `batch_runner.py`、`mini_swe_runner.py`、`trajectory_compressor.py`、`evals/` |
| 容器怎么部署 | `Dockerfile`、`docker-compose.yml`、`docker/entrypoint-dispatch.sh` |
| Nix 怎么打包/部署 | `flake.nix`、`nix/hermes-agent.nix`、`nix/nixosModules.nix`、`nix/homeManagerModules.nix` |

## 小结与思考题

hermes-agent 的顶层结构呈现出一种"核心窄、边缘宽"的形态:少数几个万行级 Python 文件(`run_agent.py`、
`cli.py`、`hermes_state.py`)构成运行时核心,`tools/`、`plugins/`、`skills/`、`optional-mcps/` 这些"边缘
目录"则数量庞大、可以无限增长而不影响核心——这与 AGENTS.md 开篇"它主要通过 plugins 和 skills 扩展,
而不是靠做大核心"的定位完全一致。技术栈上,Python 承担运行时和 CLI,TypeScript/Node 承担三种不同形态
的前端(终端渲染、桌面应用、Web 仪表盘),C 只在一个非常局部但性能敏感的位置(FTS5 中日韩分词)出现,
Nix 和 Docker 则是两条并行但定位不同的部署路径。

1. 如果要新增一个"WeCom(企业微信)以外的第三个国产 IM 平台"支持,应该新建哪个目录下的哪个文件?需要
   同时改动 `toolsets.py` 吗?
2. `hermes_state_common.py` 存在的唯一理由是"避免循环导入"。如果不拆出这个文件,直接把常量放进
   `hermes_state.py` 然后让三个 mixin `from hermes_state import XXX`,会在什么时候真正触发
   `ImportError: cannot import name ... (most likely due to a circular import)`?
3. `apps/bootstrap-installer` 用 Tauri+Rust,`apps/desktop` 用 Electron+TypeScript——两者都是"给 Hermes
   做一个桌面壳",为什么选择了不同的技术栈?（提示:两者解决的问题体量不同，一个是轻量安装向导，一个
   是长期运行的聊天应用。）
