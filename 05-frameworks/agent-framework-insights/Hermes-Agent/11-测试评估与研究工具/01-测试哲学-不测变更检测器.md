# 测试哲学：不测变更检测器

> Hermes Agent 的 `tests/` 目录下有 3477 个 Python 测试文件，`AGENTS.md` 用将近 200 行专门讲"怎么写测试才不是在浪费工程时间"。这篇文章的核心是其中最容易被忽视、也最反直觉的一条规则——"不要写变更检测器测试"（don't write change-detector tests）：目录快照、枚举计数、硬编码的模型列表看起来像是在增加覆盖率，实际上只是在给下一次正常的数据更新埋一颗地雷。本文用 `AGENTS.md` 的原文和真实反例，把这条规则和它周围几条同源规则一次讲透。

## 学习目标

- 理解 Hermes 测试基础设施的两条硬约束：必须用 `scripts/run_tests.sh` 而不是直接跑 `pytest`，以及每个测试文件在独立子进程里运行意味着什么。
- 理解"不要伪装宿主 OS"（Don't fake the host OS）规则要解决的具体问题，以及它和"用平台作为纯函数输入"之间的区别。
- 完整拆解"不要写变更检测器测试"（Don't write change-detector tests）：什么样的断言是变更检测器、为什么它们有害、应该改写成什么样的不变量断言。
- 理解"永远不要在测试里读取源代码"（Never read source code in tests）规则禁止的具体反模式，以及正确的替代做法（抽出纯函数、依赖注入）。
- 理解 CI 变更分类器（`scripts/ci/classify_changes.py`）如何要求测试按语言/子系统正确归位，否则会在特定 PR 上悄悄漏跑。
- 能够把 Hermes 这套测试哲学和 DeepSeek Harness《Verify the World, not the Self-Report》一文的哲学对照起来，说清楚两者的相同底色和不同侧重。

## 一、基础设施：为什么不能直接跑 `pytest`

`AGENTS.md` 的 Testing 一节开篇就是一条硬性规定：

> **ALWAYS use `scripts/run_tests.sh`** — do not call `pytest` directly. The script enforces hermetic environment parity with CI (unset credential vars, TZ=UTC, LANG=C.UTF-8, per-file subprocess isolation via `scripts/run_tests_parallel.py` — no xdist, worker count auto-scaled from CPU count). Direct `pytest` on a 16+ core developer machine with API keys set diverges from CI in ways that have caused multiple "works locally, fails in CI" incidents (and the reverse).

这段话背后的具体动机被列成了一张对照表：

| | 不用 wrapper | 用 wrapper |
|---|---|---|
| Provider API keys | 环境变量里有什么就是什么（会自动探测出一堆密钥） | 除了少数几个显式保留的变量，全部 unset |
| HOME / `~/.hermes/` | 你本机真实的 config+auth.json | 每个测试独立的临时目录 |
| Timezone | 本地时区（比如 PDT） | UTC |
| Locale | 随便什么 | C.UTF-8 |

核心矛盾在于：开发者本机往往是一台 16 核以上、配置了真实 API 密钥、时区不是 UTC 的机器，如果直接跑 `pytest`，很多测试的运行环境和 CI 完全不同——`describe.skipIf`/`pytest.mark.skipif` 之类基于密钥探测的跳过逻辑会在本机意外触发真实网络请求，时区/locale 相关的断言在本机和 CI 上可能得到不同结果。`scripts/run_tests.sh` 的做法很直接：清空并重建一个白名单环境变量集合，强制 `TZ=UTC`、`LANG=C.UTF-8`，让"开发者本机跑通"和"CI 跑通"变成同一件事。

`AGENTS.md` 还明确了每个测试文件运行在独立子进程里这件事本身就是一种隔离设计：

> **Subprocess-per-test-file isolation**: Every test file runs in a freshly-spawned Python subprocess via `run_tests_parallel.py`. This means module-level dicts/sets and ContextVars from one test file cannot leak into the next.

这解决的是模块级全局状态跨文件污染的问题——如果所有测试文件跑在同一个进程里，一个测试文件里被修改过的模块级字典或 `ContextVar`，可能会悄悄影响另一个文件的断言结果，而且这种污染往往只在"恰好按某个顺序跑"时才会复现，排查成本极高。用子进程换隔离性，代价是启动开销，`AGENTS.md` 给出的补偿是"worker 数按 CPU 核数自动扩展"，用并行度换回单文件隔离带来的时间损失。

配套的 flake 处理策略也值得一提：失败的测试文件会在一个全新子进程里自动重跑一次（`--file-retries`，默认 1 次），重跑通过算绿，但会在 `⚠ FLAKY` 汇总区里连同两次尝试的输出一起打印出来——`AGENTS.md` 特别强调"FLAKY 报告是需要修的 bug，不是可以忽略的噪音"，并要求时序敏感的测试不能假设跑在一个安静的 runner 上（宽松的墙钟阈值 ≥ 2s、事件驱动的同步、禁止 `assert not _wait_until(...)` 这种负向计时竞争）。

## 二、不要伪装宿主 OS

Hermes 同时支持 Linux、macOS 和原生 Windows，很多行为在不同宿主上真实存在差异。`AGENTS.md` 的规则很干脆：

> Those differences are tested by running on the host, not by patching `sys.platform`.
>
> The line: **if the test needs the interpreter to believe it is on another OS in order to pass, it belongs on that OS.**

区分标准给得也很具体：`hidden_windows_child_options(opts, is_windows=True)` 这种把平台当作输入参数传进去的纯函数调用不算伪装宿主（"platform as data"），但如果先设置一个模块级的 `IS_WINDOWS` 标志位、再调用 `windows_detach_flags()` 去读这个全局状态，就是真正的伪装。前者测的是函数的输入输出关系，和运行它的机器实际是什么系统无关；后者测的是"如果我们相信自己在 Windows 上，代码会不会分支到正确的路径"，却从来没有真的在 Windows 上验证过这条路径本身是否正确。

对于确实需要在真实 Windows 进程拓扑上验证的场景（venv-holder 扫描、进程树亲缘关系、detach 语义），`AGENTS.md` 描述了一条按需触发的 `wine2e` 通道：只在推送到 `wine2e/**` 分支时才会在真实 `windows-latest` runner 上跑 `test_venv_holder_windows_live.py`，PR 和主干上完全不触发,不产生额外成本。这条通道解决的是"mock 永远无法复现真实 Windows 进程行为"这个更进一步的问题——和下一篇文章要讲的 evals 体系"拥抱真实性而非仿真"的思路是同一种态度。

## 三、不要写变更检测器测试

这是本文的核心，也是 `AGENTS.md` 用最长篇幅、给了最多正反例讲的一条规则。定义写得很精确：

> A test is a **change-detector** if it fails whenever data that is **expected to change** gets updated — model catalogs, config version numbers, enumeration counts, hardcoded lists of provider models. These tests add no behavioral coverage; they just guarantee that routine source updates break CI and cost engineering time to "fix."

三个反例直接抄自文档，每一个都对应一种常见但错误的直觉：

```python
# catalog snapshot — breaks every model release
assert "gemini-2.5-pro" in _PROVIDER_MODELS["gemini"]
assert "MiniMax-M2.7" in models

# config version literal — breaks every schema bump
assert DEFAULT_CONFIG["_config_version"] == 21

# enumeration count — breaks every time a skill/provider is added
assert len(_PROVIDER_MODELS["huggingface"]) == 8
```

这三个例子分别对应"目录快照测试"（把当前某个具体模型名字断言进去，模型每上新一次这条测试就要改一次）、"版本号字面量测试"（把当前的 schema 版本号写死，schema 每升一次这条测试就要改一次）、"枚举计数测试"（断言某个 provider 目前有几个模型，每加一个模型这条测试就要改一次）。这三种写法的共同点是：它们描述的不是"这段代码应该具备什么行为"，而是"数据现在长什么样子"——而这份数据本身就是被设计成会经常变化的东西（模型目录、配置版本、provider 列表）。

对应的正确写法同样直接给在文档里：

```python
# behavior: does the catalog plumbing work at all?
assert "gemini" in _PROVIDER_MODELS
assert len(_PROVIDER_MODELS["gemini"]) >= 1

# behavior: does migration bump the user's version to current latest?
assert raw["_config_version"] == DEFAULT_CONFIG["_config_version"]

# invariant: no plan-only model leaks into the legacy list
assert not (set(moonshot_models) & coding_plan_only_models)

# invariant: every model in the catalog has a context-length entry
for m in _PROVIDER_MODELS["huggingface"]:
    assert m.lower() in DEFAULT_CONTEXT_LENGTHS_LOWER
```

把这几个例子拆开看，能提炼出一条共同的判据：

> The rule: if the test reads like a snapshot of current data, delete it. If it reads like a contract about how two pieces of data must relate, keep it.

`_PROVIDER_MODELS["gemini"]` 里具体有哪几个型号会随时间变化，但"这个 provider 的目录里至少有一个模型"这件事是一个稳定的契约，不会随发布节奏波动。`_config_version` 具体等于几会变，但"迁移逻辑总能把用户配置里的旧版本号升到当前最新版本号"这件事是稳定的契约。`moonshot_models` 和 `coding_plan_only_models` 具体各自包含哪些型号会变，但"这两个集合永远没有交集"这件事是稳定的契约。`_PROVIDER_MODELS["huggingface"]` 里具体有哪些模型会变，但"目录里的每一个模型都能在上下文长度表里查到"这件事是稳定的契约。

`AGENTS.md` 最后补了一句对评审流程的具体要求：

> Reviewers should reject new change-detector tests; authors should convert them into invariants before re-requesting review.

这把这条规则从"建议"提升成了"评审门槛"——不是靠作者自觉，而是靠 code review 环节主动拒绝。

## 四、永远不要在测试里读取源代码

这条规则和"变更检测器"是近亲，但针对的是另一种更隐蔽的反模式：

> A test that reads a source file's text is testing *the shape of the source code*, not its behavior. This is a hard antipattern, banned outright. Any test that reads a .py, .ts, .tsx, etc., file is suspect.

文档给出的具体危害列了四条，其中最尖锐的一条是"它可能在实现被悄悄弄坏时依然通过，却在一次正确的重构改变格式/变量名/控制流（但运行时行为完全不变）时失败——两个方向的失败都是错的"。反例是这样的：

```ts
const source = fs.readFileSync(path.join(__dirname, 'main.ts'), 'utf8')

test('backend spawn hides the Windows console', () => {
  assert.match(source, /spawn\(\s*backend\.command,\s*backend\.args[\s\S]{0,300}hiddenWindowsChildOptions/)
})
```

这段代码用一个正则去匹配源码文本里"调用点附近出现了 `hiddenWindowsChildOptions`"这件事，本质上是在验证"这段代码看起来像是接了某个函数"，而不是验证"这段代码执行后确实产生了正确的效果"。文档给出的正确做法是把逻辑抽成一个小的、可独立调用的纯函数，然后真的调用它、断言真实输出：

```ts
// backend-spawn.ts
export function hiddenWindowsChildOptions(options: SpawnOptionsLike = {}, isWindows = process.platform === 'win32') {
  if (!isWindows || 'windowsHide' in options) return options
  return { ...options, windowsHide: true }
}

// backend-spawn.test.ts
test('windowsHide defaults to true on Windows, is left alone elsewhere', () => {
  assert.equal(hiddenWindowsChildOptions({}, true).windowsHide, true)
  assert.equal(hiddenWindowsChildOptions({}, false).windowsHide, undefined)
  assert.equal(hiddenWindowsChildOptions({ windowsHide: false }, true).windowsHide, false)
})
```

文档最后一句话点出了这条规则真正想推动的工程行为：

> If the logic lives inline in a god-file (`main.ts`, `cli.py`, `gateway/run.py`) and extracting it feels disruptive: that's the actual signal to do the extraction, not to regex around it.

也就是说，当你发现自己想用正则去匹配源码文本才能测试某个逻辑时，这个冲动本身就是一个信号——真正该做的不是绕过去写一个脆弱的字符串匹配测试，而是把这段逻辑从巨型文件里抽出来，变成一个可以直接调用、直接断言输出的函数。

## 五、测试不得写入 `~/.hermes/`

最后一条相对独立但同样重要的隔离规则：

> The `_isolate_hermes_home` autouse fixture in `tests/conftest.py` redirects `HERMES_HOME` to a temp dir. Never hardcode `~/.hermes/` paths in tests.

`tests/conftest.py` 里的 `_isolate_hermes_home` 是一个 autouse fixture，对每个测试自动生效，把 `HERMES_HOME` 重定向到临时目录，避免测试读写开发者本机真实的配置和认证文件。对于涉及多 Profile 的测试，文档额外提醒要连 `Path.home()` 一起 mock，因为 `_get_profiles_root()` 之类的函数是从 `Path.home()` 而不是 `HERMES_HOME` 推导路径的：

```python
@pytest.fixture
def profile_env(tmp_path, monkeypatch):
    home = tmp_path / ".hermes"
    home.mkdir()
    monkeypatch.setattr(Path, "home", lambda: tmp_path)
    monkeypatch.setenv("HERMES_HOME", str(home))
    return home
```

这条规则和前面"不伪装宿主 OS"、"子进程隔离"其实是同一种工程直觉的不同侧面：测试的执行环境必须和被测代码实际依赖的资源（文件系统路径、操作系统、进程状态）保持真实、干净、可重复的对应关系，任何一处"图省事"的捷径都会在未来某个时间点变成一次隐蔽的污染或误报。

## 小结与思考题

Hermes 这套测试哲学的主线是：**测试要为"代码行为是否符合预期契约"提供证据，而不是为"数据当前长什么样子"拍一张快照**。子进程隔离、不伪装宿主 OS、不写变更检测器、不读源码字符串、不碰真实 `~/.hermes/`——这五条规则表面上分散在不同话题下，但都在防止同一类问题：一个测试通过与否，不应该取决于和被测行为无关的东西（进程间残留状态、假装的操作系统、模型目录当前的具体内容、源码的格式、开发者本机的真实配置）。

和 DeepSeek Harness《测试哲学：Verify the World, not the Self-Report》一文对照来看，两者哲学同源，但强调的方向不同：DeepSeek Harness 的核心命题是"被测系统（大模型）会生成一份听起来可信的自我报告，测试不能拿这份报告当证据，必须独立验证外部世界的真实状态"，解决的是"agent 测试相较传统软件测试多出的信任问题"；Hermes 这里强调的"不测变更检测器"解决的是另一个更传统、但同样容易被忽视的问题——"一个技术上会通过或失败的测试，是不是在测试一件真正稳定、值得被断言的事情"。前者关心断言的证据来源是否可信，后者关心断言本身描述的关系是否稳定。两者合在一起，其实构成了"什么才算一个好断言"这个问题的两个正交维度：**证据要独立于自我报告，关系要独立于易变数据**。

思考题：

1. `assert len(_PROVIDER_MODELS["gemini"]) >= 1` 这种"至少有一个"的断言，本身会不会退化成另一种意义上的弱测试——它无法捕获"目录被整个清空成只剩一个哑元模型"这类回归。你会如何在不变成变更检测器的前提下，让这条断言对这类回归更敏感？
2. "不要在测试里读取源代码"这条规则的反例是用正则匹配调用点。如果某个不变量确实只能通过静态分析才能验证（比如"所有导出的 provider 类都必须实现某个接口方法"），这种检查应该放进测试套件，还是放进一个独立的 lint/类型检查工具链？两者的边界在哪里？
3. `wine2e` 通道只在推送到 `wine2e/**` 分支时触发，PR 和主干上完全不触发。这种"默认关闭、按需触发"的设计避免了成本，但也意味着如果没有人主动推送到这个分支，相关的真实 Windows 回归可能长期不会被发现。你会如何设计一个更主动、但仍然不给日常 PR 增加成本的触发策略？
