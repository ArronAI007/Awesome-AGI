# 终端环境抽象与七种后端实现

> Hermes 把"在哪里跑命令"这件事收敛成一个统一模型:每条命令都是一次全新的 `bash -c` spawn,不保留长驻 shell 进程;而"上一条命令 export 的变量、定义的函数,这条命令还看得见"这个用户直觉,靠一份在 init 时抓取、每次命令前重新 source 的会话快照来兑现。`tools/environments/base.py` 里的 `BaseEnvironment` 把这套流程抽成基类,`local`/`docker`/`ssh`/`singularity`/`modal`/`daytona`/`vercel_sandbox` 七个子类各自只需要实现"怎么 spawn 一个 bash 进程"。本篇通读这份抽象的设计取舍,再逐一过一遍七种后端的定位,最后看 `agent/terminal_env_registry.py` 如何在"内置后端"和"插件后端"之间划清边界。

## 学习目标

- 理解为什么 Hermes 选择"每条命令一个全新子进程"而不是维护一个长驻 shell 会话,以及"会话快照 + 每次重新 source"是如何在两者之间找平衡的。
- 弄清 CWD(当前工作目录)在跨进程模型下是怎么持久化的——stdout 内嵌标记 vs 本地临时文件两条路径。
- 通读七种后端(local/docker/ssh/singularity/modal/daytona/vercel_sandbox)各自的定位:哪些是本地/自托管,哪些是云端 serverless、空闲即休眠。
- 理解 `agent/terminal_env_registry.py` 的注册路由机制:内置后端保留名字,插件可扩展自定义后端,但不做"最优后端自动选择"。
- 理解 `TERMINAL_ENV`/`terminal.backend` 这个配置项在整个选择链路里的唯一权威地位。

## 背景与设计动机

一个朴素的实现方式是:agent 启动时开一个长驻的 bash 进程,每次工具调用把命令写进它的 stdin,再读 stdout。这样"cd 之后目录保持"、"export 的变量后面还在"都是 shell 自带的语义,不需要额外工程。但长驻 shell 会话有一个致命问题:一旦某条命令把 shell 干挂了(比如吃满内存后被 OOM killer 杀掉、命令自己调用了 `exec` 替换掉当前进程、或者干脆卡死不返回),整个会话的状态——包括还没来得及持久化的 cwd、环境变量——就跟着一起丢了,而且这类故障往往很难跟"命令本身执行失败"区分开。

Hermes 的做法反过来:**放弃长驻进程,把持久性搬到进程外**。`tools/environments/base.py` 顶部的模块 docstring 直接点明了这个模型:

```python
# tools/environments/base.py:1-7
"""Base class for all Hermes execution environment backends.

Unified spawn-per-call model: every command spawns a fresh ``bash -c`` process.
A session snapshot (env vars, functions, aliases) is captured once at init and
re-sourced before each command. CWD persists via in-band stdout markers (remote)
or a temp file (local).
"""
```

每条命令都是一个全新的 `bash -c` 进程,天然不受"上一条命令弄脏了 shell 状态"的影响——一条命令卡死或者被杀,顶多损失这一次调用,不会连累整个会话。代价是"cd 之后目录保持"这类用户直觉不再是免费的,需要工程手段补上。

## 核心机制详解

### 会话快照:一次捕获,每次重新 source

`init_session()` 在后端构造完成后跑一次,把当前 shell 的环境变量、函数定义、alias 全部 dump 进一个快照文件:

```python
# tools/environments/base.py:764-773(节选)
def init_session(self):
    """Capture login shell environment into a snapshot file.

    Called once after backend construction.  On success, sets
    ``_snapshot_ready = True`` so subsequent commands source the snapshot
    instead of running with ``bash -l``.
    """
```

快照文件用 `mktemp` + `mv` 做原子替换(避免并发命令读到半写文件),写入内容分三块:`export -p` 导出的环境变量、过滤掉 `_` 前缀私有函数后的函数定义、以及 `alias -p` 导出的别名。之后每条命令在 `_wrap_command()` 里先 `source` 这份快照,跑完命令后再把最新的环境状态重新 dump 回同一份快照文件:

```python
# tools/environments/base.py:953-956(节选)
if self._snapshot_ready:
    parts.append(
        f"source {_quoted_snap} >/dev/null 2>&1 || true"
    )
```

```python
# tools/environments/base.py:1013-1019(节选)
if self._snapshot_ready:
    parts.append(
        f"__hermes_snap_tmp=$(mktemp {_snap_tmp_template}) && "
        f"{{ {_export_dump_excluding_session_vars(_snap_tmp, passthrough_names)} "
        f"&& mv -f {_snap_tmp} {_quoted_snap}; }} "
        f"2>/dev/null || rm -f {_snap_tmp} 2>/dev/null || true"
    )
```

这就是"两种模型之间找平衡"的具体做法:每条命令依然是独立进程,互不牵连;但通过"跑之前先读快照、跑完之后再写快照"这一对操作,让用户在体验上感觉不到进程边界——`export FOO=bar` 之后的下一条命令依然能看到 `FOO`。快照里专门排除了一批每会话变量(`HERMES_SESSION_*`、`HERMES_UI_SESSION_ID` 等前缀),原因写在模块级注释里:一个长驻后端可能同时服务多个并发会话(消息网关、TUI、桌面/网页面板都会把终端收敛成同一个"default"环境实例),如果第一个会话的 `HERMES_SESSION_ID` 被写进共享快照,后面的会话 `source` 这份快照就会看到一个属于别人的会话身份——这是一个真实修复过的跨会话泄漏问题。

### CWD:远程走 stdout 标记,本地走临时文件

既然每条命令都是全新进程,`cd` 到的目录同样不会自动带到下一条命令,需要单独想办法追踪。远程/容器类后端(Docker、SSH、Modal、Daytona、Singularity)统一走一种方案:命令执行完之后,再 `printf` 一行内嵌了 `__HERMES_CWD_{session}__` 标记的 `pwd -P` 输出,父进程从 stdout 里把这段标记解析出来、更新 `self.cwd`,再把这行标记从最终呈现给模型的输出里剥离掉:

```python
# tools/environments/base.py:1027-1029
parts.append(
    f"printf '\\n{self._cwd_marker}%s{self._cwd_marker}\\n' \"$(pwd -P)\""
)
```

```python
# tools/environments/base.py:1410-1421(节选)
def _extract_cwd_from_output(self, result: dict):
    """Parse the __HERMES_CWD_{session}__ marker from stdout output.

    Updates self.cwd and strips the marker from result["output"].
    Used by remote backends (Docker, SSH, Modal, Daytona, Singularity).
    ...
    """
```

之所以选 stdout 内嵌标记而不是"写一个远程文件、再读回来",是因为对 Docker/SSH/Modal 这类后端,`env.execute()` 本身就是走一次进程调用拿到 stdout——复用同一条通道比额外发起一次"读文件"往返更省一次网络/exec 开销。本地后端(`LocalEnvironment`)则额外走一条临时文件路径(`_cwd_file`),因为本地场景下直接读写宿主机文件系统的成本几乎为零,不需要绕道 stdout 解析。

### `_wrap_command`:一条命令背后拼出的完整脚本

每条命令实际发给 `_run_bash()` 的,并不是模型写的原始命令本身,而是 `_wrap_command()` 拼出的一整段脚本:保存/恢复profile-scoped 直通变量 → source 快照 → 注入 `AI_AGENT`/`HERMES_AGENT` 归属标记与 `GIT_PAGER=cat`/`PAGER=cat` 防止分页器卡死 → `cd` 到目标目录 → `eval` 真正的命令 → 重新 dump 快照 → 打印 CWD 标记 → `exit` 对应的返回码。这条流水线跑在同一个 `bash -c` 调用里,对模型呈现出"像是一个持续会话"的效果,但底层每一次都是全新进程——这正是抽象设计上"用工程手段模拟连续性,而不是真的维护连续性"的核心取舍。

## 七种后端:定位与适用场景

`BUILTIN_BACKEND_NAMES` 里登记了八个名字,对应 README 里对外宣传的"七种终端后端"(`managed_modal` 是 Modal 的托管模式内部别名,不单独计数):

```python
# agent/terminal_env_registry.py:40-43
BUILTIN_BACKEND_NAMES = frozenset({
    "local", "docker", "singularity", "modal", "managed_modal",
    "daytona", "vercel_sandbox", "ssh",
})
```

README 对这七种后端的定位总结得很直接:

> Seven terminal backends — local, Docker, SSH, Singularity, Modal, Daytona, and Vercel Sandbox. Daytona and Modal offer serverless persistence — your agent's environment hibernates when idle and wakes on demand, costing nearly nothing between sessions.

逐一看每种后端的定位:

- **local**(`tools/environments/local.py`):默认后端,命令直接跑在宿主机上,`is_local = True`。零隔离,零额外成本,适合"我信任自己的操作系统"这个默认前提下的日常使用。
- **docker**(`tools/environments/docker.py`):在容器内跑命令,文档明确写着"安全加固"——`--cap-drop ALL`、`--security-opt no-new-privileges`、可配置的 `--pids-limit`/CPU/内存限制,外加可选的 bind mount 做文件系统持久化。适合本地/自托管但又想要一层容器级隔离的场景。
- **ssh**(`tools/environments/ssh.py`):通过 SSH ControlMaster 连接复用,把命令跑在一台远程主机上。适合"我有一台常驻服务器,想让 agent 在那台机器上干活"的场景。
- **singularity**(`tools/environments/singularity.py`):Apptainer/Singularity 持久化容器,同样是安全加固(`--containall`、`--no-home`、能力裁剪),额外支持可写 overlay 目录跨会话保留状态——这是 HPC/科研集群场景常见的容器方案,和 Docker 面向的运维场景形成互补。
- **modal**(`tools/environments/modal.py`)与其托管变体 **managed_modal**(`tools/environments/managed_modal.py`):基于 Modal 云 SDK 的 `Sandbox.create()`/`Sandbox.exec()`,serverless、空闲时休眠、按需唤醒,是 README 里"costing nearly nothing when idle" 的两个例子之一。
- **daytona**(`tools/environments/daytona.py`):Daytona 云沙箱 SDK,支持"持久化沙箱"——cleanup 时 stop、下次创建时 resume,文件系统状态跨会话保留,同样属于空闲即休眠的 serverless 类型。
- **vercel_sandbox**(`tools/environments/vercel_sandbox.py`):Vercel Sandbox 云端沙箱,同样支持基于快照元数据的持久化恢复。

七者共享同一份 `BaseEnvironment` 契约,消费方(`terminal_tool`、`code_execution_tool` 等)不需要关心底层到底是本地子进程还是云端 SDK 调用——这也是为什么 `_ThreadedProcessHandle` 存在:Modal/Daytona/Vercel 这类没有真实 subprocess 的 SDK 后端,靠它把一次阻塞的 `exec_fn() -> (output, exit_code)` 包装成看起来像 `subprocess.Popen` 的 `ProcessHandle`。

## 注册与路由:内置保留名 + 插件扩展,不做自动择优

`agent/terminal_env_registry.py` 的模块 docstring 把这层设计的边界写得很清楚:

```python
# agent/terminal_env_registry.py:11-16
Unlike the image/video/web/browser registries there is **no active-provider
resolution here**: the active backend is whatever ``TERMINAL_ENV`` /
``terminal.backend`` names, exactly as for built-in backends. The registry's
only job is mapping that name to a provider instance (and answering the
classification questions the core historically answered with frozensets of
built-in names).

Built-in backend names are reserved — :func:`register_provider` rejects a
provider whose ``name`` collides with one, so a plugin can never shadow the
in-tree docker/modal/... implementations.
```

`register_provider()` 在名字校验里直接拒绝跟内置后端撞名的注册:

```python
# agent/terminal_env_registry.py:74-78
if name in BUILTIN_BACKEND_NAMES:
    raise ValueError(
        f"Terminal backend name '{name}' is reserved for the built-in "
        f"{name} backend and cannot be registered by a plugin"
    )
```

这套注册表本身没有"哪个后端更好、自动选一个"的逻辑——它唯一的职责是把一个名字映射到一个 provider 实例。真正决定"这次用哪个后端"的,完全是 `TERMINAL_ENV` 环境变量或 `terminal.backend` 配置项这一个入口(`tools/terminal_tool.py` 里 `os.getenv("TERMINAL_ENV", "local")` 反复出现,默认值就是 `"local"`)。

这是一处刻意的设计取舍:七种后端在隔离强度、成本、可用性上差异巨大(本地零隔离但零延迟,Docker 容器级隔离但需要 Docker 守护进程,Modal/Daytona serverless 但依赖网络和云端账号),"哪个最优"这个问题本质上无法脱离部署上下文回答——一个 CI 场景可能就想要本地后端的零延迟,一个多租户场景可能必须要 Docker 或云沙箱的隔离。与其让框架代为猜测,不如把决定权完全交给运维配置,注册表只负责"名字到实现"这一层纯粹的映射,不掺杂任何启发式择优。这也解释了为什么插件能新增自定义后端(比如接入某个私有云沙箱 API)却不能覆盖内置实现——保留名字机制保证了 `docker`/`modal` 这些用户已经建立心智模型的名字,行为永远由 in-tree 实现决定,不会被一个同名插件悄悄替换掉。

## 小结与思考题

Hermes 的终端后端抽象用"每条命令一个全新子进程 + 会话快照重新 source"解决了"进程隔离性"和"用户体验连续性"这对看似矛盾的需求:命令级别的故障不会拖垮整个会话状态,而 cwd、环境变量、函数、别名又能在用户看来"记得住"。七种后端共享同一份 `BaseEnvironment` 契约,从零隔离的 `local` 到容器级的 `docker`/`singularity`,再到 serverless、空闲即休眠的 `modal`/`daytona`/`vercel_sandbox`,覆盖了从本地开发到云端常驻的完整光谱。`terminal_env_registry.py` 用"内置名字保留 + 插件可扩展"划清了框架边界,同时明确放弃了"自动选最优后端"这件事——完全交给 `TERMINAL_ENV`/`terminal.backend` 配置项决定,把判断权留给最了解部署上下文的人。

思考题:

1. 会话快照排除了 `HERMES_SESSION_*` 等每会话变量,却保留了用户自己 `export` 的普通变量。如果一个 skill 在会话中途临时设置了一个敏感 API key 到环境变量里,这个值会被写进共享快照吗?这对多会话共享同一个后端实例意味着什么风险?
2. `_ThreadedProcessHandle` 让 Modal/Daytona/Vercel 这类没有真实 subprocess 的 SDK 后端也能满足 `ProcessHandle` 协议。如果要新增一个基于 gRPC 长连接的云沙箱后端,需要在这个适配层做哪些取舍,才能让 `_wait_for_process()` 的中断/超时/输出截断逻辑照常工作?
