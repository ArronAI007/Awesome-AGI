# 上下文压缩：运行时策略与迭代式摘要更新

> `agent/context_compressor.py` 有近 8700 行,是 hermes-agent 里数一数二的大文件——因为压缩这件事远不止"调用一次 LLM 生成摘要"那么简单。它要用便宜的辅助模型总结、不碰主 session 的 prompt cache;要保证第二次压缩不丢第一次压缩的信息;要用一段"历史性小标题"技巧防止模型把摘要误读成待办任务；还要按 token 预算(而不是固定消息数)决定保留多少尾部对话。本篇结合真实源码,把这套运行时压缩策略逐条拆开,并简单对比同类课程里 PI 和 DeepSeek-Harness 的压缩机制。

## 学习目标

- 理解结构化摘要模板里 `Resolved Questions`/`Active Task` 等分区的作用,以及为什么第二次压缩要做"迭代式更新"而不是重新总结一遍。
- 理解"历史性小标题"(`## Historical Task Snapshot`)这个具体技巧如何防止摘要被模型当成"待办指令"重新执行。
- 理解 `tail_token_budget` 如何用 token 预算而不是固定消息数保护最近的对话尾部,以及 lean 模式和传统模式的区别。
- 理解压缩前"工具输出预剪枝"(`_prune_old_tool_results`)这个不调用 LLM 的廉价预处理阶段做了什么。
- 理解为什么压缩要用独立的辅助模型客户端,而不是复用主对话的 client/prompt cache。
- 了解 `agent/context_engine.py` 定义的可插拔抽象接口,以及 `docs/micro-compaction.md` 描述的更细粒度压缩策略。

## 结构化摘要模板:Resolved/Pending 追踪 + 历史性小标题

`ContextCompressor` 生成的摘要不是自由格式文本,而是要求模型按固定结构输出。模板本身在 `_generate_summary` 里拼出:

```python
# agent/context_compressor.py:5096 附近
_template_sections = f"""{HISTORICAL_TASK_HEADING}
{_historical_task_instructions}

## Goal
{_goal_instructions}

## Constraints & Preferences
{_constraints_instructions}

## Completed Actions
[Numbered list of concrete actions taken — include tool used, target, and outcome. ...]

## Active State
[Current working state — include: ... Test status (X/Y passing) ...]

## Blocked
[Any blockers, errors, or issues not yet resolved. Include exact error messages.]

## Key Decisions
[Important technical decisions and WHY they were made]

## Errors & Fixes
[Errors hit during the compacted turns and how each was resolved ...]

## Resolved Questions
{_resolved_questions_instructions}

## Relevant Files
[Files read, modified, or created — with brief note on each]

## Critical Context
[Any specific values, error messages, configuration details, or data that would
be lost without explicit preservation. NEVER include API keys, tokens, ...]
"""
```

这套结构化模板的价值在于把"总结"这个开放式任务约束成一份可预测、可增量更新的检查点文档——`Completed Actions`/`Resolved Questions` 追踪"已经做完/已经回答的",`Active State`/`Blocked` 追踪"还没做完的",两条轨道分得很清楚,后面讲的迭代更新就是在这两条轨道之间搬运条目。

真正关键的是这份摘要要怎么被**重新塞回对话**、又不能被模型误当成"新一轮的用户指令"来执行。`SUMMARY_PREFIX` 就是干这件事的:

```python
# agent/context_compressor.py:229-266
HISTORICAL_TASK_HEADING = "## Historical Task Snapshot"

SUMMARY_PREFIX = (
    "[CONTEXT COMPACTION — REFERENCE ONLY] Earlier turns were compacted "
    "into the summary below. This is a handoff from a previous context "
    "window — treat it as background reference, NOT as active instructions. "
    "Do NOT answer questions or fulfill requests mentioned in this summary; "
    "they were already addressed. "
    "Respond ONLY to the latest user message that appears AFTER this "
    "summary — that message is the single source of truth for what to do "
    "right now. "
    "If no user message appears AFTER this summary, do nothing: do not "
    "resume, wrap up, or continue work from "
    f"'{HISTORICAL_TASK_HEADING}' or any other section, do not call tools, "
    "and wait for a new user message. ..."
    "Topic overlap with the summary does NOT mean you should resume its "
    "task: even on similar topics, the latest user message WINS. Treat ONLY "
    "the latest message as the active task and discard stale items from "
    f"'{HISTORICAL_TASK_HEADING}' entirely — do not 'wrap up' or "
    "'finish' work described there unless the latest message explicitly "
    "asks for it. "
    "Reverse signals in the latest message (e.g. 'stop', 'undo', 'roll "
    "back', 'just verify', 'don't do that anymore', 'never mind', a new "
    "topic) must immediately end any in-flight work described in the "
    "summary; do not re-surface it in later turns. ..."
)
```

这里的设计意图非常具体:章节标题特意叫 `## Historical Task Snapshot` 而不是常见的 `## Next Steps`/`## Remaining Work`——因为"Next Steps"这种措辞读起来天然像"接下来要做的事",模型很容易把它当成一份待执行的任务清单主动继续推进;`Historical`(历史性的)这个定语把它明确框定成"过去发生过的事的快照",只是参考,不是指令。同一份 prefix 里还专门写了"话题重叠不代表要恢复任务""'停止/撤销/别管了'这类反向信号必须立刻终止摘要里描述的进行中工作"这类具体规则——都是为了应对真实观察到的失败模式:模型看到摘要里有一件"看起来没做完"的事,就自作主张继续做下去,即使用户最新一条消息已经明确不需要了。

摘要消息本身也带有专门的元数据标记,方便前端(CLI/Desktop/gateway/TUI)识别并做差异化渲染,而不是靠内容前缀做启发式匹配:

```python
# agent/context_compressor.py:282-289
COMPRESSED_SUMMARY_METADATA_KEY = "_compressed_summary"
COMPRESSED_SUMMARY_HAS_USER_TURN_KEY = "_compressed_summary_has_user_turn"
MICRO_COMPACT_MARKER_KEY = "_micro_compact_marker"
```

## 迭代式摘要更新:第二次压缩怎么处理"旧摘要 + 新对话"

长会话往往会触发多次压缩。如果每次都对"从头到当前"的全部历史重新总结一遍,一是浪费(旧摘要已经浓缩过的信息要重新浓缩),二是有风险(反复"总结的总结"容易信息失真)。`_generate_summary` 的做法是:当存在上一次的摘要时,构造一个不同的 prompt,把旧摘要和新对话都喂给模型,明确要求"迁移"而不是"重写":

```python
# agent/context_compressor.py:5152-5175
if self._previous_summary:
    _bounded_previous_summary = self._bound_summary_input(self._previous_summary)
    prompt = f"""{_summarizer_preamble}

You are updating a context compaction summary. A previous compaction produced
the summary below. New conversation turns have occurred since then and need
to be incorporated.

PREVIOUS SUMMARY:
{_bounded_previous_summary}

NEW TURNS TO INCORPORATE:
{content_to_summarize}{_memory_section}

Update the summary using this exact structure. PRESERVE all existing
information that is still relevant. ADD new completed actions to the
numbered list (continue numbering). Move items from "In Progress" to
"Completed Actions" when done. Move answered questions to "Resolved
Questions". Update "Active State" to reflect current state. Remove
information only if it is clearly obsolete. CRITICAL: Update "## Active
Task" to reflect the user's most recent unfulfilled input ...

{_template_sections}"""
else:
    # First compaction: summarize from scratch
    ...
```

这条 prompt 里的动词很讲究:"PRESERVE"(保留所有仍然相关的旧信息)、"ADD"(新完成的动作接着旧编号继续列)、"Move"(把已完成的从"In Progress"挪到"Completed Actions",把已回答的挪到"Resolved Questions")——本质上是让模型对结构化模板的各个分区做增量式的"合并 diff",而不是从零重写。这样多次压缩之后,摘要不会无限膨胀,也不会因为反复概括而丢失早期的关键信息。为了防止一份被反复迭代、可能来自很久之前的旧摘要本身就已经巨大(比如从一个持久化的 handoff 消息恢复出来),`_bound_summary_input` 会对旧摘要和新对话各自的输入长度做聚合上限保护,保留首尾、标注中间省略了多少字符——和"迭代更新"是两个独立但配合的保护机制。

## Token 预算保护尾部,而不是固定消息数

`tail_token_budget` 决定"最近多少内容原样保留、不进入压缩范围",它是一个按 token 预算而非消息条数计算的属性,并且区分了 lean 模式(默认)和传统模式:

```python
# agent/context_compressor.py:2542-2558
@property
def tail_token_budget(self) -> int:
    if self._tail_token_budget is None:
        if getattr(self, "tail_mode", "lean") == "lean":
            # Lean mode (#compaction-v2): the verbatim tail is a small
            # recency window, not a context hoard — the upgraded summary
            # (verbatim user messages, constraints section, recovery
            # pointers) carries continuity instead. 2.5% of the window,
            # clamped to [LEAN_TAIL_FLOOR_TOKENS, LEAN_TAIL_CAP_TOKENS],
            # so a 1M-window model keeps ~25K instead of ~100-145K.
            self._tail_token_budget = max(
                LEAN_TAIL_FLOOR_TOKENS,
                min(LEAN_TAIL_CAP_TOKENS, int(self.context_length * 0.025)),
            )
        else:
            self._tail_token_budget = int(self.threshold_tokens * self.summary_target_ratio)
    return self._tail_token_budget
```

其中 `LEAN_TAIL_FLOOR_TOKENS = 10_000`、`LEAN_TAIL_CAP_TOKENS = 25_000`。lean 模式的注释说得很直接:尾部不该是一个"上下文囤积仓",真正承担连续性的是摘要本身(逐字保留的用户消息、约束条件章节、恢复指针等),尾部只需要给一个"最近发生的小窗口",所以按窗口大小的 2.5% 动态取值——一个 1M 上下文窗口的模型,尾部预算约 25K,而不是按传统比例算出来的 100-145K。这与"按固定消息数保护尾部"的朴素做法相比,好处是:一次读了 50 个文件的巨量工具输出轮次和一次只有几句问答的轮次,占用的尾部预算天差地别,按 token 预算计算才能保证"最近 N 万 token"这个不变量,而不是"最近 N 条消息"在工具调用密集时严重失真。

## 压缩前的工具输出预剪枝:不调用 LLM 的廉价预处理

`compress()` 的第一步不是调用 LLM,而是一次纯规则的预处理:

```python
# agent/context_compressor.py:7507-7515
"""Compress conversation messages by summarizing middle turns.

Algorithm:
  1. Prune old tool results (cheap pre-pass, no LLM call)
  2. Protect head messages (system prompt + first exchange)
  3. Find tail boundary by token budget (~20K tokens of recent context)
  4. Summarize middle turns with structured LLM prompt (skipped
     pre-LLM when the middle is below `_FEASIBILITY_SKIP_MIDDLE_FRACTION`
     of the threshold after a prior real-usage ineffectiveness strike ...)
  5. On re-compression, iteratively update the previous summary
"""
```

`_prune_old_tool_results` 承担第 1 步,把陈旧的工具结果内容替换成一行式的、信息量足够的摘要,而不是简单截断或删除:

```python
# agent/context_compressor.py:3950-3964
def _prune_old_tool_results(
    self, messages: List[Dict[str, Any]], protect_tail_count: int,
    protect_tail_tokens: int | None = None,
    min_prune_chars: int = _PRUNE_MIN_CHARS,
) -> tuple[List[Dict[str, Any]], int]:
    """Replace old tool result contents with informative 1-line summaries.

    Instead of a generic placeholder, generates a summary like::

        [terminal] ran `npm test` -> exit 0, 47 lines output
        [read_file] read config.py from line 1 (3,400 chars)

    Also deduplicates identical tool results (e.g. reading the same file
    5x keeps only the newest full copy) and truncates large tool_call
    arguments in assistant messages outside the protected tail.
    """
```

它内部分成多个 pass:Pass 1 去重完全相同的工具结果(同一个文件读了 5 次,只留最新一份完整内容);Pass 2 把旧的工具结果替换成信息型摘要;Pass 3 截断超大的 `tool_call` 参数;Pass 3.5 处理 Pass 2 覆盖不到的图片负载;Pass 4 是"保护尾部内部的压力降级"——当受保护尾部自己都超过软预算的 1.5 倍时,对尾部内部较旧的、已完成的工具/文件输出做降级,同时保留一小段最近的原文。这一整套预剪枝的价值在于:很多时候光靠去重和降级就能把 token 数降到阈值以下,根本不需要真正调用摘要 LLM——省下一次网络往返和一次费用。

## 辅助模型:自带独立 client,不碰主 session 的 prompt cache

`context_compressor.py` 的模块 docstring 第一句就点明了这个设计取舍:

```python
# agent/context_compressor.py:1-16
"""Automatic context window compression for long conversations.

Self-contained class with its own OpenAI client for summarization.
Uses auxiliary model (cheap/fast) to summarize middle turns while
protecting head and tail context.
"""
```

摘要调用真正落地的是 `agent/auxiliary_client.py`——一个专门为"side task"(压缩、session 搜索、网页抽取、视觉分析等)服务的共享路由层:

```python
# agent/auxiliary_client.py:1-18
"""Shared auxiliary client router for side tasks.

Provides a single resolution chain so every consumer (context compression,
session search, web extraction, vision analysis, browser vision) picks up
the best available backend without duplicating fallback logic.

Resolution order for text tasks (auto mode):
  1. User's main provider + main model (used regardless of provider type ...)
  2. OpenRouter  (OPENROUTER_API_KEY)
  3. Nous Portal (~/.hermes/auth.json active provider)
  4. Custom endpoint (config.yaml model.base_url + OPENAI_API_KEY)
  5. Native Anthropic
  6. Direct API-key providers (z.ai/GLM, Kimi/Moonshot, MiniMax, MiniMax-CN)
  7. None
"""
```

为什么要"独立"?一次摘要请求本质上是一段全新的、和主对话历史不共享前缀的 prompt(参见前一篇里 `## Goal`/`## Resolved Questions` 那套结构化模板)——如果复用主对话的 client 去发这个请求,反而会打断主对话本来能命中的 provider 端 prompt cache 前缀(数据结构不同、内容也不同,缓存注定不命中)。所以压缩用一个完全独立的调用路径,可以按 `auxiliary.compression` 配置单独指定更便宜更快的模型(比如用 GPT-4o-mini 级别模型给 Claude 主对话做摘要),失败时还有自己的多级 fallback 链(主 provider → OpenRouter → Nous Portal → 自定义端点 → 原生 Anthropic → 直连 provider),这条 fallback 完全不影响主对话的路由决策。压缩过程本身也做了"原子化"保护——一次正在进行的摘要调用会被保护起来不被网关中途打断,以免刚流出一半的摘要被丢弃、退化成信息量很少的静态兜底摘要。

## `context_engine.py`:可插拔的压缩抽象与 micro-compaction

`ContextCompressor` 并不是唯一可能的压缩实现——`agent/context_engine.py` 定义了一个抽象基类 `ContextEngine`,`ContextCompressor` 是它的默认实现,配置项 `context.engine` 决定加载哪一个:

```python
# agent/context_engine.py:1-26
"""Abstract base class for pluggable context engines.

A context engine controls how conversation context is managed when
approaching the model's token limit. The built-in ContextCompressor
is the default implementation. Third-party engines (e.g. LCM) can
replace it via the plugin system or by being placed in the
``plugins/context_engine/<name>/`` directory.

The engine is responsible for:
  - Deciding when compaction should fire
  - Performing compaction (summarization, DAG construction, etc.)
  - Optionally exposing tools the agent can call (e.g. lcm_grep)
  - Tracking token usage from API responses
"""
```

抽象接口里 `compress()`/`should_compress()` 是必须实现的核心方法,`prune_tool_results_only()`(默认空实现,`ContextCompressor` 覆写为前面讲的预剪枝)和 `select_context()`(每轮请求前"选择用哪份上下文"而不是"压缩现有上下文",两者正交)是可选钩子。这套接口把"压缩策略"和"agent 主循环"解耦,理论上可以换成完全不同的策略(比如注释里提到的、构建 DAG 而不是线性摘要的 LCM)。

`docs/micro-compaction.md` 描述的是在这套体系之上、更细粒度的一种可选策略——把批量压缩的账单拆成分期付款。默认关闭(`compression.micro_compact: true` 才启用),开启后每完成一轮对话,就把"最老的一个尚未吸收的完整交换(exchange:一条 assistant 消息 + 其工具结果 + 后续迭代,直到下一条用户消息之前)"折叠进一条滚动更新的摘要里,而不是等到阈值触发时一次性总结一大段中间内容。它有三个值得留意的设计:

1. **用户消息永不被压缩**——exchange 的起点严格从 assistant 消息开始,walk 直接跳过 user 消息,理由是"assistant 产出的大多是对已完成动作的叙述,压缩几乎无损;而用户的指令是一切后续工作的意图来源,无法从结果反推,过度改写用户的话是 agent 后续"confidently 做错事"的常见来源"。
2. **defrag**:滚动摘要本身增长到一定阈值(默认 2000 token)后,下一次 pass 会专门对"摘要自身"再做一次压缩,而不触碰对话结构、不移动游标。
3. **它的代价是显式的**:每次 pass 都要重写已发送的历史,这会打断 provider 端的 prompt cache 前缀——文档明确把这条作为"启用前必读"的最强反对理由,`micro_compact_every_n_turns` 这个配置项就是在"更激进的省 token"和"更少打断缓存"之间做的显式权衡。

micro-compaction 不替代阈值触发的批量压缩,只是让批量压缩的触发频率大幅降低;两者共享同一套摘要标记格式,可以互相识别、互相操作。

## 小结:与 PI、DeepSeek-Harness 的对比

三门课程都在解决同一个问题——上下文窗口有限、历史必须折叠——但落点各不相同。PI 的压缩(`compaction.ts`)围绕"裁剪点算法 + 分裂轮次"展开,核心难题是"在树形会话模型里找一个不切断 `toolCall`/`toolResult` 配对的切点";DeepSeek-Harness 的 `BasicCompactionEngine` 强调两个独立触发点(主动压力检测 `agent/pre-step` 与被动溢出恢复 `agent/request-error`)和"剪枝→选区→摘要→替换"四阶段事务,靠 `compaction/start`/`compaction/end` 标记对做崩溃可恢复性。hermes-agent 的 `ContextCompressor` 在裁剪逻辑上与二者相似(都要保护首尾、不能切断工具调用配对),但它的独特之处集中在两点:**结构化模板的双轨追踪**(`Completed Actions`/`Resolved Questions` 记录已完成,`Active State`/`Blocked` 记录未完成,配合"历史性小标题"防止摘要被读成待办)和**真正的迭代式摘要更新**(用"PRESERVE/ADD/Move"这类显式动词让模型对已有摘要做增量合并,而不是每次都重新总结全部历史)。此外,micro-compaction 把"批量一次性压缩"进一步拆成"每轮增量吸收 + 定期 defrag"的分期付款模式,是另外两门课程都没有的一种细粒度策略。

思考题:

1. `SUMMARY_PREFIX` 里专门写了"reverse signals(停止/撤销/别管了)必须立刻终止摘要里描述的进行中工作"这条规则,这暗示了什么样的真实失败案例?如果没有这条规则,你能想象出模型会犯什么具体的错误吗?
2. 迭代式摘要更新要求模型"移动"条目(In Progress → Completed Actions,未回答 → Resolved Questions)。如果模型在某一次迭代更新时漏掉了某个仍然相关的旧条目(既没保留也没移动),这个信息会不会在后续的压缩里被永久找回?你觉得这套机制有没有针对"信息静默丢失"的兜底手段?
3. micro-compaction 用"每轮吸收一个 exchange"的方式摊薄压缩成本,但代价是每次 pass 都要重写已发送历史、打断 prompt cache。如果一个 provider 的 cache 命中折扣特别高(比如缓存读远比未缓存读便宜很多),你会建议用户开启 micro-compaction 吗?换一个 `micro_compact_every_n_turns` 的取值能不能缓解这个矛盾?
